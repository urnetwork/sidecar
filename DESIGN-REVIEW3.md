# Review: Sidecar infrastructure technical design

Reviewed: `DESIGN.md`, draft for peer review, 2026-11-03, owner decisions of 2026-11-03 applied. About 9,256 lines. Nothing in it is implemented.

Verdict: **needs revision before G0.** Do not freeze format 1, the config-repo grammar, `record.proto`, or ciphersuite 0x0010 on this text. Storage and GKM, as specified, do not hold a key that decrypts repo contents, and the metadata list is honest about what servers see. The commit protocol, the revocation bound, the approval gate, the P0 schedule, the site-loss restore, and the outbound-mail proof do not do what the surrounding sections say they do.

Seven findings are critical. They are places an implementer would either ship a false security claim or be unable to choose a single behavior. The major findings are underspecification, owner-question recommendations that are unsafe as written, and schedule holes. Owner decisions X1–X20 and 1–111 are taken as settled. Several of them leave a hole the text then describes as closed.

## Critical

### C1. A ref commit does not publish the entry versions it names

§11.8 steps 5 and 6 (lines 4416–4439). Step 5 writes the push object, each index entry, each directory delta, and possibly `log/<n>`, all before step 6's `If-Match` on `head/<repo>/<ref>`. A version is committed only once the head window or a log page names its push id (line 4439). Path-level compare-and-swap reads the newest *committed* version (lines 4426–4427). §11.14 says pushes to one ref meet only at step 6. §11.15 records that no store condition spans two objects, and the protocol still mutates several objects before the only commit point.

Two pushes of the same path can both observe committed version `v`. The first installs an uncommitted entry. The second gets 412, rereads, sees that the committed version is still `v`, and overwrites the entry. The first push's step 7 then sees no committed change and wins the head. The head names a push id the entry object no longer holds. A loser that "removes what 5 wrote" can delete the winner's bytes on the way out. Disjoint pushes share the hole on the directory object, which the design says they must merge, and on `log/<n>`, which is written with `If-None-Match` before either head commit. A timeout after a quorum write whose response was lost is unspecified: step 7 handles 412, and a retry can miss a head that already contains this push id.

Format 1 should not freeze until every entry version, directory delta, and log page is an immutable object keyed by push id, the head `If-Match` is the only read-modify-write, cleanup deletes only objects that push id created, and a retry that finds its push id in the head returns success. §22 needs an invariant a model check can fail: a head that names `Pa` means `Pa`'s entry bytes are still readable.

### C2. Path-level success and a git ref are two histories

§11.7 (lines 4356–4358) says one evs push carries one git push, and the sealed metadata holds that push's commits. Step 7 commits a second push from the same `base_version` whenever the paths are disjoint, without the client rebasing. The local hook (lines 4487–4488) says a lost race is an ordinary non-fast-forward. D-EVS-8 says conflicts are never auto-resolved. Export (line 4518) rebuilds plain git with the original oids and checks `git fsck`.

After two disjoint pushes the index tip contains both files and neither sealed commit does. A checkout of either original oid disagrees with a head read. Export cannot both preserve those oids and point the ref at the tree the index serves. Head mode writes `EvsPush` with its own codec and never runs the committer hook, so the forced git identity (owner decision 81) is not a property of the storage protocol. The bare-repo lock against `receive-pack`, tree encoding, and recovery after a crash between the local accept and the debounced push are not specified.

The same push path inlines files that pad to 16 KiB inside the push POST (lines 4369, 4421), up to 10,000 changes. `client_max_body_size 16m` is global (`warp/warpctl/config.go`). A push of a few thousand small files, which is also the IOPS strategy that keeps those files off the HDDs, is rejected by the load balancer the design cites.

Pick one model in the format-1 text. Either the client retries on any concurrent commit, and the sealed tree contains every path committed since `base_version`, or the ref tip is a deterministic merge whose tree is defined as the index and export says so. Keep inline bodies out of the buffered POST. State that LFS, tags, replace refs, and partial-clone filters are outside v0.

### C3. The P0 does not close before the daemon, and a 7-day `exp` is not what the server enforces

D-TRUST-3 (line 1243) says no sidecar ships before stage 1, and no desktop sidecar ships before stage 2, because stage 2 is what stops persisting the network credential. D-PHASE-3 (line 7959) merges stage 1 log-only in M0 so the 14 log-only days overlap M1. §23.4 puts the desktop daemon in M1 (line 7885) and stage 2 at M3's exit (line 7887). Through M1 and M2 a same-user agent does not need the sidecar token. `.auth_state` still stores `by_jwt` beside `by_client_jwt` (`sdk/local_state_auth.go`). That network token never hits the client-token gate.

The current bug is real and the inventory is right. `refuseClientAdmin` is `NetworkRefusesClientAdmin` (`server/api/route_authz.go`). The 27 AppAdmin routes, including `POST /auth/code-create`, the seed-phrase routes, and `network-delete`, still take an ordinary client token. `AuthCodeCreate` still has the client-token refusal commented out (`server/model/auth_model.go`). Stage 1 refuses a child or an `admin_refused` row, and a top-level client minted with the network credential through `POST /network/auth-client` has no such row.

D-TEAM-14 does not create a 7-day server lifetime. While `reject_expired` is off, a passed `exp` is accepted (`server/session/by_jwt.go:496–502`). A token with a root-client claim or a session id is cut off only at `AcceptUntil`, which is `exp` plus `SessionGrace` of 60 days (`server/session/session_state.go:15, 29–46`). §7.4 cites AUTH.md as that horizon. Refresh is an ordinary Client route with no proof of possession, so a JWT inside the horizon can be renewed. The sentence that auth codes die with their `api_key_id` (line 2930) cites AUTH.md:202, which is the open gap: a code minted by an API key logs in as a network token that survives removal of the key.

After all three stages, a marked sidecar token still reaches Client routes the stages never name, including `POST /network/auth-client` and the client payment routes. That is short of a network login. It is account power I-6 does not mention.

Enforce stage 1, for real, and stage 2, and stop persisting `by_jwt` in `.auth_state` and extension storage, before any daemon build can enroll. Add a hard `exp` check that does not depend on `reject_expired` or the root-client claim, and reject refresh that lacks a ClientKey proof (Q-CORE-4, below). Describe AUTH.md:202 as the gap being closed.

### C4. Harness evidence is a signature by the sidecar that was asked

§16.6 (lines 5998–6024) and I-8. Owner decision 75 says the harness prompt counts as approval for a single-device user. `harness_ok` signs channel `harness` with the requesting sidecar's identity key when a hook event matches session, tool, and the SHA-256 of the arguments, the member has no other device and no presence key, and the evidence list includes `harness`. Hook events arrive as `ur hook` on the daemon socket. That socket admits every peer with the daemon's uid (line 6033). The hello's harness, agent, and pid are client-supplied. Ancestry joins an MCP session to a run (line 6055). It does not pin the hook peer to the harness binary `ur install-harness` sealed.

Taint does not drop the harness channel. A tainted run needs a fresh decision, and harness is still a legal channel for it. §8.5's `evidenceDefault` includes harness, and the implicit document's request rules omit `evidence`, so Community and Pro inherit it. Those decisions are what the server stores and what api-10 accepts. Shell and other harness-native tools sit outside the gate, so the agent can run `ur hook` and then the outward tool. Another device cannot tell this from a person at `/dev/tty`: both are a signature by the same sidecar over a hash the sidecar ingested.

This is the prompt-injection case I-8 and I-9 exist for, on the default evidence list, and it authorizes server-side publish, DNS, and mail. Keep decision 75, and bind a harness decision to the pinned harness binary whose pid is the hook's peer. Refuse hook events whose peer is the agent or a child of the MCP relay. Until that exists, leave `harness` out of `evidenceDefault` and out of the implicit document, and require `device` or `presence` for every server-gated action. A tty confirmation can stay.

### C5. A withheld removal is not bounded by 24 hours

§2.10 (line 1219) tells a compelled operator that a withheld Remove exposes new writes for up to 24 hours in shared groups. D-TRUST-10 (line 1257) is the mechanism: writers stop after 24 hours without a consistent `HeadCheck` with another reader device. §6.4 alarms on a conflict or on a higher pin the server then withholds. It asks for the member's own devices first. One agreeing peer refreshes `witnessed_at`. HeadCheck rides connect, which the operator carries.

I-15 and R-KEYS-4 say a removed member reads nothing new. §8.12's rule, never encrypt to an epoch a non-reader holds, binds only devices that have seen the new projection. A server that delivers the revocation to the revoking device, drops HeadCheck between that device and the others, and lets the others witness each other on the old pin meets D-TRUST-10 for everyone except the revoker. Those devices keep writing to the epoch that still contains the removed member. evs is the same adversary and will not close the gate an honest server would. In a member's own repos the design already lets writers continue on an alarm, so a withheld removal there has no bound. v0's pilot is personal networks (owner decision 102).

Fail closed unless a writer has a fresh witness that the current projection is the newest pin held by a quorum of the repo's readers. A peer that is merely behind must not count. A device that learns a higher pin and cannot fetch it stops sealing immediately. State the single-device case as having no bound.

The same wait exists on the honest path. §7.10 revokes tokens at once and queues the MLS Remove for a grantor leaf. SCIM `active=false` can wait up to 7 days for an admin signature (line 3048). Until that commit, honest members still encrypt to the removed sidecar. Server denial stops that holder from fetching. It does not stop new ciphertext from being sealed to their key. Publish the projection and the Remove as one admin action, and do not treat a SCIM queue as removal.

### C6. The outbound proof is a sketch, and TLS 1.2 shows recipients to the edge

§14.5 (lines 5328–5396) and smtp-2. `SmtpProof` is named and never defined. Public inputs, the transcript binding, and whether application keys leave the circuit are not stated. The diagram says pi1 "commits key, IV" while Z2 is an in-circuit XOR. A verifier that learns the client write key decrypts the message. Z1–Z6 are checks, and the relation is deferred to a future `smtpproof/SPEC.md`. pi2 is "Z2–Z6 over every later record," which includes the BDAT body, while the speed gate is a 4 KiB header and 10 recipients. The section's own cost for opening a body in-circuit is minutes per 100 KiB. That gate does not describe a real message if Z2 covers the body, and it does not constrain the body if Z2 covers only the commands.

E2 discloses the TLS 1.2 server write key to smtpedge. smtp-2 says that key opens the MX's replies, and that some MTAs echo recipient addresses in those replies. Exchange Online is a required interop target and needs a TLS 1.2 circuit (line 5386). TLS 1.3 disclosure of the server handshake traffic secret does not decrypt application data. The 1.2 key block does. §2.8's statement (line 592) says servers never receive plaintext content or keys, in any mode. R-TEST-3 makes that a test. The metadata list tells the truth. The sentence above it, and the directive at line 17, do not. D-SMTP-10 says the key is not stored. Receipt is the problem.

X-UR-Ref's MAC (line 5411) is `HMAC(key, send_id ‖ network_id ‖ day)`. It is not bound to the Message-ID or the DKIM signature. Medium confidence (line 5445) is "the MAC verifies and matches that IP and time," with no requirement that the verified DKIM `d=` be the network inside the MAC. A customer who receives another network's mail can copy that reference into their own complaint, from the same shared pool address, inside the ±10 minute window, and halt the victim. High confidence still checks the victim's signature. Medium confidence, used on its own, does not.

Freeze the relation before other M9 work. Public inputs are the observed ciphertext, a hash of the disclosed TLS 1.3 handshake secret, and the preamble fields. The TLS 1.2 server write key is not an input the edge holds; server Finished is checked in-circuit, or TLS 1.2 is refused. State that body bytes are not witnesses and that Z2 covers EHLO, MAIL, RCPT, the BDAT command, the chunk tail, and QUIT. Put RCPT-command lengths in the metadata list or pad those commands. Bind X-UR-Ref under the message's DKIM signature, and ignore a medium join whose MAC network is not the verified `d=`. The M9 gate's "two engineers argue soundness" needs that spec to argue about. Go's `KeyLogWriter` does not export the TLS 1.3 handshake secret (the design cites this); forking the client handshake to extract it is a second TLS implementation and belongs in the same gate.

### C7. Site loss does not restore the rows names and mail live on, and the RPO sentence is false

Line 6950: "No object waits for a copy, so owner decision 89's RPO bounds (5 min metadata, 1 h segments) hold." The table under it gives quorum failures RPO 0 and site loss "all server-held objects there." Decision 89's off-site lag was superseded by decision 94. Nothing ships metadata every 5 minutes or segments every hour. Quorum writes are RPO 0 for a drive or one host. Site loss is total for anything no device still holds. General git repos have no required device copy (line 4541).

§19.10 restores "Postgres from planetoid's newest dump" and empty buckets. Sidecar tables are removed from those dumps (`pg_dump --exclude-table-data`, §19.6) into a 14-day sidecar dump that the runbook never restores. That dump is the only off-site copy of `dns_label` (tombstoned for I-14), the DNS and mail routing tables, `sidecar_identity`, `network_admin_event`, and the abuse and TLS tables. Devices do not hold the zone. Restoring without `dns_label` reopens alias takeover.

D-TRUST-7's reason is that no backup may outlive a published TTL, and §19.6 keeps the sidecar dump 14 days. ops-2 says 14 days past each row's TTL. One of those cuts a 400-day admin log to 14 days. The other extends a 24-hour connection record by 14 days. `hold/` is a metadata-cluster object, so a preservation hold dies with the site. Key slots die with the site on purpose (decision 90); record-class re-seed, which replays pushes and segments, does not restore those slots, so the procedure in §11.13 does not bring a record repo back even when a mirror has it.

Delete the sentence that the old RPO bounds hold. State the real figures: RPO 0 after a quorum ack, write outage from the second host until a spare is fitted, site-loss recovery equal to whatever devices still hold. Restore the sidecar dump in §19.10, and pick one retention rule. Say which objects a mirror must re-upload for a record-class repo to be readable, including slots. The 4-hour RTO depends on the cold spare in Q-OPS-1, which is still an unconfirmed M0 residual, and until M6 it is staffed hours only.

## Major

### Cryptography claims

**The content-key ladder is not MLS forward secrecy or post-compromise security.** D-KEYS-1's reason for MLS is tree post-compromise security (line 4122). §10.5 then leaves the data keys outside the tree. `RK_g` is wrapped under an MLS exporter secret the same paragraph cites as not forward-secure, cached for every generation, and unchanged by Add and Update. `RK_g` opens every earlier generation through `GenLink`. An Update heals the leaf. It does not rotate `RK_g`. A thief who copied the keychain reads the current generation until the next `remove`, `request`, or 30-day rotation, and reads every earlier generation after that. A new member receives the archive. Say that in §2.10 in those words, or rotate the content key on Update. `ur evs rekey` is the on-demand half of owner decision 64 and is scheduled as v1 (§10.16, §11.21). Ship it with removal. Until a file is re-checkpointed, a removed member who kept `RK_g` still opens it. §2.10's "cached data" is narrower than that.

**Harvest-now-decrypt-later is passive-only, and the ladder makes a later signature break retroactive.** The ciphersuite name matches draft-ietf-mls-pq-ciphersuites: X-Wing KEM `0x647a`, HKDF-SHA256, AES-128-GCM, Ed25519. Go 1.27.3's `crypto/hpke.MLKEM768X25519` is that KEM. The draft's own limit is that the Ed25519 suites give post-quantum confidentiality against passive attackers. §10.9 allows an external resync on the same `sidecar_id` and identity key. KeyPackages and the projection publish that identity key. A later Ed25519 forgery signs a fresh credential, external-commits, unwraps `RK_g`, and walks the ladder. R-KEYS-12 and Q-KEYS-2 say residual none. State the passive-only limit. Keep external resync from being authorized only by an Ed25519 key GKM has already published. The conformance plan runs mlswg vectors as suite `0x0001`. Nothing in it interoperates the suite that seals path secrets. Freeze 0x0010 at M2's exit, on one Welcome, commit, and decrypt against a second stack whose KEM is Go's `MLKEM768X25519`, including the `UR evs 1.0 kek` exporter and the GenWrap additional data.

**Q-ACL-9 (a) breaks removal.** The recommendation gives tagged, ephemeral, and cloud sidecars a static X-Wing wrap of `RK_g` and lets any writer, wrapped ones included, sample the next generation. There is no tree Update that excludes them. A Delegation's admitted agents share one private key (§10.5, line 3957), so reaping one does not take the key back, including on the config repo. I-15 says a reap starts a new generation. The wrap text says a reaped sidecar reads until `DelegationRevoke`. Owner decisions 1 and 60 said per-device wraps are not the v0 distributor. Reject (a), or rewrite it so a non-leaf never samples `RK`, a removed sidecar is never the signer of the rotation that excludes it, and a Delegation key is not a shared long-term read credential. Leaves for every reader, option (c), matches the removal invariant already written. The 1,000-leaf cap against 5,000 Team admissions (line 3023) is the cost of (c), and it is a real M2 problem. It is a smaller problem than a wrap the removed party can reissue.

### Identity and policy

**The authority grammar already crowns one recovery key.** Decision 110 is k-of-n for authority-key changes. §7.9's `authority` production (lines 2996–2999) is k admin signatures, or the subject's own or an Owner's recovery key through a 72-hour window. §5.6 and §10.9 treat that as the live recovery path, including an external commit. Q-TEAM-11 is unanswered, and D-PHASE-2 says an unanswered blocker is not implemented as its recommendation. The byte format would ship option (a). "Through a 72 h window" is also not the delay §22's replay test describes ("apply only after 72 h unvetoed"). If the Welcome is issued when the signature is published, a veto cannot unread. If the signature is inert for 72 hours, the new device is not yet a grantor, and Q-KEYS-13 (a) allows Adds only from grantor leaves, so a lost fleet has nobody to commit the join. For k>1, recommendation (b) means a team that loses every admin device cannot recover the AdminSet with recovery codes, which contradicts the freeze sentence at line 3025. Personal networks are k=1, so (b) collapses to (a) there and the veto does not exist. Keep the recovery key as one signature toward k, make the 72 hours a real delay during which no Welcome or wrap is valid, and state the all-admins-lost outcome as a new network when k>1.

**The id-only projection is not the policy the client evaluates.** `autogroup:untagged` is defined as untagged non-sidecars (line 3228). The implicit document's comment grants the same name to untagged sidecars (lines 3293–3295), which is decision 105. Two compilers publish different `AclRows` for one file. The implicit document also grants `autogroup:member` write and admin on `evs:*` (line 3296). That is the Community and Pro default until someone writes a policy, and it is wider than decision 105's reach sentence. `has_document` is not in the `allowed` formula (lines 3314–3318). A v1 projection with empty rules can be deny-all at the gate and allow-all on the client. §8.11 requires the intersection of both networks' grants. `allowed` does not, so example 4 admits the partner from one signature. Group edits are not in `rev/`, and service tokens last 15 minutes and contracts up to 60, so a dropped group member keeps the old scope through that window. One definition, one test vector for an untagged sidecar and for `has_document=false`, the implicit document copied into the projection the gate evaluates, §8.11's intersection inside `allowed`, and a subject epoch that voids tokens on atom changes.

**Every admitted sidecar reads the directory and `K_sock`.** Decision 6 is settled and should be stated as a consequence: tagged, ephemeral, and delegation sidecars are full readers of the config repo for the life of the epoch, including the policy source, the admin set, group emails in the worked example, and the 32-byte socket-name key (§9.4). Deposit-only on data repos does not apply to config. Keep `K_sock` out of that set if internal names must stay hidden from CI. Store group members as `member_id`s.

**JIT links a pre-registered email.** Identity is `(idp_id, sub)`, and the same sentence (line 2893) links an existing user for verified-domain emails. Domain verification is a DNS TXT record. A password user who registered `alice@acme.com` before the domain was verified becomes the link target, and SSO-required mode drops other sign-ins only after it is turned on. Link on `(idp_id, sub)`. Attach an existing account only after that account completes a login.

**Q-TEAM-10 (a)** is safe for non-admin devices only if the delta cannot change a role, touch the AdminSet, or admit an admin's device unless k signatures are present. A stolen device that can still sign otherwise admits a second device of the same member, and removing the stolen one leaves the new leaf. D-TEAM-16 has already written (a) into the format. Take it back out until the owner answers.

### Protocol, sockets, and the overlay

**§6 is not a wire spec.** `Error`, `StreamReject`, and `StreamReset` codes are `uint32` comments. §9's dialer branches on `retry`, `busy`, `denied`, `invalid`, and `quota` with no numbers. A response "echoes the request id, plus ERROR" does not say whether `Envelope.type` stays the request type. `StreamClose.final_offset` is not defined as next-byte or last-byte. `Hello.initial_window` is 16 KiB and `StreamOpen.window` is a second credit, against a 256 KiB desktop minimum. `K` "derives from `K_sock`" with no HKDF label. The listing seal names the AEAD and the pad and not the nonce or the additional data. `GET /sidecar/sync/poll` specifies the 204 and not the 200 body. `PushReset` carries at most 48 versions with `complete=false` and no rule that a client ignores the snapshot until `complete=true`. evs and gkm topics are per repo and per group, so 48 is not a full resync, and a trailing loss has no later sequence to notice. §6.8's "correctness never depends on delivery" is false for the hour until the refetch if the client applies a partial reset. Number the codes, define the poll body, require `complete=true`, and on a missing tail call `GET /sidecar/sync/versions`.

**C13 does not say which id is sealed.** Providers see window-client ids. Grants use the sidecar subject. C13 says the signer fills `source_subject_client_id` and, for FriendsAndFamily, `source_network_id`, and not that it copies the stored ancestor and ignores the request. Sealing today's `StoredContract.source_id` makes `AllowDial` miss every sidecar grant. The companion path sets `ProvideModeStream` unless both sides are Network (`connect_controller.go`). Nothing says a share's return contract keeps the seals and is not a second escrow. Write the signer rule, and state that a FriendsAndFamily companion inherits the seals and that only the dialer's network is escrowed for both directions.

**Decision 66 removes caps and does not bound the control plane.** Registrations are a full set per client, renewed every 15 seconds, with no maximum names or calls (§9.10). Find signs two tickets and only then does the listener apply the transfer quota. An authenticated client with no byte traffic can pin Redis and the signing key. Keep the decision's "no cap on established forwards." Add a separate control-plane limit that returns `unavailable` before the ticket is signed, and reject registration and Find when the network is spent.

**The overlay /16 both captures CGNAT and is dropped because of it.** §17.4 installs the block and, on a local overlap, /32s per peer. §17.7 says the sdk drops any exported prefix that overlaps `connect.LocalIpv4Networks()`. A carrier /32 inside the network's /16 overlaps the block, so the whole block is dropped. Apps capture 0/0 and exclude only RFC 1918, so a tun /16 inside 100.64/10 is captured and black-holes the carrier. There is no cross-network uniqueness: a device that sees one block twice routes it to the first-joined network. Pick one rule in both subsections: on overlap, install /32s for known peers, and do not drop the block because one local address overlaps it. Leave Q-BRIDGE-7's "any /16" unset until that rule exists.

**M4 ships allow-all to LAN and loopback for untagged sidecar sources.** Rules 3–4 (lines 6333–6335) are ordered before the loopback deny. With no document, an untagged source Passes, including a packet aimed at `127.0.0.1` itself. The "never a daemon listener" exclusion is only on the overlay-to-loopback map, so the local API, MCP, git, and mail listeners are reachable by a direct dial. `connect/ip_security.go:567–569` really does allow Network before the public check. Q-TRUST-7 (b) would narrow this for marked sidecars. §23.6 does not block M4 on it: decisions 50 and 105 ship either way (line 7908). Fail closed for a marked sidecar until the owner answers. Keep decision 105's app-device reach for clients that are not marked sidecars.

**Q-BRIDGE-2.** Agree with a fixed single window client per target, Required, window size 1, `OverrideAllowDirect=false`. The production path for that already exists (`ProviderSpec{ClientId}`). `DefaultMultiClientSettings` wants six client graphs and is the wrong default. Own-client links stay the iOS fallback after measurement. C13 is still required, because the provider sees the window id (the seal issue above).

**Q-CTX-4.** Agree with (a), the live sharer in §9. `ur share` is a running socket with a use count on the transfer balance (R-CTX-31). §9 does not design it today. §11 should not take it. Put the question on the M2 blocker list. Option (b) would change format 1, which freezes at M2, and §23.6 currently waits for neither.

### Mail, DNS, and the TLS edge

**Foreground iOS is not a receive path.** The edge cannot queue (line 5697), and a miss closes in the handshake, the same row as an unknown SNI (line 5656). Sender retries run on the sender's clock, 14 hours to 5 days. An iOS wake only resyncs (line 5702). Nothing in the wake path tells the remote MTA to connect while the app is open. Always-on `ur daemon`, Android while the VPN is up, and two Team receivers are real SMTP. A sign-up code arrives only if some later retry lands inside a foreground interval the sender does not know about. When the sender gives up, the message is gone. D-MAIL-9's census measures SNI and CHUNKING. It does not measure this overlap, and BS1 waits on the census. Stop describing foreground iOS as receiving, and block the consumer launch on an always-on receiver the same way it is blocked on SNI loss. Use a retryable close for offline networks and a cacheable failure for unknown names. Do not add an edge queue. That would break the directive, and the design is right to refuse one.

**A Team custom name on 443 is terminated.** The stream map sends `*.ur.network` to tlsedge and everything else, including no SNI, to today's terminating HTTP servers (lines 5004–5030). A customer CNAME keeps the client's SNI as `<host>.<domain>`, which does not match the wildcard. §13.5 maps that SNI only after the connection has reached tlsedge. Visitors get the platform certificate. Render exact platform names to the HTTP socket, and `*.ur.network` plus each custom host to tlsedge. The `*.ur.network` split itself matches the pinned nginx: `ssl_preread` is available, stream ports already send PROXY v1, and `realip` from a unix socket runs before `limit_req`, so the 450/minute key survives if the HTTP listeners move as written.

**The first DKIM record on a burner deletes its MX.** The wildcard owner is coherent: `*` carries A, AAAA, and MX and no CNAME, and ordinary burners synthesize to `mx.<net>`. A replying burner's `<sel>._domainkey.<blabel>` makes `<blabel>` an empty non-terminal. RFC 4592 then returns NODATA for `<blabel>` MX and A, rather than the wildcard. The zone table says the empty non-terminal "takes `*`'s records, MX included." It does not. Receive-only burners work. The first reply, which decision 79 needs for strict DMARC before the PSL listing, is what removes inbound mail for that address. Copy A, AAAA, and MX onto `<blabel>` in the same journal write as the first `_domainkey` child, and delete them when the selector is removed.

**Shared sending IPs have no drain.** v0 sends from the shared lb addresses (decision 34, line 5412). Those addresses have no PTR. Halts stop one network's new preambles. They do not withdraw an address from the pool. Q-SMTP-6 (b) moves the listing off the HTTPS addresses and still leaves one mail pool shared, with nowhere for a burned address to go. Per-network DKIM does not keep a blocklist off the IP. Treat spare mail-only addresses, PTRs before the first send, a ramp, and an automatic pull of a listed address as part of the sending design. The HE port-25 request is an M0 lead time (line 7927) and the address choice is an M9 decision (line 7913). Ask for the addresses when the ticket is opened.

**M7 does not wait on a second site for DNS.** Both name servers are at one site, and the gateways leave through one provider. From the DS onward, that outage fails DNSSEC, so DANE senders defer and inbound mail stops. §12.16 says Q-DNS-7 blocks M7 only if the third NS is adopted. Make the third NS a precondition of the DS, with the ZSK exposure of an off-site signer written down. If the owner keeps one site, say in the launch criteria that a site loss deletes inbound mail for the retry window.

**Q-MAIL-13 (b) is the wrong label.** A forward-confirmed PTR or a DKIM `d=` on an operator list is not evidence this message took a DANE or MTA-STS path. REQUIRETLS, option (a), is the sound label. It will rarely show. That is what the section already found.

**The platform listener is a real exception the directive sentence denies.** `rpt.bringyour.com` terminates TLS and parses report headers (line 5666). The metadata list discloses it (mx-4). The directive (line 18) and the X6 summary say inbound TLS never terminates at a URnetwork edge. Name the report host in that sentence. Header-only parse of abuse reports, with the raw bytes sealed to the network mail key, can stay.

`helo_name` is a value smtpedge issues and Z4 checks (lines 5350, 5370). smtp-1 and smtp-2 do not name it. I-18's guard has nothing to point at.

### Operations, quotas, tests, and the schedule

**Relayed same-network bytes are debited at close.** Edges reserve a lease. evs journals every 60 seconds and refuses from a list. Relayed traffic waits for the close report (§20.6), and a Network contract escrows nothing. `DefaultContractExpiration` is 60 minutes. One such contract at 100 Mbit/s is on the order of 45 GiB, against a Community balance of 30 GiB/day, and nothing limits how many run together. Decision 66 makes this balance the only cap on sockets and forwards. Debit from checkpointed reports during the contract, refuse `CreateContract` once the network is spent, and count one contract once. The §22 test that checks idempotence of one close report does not cover this. §20.15 rates the overshoot low and cites the evs events, which are a different path. D-QUOTA-6 says downgrade breaks no inbound address, and §20.7 withholds custom domains after 14 days. A custom MX is an inbound address. Reconcile those two sentences.

**M5's abuse clocks do not match the staff.** Machines act on listed phishing and high-confidence mail joins. Other reports wait 72 hours or 7 days. Decision 95 is business-hours staff through M5. A registrar ticket against `ur.network` takes the third-level names with it (the design quotes the ICANN rule). Q-ABUSE-6's pager covers registrar and law-enforcement emergencies and does not cover a phishing name on a Saturday. Publish clocks that match the staff, or staff the 1-hour and 4-hour clocks when public names turn on. Sockets and forwards need an abuse switch that does not wait for a close report.

**§21.9 understates what a warrant returns.** connect-1 stores source and destination client ids and close reports that pair them, and unpaid contracts are kept for hundreds of days. The production paragraph says connect keeps no dial records. Rewrite it: contract pairs, edge records, and gkm sidecar ids are producible; content, keys, and inbound sender addresses are not. A hold cannot outlive the site or a slot shred. Leave holds blocked on Q-EVS-7.

**M3 and M5 have no deployment path that satisfies both the migration catalog and decision 107.** A migration's version is its slice index plus one (`server/db_migrations.go:163–165`), and an applied row cannot move. Q-OPS-8 (a) merges each group's SQL at Gn-out and, until RS1, builds dark deploys from the `sidecar` branch. A dark deploy during the milestone is before that merge, and startup will apply the tail to whatever database it is pointed at. The next weekly `main` merge re-appends the tail. Option (b) keeps the tail off production, runs the pilot on canary, and holds M5's edges until RS1. M3's exit is a production file cluster. M5's exit is a dns edge on the user root in main. Neither option meets both. There is one `sidecar` branch per repo. server's branch merges at M4's exit while team B is already committing M5 to that branch, so the RS1 merge publishes in-progress mail commits. After RS1 the text says releases are flag flips from `main` and does not say where M7–M9 commits go. Before M1, pick Q-OPS-8 and add the mechanical rule: production binaries contain only migrations already on server `main`, and a dark deploy is not what applies a tail. Keep mail's server commits off the revision RS1 merges.

**The internal gates do not exercise the suite or the proof that ship.** Decision 99 removes an external review. §23.8 freezes 0x0010 at M2's *entry*. The differential tests are M2's *exit*, and they run the mlswg vectors as `0x0001`. The M9 gate is a prose note by two non-authors plus a corpus of four attacks, with the prover and the verifier in one tree. Canary has no edges or mail, and the `ssl_preread` split first sees production 443 at the rollout. Move the format and suite freezes to the exit review. Require the 0x0010 interop above. For the preamble, require one independent checker of the public relation and a mutated witness per Z-check. Run the stream map on a drained interface before it serves the platform vhost.

**Head readers cannot bind the file they were served.** Q-EVS-6 recommends trusting evs for changes older than the 64-version window. The window stores at most 1 KiB of changed token paths, then only prefixes (lines 4392–4395). The index entry is not signed. `HeadCheck` carries the config head, MLS heads, and the projection (lines 2510–2518). It does not carry evs ref pins. `EvsHeadCheck` is v1. A phone in head mode, which is the iOS mail path, cannot tell a current entry from an older sealed entry of a quiet file. Disagree with (a). Put `(token path, entry_sha256)` in the head the reader already verifies, including files older than the window. Option (b)'s extra put per directory level would serialize disjoint updates and should stay rejected. Option (c), phones replay everything, fights the working-set budget. Give `evs:<repo_id>` one repo-scoped version so a hint for a second ref is not dropped because the first ref's version is higher.

**GC and quotas cannot see the bytes they account.** A log page stores push id, statement hash, and token paths or prefixes. It does not store sizes or segment ids. Locators ride in cleartext entry versions outside the signed `EvsPush`, and step 4 checks that a segment exists, not that the locators hash to `entry_sha256`. A taskworker that trusts those locators deletes live history or pins garbage. Inline bodies, the common object under the IOPS plan, are not segments at all. Soft quotas reconciled nightly from the log will not enforce 1/20/200 GB. Erasure rewrites `slot/` and leaves ciphertext in the index, the push log, and the pack. Put segment id, offset, length, and padded size in the signed push. Define GC as a walk of retained pushes. State that v0 erasure is key destruction, and that packs keep ciphertext for the life of the repo, or bring compaction into the same milestone as erasure. A re-seed must refuse a segment an erasure record still covers.

**Path tokens work for a client that already knows the path, and the rotation is not specified.** `t_i = HMAC-SHA256(K_path_p, t_{i-1} ‖ name_i)[:16]` plus a sealed directory name table is enough to list and to subscribe by prefix without the server learning names. Ref ids are "keyed from `RK_1`" with no HMAC inputs, so no client can derive `head/<repo>/<ref>` for `main`, and a removed member who kept `RK_1` can test new branch names for the life of the repo. §11.5's bound is true of path tokens and false of ref ids. `name_i` is not tied to raw git path bytes, so NFC and NFD split a tree. `K_path` is per repo, so the same path on two refs is the same token sequence, which evs-11 does not list. Rotation does not say how a head-mode client that cannot decrypt every name computes the map, what happens to directory deltas mid-copy, or how prefix leases move to the new tokens. Publish the ref-id HMAC, define `name_i` as the raw git path bytes, define the root key, and bump a lease generation on the epoch push.

**Q-OPS-2 should not freeze the locator.** The ~400 HDD PUT/s figure assumes the 16 KiB inline path already works, and on the design's own trigger (repack at half the measured rate) that figure is already in the band where repack is required. Reserve a pack address, or an explicit format bump, before format 1. The ~500–800 PUT/s ceiling is not in the text of owner decision 20.

### Client embedding

**`record.proto` is not a semantics-free envelope.** X20 leaves the record to RECORD.md and then freezes the proto at M3. The proto already fixes three logs with a reader and writer matrix, a closed `kind` inventory, and a per-writer chain with no log-wide sequence. The leaf hash is SHA-256 of `0x00 || header bytes`, and neither the header nor `CanonicalAction` names an encoding or a version. The body salt lives in a §11 slot, so a disclosure packet that holds only the `RecordEntry` cannot recompute `body_commitment` after erasure. Give both messages a version, specify the hashed bytes as the stored canonical protobuf with unknown fields preserved, and state that the three-log matrix is a semantic commitment. Do not call the current field set frozen.

**The tool catalog does not close the trusted action.** The prose says no tool changes policy or returns keys. `evs_write` is a write against any repo the subject may write, and an admin's untagged sidecar is a config writer. `CanonicalAction` has no DNS name, rdata, alias, repo path, or socket name, while `dns_set`, `mail_alias_create`, and `socket_listen` are outward actions. `preview` is agent text the approver is told not to trust, so it cannot carry the trusted rdata. No tool is marked against the transfer meter. Refuse `evs_write` on `config` and on any statement whose purpose is `authority`, `acl`, or `approval`. Extend `CanonicalAction` with the daemon-built fields each outward tool has.

**One browser sidecar is the plaintext boundary, and the label does not constrain it.** Decision 76 is settled: pages may decrypt, clearly labeled, and this is undetectable (EX7). §18.8 uses one worker for ur.io/recurd, the team console, and the quick tools, with no origin check and no sender check. `GetSecret` returns a base64 string to the page. The current extension injects a content script on `https://ur.io/*`, `https://manager.bringyour.com/*`, and `http://localhost/*`. Read-only at RS1 still decrypts records and the config repo. An XSS on any surface that shares the worker is the decryptor. Keep decision 76, and specify one origin per surface or a worker origin the page cannot script, a postMessage allowlist with no localhost in production, and secrets that never return to the page as strings. Say in §2.4 that script running beside the served page is inside the plaintext boundary.

**A failed size spike has no browser path that meets X14.** `sdk/js/wasm/sdk.wasm` on disk matches the cited ~75 MB. The budget is 40 MB. D-SDK-6 says the HTTPS-only worker needs neither C4 nor C17. HTTPS-only removes the need for a WebSocket carrier. It does not remove the binary. The native companion does not decrypt ur.io, and a hosted sidecar is forbidden. Before M4, define the miss: a decrypt-only js main that does not import connect's IP stack, or an explicit slip of page decrypt past RS1. State that X-Wing and MLS run as pure Go in the worker, and that the worker is single-threaded so the long-poll must not depend on a second OS thread.

**Q-SDK-5.** Disagree with trying the root package first. A device role that imports the sidecar root links every untagged root `init` and every descriptor in `protocol`. The 1 MiB gate is not large enough for X-Wing and an in-house MLS. Adopt a leaf `sidecar/device` that does not import the root, and give the bridge messages their own package so importing `protocol` does not register `record.proto`. The tunnel stays keyless. A compromised network extension still sees tunnel bytes and holds `BridgeState`. That is a routing-integrity row §2.10 should have. It is not a reason to put the sidecar in the tunnel.

**The sandbox operator is not in the threat model.** Decision 49 runs `ur` inside the VM and dials through the sandbox's HTTP CONNECT proxy. §2.4's outside list includes model providers and CAs and does not include the sandbox operator. A snapshot of the VM is the key. A CONNECT proxy that does not terminate TLS sees the destination name, sizes, and timing. A proxy CA plus an unpinned dial of `api.bringyour.com` sees the bearer token, because Go uses the VM trust store. Ev's and MLS payloads are ciphertext before that TLS, so a TLS-terminating proxy sees what the server is allowed to see, plus the token. Put the sandbox operator inside the device boundary, next to the harness, and pin those hosts.

## What holds

- A file-cluster or GKM compromise does not decrypt repo contents. `RK_g` is stored as `GenWrap` under an epoch exporter key, `GenLink` under the next generation, `RecoveryWrap` under the member's X-Wing recovery key, and `C_g` is a commitment. The reading of "one session key stored in GKM" matches I-1. Epoch order by `If-None-Match` is specified tightly enough to build.
- For a client that knows the plaintext path, the parent-chained token and the sealed directory table support a head read, a directory listing, and a prefix lease without the server learning names. Content-addressed segments with `If-None-Match` are a sound blob layer. Unversioned buckets are the right primitive for a slot delete.
- Server-minted ghost leaves are closed if clients enforce §10.9: a credential needs a `SidecarAdmit` chained to the genesis, and the server cannot sign that. Genesis with `If-None-Match` is a sound one-winner bootstrap. Public `GET /key/<id>` remains the legacy channel, and EX6 says so.
- ControlId push is possible on today's code. Sends *to* ControlId are refused. The resident already sends frames as ControlId. A peer can forge a zero source on a P2P carrier, and D-PROTO-8 rejects that carrier. Required is not negotiated: plaintext application frames are discarded. The sidecar must not share the sdk provider's Opportunistic client.
- The `*.ur.network` SNI split preserves client IPs and does not terminate. Certificate issuance sees the public key and the names. Per-device keys, no shared wildcard private key, and CT watch match X1. Inbound customer mail is spliced from the ClientHello. The edge does not see post-TLS mail. Deposits are sealed to the drop key, and `250` waits on evs.
- DKIM before the PSL listing is the right shape: the envelope domain does not SPF-align, `_dmarc.<root>` stays strict so one network's selector cannot align as another network's From, and per-burner selectors exist for that reason. The zone bug is the empty non-terminal, not the alignment plan.
- Quorum inside one erasure set matches the failure table: writes return at N/2+1, a second host stops writes and not reads. Tier math matches decision 27. Edge leases and the evs over-limit list are real enforcement points. The privacy harness (canaries, the schema guard, revocation with the gate off) is the right shape for I-18.
- URnetwork never hosts the sidecar. The iOS app and `ur daemon` hold it. The tunnel stays keyless. Local IPC is a uid check. `server/mcp` stays a separate, server-visible tool set. Wake pushes carry a topic class and a version.
- The milestone order for connect changes is consistent. Receive-only burners until the proof gate, DNSSEC soak before DANE, and the file cluster ordered in M0 are sequenced correctly. Decision 91 and decision 99 are not hidden.
