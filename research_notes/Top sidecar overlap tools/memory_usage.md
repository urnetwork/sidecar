# Agent memory and project-context tools that overlap git-fronted storage

Research date: 2026-10-31. Scope is job 1 only (real-time encrypted storage with a git front end, for AI-agent context and project storage), plus jobs 5–7 when the same product does them (easy auth and team management, an admin audit trail, a userspace subprocess with a text interface). Shared memory across people and agents is called out per product. The unreleased product was not researched.

Pages opened in full or in a long extract are marked **opened**. Figures that came only from a search-result extract of a page are marked **search extract** and are weaker. GitHub stars are a weak signal wherever they appear.

## What are the most widely used agent-memory or project-context products in 2025–2026?

### Takeaway

By people, the widely used “memory” in 2026 is project instruction files inside coding agents, not dedicated memory startups. JetBrains’ May–July 2026 survey of professional developers puts Claude Code first (about 39% use it at work), then GitHub Copilot (21%), OpenAI Codex (16%), and Cursor (12%). Stack Overflow’s 2026 AI chapter names Claude Code (66%) and GitHub Copilot (59%) as the coding-agent leaders. Among dedicated memory libraries, PyPI download volume puts the `langgraph` package far above `mem0ai`, but LangGraph downloads measure an orchestration framework, not use of its memory feature. Mem0 is the highest-download library whose product is memory. Letta MemFS is the closest git-backed agent memory and has only star counts. No opened source shows a widely used product that is real-time, encrypted, and git-fronted at once.

### Inferences

- “Most used” splits by metric. Survey reach: Claude Code, then Copilot, Codex, Cursor. Package installs of a memory-named library: Mem0, then Graphiti, with LangGraph larger only if the whole framework is counted. Closest shape to a git memory filesystem: Letta, which the surveys do not mention.
- Coding-agent survey share is not a count of people who turned on memory. Claude Code loads `CLAUDE.md` when the file exists; Copilot Memory became generally available on 28 Oct 2026, three days before this note, so almost none of the May–July Copilot survey share is the new memory product.
- Download totals that include CI (pepy says CI is included; Benchclaw says pypistats includes automated installs) are an upper bound on adoption, not users. Mem0’s two figures (about 2.55M vs about 2.02M) disagree and both can be true because the windows and endpoints differ.

### Gaps

- No opened Anthropic, Microsoft, GitHub, or Cursor page gives a late-2026 absolute user count for Claude Code, Copilot, or Cursor. Aggregators conflict and were not treated as fact (see the ranking section).
- Stack Overflow’s opened narrative rounds to 66% and 59% and does not show the base. The 65.5% / n=12,255 table was not opened.
- npm download counts for `@anthropic-ai/claude-code` and `@letta-ai/letta-code` were not opened. Letta, Zep Cloud, Continue, and both AgentMemory projects have no opened user or download figure.
- Codex, Cline, OpenCode, and Windsurf appear in surveys but their memory or rules formats were not opened, so they are not scored for job-1 overlap below.

## What exact overlap does each product have with a git front end, encryption, real-time sync, and team sharing?

### Takeaway

Letta MemFS is the only opened product that stores agent memory as a git repository the agent edits with ordinary files, and the only one that documents org-owned git repos shared across agents. It does not, in the pages opened, claim encryption or real-time sync; sync is commit and push, and shared repos are cloud-only. Claude Code, Cursor, and Copilot custom instructions are git-shaped only because they are Markdown in a repo; their automatic memories are not a git front end. Mem0, Zep/Graphiti, and LangGraph store database or graph records, not git. Mem0 is the only one of this set with an opened-or-extracted vendor encryption claim (at rest, in transit, BYOK), and that claim is not end-to-end and not git. Nobody in the opened docs claims real-time encrypted git storage.

### Cited Findings

- **Letta MemFS (closest to job 1).** “The memory itself is part of the agent’s state, held in a git repository that belongs to the agent — hosted by Letta for cloud agents.” “MemFS projects that repository onto whatever computer the agent is running on, as a real checkout the agent reads and edits with ordinary file tools. Edits are local until committed and pushed, at which point they become the agent’s memory everywhere. All Letta agents use MemFS.” Files are Markdown with YAML frontmatter. “Every memory edit is committed to the MemFS git repository. This provides version history, conflict resolution, and a clear boundary between saved memory and uncommitted changes.” “Local-only agents commit to a repository on the current machine.” No semantic index by default. — [MemFS docs](https://docs.letta.com/concepts/memfs/) **opened**
- **Letta shared memory (people/agents).** “Each shared memory repository is a Git repository hosted in Letta Cloud and owned by your organization.” MemFS is one agent; the shared repo is for “knowledge and working files between agents.” “The agent must commit and push its changes. Other agents can then pull those commits.” “Shared memory repositories require cloud-hosted agents. Local agents use their own MemFS and project files.” Not a human group inbox. — [Shared memory docs](https://docs.letta.com/concepts/shared-memory/) **opened**
- **What Letta does not do, on the pages opened.** No encryption, at-rest, or end-to-end claim. Sync is git commit/push/fast-forward, not a real-time multi-writer filesystem. No admin audit-trail product described. Jobs 5–7: there is an org owner for cloud shared repos (partial team management) and a `letta` CLI (`letta shared-memory create`, `letta server` on the README extract). It is not documented as a text-protocol subprocess of an arbitrary harness. — [MemFS](https://docs.letta.com/concepts/memfs/), [Shared memory](https://docs.letta.com/concepts/shared-memory/) **opened**; [letta README](https://github.com/letta-ai/letta) **search extract**
- **Claude Code `CLAUDE.md` / rules (git only if the user commits them).** “CLAUDE.md files are markdown files” written by the user; auto memory is “notes Claude writes itself.” Project instructions at `./CLAUDE.md` or `./.claude/CLAUDE.md` are “Shared with: Team members via source control.” User instructions live at `~/.claude/CLAUDE.md` (“Only you”). `CLAUDE.local.md` is meant for `.gitignore`. Auto memory: “Each project gets its own memory directory at `~/.claude/projects/<project>/memory/`.” The directory name comes from the git repo so worktrees on that machine share it. Auto memory is on by default in local sessions. Claude can read `AGENTS.md` when no project `CLAUDE.md` is present (v2.1.277 or later). Managed policy files can be deployed by IT to a system path. — [Claude Code memory docs](https://code.claude.com/docs/en/memory) **opened**
- **What Claude Code memory does not do.** It is not a storage service. No encryption claim for these files. No real-time sync; sharing is ordinary source control, and auto memory is local to the machine, not the repo. Subagents can have their own auto memory, which is not a cross-person store. Jobs 5–7: Claude Code is a local CLI (a userspace agent the user runs). Team and Enterprise plans have Claude Code usage analytics for owners and admins (lines accepted, sessions). That is usage analytics, not an audit log of memory edits. — [memory docs](https://code.claude.com/docs/en/memory) **opened**; [usage analytics help](https://support.claude.com/en/articles/12157520-claude-code-usage-analytics) **search extract**
- **Cursor rules (git for project rules; dashboard for team rules).** “Project Rules. Stored in `.cursor/rules`, version-controlled.” “Team Rules. Team-wide rules managed from the dashboard. Available on Team and Enterprise plans.” “AGENTS.md. Agent instructions in markdown format.” “Check your rules into git so your whole team benefits.” Team Rules are free-form text, not the `.mdc` folder, and “take precedence.” Admins can enforce a rule so members cannot disable it. User Rules are global on that Cursor install. The opened doc says models do not retain memory between completions. — [Cursor Rules](https://cursor.com/docs/context/rules) **opened**
- **What Cursor does not do.** Not encrypted storage. Not real-time. Not a memory database. Project rules are static Markdown the team shares through git; Team Rules are hosted instructions, not a git repo. Cursor is the IDE/harness, not a subprocess of an arbitrary harness. No audit log of rule changes was described beyond “enforce” and the dashboard. Automatic Memories are absent from the current doc. — [Cursor Rules](https://cursor.com/docs/context/rules) **opened**
- **GitHub Copilot custom instructions (git-shaped) vs Copilot Memory (not git).** Custom instructions remain a separate mechanism. Copilot’s own memory doc says repository facts “should not be relied on as a rule that will always be followed. To provide instructions consistently, use custom instructions instead.” Copilot Memory, generally available on paid plans as of the 28 Oct 2026 changelog, stores two hosted types: “Repository-level facts” shared with collaborators, and “User-level preferences” that follow the user. Facts are viewed and deleted in repository settings, not as git files. “Forking a repository does not copy its stored memories.” Dreaming (public preview, opt-in) “proposes updates and improvements to existing skills and custom instruction files” as pull requests. Preview stat, not adoption: 93% / 42% on reviewed CLI sessions that used memory. — [Copilot Memory docs](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) **opened**; [Changelog, 28 Oct 2026](https://github.blog/changelog/2026-10-28-github-intelligence-puts-your-code-context-and-history-to-work/) **opened**
- **Copilot encryption, sync, jobs 5–7.** The memory doc does not claim a git front end or field-level encryption. It does say memories are checked for secrets and rejected, expire after 90 days by default (orgs can set repository-fact expiry from 7 to 180 days), and that some internal fields such as voting details are “not displayed on the GitHub website or included in audit logs” — which implies other memory events can appear in GitHub audit logs, but the doc does not list which ones. On Copilot Business and Enterprise, the billing org owns user-level preferences and admins can view, export, or delete them. That is team administration and a partial audit hook (jobs 5 and 6). Copilot is not a userspace subprocess of an arbitrary harness; programmatic CLI sessions have memory off unless `--enable-memory` is passed. Sync across Copilot clients is “facts captured by one surface can be used by another,” not real-time git. — [Copilot Memory docs](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) **opened**
- **Mem0 (highest-download memory product; not git).** GitHub describes it as “The Memory Layer for AI Agents — Drop-in memory infrastructure for AI agents and apps.” A security marketing page extract says “SOC 2 & HIPAA compliant,” “SOC 2 Type I certified, HIPAA-compliant, and undergoing SOC 2 Type II audit,” “BYOK encryption,” and “audit-ready logs, encrypted storage, and flexible deployment options.” A trust-center extract lists SOC 2 Type I Compliant, SOC 2 Type II In Progress, HIPAA Self-Attested, Encryption at rest, and Encryption in transit. A fetch of `https://mem0.ai/security` on 2026-10-31 redirected to `https://trust.mem0.ai/`, and that trust page returned no body, so the compliance sentences are from search extracts, not a successful full-page open. The two HIPAA wordings disagree (“compliant” vs “self-attested”). No git front end, no real-time filesystem, and no text protocol for an arbitrary harness were in those extracts. Self-host vs cloud is implied by “flexible deployment” but the OSS encryption story was not opened. Jobs 5–6 are partial and vendor-claimed (accounts, audit-ready logs), not demonstrated from docs opened here. — [mem0.ai/security](https://mem0.ai/security) **search extract; live fetch redirected**; [trust.mem0.ai](https://trust.mem0.ai/) **fetch returned no content**; [GitHub](https://github.com/mem0ai/mem0) **search extract**
- **LangGraph.** “Short-term memory (thread-level persistence)” is a checkpointer. Production example is `PostgresSaver`; docs also show MongoDB, Redis, and Oracle savers, plus `InMemorySaver`. “Long-term memory” is a store of user- or application-specific items across conversations (`InMemoryStore`, `PostgresStore`). Not git, not a hosted memory product, no encryption claim in the memory doc. Sharing across people is whatever namespace the application writes. Not a team-admin or audit product. Not a harness subprocess. The download count is the framework, which “provides the infrastructure for durable execution, streaming, human-in-the-loop, persistence, memory, and more.” — [LangGraph memory](https://docs.langchain.com/oss/python/langgraph/add-memory) **opened**; [pepy](https://pepy.tech/projects/langgraph) **opened**
- **Zep / Graphiti.** Zep’s site positions a hosted “context layer” and agent memory on temporal context graphs. Graphiti is the open-source graph engine. Benchclaw quotes the Zep repo: it “is not Zep’s product” and Community Edition is unsupported (announcement dated in that article as read on 2026-10-12; the announcement itself is from 2025). Not git. Encryption and real-time sync were not quoted from a page opened here. An MCP server is mentioned on a Graphiti marketing extract, which is a tool protocol, not a git front end. — [Benchclaw](https://benchclaw.io/ai-agent-memory/) **search extract**; [Graphiti page](https://www.getzep.com/platform/graphiti/) **search extract**
- **Aider.** Local terminal pair programmer. pepy package `aider-chat`. The README extract says it “maps your codebase” and edits projects in the terminal. ## Who is actually on top by the best available use metric, and how weak is that ranking?

### Takeaway

For people using a project-context mechanism in 2026, Claude Code is first on both opened surveys (JetBrains about 39% of professionals at work; Stack Overflow about 66% of coding-agent users), with GitHub Copilot second and Cursor well behind. That ranks the agents, not the memory files inside them, and it does not measure encryption or git sync. For a product whose job is memory, Mem0 is first on opened package downloads (about 2.0–2.6 million in a recent month, CI included), far below `langgraph` only because LangGraph’s 56 million last-30-day downloads count the whole framework. Letta, the only real git memory filesystem in this set, cannot be placed on either scale. The ranking is weak because the metrics are not the same thing and none of them counts “real-time encrypted git storage,” which no opened vendor claims to ship.

### Inferences

- Best people-metric: Claude Code, then Copilot, then Cursor, with Codex between Copilot and Cursor on JetBrains but not scored here for overlap. This ranking is reasonably strong for “which agent do developers use,” and weak for “which memory store do they use,” because the surveys do not ask about `CLAUDE.md`, rules, or Copilot Memory.
- Best dedicated-memory metric: Mem0 over Graphiti over (unknown) Letta and Zep. LangGraph should not be called the top memory product. Its download lead is about 20× Mem0 and the memory APIs are optional. Counting it first would answer “what library gets imported,” not “what memory product is used.”
- Best overlap with job 1 is Letta, and that is the worst-measured product in the set. Popularity and overlap point at different tools. Nothing reviewed is a widely used real-time encrypted git memory service.
- Copilot Memory’s 28 Oct 2026 general availability can change the “hosted team memory” picture quickly. The May–July surveys and the 93%/42% preview quality stats do not say how many repositories have memories turned on.

### Gaps

- No single metric covers agent-memory products and coding-agent instruction files. A rank that mixes 39% of developers with 2.6M PyPI downloads is not a market share.
- Letta npm downloads, Mem0 hosted-tenant counts, Zep graph counts, and Copilot Memory enablement were not available from opened primary pages.
- Survey non-response and vendor-run fieldwork (JetBrains sells a competing AI assistant, listed at about 9%) can bias levels. The Claude Code vs Copilot order matches the independent Stack Overflow narrative, which is the reason the order is still usable. Levels should not be treated as precise.
