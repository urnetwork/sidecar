# User-reported gaps in shared agent channels and admin audit trails

As of 31 October 2026. Scope is user evidence (a person’s own words on a page that was opened) about Slack agents (Claude in Slack, Cursor Slack), AgentMail, Resend Inboxes, and enterprise audit logs for GitHub Copilot, Cursor, and Claude. Dust and Devin are included only where users discuss their audit logs. Vendor documentation is labeled as a product limit, not as demand. Feature announcements are not treated as demand.

Reddit pages for Claude Slack and Claude Enterprise admins did not load when fetched (old.reddit.com returned only a shell). Those threads are not quoted below.

## What do users say is missing when people and agents share a Slack thread or an email inbox?

### Takeaway

Opened user reports are about Cursor in Slack, not a general “shared inbox” product gap. Three independent Cursor users describe setup that dies after admin approval, an agent that cannot use private DMs or an existing DM thread, and a cloud agent that receives thread text but not stable thread IDs and, at times, not the screenshots in that thread. Claude’s own docs describe admin approval, a hard cap on how much of a Slack thread the bot sees, and chat history that does not cross into claude.ai; no user complaint page for those Claude limits loaded. AgentMail’s opened complaints are deliverability, inbox-count pricing, and a create-then-send race, not a missing shared history. Resend Inboxes is nine days old (announced 22 October 2026); no user complaint about it was found.

### Cited Findings

- Cursor Slack, setup after admin approval. Robin_Schmidt, 28 October 2026: “Our Slack admin approved it, and Slack sent the message ‘Your request to install Cursor has been approved.’” The install page then showed “Internal Server Error”, the dashboard Slack row had Connect greyed out, and `/invite @Cursor` returned “A valid member name is required”. Impact, in the same post: “Slack-triggered automations can’t fire in any channel.” Cursor staff (same thread) said the 500 was on Cursor’s side and “failing for everyone”, and that the greyed Connect button “is only available on paid plans”. — [Cursor forum](https://forum.cursor.com/t/slack-app-install-fails-with-internal-server-error-at-api-install-slack-app-and-connect-is-greyed-out/176474)
- Cursor Slack, private DMs. SeanCorc, 23 May 2026: “When I try to invoke cursor slackbot from private dms I cannot”. After a workaround, same user: “Ah I see I have to create a new chat - can’t just add it in the existing thread. Ideal is that I can just from any message do a @cursor private dm, private channel, or public channel”. Staff called channel-only mentions “a known limitation”. — [Cursor forum](https://forum.cursor.com/t/cursor-slack-bot-in-private-dms/161402)
- Cursor Slack, thread context the agent cannot use. Robin Weston, 18 March 2026: “when I trigger Cursor from Slack, it doesn’t pass the thread ID (or even the channel) in the context.” The pasted context had channel name and message text, with images reduced to “[Image 1]”. Sometimes images don’t get carried over at all from Slack into the cloud agent.” Staff said vision bytes can reach the model but “the agent can’t download them or attach them anywhere as files.” — [Cursor forum](https://forum.cursor.com/t/missing-slack-images-and-thread-context-in-cloud-agents/155130)
- Vendor limit, Claude in Slack, not a user complaint. A Slack admin must approve the app; a non-admin sees “Request to install”. “Conversations you start in Slack don’t appear in your claude.ai chat history.” Help center: a channel mention includes the last 20 messages; a thread mention includes the last 50; forwarding a thread includes the last 100. - Vendor limit, Claude Tag troubleshooting (docs, not a user post). - AgentMail, opened user and commenter statements, none about a shared human/agent transcript. HN commenter (username not in the matched extract): “Looked into this for my clawdbot, but ended up just using himalaya CLI connected to a new Gmail.” Founders replied: “We have had some users get banned from Gmail for using it Clawdbot.” Another commenter asked for “10x the amount of inboxes per plan” if volume limits stay, for “100s of agents that send limited email each.” A different commenter attacked deliverability (“you have no idea” about reputation and Proofpoint), which is skepticism at launch, not a post-use bug report. Founders said allowlists exist and they were “beginning some work on prompt isolation within api soon.” — [HN launch thread](https://news.ycombinator.com/item?id=46812608)
- AgentMail SDK, not a shared-inbox gap. GitHub issue, 5 April 2026: `inboxes.messages.send()` immediately after `inboxes.create()` returns 404 “Inbox not found” for about 1–2 seconds, while `inboxes.list()` already shows the inbox. Workaround stated by the reporter: “Adding a ~2 second delay”. — [agentmail-node #14](https://github.com/agentmail-to/agentmail-node/issues/14)
- Third-party wrapper, not AgentMail’s product. israelkalush-lgtm, 20 March 2026, on OpenClaw’s AgentMail plugin: WebSocket `message.received` events are “silently dropped — no auto-reply is generated, no error is logged,” while the same credentials work in a standalone script. Email is visible in the AgentMail dashboard. — [openclaw #51168](https://github.com/openclaw/openclaw/issues/51168)
- Resend Inboxes. Announced 22 October 2026 as a shared inbox “worked by people and agents side by side.” That sentence is the vendor’s claim, not a user request. Searches of GitHub release notes, the announcement post, the launch video’s comments, and the days after 22 October found no user report that a person and an agent lose thread history, cannot see the thread, or lack an audit of who replied. YouTube comments are about the video (“This could have been an email”, “is there a better cheaper alt?”), not product gaps. A 19 October 2026 r/SaaS post about Resend suspending a multi-tenant account is three days before Inboxes and is about transactional sending, so it is not evidence about Inboxes. — [Resend announcement](https://resend.com/blog/announcing-inboxes)

### Inferences

- The shared-channel complaints that were actually opened are narrow and operational: the bot is not installed, it is not in the DM, or the cloud agent gets a lossy copy of the Slack thread (no IDs, images that are not files and sometimes not present). They are not requests for one canonical record of the Slack conversation plus the code change.
- Claude’s split history and 20/50-message window are product limits. Without a loaded user thread, it is not established that users are asking Anthropic to merge Slack and claude.ai history.
- AgentMail’s opened friction is “email is hard” (Gmail bans, reputation, inbox quotas, a propagation race), which matches the problem the founders said they were replacing. It is not evidence that buyers want an admin audit trail inside the inbox.

### Gaps

- Reddit threads that look relevant did not load: Claude Slack connector/email mismatch (October 2025), a Claude Code user describing Slack as memory because session files drop context (30 April 2026), and Slack DM access blocked without admin OAuth (9 January 2026). Those cannot be quoted.
- No opened user statement that Claude in Slack “cannot see the thread” beyond the vendor’s 20/50/100 message caps.
- No opened user complaint about Resend Inboxes. Nine days is too short to treat silence as satisfaction.
- Dust and Devin are not inboxes in the reports that were opened. No user discussion of them as shared channels was found.

## What do admins or developers say they cannot see: prompts, tool calls, what the agent changed, local sessions versus cloud sessions?

### Takeaway

Cursor has a real, repeated complaint: the Enterprise audit log is an admin log, and developers still cannot see prompts, per-tool records, or whether a human approved the command that ran, especially on a local machine. GitHub’s own Copilot docs say the audit log omits local prompts; two opened GitHub discussions ask how to get prompt or suggestion text, and a third asks whether admins can see prompts at all (a privacy question, not a demand for more logging). Claude’s opened help page says audit-log export omits chat title and content. No opened user post was found complaining about that Claude omission, or about Dust or Devin audit logs.

### Cited Findings

Vendor limits (product docs, not user demand):

- GitHub, page opened 31 October 2026: the Copilot audit log records plan and policy changes and “Agent activity on the GitHub website.” “The audit log does not include client session data, such as the prompts a user sends to Copilot locally.” GitHub says a custom solution is required, “for example, some companies use custom hooks to send Copilot CLI events to their own logging service.” Retention on the page is 180 days. — [Reviewing audit logs for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/review-audit-logs)
- Cursor docs, retrieved as the compliance page: “Payloads carry identifiers, names, and changed settings, never prompts, agent output, generated code, or credentials.” Explicitly not logged: agent responses, prompts, and generated code (hooks are the suggested path); Grok Bot shell and browser actions (those are separate Action Recording / OpenTelemetry events); Cloud Agent automation runs; failed sign-ins; secret values. Audit logs are Enterprise-only. — [Cursor compliance and monitoring](https://cursor.com/docs/enterprise/compliance-and-monitoring)
- Claude help page, opened: “title and content of chats and projects are not available to be exported in audit logs (only their unique identifiers will be exported).” Chat inputs and outputs are a separate Primary Owner data export, not the audit log. Enterprise only, 180 days, email link valid 24 hours. “You can’t export data using the Export logs button if your organization uses customer-managed encryption keys.” Events that are recorded include `conversation_created`, `conversation_deleted`, and `conversation_renamed` (the rename event can carry `new_name`), plus file upload, without message bodies. — [Access audit logs](https://support.claude.com/en/articles/9970975-how-to-access-audit-logs)
- Claude Compliance API, vendor article as returned in search (full article was not re-fetched). Anthropic says session endpoints return “prompts, responses, and tool activity” in one session record for Cowork and for Claude Code CLI and desktop. The same article: “This beta doesn't include Claude Code on the web, Claude Code accessed through the Claude Platform, or sessions run on Amazon Bedrock, Google Cloud's Vertex AI, or Microsoft Foundry.” A separate help page says HIPAA local mode’s Compliance API can read local Claude Code and Cowork content, and “Audit logs and data exports don't include session content.” — [Compliance API coverage note](https://claude.com/resources/articles/compliance-api-cowork-and-claude-code); [HIPAA local mode](https://support.claude.com/en/articles/17318731-use-claude-code-local-mode-and-claude-cowork-local-mode-on-a-hipaa-ready-enterprise-plan)
- Dust and Devin, vendor only. Dust’s Enterprise audit log documents `agent.executed` and `tool.executed` and says it can tell human actions from AI actions via metadata. Devin’s audit schema includes `create_session` and `send_message` with `session_id` and `privacy_mode`; the opened schema snippet does not show message body or tool arguments. No user post was found objecting to either limit. — [Dust audit logs](https://docs.dust.tt/docs/user-documentation/admins/audit-logs/audit-logs); [Devin audit logs](https://docs.devin.ai/enterprise-api/audit-logs)

User statements, Cursor (each person counted once in the next section even if they posted twice):

- Trong Vo, 6 May 2026, team admin: “I am managing a team using Cursor, and I want to control or monitor employees’ prompt/response data. I’ve checked both the dashboard and the API but couldn’t find this capability.” Cursor staff Mohit, same day: “Cursor does not expose prompt or response content to team admins. This is an intentional privacy boundary — even on Teams and Enterprise plans, individual conversation content is only visible to the user who created it.” Staff pointed at per-member usage stats and a per-machine `beforeSubmitPrompt` hook. — [Cursor forum](https://forum.cursor.com/t/control-or-monitor-employees-prompt-response-data/159854)
- Ville Pispa, 30 March 2026: “None of these proposals or decisions are persisted in any queryable, exportable form.” He quotes the product line “We do not log agent responses or generated code content” and says hooks “cover prompts submitted and code generated — but not tool call proposals, approval/rejection decisions, timestamps, or which model requested the action.” The question he says orgs cannot answer: “What did the AI agent do, and did a human authorize it?” He asks for the trail on the Enterprise SIEM stream and as local JSONL next to transcripts. — [Cursor forum](https://forum.cursor.com/t/platform-level-audit-trail-for-agent-tool-call-proposals-and-user-approval-decisions/156247)
- Aleksey Safonov, 23 June 2026, same thread: a log of propose / decide / result is still not enough. “without exact action binding, it may still be impossible to prove that the executed action was precisely the action the user approved.”
- Raffaele Preziosi, 6 May 2026, same thread: the IDE shows an approval wait “but that state is not exposed as a hook/event,” so local tools cannot tell “model is working” from “agent is blocked waiting for the user.” He bumped the thread on 25 July 2026.
- znuttyone, 9 October 2026, same thread, local machine: “no audit trail for commands requested on a user’s local machine.” A command-approval card appeared; “the agent could not find a record of the request, and that there is no system-wide audit trail.” “Right now a request against my own machine can’t be traced to its source.” He set local commands back to ask-first.

### Inferences

- On Cursor, “what the agent changed” and “did a person approve it” are the complaint, more than “show me the whole chat.” Ville, Aleksey, and znuttyone want the proposal, the decision, and the executed command tied together. Ayush explicitly does not want full dumps. Trong Vo is the one opened admin who asked for prompt and response text, and staff refused that as a privacy boundary.
- Local versus cloud is a Cursor hook/OTel gap, confirmed by staff: one export path covers IDE, CLI, and Cloud Agents for counts and lifecycle, and still does not record each tool or MCP call. znuttyone’s gap is local and worse: the command card is not in any transcript he or the agent could search.
- GitHub’s split is documented and echoed by users: website agent actions can be in the audit log (`actor:Copilot`); local IDE/CLI prompts are not. The opened GitHub threads do not show admins saying they cannot see what the coding agent changed on GitHub.com. They show people asking about prompt text.
- Claude’s audit log, on the page that was opened, is an event log with conversation IDs and not message bodies. Content is a different export, and CMEK blocks the audit-log button. The local-versus-Bedrock/cloud hole is a vendor statement. No user was found, on a page that loaded, saying they hit that hole.

### Gaps

- No opened user complaint that Claude Enterprise audit logs omit prompts, or that Bedrock, Vertex, Foundry, or cloud Claude Code sessions are missing from the Compliance API. The omission is documented by Anthropic; demand for a fix was not found.
- No opened user complaint about Dust or Devin audit logs. Do not infer that those logs include or exclude prompt text beyond the schema snippets above.
- The 26 December 2025 Cursor hooks post’s username was not recovered. Archit Baweja’s February 2026 “Access Cursor CLI logs” follow-up was only seen as a related-topic excerpt and was not opened, so it is not counted.
- Copilot discussion replies that “admins cannot see prompts” are unverified against a staff answer. The GitHub doc is the vendor source of that limit.

## Are people asking for one record of the conversation and the action, or are the complaints narrower?

### Takeaway

Narrower. The opened requests are for a specific missing field: prompt text for a team admin, tool-call parameters in the CLI, or a queryable chain of proposed tool call, human decision, and what actually ran. One Cursor thread asks for that chain on the existing Enterprise stream and in a local JSONL file beside the transcript. That is an action record linked to an approval, not one object that stores the Slack or email conversation and the code change together. Nobody who was opened asked for a single inbox-plus-audit product.

### Cited Findings

- Ville Pispa, 30 March 2026, asks to “Append to existing Enterprise audit log stream” and “persist locally… (JSONL alongside agent transcripts).” The fields are timestamp, model, tool type, parameters, accept/reject/auto-approve, and success/failure. He does not ask for the chat text in that record. — [Cursor forum](https://forum.cursor.com/t/platform-level-audit-trail-for-agent-tool-call-proposals-and-user-approval-decisions/156247)
- Aleksey Safonov, 23 June 2026, same thread: three records, ActionProposed, ActionDecided, ActionCompleted, sharing an `action_id`, so the trail can prove “the executed action was exactly the action that was approved.” Still an action lifecycle, not a conversation archive.
- znuttyone, 9 October 2026, same thread: “which agent, subagent, or routine asked, when, why, the exact command, the approval decision, and the result, all searchable by request ID.” “Why” is the closest any opened user comes to wanting the conversation. He still describes a command audit, and he says the agent could not find the request inside existing transcripts.
- Ayush Shyam Agrawal, 4 September 2026: “Native observability would make Cursor the system of record for agent behavior — not just the IDE.” He defines that record as spans with redacted I/O summaries, “not full dumps,” plus parity for Cloud Agents. — [Cursor forum](https://forum.cursor.com/t/native-agent-observability-sessions-mcp-tool-spans-export-hooks-are-not-enough/170626)
- Trong Vo, 6 May 2026, wants “employees’ prompt/response data” in the dashboard or API. That is conversation content, and he does not mention tool calls or a joined action record. — [Cursor forum](https://forum.cursor.com/t/control-or-monitor-employees-prompt-response-data/159854)
- Akshay Rajpal, 21 November 2025, wants CLI logs to show the tool calls and thinking he already sees in the IDE chat. That is parity with the transcript, not a new combined admin record. — [Cursor forum](https://forum.cursor.com/t/no-cursor-cli-logs/143566)
- Robin Weston, 18 March 2026, wants the Slack screenshot to survive into the cloud agent so it can be attached to a ticket. That is thread context for the action, and he does not ask for an admin log of both. — [Cursor forum](https://forum.cursor.com/t/missing-slack-images-and-thread-context-in-cloud-agents/155130)
- GitHub discussions #188459 and #120745 ask for prompt text or suggestion text. They do not ask to join that text to the pull request or shell command the agent made.
- Vendor, not demand: Anthropic’s August 2026 Compliance API note says Cowork and local Claude Code sessions can come back as one server-side transcript of prompts, responses, and tool activity. That is Anthropic shipping a combined session record. It is not a user request, and the same note excludes web, platform, Bedrock, Vertex, and Foundry sessions. — [Compliance API coverage note](https://claude.com/resources/articles/compliance-api-cowork-and-claude-code)

### Inferences

- “One record” shows up only as a vendor description (Claude Compliance API session transcript) or as Ayush’s phrase “system of record,” which he immediately narrows to redacted spans. The user language that repeats is “audit trail” for the command and the approval.
- Conversation content and action content are separate complaints, often from people with opposite privacy preferences. Trong Vo wants admins to read prompts. BKSX0 wants to know that admins cannot. Cursor staff and the GitHub doc both treat prompt text as out of the admin audit log on purpose. The action/approval trail is what regulated-sounding Cursor users say is still missing after that privacy line.
- Shared Slack or email and the admin audit log are not the same complaint in the pages that were opened. Slack reports are about the agent’s context. Audit reports are about the IDE or cloud agent’s tools. No opened user ties an email inbox to an enterprise audit event.

### Gaps

- No opened user asked to merge a Slack thread, an email thread, and the agent’s tool log into one record. Absence is not a finding that they would reject it.
- Claude’s combined Compliance API transcript may already cover the “one session record” case for local Claude Code and Cowork. Whether admins find it incomplete was not visible in a user post that loaded.
