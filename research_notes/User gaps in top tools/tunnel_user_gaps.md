# User-reported gaps when publishing a local port (ngrok, dev tunnels, Cloudflare Tunnel, Tailscale Serve/Funnel)

Scope: what people say goes wrong when they expose a local service, especially for an agent UI or a webhook, as of 2026-10-31. Prefer 2025–2026. Quotes below are from pages opened for this note. Lines labeled **vendor limit** are product documentation, not a complaint. Reaction counts are included only when that page showed them.

Reddit threads turned up in search (ngrok splash page, traffic-policy errors, Funnel ports) but old.reddit.com returned a login wall, so those threads are not cited. The archived `inconshreveable/ngrok` client was not a useful 2025–2026 source; recent complaints are on current ngrok, cloudflared, Tailscale, and Microsoft docs.

## What do users say goes wrong or is missing when they expose a local service, especially for an agent or a webhook?

### Takeaway
The opened 2025–2026 complaints cluster on four failures: a public HTTPS URL that anyone can call, a login gate that a webhook or non-browser client cannot pass, a name or process that does not survive the next run, and a public path that looks up while it is actually down. Request-level audit is mostly a documented product limit, not a thread of user complaints that this pass could open.

### Cited Findings

#### ngrok

- **Vendor limit (interstitial, still current).** Free-tier HTML browser traffic gets an interstitial. The visitor must click Visit; a cookie then hides it for that domain for 7 days. Programmatic API access is documented as unaffected. Bypass is the `ngrok-skip-browser-warning` header, a non-default User-Agent, or any paid plan. — [Free Plan Limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)
- **User, agent UI, 2026-02-11.** thleonard, developing a local MCP server for Claude.ai: “With ngrok (free plan), HTTP requests hit an interstitial browser warning page unless they include the header: `ngrok-skip-browser-warning: true`.” Iframe asset requests do not send that header, “they receive the interstitial HTML page instead of the expected JS/CSS assets. This breaks widget UI rendering.” The issue shows 3 thumbs-up reactions. Closed as not planned on 2026-02-16. antonpk1 (Anthropic) the same day: “We recommend using cloudflared instead of ngrok for local MCP development. It's free, has no interstitial pages, and requires no extra headers.” — [anthropics/claude-ai-mcp#53](https://github.com/anthropics/claude-ai-mcp/issues/53)
- **Vendor limit (stable name on the free dev domain).** The free plan includes one auto-assigned dev domain. “It doesn't change when you restart the agent, and `ngrok http` uses it automatically.” Custom names, reserved domains, and bringing your own domain require a paid plan. — [Free Plan Limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)
- **Vendor limit (visitor login is capped, not absent).** Free monthly quotas include 20,000 HTTP requests, 1 GB data transfer out, 500 webhook verifications, and “Traffic identities (OAuth/OIDC MAU) | 3 / month.” Also 10,000 logs and events per month, 3 online endpoints, 1 user, 5 traffic-policy rules per policy. — [Free Plan Limits](https://ngrok.com/docs/pricing-limits/free-plan-limits)
- **Vendor limit (dashboard SSO is a paid add-on; this is not visitor auth).** “Dashboard Single Sign-On is available on the Pay-as-you-go plan with the SSO & RBAC add-on enabled.” The same page says endpoint OAuth is a different feature. No 2025–2026 user post complaining about paying for dashboard SSO was opened. — [SSO docs](https://ngrok.com/docs/iam/sso)
- **Vendor limit (what the admin record keeps).** Cloud Traffic Inspector: free accounts keep 24 hours; Hobbyist and pay-as-you-go keep 72 hours; a pay-as-you-go add-on goes up to 90 days; after that, events are purged. The local agent UI at port 4040 shows HTTP request and response bodies, but “If an entity-body is too long, ngrok may only capture the initial portion of the request body.” “Inspection is only supported for HTTP endpoints. TCP and TLS endpoints don't support inspection and don't show up in the inspection interface.” Local replay does not re-apply cloud endpoint policies. — [Traffic Inspector](https://ngrok.com/docs/obs/traffic-inspection); [agent web inspection](https://ngrok.com/docs/gateway/agent/web-inspection-interface)
- **User, tunnel dies, 2025-07-17, one wrapper.** ananyo141, `fm ngrok` on macOS: “after some time or if the device is suspended/locked, the command keeps running but the tunnel is broken.” Expected: “Even after multiple suspend/lock or a long time, the connection to the ngrok tunnel should be persistent.” The same report says native ngrok inside the container “is persisted even after multiple restarts,” so this is not evidence that the ngrok agent itself drops on sleep. — [rtCamp/Frappe-Manager#269](https://github.com/rtCamp/Frappe-Manager/issues/269)

#### Microsoft dev tunnels and VS Code port forwarding

- **Vendor limit (still preview).** “This feature is currently in public preview. This preview version is provided without a service-level agreement, and it's not recommended for production workloads.” Also: “Dev tunnels is for adhoc testing and development, not for production workloads.” Page `updated_at` 2026-02-12; `ms.date` 2025-03-27. The preview banner was still on the page when opened. — [What are dev tunnels?](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/overview)
- **Vendor limit (private means the owner’s login; public means anyone with the link).** VS Code Ports, page dated 2026-10-28: by default a forwarded port is Private and “you'll be required to sign in with the same GitHub account you used to start the port forwarding process.” Public ports “don't require sign in.” “If you've opened a Public port, any user with your link can access the forwarded service.” “Port forwarding currently exposes only locally-running services. Remote connections aren't supported yet.” Bandwidth and active-machine limits exist and “are subject to change.” — [VS Code port forwarding](https://code.visualstudio.com/docs/debugtest/port-forwarding)
- **Vendor limit (anonymous, tokens, and an interstitial).** Default access is the creating Microsoft, Entra, or GitHub account. `--allow-anonymous` removes authentication. A client access token can be sent as `X-Tunnel-Authorization: tunnel <TOKEN>` so a non-interactive client need not be anonymous. “The tokens expire after some time (currently 24 hours).” First browser GET of a web-forwarding URL shows an anti-phishing interstitial unless the method is not GET, `Accept` is not `text/html`, the request has `X-Tunnel-Skip-AntiPhishing-Page` or `X-Tunnel-Authorization`, or the user already clicked continue. — [Dev tunnels security](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/security)
- **Vendor limit (the route for the next run).** `devtunnel host` without a prior `devtunnel create` “creates a temporary tunnel that is deleted once the connection is closed.” Unused tunnels are deleted after 30 days of no activity (sliding window; custom expiration 1 hour to 30 days). Anonymous access can be time-limited from 1 hour to 30 days and is then removed. Microsoft’s own advice: reuse one tunnel so “the dev tunnel web forwarding URL can be stable instead of changing on every use.” — [Dev tunnels FAQ](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/faq)
- **Vendor limit (quotas, including the 10-port cap).** Limits reset monthly: 5 GB bandwidth per user, 10 tunnels per user, 1,000 active connections per port, 10 ports per tunnel, 1,500 HTTP requests per minute per port, up to 20 MB/s per tunnel, 16 MB max web-forwarding HTTP request body. — [Azure subscription limits, Dev tunnels](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits#dev-tunnels-limits)

#### Cloudflare Tunnel, cloudflared, and Quick Tunnels

- **Vendor limit (quick tunnel is a public, disposable URL).** Docs last updated 2026-09-30. “Anyone with the URL can access your local service. The URL stops working when you stop the `cloudflared` process.” Limitations: no uptime guarantee; 200 in-flight requests, then HTTP 429; no Server-Sent Events; “Email authentication requires an interactive browser session. It does not support non-interactive clients.”; “The hostname changes each time you create a Quick Tunnel.” Quick Tunnels are “for testing and development.” — [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
- **User, the new email gate does not stay logged in, 2026-10-06, still open.** decli, cloudflared 2026.10.0 on macOS, `--allowed-mail`: “the authenticated session expires roughly 5 seconds after a successful One-Time PIN login.” After that, “every GET is redirected back to the login page and every non-GET request gets a plain `401 Unauthorized`.” “In practice the protected site cannot be used.” Expected: “After passing the email check, the session should last long enough to use the site.” The reporter says the code’s own cap is 4 hours. The issue shows 6 thumbs-up reactions, plus other emoji reactions. — [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752)
- **Same bug, more than one person.** CarlosBreiCo, 2026-10-07, Windows, cloudflared 2026.10.0: the HTML arrives, then CSS, JS, and manifest requests are sent back to `login.trycloudflare.com`, which “looks like an application CSP bug.” “Until the broker issues a sane `identity_exp`, `--allowed-mail` quick tunnels are effectively unusable.” The same origin without `--allowed-mail` “serves everything end-to-end.” gerrywastaken, 2026-10-08: “I spent so long thinking this was an issue on my end. … So much wasted time and retyping of my email address every damn time.” lxtuyen, 2026-10-09: “I'm experiencing the same issue.” — [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752)
- **User, wants a record of the auth decision without the request, 2026-10-18.** jinkoushibatakumi-code, cloudflared 2026.10.1, Ubuntu: after a fresh PIN, a same-origin JSON POST returned plain `401`. “Existing info-level tunnel logs did not record the authentication outcome.” Asked: “Is there a supported fix, or a way to obtain only the authentication outcome without exposing sensitive request data, weakening protection, or restarting/regenerating the tunnel?” — [cloudflare/cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752)
- **User, quick-tunnel hostname and an agent connector, 2026-02-11.** thleonard, alternatives considered: “Cloudflared tunnels in free plan avoids this issue but generates a new random URL each run, which forces to create a new connector each time the tunnel is killed (which is painful).” antonpk1, 2026-02-16, agrees the URL changes when the tunnel process is killed, and says you can edit the existing connector rather than recreate it, and that you need not restart cloudflared when only the local server restarts. — [anthropics/claude-ai-mcp#53](https://github.com/anthropics/claude-ai-mcp/issues/53)
- **Vendor limit (tunnel “audit” is not a request log).** Tunnel audit logs, last updated 2026-05-01, record only three actions: Registered (connector connected), Unregistered (connector disconnected), and CNAME add (a DNS record for the tunnel). They do not record the HTTP request or body. — [Tunnel audit logs](https://developers.cloudflare.com/cloudflare-one/insights/logs/dashboard-logs/tunnel-audit-logs/)

#### Tailscale Serve and Funnel

- **Vendor limit (Funnel is beta, public, and three ports).** Page last validated 2026-01-20. “Tailscale Funnel is currently in beta.” It shares a local service “for anyone to access—even if they don't use Tailscale.” Serve is the alternative “only with other devices in your tailnet.” Limitations: only the tailnet `ts.net` DNS name; “Funnel can only listen on ports `443`, `8443`, and `10000`”; TLS only; “Traffic sent over a Funnel is subject to non-configurable bandwidth limits”; the same port cannot be Serve and Funnel at once (the latest command wins, and the port is then either fully private or fully public). — [Tailscale Funnel](https://tailscale.com/kb/1223/tailscale-funnel)
- **Users, wrong port looks configured and then times out. Repeated into 2025–2026.** dkokotov, 2024-01-04, issue still open: `tailscale funnel --https=9443` prints “Funnel on” and works inside the tailnet, “but requests from the outside will time out.” “one can only expose a maximum of 3 different services via Funnel as far as I can tell.” Two thumbs-up. AnklePanker, 2025-03-29: “I have ran into the same issue.” Narvath, 2025-10-24: an Immich funnel “worked for some time and then became unreachable” and `funnel status` “shows no active funnel.” “I guess I'll use 443, 8443 or 10000.” alexwlchan (Tailscale), 2026-07-31: the CLI should be using `CheckFunnelPort` and is not. — [tailscale/tailscale#10742](https://github.com/tailscale/tailscale/issues/10742)
- **Users, TCP mode has the same three ports, 2025.** kellytrinh, 2025-01-14: external monitoring of Minio works on 443, 8443, and 10000 and hangs on 10001. “I want to avoid clashing with HTTPS port and run consistent with internal minio port setup.” liweishu, 2025-08-03, quoting the docs’ allowed-port line: “TCP cannot be mounted through the URL path, and even less than three ports are really insufficient.” Issue still open. — [tailscale/tailscale#14625](https://github.com/tailscale/tailscale/issues/14625)
- **Users, public Funnel down while the tailnet path still works, 2026-08-04.** singh45393-png, Tailscale 1.102.1: status shows Funnel on for 443 and 10000, tailnet clients work, “External users (friend's device, phone on LTE) cannot access the Funnel URL.” Browser: `ERR_CONNECTION_CLOSED` or `SSL_ERROR_SYSCALL`. “The Funnel was working 2 days ago … and stopped working suddenly.” brad0rnz the same day: “Same issue,” with `peerapi: ingress: denied; no ingress cap`. MHEAD666-DOT: broken on 1.102.1, fixed by downgrading to 1.96.4 with no other change; `funnel status` “reports ‘on’ even when the actual public path is completely broken.” IckeSH: 1.98.10 worked, 1.102.1 did not, 1.98.10 worked again (2 thumbs-up on that comment). rknightion: same on Fedora (2 thumbs-up). hyblon and alastairherd: same on Debian arm64 and Raspberry Pi OS. bradfitz (Tailscale) the same day: pull 20745 is the fix for 1.102.2. The issue was closed that day. — [tailscale/tailscale#20739](https://github.com/tailscale/tailscale/issues/20739)
- **The 1.102.1 fix did not reach every install.** TobiasWooldridge, 2026-08-18: “This regression is still affecting the current macOS App Store build” 1.102.1. Tailnet HTTP 200; public anycast closes during TLS. Homebrew 1.102.2 does not help because the App Store daemon is still 1.102.1. Asked Tailscale to ship the fix on the App Store channel. — [tailscale/tailscale#20739](https://github.com/tailscale/tailscale/issues/20739)
- **A later “same symptom” report was withdrawn.** Martin3225, 2026-09-13, claimed intermittent Funnel failure on 1.102.4. On 2026-09-15 the same person wrote that comment “was wrong” and the cause was a tun MTU below 1280, which dropped IPv6 and therefore Funnel ingress. bcreane (Tailscale), 2026-09-14, described a separate mechanism: if the node’s control connection drops, “control immediately removes it as an ingress target” and external clients fail the TLS handshake until control returns. That is a vendor explanation on the issue, not a count of how often users hit it. — [tailscale/tailscale#20739](https://github.com/tailscale/tailscale/issues/20739)

### Inferences
- For an agent widget or a browser that cannot set a custom header, ngrok’s free interstitial is a functional break, not a warning the user can click through. A webhook POST is in the class ngrok says the interstitial does not affect. Those are different jobs.
- Cloudflare’s October 2026 attempt to stop “anyone with the URL” (`--allowed-mail`) is the feature users are hitting, and on the builds they reported it does not keep a session. Because it requires a browser, it also cannot be what a webhook sender uses, even after the session bug is fixed.
- Dev tunnels’ private mode is a login, so a webhook caller that cannot sign in with the owner’s GitHub or Microsoft account must be made anonymous (world-readable) or given a header token that the vendor says lasts 24 hours. That is the same fork as Funnel versus Serve: identity-gated, or public.
- “The tunnel died” in the opened 2026 Funnel thread was a client regression (ingress capability denied), plus a later vendor note that a dropped control connection removes the node as an ingress target. It is not the same failure as a quick tunnel whose process exited.

### Gaps
- Reddit, the ngrok community forum, and the Cloudflare community thread about Access requests producing no logs were not opened (login wall or not fetched). Search snippets from those places were not used.
- No opened 2025–2026 user post was found that says ngrok’s Traffic Inspector dropped a request they needed. The retention and body-truncation limits above are vendor text.
- A search snippet of a different ngrok page said OAuth is included up to 5 MAUs. The free-plan page that was opened says 3 MAUs per month. The 5-MAU page was not opened, so the conflict is unverified.
- No opened user thread was found for the VS Code “PortsPerTunnel (10)” ghost-port error. The number 10 matches the vendor port quota above. Whether users still hit stale ports in 2026 was not confirmed on a page opened here.
- Named Cloudflare Tunnel (account plus a domain) was not separately mined for user complaints. Quick-tunnel limits do not automatically apply to named tunnels.

## Which complaints line up with these jobs: authenticated reach to a local service, a public TLS name that is not world-readable, an admin record of what was called, and keeping that route for the next run?

### Takeaway
Authenticated reach and “not world-readable” are the same gap in the opened reports: the public name is either open to anyone who has it, or the lock in front of it is a browser login that webhooks cannot pass and that, on Cloudflare quick tunnels in October 2026, does not stay unlocked. An admin record of each call is a vendor gap more than a user thread. Keeping the route is a real user complaint for quick tunnels and for Funnel when the public path or the control connection drops; ngrok’s free dev domain and a created dev tunnel are the documented counters, with idle expiry and a 24-hour token on the Microsoft side.

### Cited Findings

#### Authenticated reach to a local service
- **Vendor limit.** Dev tunnels and VS Code ports are private to the creating account unless made public, extended to a tenant or GitHub org, or called with a tunnel token. Public means no sign-in. The token header exists specifically “for non-interactive clients” so anonymous access is not required. Tokens last 24 hours. — [Dev tunnels security](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/security); [VS Code port forwarding](https://code.visualstudio.com/docs/debugtest/port-forwarding)
- **Vendor limit.** Quick-tunnel email login “does not support non-interactive clients.” — [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
- **Users.** The October 2026 `--allowed-mail` reports are people trying to use that login and failing within seconds, including non-GET calls that become a bare 401. That is authenticated reach not working, not a request to remove it. — [cloudflared#1752](https://github.com/cloudflare/cloudflared/issues/1752)
- **Vendor limit.** Funnel is for people who do not use Tailscale. Serve is the tailnet-only path. One port cannot be both; the last command makes that port fully public or fully private. — [Tailscale Funnel](https://tailscale.com/kb/1223/tailscale-funnel)
- **Vendor limit.** ngrok visitor OAuth/OIDC is capped at 3 monthly active users on the free plan. Dashboard SSO is a separate pay-as-you-go add-on. The interstitial is not a login. — [Free Plan Limits](https://ngrok.com/docs/pricing-limits/free-plan-limits); [SSO docs](https://ngrok.com/docs/iam/sso)

#### A public TLS name that is not world-readable
- **Vendor limit, and the mismatch.** Quick tunnels: “Anyone with the URL can access your local service,” unless `--allowed-mail`, which is browser-only and, in the opened bug, does not hold a session. VS Code Public: “any user with your link can access the forwarded service.” Funnel: “anyone to access—even if they don't use Tailscale.” Dev tunnels’ private URL is not world-readable, but it is also not usable by a webhook that cannot log in as the owner; anonymous access is the documented escape, and the security page warns that anyone who can guess the tunnel ID can then connect. — [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/); [VS Code port forwarding](https://code.visualstudio.com/docs/debugtest/port-forwarding); [Tailscale Funnel](https://tailscale.com/kb/1223/tailscale-funnel); [Dev tunnels security](https://learn.microsoft.com/en-us/azure/developer/dev-tunnels/security)

### Inferences
- The job “public TLS name that is not world-readable” is the one these tools split in half. Serve and a private dev tunnel are not world-readable and are not public to a webhook. Funnel, a public dev-tunnel port, and a quick tunnel without email auth are public TLS names that are world-readable to anyone who has the URL. The middle (a stable public name, a caller that is not a browser, a check that is not “knows the URL”) is where the opened complaints sit: email PIN that dies, OAuth capped at 3 MAUs, tokens that last 24 hours, and an interstitial that is not access control.
- “Keeping that route for the next run” splits into the name and the process. ngrok’s free dev domain and `devtunnel create` keep the name. None of the four keep serving if the local agent is gone. Funnel adds a third failure: the name and the local client can both look fine while the public ingress path is down.

### Gaps
- No opened user compared these four products head to head, and no ranking is implied.
- Cloudflare Access on a named tunnel (Google or GitHub login in front of a stable hostname) was not reviewed as a user topic. It may already be how some people get a public name that is not world-readable. Quick-tunnel `--allowed-mail` is not that product, and the docs say it cannot authenticate a non-interactive client.
- Whether ngrok’s 3-MAU OAuth cap is what stops people putting a real login on a free tunnel was not confirmed by an opened user post.
