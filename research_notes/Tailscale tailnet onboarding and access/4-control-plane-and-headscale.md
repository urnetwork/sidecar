# Tailscale control plane & trust model, admin automation surface, and Headscale (as of Nov 2026)

Scope note: This covers the control-plane / trust-model layer. Adjacent researchers cover SSO, device-join UX, and ACL syntax, so those are referenced only where they bear on the control plane. Date stamps are given where pages provided them (e.g., the tailnet-lock KB page was "Last validated Dec 2, 2025"; Headscale's latest release is v0.29.3).

## Q1: Architecture — control plane vs. data plane, and what the coordination server can/cannot see

### Takeaway
Tailscale cleanly splits a centralized **control plane** (the coordination server, a "shared drop box for public keys" that distributes keys, identity, policy, and coordination metadata) from a peer-to-peer **data plane** (WireGuard mesh). The control plane necessarily sees and stores all device *public* keys, device/connection metadata, user-identity mappings, and the full ACL policy it enforces — but private keys never leave devices and payload traffic is end-to-end encrypted, so it carries/decrypts no user data.

### Cited Findings
- The coordination server "manages control plane operations and keeps a connection to all tailnet devices. It handles device discovery, authentication, key distribution, and policy enforcement" and "distributes routing configurations and access control policies to clients, which turn them into data plane configuration." — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes)
- Core control-plane functions: "maintain a registry of all devices in a tailnet… to populate device data on the Tailscale admin console, select DERP servers, apply device posture policies, and facilitate connections," plus "distributing subnet routes, configuring DNS settings, managing IP address assignments, and updating network configurations." — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes)
- The control plane acts "like an air traffic controller" making high-level decisions; the **data plane** "runs on each device and moves encrypted packets over WireGuard," handling "encryption, forwarding, routing rules, and connection health." — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes)
- **What the control plane stores/distributes:** "Device public keys and certificates"; validated device identities and tracked registrations; access control policies (which it *enforces*, giving "devices only… public keys for peers they're allowed to reach"); endpoint info for NAT traversal plus device metadata (IP addresses, client versions); device posture policies; DNS name servers. — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes)
- **User authentication is outsourced:** "Tailscale's coordination server does not handle user authentication… [but] does manage authentication tokens and their lifecycles and enforce access control policies." Identity comes from an external OAuth 2.0 / OpenID Connect / IdP. — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes)
- **Private keys stay on device:** "Private keys are generated on each device and never leave it." / "All device public keys are stored on the coordination server." — [Control and data planes](https://tailscale.com/docs/concepts/control-data-planes); "the private key never, ever leaves its node." — [How Tailscale works](https://tailscale.com/blog/how-tailscale-works)
- **No traffic through control plane:** "Tailscale doesn't route any traffic through the coordination service." The coordination server "is essentially, a shared drop box for public keys… It just exchanges a few tiny encryption keys and sets policies." Each node "leaves its public key and a note about where that node can currently be found." — [How Tailscale works](https://tailscale.com/blog/how-tailscale-works)
- **End-to-end encryption:** "Tailscale node connections are end-to-end encrypted" and "The so-called 'control plane' is hub and spoke, but that doesn't matter because it carries virtually no traffic. The data plane is a mesh." — [How Tailscale works](https://tailscale.com/blog/how-tailscale-works)
- **Availability dependency:** If the coordination server is down, "existing connections and cached policies keep working," but devices "won't be able to establish new connections, alter their keys, or retrieve network policy updates until the coordination server comes back online." — [What happens if the coordination server is down?](https://tailscale.com/docs/reference/coordination-server-down)

### Inferences
- To deliver SSO, device approval, and ACL enforcement, the control plane *must* hold a rich metadata graph even though payloads are E2EE: (1) every node's public key; (2) the identity-to-device mapping and auth tokens (from the IdP); (3) the complete ACL/policy, since it decides which peer public keys each node receives; (4) connection/endpoint metadata (who is talking to whom, from where) for NAT traversal and DERP selection; (5) posture data. This is the "metadata the network sees" surface — the social graph, membership, and identities are visible to Tailscale by construction, even though packet contents are not.
- The `control-data-planes` page notably does **not** state in one place "the server cannot read payloads"; that claim rests on the "private keys never leave the device" + "end-to-end encrypted" statements in the architecture blog. The two sources are consistent, so the E2EE-of-payloads claim is well-supported; it is just split across pages.

### Gaps
- Tailscale's docs describe what the control plane stores functionally but do not enumerate a formal data-retention schedule for control-plane metadata (node endpoints, last-seen) in the pages reviewed.

## Q2: Tailnet lock and key authority (central)

### Takeaway
Tailnet Lock lets a tailnet distrust its own coordination server for *node admission*: new node keys must be cryptographically signed by one of the tailnet's own **trusted signing nodes**, verified by every peer via a **Tailnet Key Authority (TKA)**, so "even if Tailscale were malicious or Tailscale infrastructure hacked, attackers can't send or receive traffic in your tailnet." It protects membership authenticity, not metadata confidentiality, and has real limitations (TOFU bootstrap, device-key theft, mutual exclusivity with device approval).

### Cited Findings
- **What it is / trust shift:** Tailnet Lock stops a node from joining "unless trusted nodes sign it," placing trust "in your own nodes rather than in the coordination server." — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Threat addressed (compromised control server injecting nodes):** "If Tailscale were malicious, and stealthily inserted new nodes into your network, then Tailscale could send or receive traffic to your existing nodes in plaintext." Tailnet Lock prevents this. — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Node-key signing:** Each node has a node key and a **Tailnet Lock key (TLK)**. A new node's node key "requires a signature from a Tailnet Lock key"; the coordination server distributes the signed key, and peers verify the signature before allowing connections. CLI: `tailscale lock sign` "Signs a node key and transmits the signature to the coordination server." — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock); [tailscale lock CLI](https://tailscale.com/docs/reference/tailscale-cli/lock)
- **TKA:** The Tailnet Key Authority tracks which TLKs are trusted and verifies both node-key signatures and signatures on requests to change the trusted set. "The TKA storage mechanism is a cryptographic chain" that "can grow unbounded as customers change the tailnet's configuration." — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Trusted signing nodes:** Defined as "nodes that can be used to sign new nodes into the tailnet." You set the initial set at enablement and can add/remove later. Minimum **two** signing nodes to enable; maximum **20**. — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Signing routes:** Add a node via a client-app signing link (macOS, Windows, iOS only) or via `tailscale lock sign` from a trusted node. — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Trust on first use (TOFU):** Nodes rely on the initial Tailnet Lock state sent by the control plane ("Trust on first use (TOFU)"); to detect a compromised bootstrap, run `tailscale lock status` on each node and confirm all show the same signing keys. — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Disablement secrets:** Disabling requires a disablement secret; initialization generates **ten** but only **one** is needed; one can optionally be given to Tailscale support. If you lose your secrets and gave none to support, "the tailnet cannot be recovered." — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Limitations:** keys should be rotated "at most once per year" to limit TKA growth; Tailnet Lock and device approval are "mutually exclusive"; TLKs are stored on the device, so "If the device is compromised, the key can be obtained"; Android devices cannot be signing nodes; Tailscale "advises against" signed auth keys ("signed auth keys are not recommended"). — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)
- **Plan gating:** Available on the Personal and Enterprise plans. Page "Last validated Dec 2, 2025" (not labeled beta). — [Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock)

### Inferences
- Tailnet Lock closes the "malicious/compromised control server injects a rogue node" hole but does **not** change what the control plane *sees*: policy, identities, node public keys, and connection metadata still flow through and are stored by Tailscale. It is an integrity/authenticity control over membership, not a confidentiality control over metadata. This is precisely the distinction relevant to a design (like the caller's recURd) that wants relays/coordination to see only ciphertext.
- Its guarantees are bounded by endpoint security (a stolen TLK forges admissions), by the TOFU bootstrap (a node whose first-ever lock state was tampered with has no independent anchor except cross-checking `lock status`), and by the mutual exclusion with device approval (you cannot layer both admin gates).

### Gaps
- The KB pages reviewed do not specify the exact signature algorithm/curve used for TLKs (open-source `tailscale` client source would confirm; not fetched).

## Q3: DERP relays

### Takeaway
DERP ("Designated Encrypted Relay for Packets") servers relay DISCO discovery packets and, as a fallback when direct connections fail, already-encrypted WireGuard packets; they cannot decrypt traffic because private keys never leave devices. Clients learn DERP servers from a control-server-supplied "DERP map" and pick a home region by latency; the docs describe no separate DERP-server authentication beyond the end-to-end WireGuard crypto.

### Cited Findings
- **What DERP relays:** DERP servers "primarily use the DISCO protocol to send discovery messages" to set up direct connections, and when used as fallback "relay… encrypted WireGuard traffic between the two devices." — [DERP servers](https://tailscale.com/kb/1232/derp)
- **Cannot see plaintext:** "it's impossible for a DERP server to decrypt your traffic," because "Tailscale private keys never leave the local device that generated them." / "there is never a way for a DERP server to decrypt your traffic." — [DERP servers](https://tailscale.com/kb/1232/derp); [How Tailscale works](https://tailscale.com/blog/how-tailscale-works)
- **Selection / DERP map:** Each client gets a DERP map from the coordination server and picks a home DERP by latency. — [DERP servers](https://tailscale.com/kb/1232/derp)
- **Operation/footprint:** Tailscale runs DERP in many regions (incl. US, UK, Germany, Japan, Singapore, Brazil, Canada, Australia); "Most regions have at least three DERP servers." Users can run custom DERP via the `cmd/derper` binary (advised against in most cases). — [DERP servers](https://tailscale.com/kb/1232/derp)
- **Acronym:** Official current expansion is "Designated Encrypted Relay for Packets." — [DERP servers](https://tailscale.com/kb/1232/derp). (Note: third-party/blog sources give incorrect expansions such as "Detoured Encrypted Relay for Packets" or "Distributed Ephemeral Relay Protocol" — use the official one.)

### Inferences
- DERP trust rests entirely on the WireGuard E2EE layer, not on authenticating the relay: a malicious relay can observe timing/volume/endpoint metadata and drop/delay packets, but cannot read or inject into the encrypted tunnel. This matches the general control-plane/data-plane confidentiality story.

### Gaps
- The DERP page does not document a cryptographic admission/authentication control for which clients a DERP will relay for (beyond the control-server-issued DERP map); whether/how `derper` restricts relaying to a tailnet's keys was not confirmed from primary docs.

## Q4: Admin API (v2) — capabilities, auth, scopes, rate limits

### Takeaway
Tailscale exposes a REST Admin API at `https://api.tailscale.com` covering devices, policy file (ACL), DNS, keys/auth keys, users, posture, webhooks, and logging; it is available on all plans. Auth is via personal API access tokens (1–90 day expiry, chosen by admin) or OAuth clients (client-credentials flow, scoped, 1-hour tokens). Fine-grained scopes exist (e.g., `devices:core`, `dns:read`, `auth_keys`, `all`, `logs:configuration:read`). Specific numeric request rate limits are not published in the docs reviewed.

### Cited Findings
- **Base URL:** "The base URL defaults to https://api.tailscale.com." — [Terraform provider docs](https://tailscale.com/docs/integrations/terraform-provider) (as summarized from the provider docs/registry)
- **Resource coverage (from endpoints/scopes referenced across docs):** devices (authorize/remove, tags), policy file / ACL, DNS settings, auth keys, users, OAuth clients, OIDC federated identities, posture integrations, webhooks, and configuration logging. Example concrete endpoint: configuration audit logs at `GET /api/v2/tailnet/{tailnet}/logging/configuration` requiring the `logs:configuration:read` scope. — [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)
- **Availability:** "The API is available on all plans." — [Tailscale API](https://tailscale.com/docs/reference/tailscale-api)
- **Access tokens (API keys):** Generated on the admin console Keys page by Owner/Admin/IT admin/Network admin; "You can choose the number of days, between 1 and 90 inclusive, for the key expiry" (90 is the max, not fixed); tokens expire automatically and can be revoked early; "Tailscale-generated API access tokens are case-sensitive." — [Tailscale API (kb/1101)](https://tailscale.com/kb/1101/api); [Tailscale API reference](https://tailscale.com/docs/reference/tailscale-api)
- **Trust credentials** are offered as the delegated, fine-grained alternative to a full-permission access token. — [Tailscale API reference](https://tailscale.com/docs/reference/tailscale-api)
- **OAuth clients:** Provide "ongoing access to the Tailscale API" via OAuth 2.0 client-credentials flow (client ID + secret exchanged for an access token). "An OAuth access token expires after 1 hour. This time cannot be modified" (`expires_in: 3600`). Clients "must be owned by the tailnet, and not by an individual user," and keep working even if the creating user loses tailnet access. — [OAuth clients](https://tailscale.com/kb/1215/oauth-clients)
- **Scopes:** "Tailscale restricts scopes to only the necessary Tailscale API endpoints needed for an operation." Examples: `dns:read` (read-only DNS), `devices:core` (read/write device list, authorize/remove machines, manage tags), `auth_keys` (generate tag-scoped auth keys), `all` (all scopes + all device tags). "Tags are only relevant for tokens with the `devices:core`, `auth_keys`, or `all` scopes." Non-owner/admin users "can create an OAuth client with only the scopes and tags for which they have permissions." — [OAuth clients](https://tailscale.com/kb/1215/oauth-clients)
- **Auth-key lifetime via OAuth:** long-lived auth keys can't be generated because they "expire after 90 days, or, for one-off keys, as soon as you use them." — [OAuth clients](https://tailscale.com/kb/1215/oauth-clients)

### Inferences
- The scope model is the delegation primitive admins use for automation: scoped OAuth clients (tailnet-owned, short-lived tokens) are the recommended machine identity, while personal API keys are human/short-project tokens capped at 90 days.

### Gaps
- **Rate limits not found:** No per-second/per-minute request limit or 429 behavior for the management API is documented in the pages reviewed; the authoritative list of endpoints and any rate limits live in the JS-rendered interactive reference at `tailscale.com/api`, which could not be parsed by fetch. (Aperture, Tailscale's LLM gateway, returns HTTP 429 on *spending* quotas — unrelated to the management API.) — searched [tailscale.com](https://tailscale.com/docs/reference/tailscale-api); treat API rate limits as undocumented/unknown.

## Q5: Infrastructure-as-code & automation — Terraform, webhooks, audit/config logging

### Takeaway
Tailscale ships an official, Tailscale-maintained Terraform provider (`tailscale/tailscale`) that manages ACL policy, keys, DNS, and device settings as code; webhooks (all plans, HMAC-SHA256 signed) push node/user/policy/device-misconfig events; and configuration audit logging (all plans, 90-day retention, read via API or admin console) records a broad set of who-did-what events, with SIEM streaming as the enterprise-grade export path.

### Cited Findings
- **Terraform provider:** Official provider is `tailscale/tailscale`, maintained and published by Tailscale in the Terraform registry. Resources include `tailscale_acl` (policy file), `tailscale_dns_*` (nameservers, `dns_preferences`, `dns_search_paths`), `tailscale_tailnet_key`, `tailscale_device_key` (key expiry), `tailscale_device_tags`, `tailscale_device_subnet_routes`, and `tailscale_service`; data sources cover devices, users, services, ACL, and 4via6 prefixes. Auth via API key *or* OAuth client (`TAILSCALE_OAUTH_CLIENT_ID/SECRET`); base URL defaults to `https://api.tailscale.com`. A `terraform state replace-provider` path exists to migrate off the older community `davidsbond/tailscale` provider. — [Manage Tailscale resources using Terraform](https://tailscale.com/docs/integrations/terraform-provider); [tailscale/terraform-provider-tailscale](https://github.com/tailscale/terraform-provider-tailscale)
- **Webhooks — plan gating:** "This feature is available for all plans." — [Webhooks](https://tailscale.com/kb/1213/webhooks)
- **Webhook event categories:** Device misconfiguration (exit node/subnet with IP forwarding disabled); Tailnet management — node lifecycle (`nodeCreated`, approved, deleted, key expiry), `policyUpdate` for policy-file changes, user events (created, approved, role changes); Webhook management (`test`, `webhookDeleted`, `webhookUpdated` — last two can't be disabled). Subscribing to a category auto-subscribes to future events Tailscale adds to it. — [Webhooks](https://tailscale.com/kb/1213/webhooks)
- **Webhook delivery/security:** HTTPS POST (port 80/443; URL must be HTTPS); JSON array payloads with `timestamp`, `version`, `type`, `tailnet`, `message`, optional `data`; retried hourly up to 24h on failure. Signed with `Tailscale-Webhook-Signature` header (`t=` timestamp, `v1=` HMAC-SHA256 over timestamp+raw body, verified in constant time); reject events >5 min old to prevent replay; per-endpoint secret that does not expire. Only Owner/Admin/Network admin/IT admin can manage webhooks. Optional formatting for Slack/Discord/Google Chat/Mattermost. — [Webhooks](https://tailscale.com/kb/1213/webhooks)
- **Configuration audit logging — availability & retention:** "Configuration audit logs are available for all plans." "Configuration audit logs are enabled by default for all tailnets, and are available for the most recent 90 days"; "The period of time that configuration logs are stored cannot be configured." — [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)
- **Audit event fields:** Timestamp, Action, Actor (user/process; for control-plane actions, "the Tailscale service"), Target (user/device/tailnet), and a Diff (old/new values; policy changes include "a full diff of the previous and updated versions"). API responses also include `eventTime`, `origin`, `eventGroupID`, target `property`, and actor display/login name and ID. "Failed login attempts are not included in Tailscale events." — [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)
- **Audit event categories:** Tailnet (policy updates, key expiry, DNS, device/user approval, MagicDNS, Taildrop, HTTPS, **Tailnet Lock**, logstream endpoints, network flow logging, webhooks, posture integrations); Billing; User (create/invite/approve/role update/suspend/restore/delete/push); Group (push); Node (create/login/approve/rename/key expiry/routes/exit settings/tags/posture attributes/logout/delete); Admin console + web login/logout; Invite & Share; and create/update/revoke/expire events for API keys, auth keys, OAuth clients, OIDC federated identities, and OAuth access tokens; plus Service events (automated Tailscale actions). — [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)
- **Audit access methods:** Admin console Logs page (filter by timeframe/action/actor); API at `GET /api/v2/tailnet/{tailnet}/logging/configuration` with scope `logs:configuration:read`, required RFC3339 `start`/`end` params, "no pagination support and no maximum page size"; and availability "as a streaming source" for SIEM. — [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)
- **Log streaming (SIEM/S3):** Both configuration audit logs and network flow logs can be streamed "to your preferred log streaming integration" — a SIEM, Amazon S3, or S3-compatible service. — [Audit logs landing](https://tailscale.com/kb/1349/audit-logs)

### Inferences
- Plan gating nuance: the *baseline* audit log (90-day, API + console) is available on all plans; the enterprise-grade differentiator is **streaming/SIEM export** (and historically log streaming has been a Premium/Enterprise feature). The pages reviewed explicitly say audit logs and webhooks are "all plans" but did **not** restate a plan tier for the streaming destinations, so I could not confirm the exact plan that gates log streaming from these pages (see Gaps).
- The audit log's category list is itself a useful enumeration of everything the control plane records as an administratively meaningful action (note it logs Tailnet Lock changes and logstream endpoints — i.e., tamper-evidence of the trust controls themselves).

### Gaps
- Could not confirm from primary docs the exact plan tier (Premium vs. Enterprise) that gates **log streaming** to SIEM/S3; the audit/webhook pages say the base features are "all plans" but are silent on the streaming tier. Note explicitly as unconfirmed.

## Q6: Headscale — open-source self-hostable control server, and parity gaps

### Takeaway
Headscale (`juanfont/headscale`, BSD-3-Clause, latest v0.29.3) is an independent, reverse-engineered, self-hosted reimplementation of Tailscale's control server, scoped to a *single* tailnet for personal/small-org use. It implements the "base" Tailscale feature set — preauth keys, OIDC/web auth, ACLs+Grants, MagicDNS, embedded DERP, subnet routers, exit nodes — but is maintained by a tiny team ("not enterprise software"), explicitly aims for "feature parity with Tailscale SaaS over time," and lags on org/identity features (OIDC groups can't be used in ACLs; no SSO roles/SCIM documented) and, critically, has no documented Tailnet Lock / key-authority / trust-anchor feature.

### Cited Findings
- **Description & license:** "An open source, self-hosted implementation of the Tailscale control server." License: **BSD-3-Clause**. "This project is not associated with Tailscale Inc." — [juanfont/headscale README](https://github.com/juanfont/headscale)
- **Maturity / latest release:** The GitHub releases page lists **v0.29.3** as newest (pre-1.0), with "Minimum supported Tailscale client version: v1.80.0." — [Headscale releases](https://github.com/juanfont/headscale/releases)
- **Scope:** "a _single_ Tailscale network (tailnet), suitable for a personal use, or a small open-source organisation"; "We focus on correctness and feature parity with Tailscale SaaS over time." Explicitly "not enterprise software"; audience is homelabbers/self-hosters; "both maintainers… have full-time jobs and families." — [Headscale FAQ](https://headscale.net/stable/about/faq/)
- **Governance:** Maintainers "work together on setting the direction"; "one of the active maintainers for Headscale is employed by Tailscale" (their contributions reviewed by others); contributions are gated ("any contribution will have to be discussed with the Maintainers before being submitted"). — [juanfont/headscale README](https://github.com/juanfont/headscale); [Headscale FAQ](https://headscale.net/stable/about/faq/)
- **Feature list (official docs):** Node registration via web auth and **pre-authenticated keys**; DNS — MagicDNS, global/restricted (split) nameservers, search domains, "Extra DNS records (Headscale only)"; file sharing — Taildrive and Taildrop; routing — tags, subnet routers, **exit nodes**, route filtering (Via); networking — dual-stack IPv4/IPv6, ephemeral nodes, **an embedded DERP server**, peer relays; policy — ACLs and **Grants**, "Some Autogroups," auto-approvers for subnet routers/exit nodes, Tailscale SSH, node attributes, tests; OIDC — basic registration and profile updates from the IdP. Claims "Full 'base' support of Tailscale's features." — [Headscale features](https://headscale.net/stable/about/features/)
- **Documented parity gaps / limitations:** "OIDC groups cannot be used in ACLs" (explicit). Funnel, Serve, and network flow logs are listed only with open issue links (status not stated as done). — [Headscale features](https://headscale.net/stable/about/features/)
- **Operational constraints:** Docker not officially supported ("we don't officially support deploying headscale using Docker"); reverse proxies/containers discouraged; running on a tailnet machine "not supported"; SQLite recommended, PostgreSQL "in 'maintenance mode'"; performance is not a primary design goal. — [Headscale FAQ](https://headscale.net/stable/about/faq/); [juanfont/headscale README](https://github.com/juanfont/headscale)
- **Reverse-engineered nature:** Maintainers are "reverse-engineering Tailscale"; a hands-on blog calls it "a reverse-engineered, compatible replacement… with imperfect compatibility." Technical sketch: client sends its WireGuard public key over HTTPS; Headscale stores it with device name/user/metadata and streams per-peer node maps to clients over a long-lived gRPC `StreamMapResponse`; assigns 100.64.0.0/10 addresses; ACLs are Tailscale-style HuJSON where a non-matching rule means "Headscale refuses to tell your [peer] about that node." — [Headscale FAQ](https://headscale.net/stable/about/faq/); [How Headscale coordinates your mesh (blog, Mustafa, Jun 2026)](https://mustafa.net/2026/06/27/how-headscale-coordinates-your-mesh-without-tailscales-servers/)
- **Exit-node parity caveat (secondary):** A third party reports that with Headscale the exit-node "flag exists, the client supports it, but the control server doesn't do anything with it" in some configs, requiring manual ACLs — note this conflicts with the official features page, which lists exit nodes as supported; likely version/config dependent. — [blog, Mustafa](https://mustafa.net/2026/06/27/how-headscale-coordinates-your-mesh-without-tailscales-servers/); cf. [Headscale features](https://headscale.net/stable/about/features/)

### Inferences
- **Tailnet Lock gap (important for the trust-model thesis):** Tailnet Lock / TKA / node-key signing does **not** appear anywhere in Headscale's official feature list, FAQ, or the technical blog, and Headscale by definition *is* the control server you now run. Self-hosting Headscale changes *who operates* the trust-bearing control plane (you, not Tailscale) but — absent a Tailnet-Lock-equivalent — does not give end nodes a cryptographic way to distrust that control server from injecting node keys. This is an inference from absence across the authoritative sources, not an explicit "unsupported" statement; see Gaps.
- **Identity/org parity:** Headscale supports OIDC login but not OIDC-group-driven ACLs, and the docs/FAQ describe no SSO roles/RBAC, no SCIM provisioning, and only single-tailnet scope — so enterprise identity-lifecycle features (role assignment, directory sync, multi-tenant org management) are effectively absent. (SSO details proper are another researcher's scope.)

### Gaps
- No explicit Headscale source statement was found that says "Tailnet Lock is not supported" (could not surface a specific GitHub issue by search); the conclusion rests on its absence from the authoritative feature list/FAQ. A direct check of the `juanfont/headscale` issue tracker would confirm.
- SCIM and SSO-role support are not mentioned in the FAQ/features pages reviewed (so presumed absent), but no page explicitly denies them.

## Q7: Other open-source / self-hosted coordination options (brief, for landscape only)

### Takeaway
Beyond Headscale, the main self-hosted WireGuard-control-plane options are NetBird (WireGuard mesh with built-in SSO/MFA + access management, self-host or free cloud) and Netmaker (self-hosted, performance-oriented mesh). Available sourcing here is comparison-site/anecdotal and promotional, so treat specifics cautiously.

### Cited Findings
- **NetBird:** described as a WireGuard-based mesh with SSO/MFA and access management, self-hostable or usable via a free cloud tier; one user found its coturn-based NAT traversal and access controls more usable than Netmaker's. — [SaaSHub NetBird vs Netmaker](https://www.saashub.com/compare-netbird-vs-netmaker); [lemm.ee anecdote](https://lemm.ee/post/11727518)
- **Netmaker:** positioned as self-hosted, open-source, full-infrastructure-control networking with a performance emphasis (vendor claims ~1223 Mbps throughput and strong self-hosting docs vs. ZeroTier — vendor figures, treat with caution). — [best-of-web/Netmaker](https://best-of-web.builder.io/library/gravitl/netmaker); [Netmaker vs ZeroTier (vendor)](https://netmaker.io/resources/netmaker-vs-zerotier)
