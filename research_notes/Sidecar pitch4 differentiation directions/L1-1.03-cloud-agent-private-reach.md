How I counted people. I read each thread in full through the GitHub REST API or Discourse JSON (read-only). A person is one distinct login who opened or commented on a thread I read, staff and bots excluded. A bare "+1" or "++" comment counts as a person. Reactions are reported separately and never added to people, because reactions cannot be de-duplicated across threads. Logins cannot be matched across GitHub and the Cursor forum, so totals across platforms may double-count someone. Vendor doc pages carried no dates; "fetched 1 Nov 2026" is the only date available for them. Quotes from vendor docs are as returned by the fetch tool, except the Claude page, which I read as raw text.

## What private resources do teams need cloud agents to reach, and how do they do it today?

### Takeaway
On the 22 threads I read, the resources people name are TCP services: databases (Postgres, Couchbase), SSH to their own VMs, internal package registries and private DNS, internal CI (Jenkins), and MCP servers on a private LAN or on the developer's own loopback. API secrets come next. 48 accounts posted on these threads across three platforms. Almost all of them report connectivity that fails ("can't connect"), not access that is too broad. Today's workarounds are moving execution onto customer machines (self-hosted pools, My Machines, self-hosted runners), Tailscale where the vendor offers it, short-lived tokens pasted into environment variables, and per-command network escalation. A much larger pull, by reactions, is for the reverse direction: people reaching and driving their own machine from elsewhere.

### Inferences
- The need is real but narrow and technical. People need TCP to a database or SSH host, internal registries and DNS, a private MCP or CI endpoint, and secrets. The visible volume is small: single-digit reactions per thread, except the Claude secrets issue. That fits a feature buyers expect inside the agent product, not a pain big enough to choose a product over.
- Users mostly ask "make it work" (TCP, TUN, DNS, credentials, routing MCP from the worker). They rarely ask "limit it". Of 48 accounts, about 6 ask for scope, approval, authorization, audit or lifecycle (next question). None asks for receipts.
- The reverse direction (reach and drive my own machine) draws hundreds of reactions. All four leading vendors now ship it themselves (next question). Leading pitch4 with "a cloud agent reaches a developer's own machine" lands where vendors already answer, unless it means one service on the laptop, granted to one cloud run.
- Codex Cloud's new TCP path is documented but, for at least 10 people in Oct 2026, not configurable or not working. A tool that delivers TCP to a database or SSH host from inside any vendor sandbox over an allowlisted HTTPS egress would solve a dated, current failure. This is an inference; I did not test it inside Codex.

## What does each cloud-agent vendor support for private networking in late 2026, on which plans, and with what security caveats?

### Takeaway
Every vendor now documents some private route, and they converge on two patterns. The first is a vendor-run tunnel or VPN client inside the vendor's VM: Codex (Tailscale only), Cursor (Tailscale beta, for HTTPS MCP only), and Devin (non-MFA VPN, or the Devin Connect gateway). The second moves tool execution onto customer machines, including a developer's laptop: Cursor My Machines and Team Pools, Claude self-hosted environments and the Remote Control "bridge environment", Copilot self-hosted runners, and Factory Remote Control with `port-forward`. Access is set per environment, shared by every session in it, and often gated to Enterprise or sales. Attribution in the logs stops at the device or tag, not the agent run. Claude-hosted sessions, Jules and OpenHands Cloud document no VPN or private-network path.

**OpenAI Codex Cloud (new experience; legacy to be deprecated)**
- Vendor claims: "Tailscale is currently the supported VPN provider." "Use the VPN to connect to TCP services such as databases or SSH." "TCP destinations must use IPv4 addresses routed through Tailscale." "TCP clients must connect through the environment’s HTTP CONNECT proxy at `proxy:8088`". "Tasks can use Tailscale split DNS and MagicDNS to reach private services by hostname." "Restricting public internet access doesn’t disable the configured VPN." — [Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments) (undated; fetched 1 Nov 2026)
- Security caveats on the same page: "Cloud identities and VPN connections can also provide shared service access." "TCP tunnels don’t intercept TLS or inject network secrets". "Detaching the VPN from a draft doesn’t revoke existing connections". The egress IP ranges "are shared across customers; keep the service’s authentication and authorization controls in place." — [Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments)
- Workload identity (OIDC) exists for Azure, GCP and AWS, with gaps. Amazon RDS IAM database login and GCP Cloud SQL IAM login are "not yet supported". It recommends tags, grants, a Reusable plus Ephemeral key tagged `tag:codex`, key expiry, device approval, and network flow logs, which "require Premium or Enterprise". It warns: "By default, Codex could reach nearly everything in your tailnet." The rollout is to Plus and higher (paraphrased by the fetch tool except the quoted line). — [Tailscale blog](https://tailscale.com/blog/codex-cloud-tailscale). OpenAI's doc says SSH, MagicDNS and split DNS work. Ten users in Oct 2026 report empty TCP grants and a refused `proxy:8088` (previous question).

With an OAuth client, Cursor mints a single-use, pre-approved key that expires in 10 minutes. The device logs out after 15 minutes with no open connection, and device names are `cursor-external-tsnet-proxy-` plus a random suffix. ### Inferences
- Pitch4's line "Codex cloud supports only Tailscale" is still accurate. The OpenAI doc now claims SSH, databases and MagicDNS over that VPN, so the stronger, current claim is that the documented TCP path was failing for users in October 2026.
- Pitch4's line "No harness vendor documents a cloud agent reaching a developer's own machine" is no longer accurate as written. Cursor names "a personal laptop" for My Machines, Claude lists a Remote Control "bridge environment" for "your own machine", Factory supports workstations plus `port-forward`, and Codex shipped Remote Control and remote SSH (closed issues with 544 and 878 reactions). What remains undocumented is narrower: a vendor-hosted agent run reaching one named service on a developer's machine under a grant that names the run and expires. Cursor's staff confirm the related case, private or loopback URL MCP from a worker, does not work by design.
- Pitch4's line "Reach is all or nothing" overstates the case. Domain allowlists, org firewall policy and default-deny gateways exist. The supported gap is that grants are per environment, not per agent run, and are shared by every user and session:

  - Claude: "every session that runs in the environment"; no org-pushed allowlist.
  - Cursor: no per-pool authorization; random device names.
  - Tailscale: one `tag:codex` for every VM.
- Network-layer logs (Tailscale flow logs; Devin gateway logs with "client address") attribute traffic to a device, tag or address, not to the task, repository, requesting user or approver. That attribution gap is something the sidecar's run-level entries could fill.
- Governance is plan- and sales-gated: Cursor Tailscale (Teams/Enterprise, sales), Cursor private connectivity and Team Pools (Enterprise), Tailscale flow logs (Premium/Enterprise). That leaves room for a cheaper team tier, if teams below Enterprise want governance at all (unproven).

## What incidents or concerns have surfaced, and which controls do buyers ask for?

### Takeaway
The documented incidents are research demonstrations, not confirmed customer breaches. Each shows reach or egress that was too broad:
- Devin's `expose_port` published ports to the internet on a prompt injection.
- Codex's dependency allowlist included `*.azure.net`.
- Claude's always-reachable Anthropic API carried files out.
- Jules had unrestricted egress.
- A hidden comment hijacked the Copilot agent.
- In October 2026, Tailscale's own SSH ("Tailworm") showed that one compromised tailnet device can move laterally.

Users and buyers ask for tag- or route-scoped grants, credentials the agent never sees, expiry and revocation, approval for non-HTTP reach, authorization for each pool or runner, and logs. On the user threads these asks come from a handful of people. In vendor-run surveys they are near-universal concerns.

### Inferences
- The demonstrated failure modes match the sidecar's design commitments:
  - Publishing to the public internet must need a person: Devin `expose_port` versus the pitch's "TLS edge … authenticated by default, short-lived".
  - Domain allowlists leak through shared or wildcard domains and through the vendor's own API (Codex `*.azure.net`, Claude `api.anthropic.com`).
  - A tailnet node is a lateral-movement foothold (Tailworm).
  - Pitch4 can cite these concrete, dated cases instead of generic MCP exposure statistics.
- Revocation and expiry are the most specific unmet control in vendor docs: Codex's VPN detach does not revoke live connections, and Cursor's laptop workers never time out. Surveys back revocation speed as a buyer gap (14 of 102 can revoke within minutes). This supports making "time-boxed, revocable, with one switch" a headline property of reach.
- What vendors already converge on (credential brokering, tag-scoped ephemeral devices, default-deny gateways with connection logs) sets the baseline. The sidecar's governance at par with these is not a differentiator. Per-run attribution and cross-vendor consistency could be.

### Gaps
- I found no confirmed production incident in 2025–2026 in which a cloud coding agent's private-network access (VPN or tailnet) was abused at a customer. All the cases are research demonstrations.
- The surveys are about agent identity broadly, are run by vendors or the press, and give no coding-agent or network-reach breakdown. No survey asks buyers to rank per-agent network grants, time limits, approvals or receipts.
- The BeyondTrust page failed to load (403). Tailworm details and patch status rest on secondary coverage.

## Would per-agent, approved, time-boxed reach with receipts be valued enough to drive adoption on its own?

### Takeaway
Probably not on its own. The user evidence asks for connectivity first, and only a handful of people ask for governance. Public attention is low: 9 HN points total and 0 comments on the Tailscale/Codex post. Each vendor is bundling its own scoped reach into its agent plan. The plausible wedge is narrower and combined. One place to give any vendor's cloud agent working TCP reach to private services, including one service on a developer's machine. Each grant is per run, expires, and names the run and the approver in its log entry. It works the same way across Codex, Cursor, Claude, Copilot and Devin. That would sell to teams running more than one cloud agent, whose security staff must approve reach today in five different consoles.

### Cited Findings
- Demand volume is low. The reach-specific Codex threads have 3–4 reactions each. Cursor's TUN/VPN request has 2 likes and 254 views over eight months, the enterprise network-access thread 207 views, and the execution-governance request 34 views. The Codex team closed a Teams user's network allowlist request for "not enough upvotes". — [openai/codex#54230](https://github.com/openai/codex/issues/54230); [#23197](https://github.com/openai/codex/issues/23197); [#11481](https://github.com/openai/codex/issues/11481); [Cursor forum 153624](https://forum.cursor.com/t/enable-tun-tap-device-support-in-cloud-agent-vms-for-vpn-connectivity/153624); [164689](https://forum.cursor.com/t/cloud-agents-corporate-network-access/164689); [172437](https://forum.cursor.com/t/pre-approved-execution-targets-for-cloud-agents-and-subagents/172437)
- The strongest single signal near this space is about credentials, not network grants: Claude's secrets issue has 213 reactions and 12 people. Anthropic answered it inside the product with proxy-injected network secrets. — [anthropics/claude-code#32733](https://github.com/anthropics/claude-code/issues/32733); [Claude cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Vendors bundle reach, often at Enterprise or through sales:
  - Cursor Tailscale beta on Teams and Enterprise, enabled through sales ([Cursor Tailscale](https://cursor.com/docs/integrations/tailscale)).
  - Cursor Team Pools for Enterprise ([Cursor runtime](https://cursor.com/docs/cloud-agent/bring-your-own-machine/choose-runtime)).
  - Devin Connect configured in enterprise settings ([Devin Connect](https://docs.devin.ai/enterprise/deployment/devin-connect)).
  - Tailscale flow logs on Premium/Enterprise ([Tailscale blog](https://tailscale.com/blog/codex-cloud-tailscale)).
- Security buyers state broad intent: 72 of 102 plan to adopt a new or replacement agent security solution within 12 months, and only 14 of 102 can revoke within minutes (press survey, Sept 2026). Only 7% of 400 believe their controls could stop a compromised agent (vendor survey, May 2026). — [VentureBeat](https://venturebeat.com/security/17-of-40-teams-that-say-they-enforce-ai-agent-permissions-still-share-the-credentials-behind-them); [Akeyless](https://www.akeyless.io/blog/2026-ai-agent-identity-security-survey/)
- Enterprise evaluators name the operating cost of today's answer, not the policy model. John_Baker asks whether admins must pre-clone repositories and manage credentials on warm workers. Derrik_Mildh and auscaster note that workers use their own git credentials and pools lack per-pool authorization. — [Cursor forum 164689](https://forum.cursor.com/t/cloud-agents-corporate-network-access/164689); [174958](https://forum.cursor.com/t/more-granular-permission-for-self-hosted-agent-pools/174958)
- Mechanisms differ across vendors: Tailscale only (Codex); Tailscale for HTTPS MCP, or PrivateLink, or workers (Cursor); no VPN, self-hosted environments or Remote Control (Claude); runners (Copilot); a non-MFA VPN or a gateway (Devin); a relay and port-forward (Factory). — sources in the vendor section above

### Inferences
- Governance alone is not a buying trigger in this evidence. It is the reason a security team approves connectivity that developers already want. Pitch4 should present reach as "private services your cloud agents can't reach today, reachable in minutes, safely", with grant, expiry and receipt as built-in properties, not as the product.
- Two sub-segments look most reachable:
  - Teams running two or more cloud agents, who otherwise maintain five mechanisms and five logs.
  - Teams below Enterprise, for whom the vendors' scoped options are sales-gated.
  - Both are inferences. Neither has a measured size or tested willingness to pay.
- The receipt that is new is attribution: run, repository, user, approver and model on each connection. Network tools attribute only to a device, tag or address (`tag:codex`, random `cursor-external-tsnet-proxy-*` names, "client address"). This ties reach to the pitch's "one write" record, which no network vendor can produce without the harness's run context.
- Competitive risk is high. Tailscale already sits inside Codex and Cursor and is adding agent-node approvals. Devin Connect already offers default-deny routes with connection logs. If OpenAI fixes TCP grants and Anthropic adds a VPN, the "make it work" gap narrows to developer-laptop targets and cross-vendor consistency.

### Gaps
- No test of willingness to pay for cross-vendor reach governance. No count of teams running more than one cloud agent against private resources.
- It is unknown whether a userspace sidecar can run inside each vendor's sandbox and egress to a relay. Possible blockers: Codex's proxy and allowlist, Cursor without TUN, Claude's Custom allowlist, Copilot's firewall, and Jules unknown. It is also unknown whether vendor terms permit it. This determines whether "any harness's cloud agent" is technically true.
- No buyer interview evidence on whether per-run attribution matters more than per-device logs.
