# Can a userspace sidecar run inside each vendor's hosted cloud-agent sandbox, carry TCP to a relay over one allowlisted HTTPS domain, and do the terms allow it? Are OpenAI and Anthropic about to close the gap? (as of 1 Nov 2026)

Scope and method. This note builds on L1-1.03 (`L1-1.03-cloud-agent-private-reach.md`) and does not repeat it. That note covered the demand threads, the 10 Codex users whose TCP grants were empty, Cursor's missing TUN thread, Devin Connect and Cursor's Tailscale integration. New here:
- Each vendor's sandbox mechanics, from docs fetched 1 Nov 2026. I used the markdown versions where they exist (`.md` URLs, GitHub's article-body API). OpenAI's policy pages returned HTTP 403 to both curl and WebFetch, so I read them through Wayback Machine captures of 23 and 28 Oct 2026.
- GitHub issues read in full through the REST API (read-only). A person is a distinct non-bot login who opened or commented on a thread I read; staff are flagged by GitHub's `author_association` (MEMBER/COLLABORATOR). People already counted in L1-1.03 are not counted again.
- GitHub code search for tunnel setups in agent config files, and the Cursor forum's Discourse search.
- The terms, usage policies and changelogs of OpenAI, Anthropic, Cursor, GitHub, Google, Cognition and Tailscale.

No vendor doc page carries a date, so "fetched 1 Nov 2026" is the only date for them. I ran no test inside any sandbox. Every feasibility rating below is an inference from documents and user reports, not a measurement.

## 1. Can a userspace sidecar run in each hosted sandbox and carry TCP to a relay over one allowlisted HTTPS domain?

### Takeaway
Yes in three sandboxes, conditional in two, and unknown in the rest:
- **Yes:** Cursor Cloud Agents (Cursor documents exactly this pattern), Copilot sessions that run on Actions, and Devin.
- **Conditional:** Claude Code on the web and Codex Cloud.
  - Both force all egress through a vendor proxy that terminates TLS with the vendor's own CA, and neither gives the sandbox DNS for outside hosts.
  - Claude keeps no process from setup into the session. The sidecar must be relaunched every session by a SessionStart hook.
  - Codex adds a per-command sandbox that by default refuses to open sockets, even a local listener. Each networked command, and so a long-running sidecar, needs network permission granted per command.
- **Unknown:** Jules (it has internet access but no documented controls) and GitHub's new default cloud sandbox (launched 28 Oct 2026), which has no hook that runs before the agent.

No sandbox documents `/dev/net/tun` except by implication (Devin's VPN clients and the GitHub runners Tailscale runs on), so the sidecar must use a userspace network stack everywhere.

### Inferences
- A sidecar that needs only one HTTPS hostname, a userspace stack and localhost/SOCKS listeners fits every sandbox's allowlist model:
  - Codex: an "Additional allowed domain".
  - Claude: Custom.
  - Cursor: the allowlist.
  - Copilot: a custom allowlist entry that also covers subdomains.
  - Devin: a hostname entry in the security profile.
  - It needs no vendor VPN support.
  - Codex requires each subdomain as its own entry, so the relay should use one fixed hostname, not per-region subdomains.
- Two hard constraints follow from the proxies:
  - (a) TLS is terminated by OpenAI's and Anthropic's proxies. Confidentiality and authentication must therefore live inside the stream, for example WireGuard or Noise over a byte stream, and mTLS to the relay will not work.
  - (b) The transport should fall back to plain HTTP/1.1 CONNECT with streaming or long-polling. WebSocket and HTTP/2 are unproven in those sandboxes, and gRPC already failed in Claude's.
- Lifecycle is the real engineering cost, not the network:
  - Every vendor keeps files but not processes.
  - The sidecar needs one start recipe per vendor: Cursor `start`, a Claude SessionStart hook, Copilot setup steps, a Codex Start skill run with network escalation, a Devin blueprint plus knowledge entry, a Jules setup script.
  - It must also survive idle pauses and pressure reaping.
- Codex is where the October pain is (L1-1.03: 10 people whose TCP reach failed), and it is also the hardest sandbox. Its default command sandbox refuses even `bind` on 127.0.0.1. A localhost port-forward from the sidecar would work only for commands that run with network or local-binding permission.
- Copilot's 28 Oct default switch removes the easiest place to start a tunnel (setup steps) unless a team picks Actions. Copilot in its new default is now closer to Claude and Codex than to Cursor.
- Two features could keep the relay credential out of the agent's view: Claude's and Codex's proxy-side credential brokering (network secrets, header placeholders substituted for HTTPS on port 443). The sidecar would hold no long-lived secret, matching pitch4's design rule. This is untested.
- Pitch4's model-access promise does not carry into the hosted harnesses. Cursor's model calls run on Cursor's servers, and Claude and Codex call their own APIs. A sidecar in the sandbox can change only the traffic that tools inside the sandbox make. "Agents reach only the team's own inference servers" can hold only for harnesses whose model calls leave from a machine the customer controls: OpenCode, Goose, Kilo BYOK, OpenHands self-hosted, or open harnesses running inside the sandbox.

### Gaps
- No hands-on test. I could not verify whether a WebSocket, an HTTP/2 stream or a long-lived chunked HTTP/1.1 stream survives Codex's Envoy proxy or Claude's agent-proxy and gateway. Idle timeouts, buffering and per-connection limits are also unknown. Running the test needs accounts in each product, which is outside read-only research.
- `/dev/net/tun` is undocumented for Codex, Claude, Jules and Copilot's cloud sandbox.
- How Cursor enforces Allowlist-only mode (DNS, SNI or a proxy), and whether it intercepts TLS, are undocumented.
- Whether the Copilot firewall covers a sidecar launched as a configured MCP server in the cloud sandbox ("does not apply directly to … MCP server processes") is unclear.
- Code-search counts are lower bounds. GitHub code search indexes only some files and branches, and private repositories are invisible.
- I found no doc for where Kilo Cloud Agents or OpenHands Cloud make their model calls (inside the container or from the vendor's backend).

## 2. Have userspace tunnels (Tailscale userspace, cloudflared, ngrok, frp, chisel, wstunnel, zrok, iroh, tailcat) worked or failed in these sandboxes?

### Takeaway
Public reports are scarce, and almost all come from Cursor and GitHub Actions, where they work. Cursor documents Tailscale userspace mode and cloudflared and says customers use them. Four public projects run Tailscale in Copilot setup steps. I found no public report of anyone running cloudflared, ngrok, frp, chisel, wstunnel, zrok or iroh inside Codex Cloud, Claude cloud sessions or Jules. The reports from those sandboxes are about the vendor's own proxy breaking ordinary HTTPS. Tailscale's new open-source `tailcat` (31 Aug 2026) is a userspace-only, no-TUN, no-account transport that its author says he gives to "sandboxed AI agents". It is the nearest neutral substitute for the sidecar's transport.

### Inferences
- Public use of userspace tunnels in hosted agent sandboxes is low. It is concentrated where the vendor documents it (Cursor) or where the sandbox is a CI runner (Copilot on Actions). Pitch4 cannot cite field evidence that a third-party userspace tunnel works in Codex or Claude cloud. A working demo there would be new.
- tailcat shows Tailscale already ships, free and open source, the transport shape pitch4 needs: userspace, no TUN, SOCKS for child processes, relays as fallback. That confirms the L1-1.06 direction to treat transports as pluggable and to sell the grant record, not the tunnel. Note also that DERP rides HTTPS, and through Claude's and Codex's TLS-terminating proxies it would hit the same unproven limits as any other WebSocket or HTTP Upgrade stream (inference).

### Gaps
- Reddit, Discord and X were not searched (login walls in earlier passes). Private success stories would not show up anyway.
- I found no reports for Jules, Devin or OpenHands Cloud, and no public issue trackers comparable to GitHub's for them.
- I did not test whether DERP or tailcat traverses an HTTP CONNECT proxy that terminates TLS.

## 3. Do the vendors' terms allow a customer-run tunnel inside their sandbox?

### Takeaway
No vendor's terms ban tunnels outright. OpenAI, Anthropic (consumer) and Google ban bypassing their "protective measures", and their egress proxies and allowlists are such measures. A tunnel to a relay that the environment owner deliberately allowlisted is arguably configuration, not bypass. Carrying traffic to destinations the vendor's controls would have refused, inside that tunnel, is the grey zone. Cursor documents third-party userspace tunnels, which makes it the lowest risk. GitHub's Actions terms tie runner activity to the repository's project. Cognition's terms have no network-circumvention clause. This is my reading, not legal advice, and no vendor has publicly addressed customer relays.

### Cited Findings
- OpenAI Terms of Use ("Effective: January 1, 2026"; Wayback capture 2026-10-23): "Interfere with or disrupt our Services, including circumvent any rate limits or restrictions or bypass any protective measures or safety mitigations we put on our Services." — [OpenAI Terms of Use (archived)](https://web.archive.org/web/20261023115502/https://openai.com/policies/row-terms-of-use/) (the live page returned HTTP 403)

### Inferences
- The defensible posture is "approved, not bypassed":
  - The sidecar connects only to a relay hostname the environment owner or admin put on the vendor's own allowlist.
  - It honours the vendor's escalation and approval prompts.
  - It forwards only to destinations the customer's grant names.
  - It records each grant.
  - Under that posture it is the customer's configuration of the vendor's control. A tunnel that silently extends reach past what an Enterprise admin set (Codex Agent Security "Only allow domains added by admins", Devin mandatory profiles, Copilot org firewall locks) is where "bypass any protective measures" bites.
  - A "respect the admin's floor" rule, visible in the record, turns a terms risk into a selling point.
- Risk ranking (inference): Cursor and Devin low; Copilot on Actions low to medium (the activity must serve the repository's project); Claude and Codex medium (explicit anti-bypass language, and the egress proxy is described as security and abuse prevention); Jules low, but its controls are undocumented.
- Because Codex and Claude terminate TLS, they can see that a long-lived tunnel exists even when the tunnel is encrypted end to end. The traffic is not covert, and the vendor can rate-limit or block it at any time. Relying on Codex or Claude is a platform risk even where the terms permit it.

### Gaps
- No vendor statement, staff reply or FAQ addresses customer-operated relays or tunnels in OpenAI's or Anthropic's hosted sandboxes. I found none on #54230, #23197, #50986 or the Claude proxy threads.
- I did not find Jules-specific terms or the GitHub Copilot product-specific terms. GitHub's Copilot terms may add agent-specific clauses.

## 5. What this means for pitch4's first-release reach promise

### Takeaway
Pitch4 can truthfully promise a cloud agent reaching a private service in Cursor, Copilot on Actions, Devin and, probably, Jules. It can promise it in Claude-hosted and Codex sessions only as "works through the vendor's own allowlist, with these limits". "Any harness" is too strong as written. The model-access promise does not extend to hosted harnesses at all. The differentiated offer is narrower and more concrete:
- one relay hostname to allowlist in each vendor console;
- a start recipe for each vendor;
- end-to-end encryption that holds even though the vendors' proxies terminate TLS;
- grants per run that expire. Today revocation varies by vendor: within a minute in Claude, never for running Copilot sessions, at next wake in Devin, and not for live connections in Codex.

### Cited Findings
- How revocation behaves per vendor (vendor claims):
  - Claude: "existing sessions follow the new setting within about a minute". — [Claude cloud environments](https://code.claude.com/docs/en/cloud-environments.md)
  - Copilot: "Allowlist changes don't apply to sessions that are already running". — [GitHub cloud sandboxes](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-sandboxes)
  - Devin: "a running session keeps the restrictions it resolved at its last wake". — [Devin security profiles](https://docs.devin.ai/product-guides/security-profiles.md)
  - Codex: "Detaching the VPN from a draft doesn't revoke existing connections". — [Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments.md)
- Hosted model calls leave from the vendor's backend: Cursor (deanrie, 2026-05-24); Claude reaches "The Anthropic API, for Claude Code's own requests, even at **None**". — [Cursor forum 161258](https://forum.cursor.com/t/dgx-spark-owners-anyone-successfully-connected-ollama-to-cursor/161258); [Claude cloud environments](https://code.claude.com/docs/en/cloud-environments.md)
- Credential brokering exists on two platforms (vendor claims): Claude network secrets are added "after each request leaves the session's VM, so the key itself stays outside the VM"; Codex "Programs receive a placeholder". — [Claude cloud environments](https://code.claude.com/docs/en/cloud-environments.md); [Codex cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments.md)

### Inferences
- **Re-scope the claim.** Change "a cloud agent reaches a private service, for any harness" to "for any harness whose sandbox allows one HTTPS hostname". Publish a dated per-vendor compatibility matrix, the table in section 1 turned into tests. This is more credible to security buyers than "any harness", and it is a small product in itself.
- **Make the transport proxy-proof.**
  - Inner end-to-end encryption, because outer TLS is terminated by OpenAI's and Anthropic's proxies.
  - An HTTP/1.1 CONNECT-compatible fallback with no WebSocket or HTTP/2 dependency.
  - A single fixed relay hostname.
  - Application-layer authentication, since mTLS will not survive the proxies and egress IPs are shared across customers.
  - Optionally, let the vendor's credential broker carry the relay token, so the agent never holds it.
- **Ship start recipes, not just a binary.** Cursor `start`; a Claude SessionStart hook that orgs can push through server-managed settings; Copilot setup steps on Actions plus an MCP-server or instructions path for the cloud sandbox; a Codex Start skill that asks for network permission; a Devin blueprint and knowledge entry; a Jules setup script. Lifecycle (relaunch on resume, survive pauses and reaping) is the engineering that tunnels do not ship.
- **Lead with Claude-hosted and Copilot cloud-sandbox sessions, and with teams running several vendors.** Neither Anthropic nor GitHub's new default offers a VPN path. Codex is where the October pain is, but OpenAI is the vendor most likely to close it, and its sandbox is the most hostile to a background sidecar today.
- **Present "respect the admin's floor" as a feature.** The sidecar never widens what a vendor's admin lock allows, and the record shows each grant within that floor. That answers the terms question and the security buyer at once.
- **Scope model access honestly.** "Agents reach only the team's own inference servers" applies to harnesses whose model calls the customer controls (OpenCode, Goose, Kilo BYOK, self-hosted OpenHands), not to Codex, Claude, Cursor or Copilot hosted agents.

### Gaps
- Willingness to pay for cross-vendor reach is still untested (L1-1.03), and so is the size of the multi-vendor segment.
- Until the transport is tested in Claude's and Codex's sandboxes, the "conditional" ratings could turn out to be "blocked", for example if their gateways cut long-lived tunnels.
