## 1. Copilot's default cloud sandbox (since 28 Oct 2026): is there a hook before the agent, does the firewall cover MCP server processes, and is /dev/net/tun available?

### Takeaway
2.02 rated Copilot's new default "unknown" because setup steps are Actions-only. That rating should move to "works per session (docs only, untested)". The docs show two start points in the cloud sandbox that run before or beside the agent:
- **Repository hooks** in `.github/hooks/*.json`. `sessionStart` fires once per job. Hooks run inside the sandbox and are restricted by the firewall.
- **MCP servers** with a startup command. A personal server is "only available in cloud sandboxes" and runs in every cloud session. GitHub says the firewall "does not apply directly" to MCP server processes.

Dotfiles cannot carry a start command: no install scripts run, and the cloud reads hooks only from the cloned repository. `/dev/net/tun` is not documented anywhere. GitHub itself says private networking is an Actions feature and that cloud sandboxes have "fewer options" for reaching organization resources.

### Inferences
- **Recipe A (respects the admin's floor).**
  - Commit `.github/hooks/sidecar.json` to the default branch, with a `sessionStart` command such as `setsid nohup sidecar up --relay relay.example.com >/tmp/sidecar.log 2>&1 &`. It must return well inside the 30-second default.
  - The relay hostname goes on the firewall's custom allowlist.
  - `sessionStart` does not fire on resume, so add a cheap idempotent `sidecar ensure` to `preToolUse`, which fires before every tool call and blocks for its duration.
- **Recipe B (per user, outside the firewall per the docs).** Configure a personal MCP server whose startup command is the sidecar, either serving MCP tools itself or launching the daemon. It needs no repository change and runs in every cloud session. Pitch4 should not sell "outside the firewall": the sidecar should still require the relay host on the org allowlist and record it (the "respect the admin's floor" rule from 2.02).
- **No setup step, so no privileged install.** The sidecar binary must arrive with the repository or be fetched from an allowlisted host by the hook, and run as an unprivileged userspace stack. Hooks see `HOME=/root`, which suggests root, but TUN availability is unknown.
- The `/workspace` working directory and `HOME=/root` look like a container, not an Actions runner (inference). That makes TUN less likely to be granted.
- **Copilot is now a strong target.** The new default has a documented per-job start point, and GitHub says private networking is Actions-only. Cloud-sandbox users therefore have no vendor route to private services.

### Gaps (only a test can settle)
- Whether a process started by a `sessionStart` hook survives across jobs in one session and across snapshot stop/resume. The docs say the sandbox "is destroyed when the job ends", yet sessions also resume from snapshots. The two statements are not reconciled.
- Whether the firewall actually leaves MCP-launched processes and their children unfiltered ("does not apply directly" is hedged), and how the firewall is enforced (DNS, SNI or proxy; TLS inspection).
- Whether `/dev/net/tun` exists or `CAP_NET_ADMIN` is granted.
- Whether a dotfiles-provided `~/.copilot/hooks/*.json` or `~/.copilot/mcp-config.json` is honored. The reference implies not.

## 2. Codex Cloud: does a background process keep network permission across turns, can it bind local listeners without Enterprise Agent Security, and what is the status of TCP grants on proxy:8088?

### Takeaway
- **Rating: works per command.** Each command that opens a socket needs escalated or added network permission.
- **Open source explains why.** The open-source Codex Linux sandbox, whose behaviour matches the cloud symptoms, blocks network syscalls with seccomp. It gives each networked command its own network namespace bridged only to the configured proxy.
- **Background processes.** A process keeps whatever sandbox it was started with for its lifetime. Background jobs can outlive a turn, but the runtime can be swapped under them. The proxy scopes access to an execution token that is unregistered when the execution's scope is dropped. Whether a background sidecar keeps proxy access after its turn ends can only be settled by a test.
- **`allow_local_binding` is not a listener permission.** It is the proxy's guard against local and private destinations. On the Cloud proxy path it defaults to true unless a requirement or profile sets it, and an explicit false cuts off the upstream proxy. Binding a listener is governed by the seccomp network filter, not by this key.
- **TCP grants.** No change. The doc still limits TCP through `proxy:8088` to Tailscale-routed IPv4. The three TCP and proxy issues have no OpenAI reply, and new reports through 31 Oct show the socket `EPERM` persisting.

### Cited Findings

### Inferences
- **A background process does keep its own network permission across turns.** Seccomp filters and namespaces are inherited at spawn and cannot be tightened later. So a sidecar started under full escalation keeps working network for as long as it lives. Two risks remain:
  - (a) The runtime can be replaced under it (#58611).
  - (b) If it was started in managed-proxy mode, its proxy access is tied to an execution attribution token that the proxy unregisters when the execution scope is dropped. It might lose the proxy when its command or turn ends.
- **The localhost port-forward breaks across commands.** In managed-proxy mode each command has its own network namespace. A listener the sidecar opens is invisible to other sandboxed commands. The port-forward pattern from 2.02 only works when the sidecar and its client run in the same escalated context, or when the managed proxy is allowed to reach `localhost`. Codex Cloud users cannot see or set that permission.
- **Codex recipe: "per command".**
  - Add the relay hostname under "Additional allowed domains".
  - Add a Start skill or AGENTS.md instruction that starts the sidecar with full escalation.
  - Wrap networked client commands as `sidecar exec -- <cmd>` and ask for escalation each time.
  - Trust the injected CA, since the proxy terminates TLS (2.02).
  - Enterprise admins who set "only domains added by admins" also disable approval-time expansion (`managed_allowed_domains_only`). The relay must then be admin-listed.
- **OpenAI's own design assumes short idle cuts.** Its `codex tcp-tunnel` uses 10-second keepalives and a 30-second idle limit, and reconnects without replaying streams. That supports pitch4 designing for reconnects, not for durable tunnels.

### Gaps (only a test can settle)
- Whether an escalated background sidecar survives turn boundaries and keeps reaching `proxy:8080` after its starting command ends.
- Whether later sandboxed commands can reach its loopback listener.
- Whether "Full access" in a cloud task removes the per-command sandbox.
- Whether `codex tcp-tunnel` is the "local forwarding tool" for `proxy:8088`.
- What the "Additional TCP ranges" field does. It appears in environment status output (#58010) but is not documented.
- The `codex-rs` tree includes a `hooks` crate. I did not check whether Codex Cloud runs repository hooks before the agent.

## 3. Claude's agent proxy and Codex's Envoy proxy: what idle timeouts and buffering apply, and do long-lived WebSocket, HTTP/2 or chunked HTTP/1.1 streams over CONNECT survive?

### Takeaway
- **No vendor documents idle timeouts, buffering or stream limits for either proxy.** Only a test can give the numbers.
- **Neither proxy is a dumb byte pipe.**
  - Claude's egress gateway parses the TLS ClientHello inside CONNECT. It resets hellos that carry ECH after about 6 seconds and kills Chromium's TLS 1.3 handshakes. It has refused `wss://` hosts with "Host not in allowlist" while HTTPS to the same service worked. It mints a session JWT of allowed hosts at session start. The session VM pauses after "a few minutes without activity", which ends any idle connection.
  - Codex's egress is Envoy chained to a Cloudflare tunnel (`envoy://cloudflare_https_tunnel/`) that "requires HTTP inspection". OpenAI's Envoy settings are unpublished. Envoy's defaults would cut an idle stream at 5 minutes and a non-streaming route at 15 seconds unless OpenAI changed them.
- **Long-lived WebSocket, HTTP/2 and chunked streams over CONNECT are unproven in both.** The evidence points to a transport made of short HTTPS/1.1 requests with heartbeats and reconnects.

- On the HTTP protocol idle_timeout: "The default idle timeout if not otherwise specified is 1 hour."

- "Envoy Upgrade support is intended mainly for WebSocket and CONNECT support". — [Envoy HTTP upgrades](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/http/upgrades)

### Inferences
- **The proxy-tolerant transport profile pitch4 should ship:**
  - (1) TLS to the relay with a plain ClientHello: no ECH. Go's and rustls' defaults are fine; Chromium's network stack is not.
  - (2) Trust the vendor CA (`/root/.ccr/ca-bundle.crt`, Codex's injected CA), because both proxies may re-terminate TLS.
  - (3) Ordinary HTTP/1.1 requests: long-polls under about 10 s (below Envoy's 15-second default route timeout), or chunked responses with heartbeats every 10–30 s (below the 5-minute stream idle default).
  - (4) Session resumption by ID so any reset costs a reconnect, not a session.
  - (5) Inner end-to-end encryption carried in HTTP bodies.
  - WebSocket and HTTP/2 should be optional upgrades, used only after a probe succeeds.
- **The sidecar must survive VM pauses.** Claude's pause model means no connection outlives a few idle minutes. Relaunch on restore with a SessionStart hook (`async: true`), and add a `PreToolUse` "ensure" hook as a backstop.
- **A Codex outage can't be fixed from inside.** Codex's egress depends on a Cloudflare tunnel behind Envoy. When it fails, the CONNECT still returns 200 and the request inside returns 503, so the sidecar should report "vendor egress down" rather than "relay down". Its health check should test a known allowlisted host and the relay separately.
- **Pitch4 should ask, not tunnel around.** One Claude user says wrapping SSH or WireGuard in HTTPS "is the wrong answer". Pitch4's framing should be "a supported, allowlisted relay with a record", and Anthropic and OpenAI should be asked to bless the relay pattern. That fits 2.02's terms reading.

### Gaps (only a test can settle)
- Actual idle cutoffs on Claude's agent proxy, upstream proxy and egress gateway, and on Codex's Envoy and Cloudflare chain. Probe keepalive intervals of 10, 30, 60, 120 and 300 s.
- Whether HTTP/1.1 chunked responses are buffered: does the first byte arrive before the response completes?
- Whether `Upgrade: websocket` to an allowlisted relay host is passed or stripped. Whether HTTP/2 via ALPN is negotiated through the re-terminating proxies.
- Per-connection byte or time caps.
- Whether a sidecar's own TLS stack (Go or rustls) passes Claude's ClientHello filter. Curl and Node pass it.

## 4. OpenHands Cloud and Kilo Cloud Agents: do model calls leave from inside the sandbox?

### Takeaway
**OpenHands Cloud: yes.** In V1 the managed platform runs the Agent Server inside the conversation sandbox. The SDK hands that server the full agent, including the LLM configuration with secrets. Users can set a custom Base URL, and `.openhands/setup.sh` runs "every time OpenHands begins working with your repository". So it is the one hosted harness where a sidecar could carry model traffic to a team's private inference server, with a per-session recipe. It is untested.

**Kilo Cloud Agents: the call leaves the sandbox, but only to Kilo's gateway.** Every turn is pinned to provider `kilo`, whose base URL is the Kilo gateway. The gateway then routes to a managed key, a BYOK key or a "custom LLM endpoint". A sidecar inside the Kilo sandbox therefore cannot carry model traffic to a private server. Rating for model access: blocked.

### Cited Findings

### Inferences
- **OpenHands Cloud recipe (untested).**
  - `.openhands/setup.sh` starts the sidecar, which exposes `127.0.0.1:PORT` forwarding to the team's inference server through the relay.
  - In Settings, under LLM and Advanced, set a custom model and Base URL `http://127.0.0.1:PORT/v1`.
  - The Agent Server's calls then leave from the sandbox through the sidecar. The model server's own sidecar can sign which weights it served, keeping pitch4's provenance story intact.
  - Two risks: save-time validation "against the backend", which may run outside the sandbox, could reject a loopback URL; and any backend-side LLM calls would bypass the sidecar.
- **Kilo is gateway-routed, like Cursor (2.02).** The only route to a team's own model is to make it reachable by Kilo's gateway as a "custom LLM endpoint". That means a public, authenticated endpoint. For pitch4, that is the "later" public TLS edge, plus an allowlist of the gateway's egress and a per-team token. It is not the in-sandbox sidecar.
- **Net effect on the model-access promise.** It reaches exactly one hosted harness, OpenHands Cloud, and only through a per-session recipe. Kilo Cloud, Cursor, Claude, Codex and Copilot are blocked for in-sandbox model access. A gateway-facing public edge is the only way to serve the gateway-routed ones.
- **Kilo is easy for reach.** Startup commands are available and internet is on by default unless an egress allowlist is set (inference from source). Reach rating: works per session, untested.

### Gaps (only a test can settle)
- Whether OpenHands Cloud accepts a loopback Base URL and routes every LLM call (titles, condensation, sub-agents) through the sandbox's Agent Server.
- Whether OpenHands Cloud restricts sandbox egress.
- Whether a repository-level `kilo.json` can add a non-`kilo` provider that a Cloud Agent turn would use. The source pins `providerID: 'kilo'`, so probably not.
- Where Kilo's "custom LLM endpoint" calls originate (gateway Worker egress IPs), and whether Kilo publishes them for allowlisting.

## 5. Ratings, start recipes, and what this means for pitch4

### Takeaway
Pitch4 can now name three hosted sandboxes as working with a per-session recipe and one as working per command:
- **Per-session recipe, docs only:** Copilot cloud sandbox (repo `sessionStart` hook or personal MCP server), Claude Code on the web (async SessionStart hook), and Kilo and OpenHands Cloud for reach (startup command and `setup.sh`).

Serving gateway-routed harnesses would need the public TLS edge, which pitch4 lists as a later release.

### Inferences
- **Differentiation.** A dated, tested compatibility matrix with one start recipe per vendor, and a `sidecar doctor` that detects which mode a sandbox is in, is more credible than "any harness". No vendor or tunnel project publishes this for hosted agent sandboxes.
- **Offering.** Ship the proxy-tolerant transport profile as the default:

Gateway-routed hosted harnesses need an authenticated public edge in front of the team's model server. That argues for either pulling a narrow "model edge" forward or dropping hosted-harness model access from the first-release claim.
