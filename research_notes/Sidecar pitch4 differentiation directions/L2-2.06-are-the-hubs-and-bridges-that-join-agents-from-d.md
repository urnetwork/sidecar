## 1. Block's Buzz: what does it capture from harnesses, where does it keep it, who can read it, and would it accept an outside entry format?

### Takeaway
Buzz already sees every harness action live. Its ACP harness streams each ACP frame, tool calls included, to the agent's owner as encrypted Nostr events. But Buzz's own spec forbids relays from storing those frames or putting them in the audit log, and calls transcript-grade durable telemetry "explicitly out of scope". What Buzz keeps durably is workspace activity (signed messages, diffs, git events, workflow steps) plus a per-turn token and cost record that only the owner can decrypt. On `main`, the harness still auto-approves every ACP permission request from Claude Code, Codex and other agents, so no approval decision is recorded. The workflow approval gate (WF-08) has at least five competing outside PRs since July and none has merged. By stated design, channel and DM content is readable by the server "so eDiscovery works on everything"; end-to-end encryption is only "a future consideration for DMs". An outside entry format would need an upstream event-kind registration. The one outside request to register an audit-trail kind has had no maintainer reply in two months, and five other outside proposals on export, encryption and extension points also have none.

**What Buzz captures from harnesses**
- The ACP harness "connects AI agents to Buzz. The harness listens for @mentions on the relay, prompts your agent, and the agent replies using the Buzz CLI." It supports "goose, codex (via codex-acp), and claude code (via claude-agent-acp)". "Tier-1 — compiled-in runtimes (Goose, Claude Code, Codex, Buzz Agent)"; "Tier-2 — preset catalog (Cursor, Oh My Pi, Pi, Grok Build, OpenCode, Kimi Code, Amp, Hermes Agent, OpenClaw)"; "Tier-3 — user custom harnesses: JSON files". — [buzz-acp README](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md) (read 1 Nov 2026)
- NIP-AO ("Agent Observability", `draft`): "This NIP defines ephemeral, encrypted event kinds for streaming internal session telemetry between AI agent processes and their owners' desktop clients via Nostr relays." Motivation: "Owners need real-time visibility into this activity for debugging, auditing, and control — without that telemetry being stored on any relay or visible to third parties." Frame kinds: `acp_read` ("Inbound ACP protocol frame (model → harness)"), `acp_write`, `turn_started`, `session_resolved`. The worked example's decrypted payload is a `tools/call` for `shell` with `"command": "ls -la"`. — [NIP-AO](https://github.com/block/buzz/blob/main/docs/nips/NIP-AO.md)
- NIP-AO's ephemerality contract: "Relays MUST NOT persist kind 24200 events to any durable storage." "Relays MUST NOT include kind 24200 events in search indexes." "Relays MUST NOT include kind 24200 events in audit logs." Clients "SHOULD buffer events in a bounded ring buffer (RECOMMENDED maximum: 800 events)" and "MUST NOT request historical kind 24200 events". The only control frame is `cancel_turn`. — [NIP-AO](https://github.com/block/buzz/blob/main/docs/nips/NIP-AO.md)
- NIP-AM ("Agent Turn Metrics", `draft`) is the durable counterpart, limited to usage: "This NIP defines a durable, encrypted event kind for recording per-turn token usage and estimated cost of AI agent sessions", "so the owner can account for token usage across agents and harnesses without the relay — or any third party — learning what the agent did or what it cost." It states: "Transcript-grade durable telemetry is explicitly out of scope — the persistence-averse reasoning behind NIP-AO's ephemerality contract applies to conversation content, not to a small usage record." The payload carries `harness`, `model`, session and turn IDs, token counts, estimated cost and an optional `pricingIdentity`; "a null MUST NOT be recorded or summed as zero." — [NIP-AM](https://github.com/block/buzz/blob/main/docs/nips/NIP-AM.md)
- The activity-feed vision lists "Permission (the control gate)" among twelve render classes and says "any compliant agent's messages, thoughts, tool calls, and turns become first-class items regardless of which tools it runs." ### Inferences
- Buzz's design choice is the key fact for pitch4. Block captures harness actions for supervision ("a window"), not for the record. It streams them to the owner and drops them, keeps only usage durably, and keeps workspace content readable by the operator for eDiscovery. A durable, team-readable record of harness actions and approval decisions, encrypted from the relay, is therefore not on Buzz's stated roadmap. It is not ruled out: the NIP-AO frame shape plus PR #7797's decision ledger would be most of it.
- Approvals are the nearest gap Buzz could close. If WF-08 and #7797 merge, Buzz would have signed approval decisions bound to an action digest, for agents run inside Buzz. Five-plus competing outside PRs over three months suggest demand without a maintainer decision. That is a weak signal of priority, not of intent.
- Buzz records only what runs through its harness. The README describes agents that act when @mentioned on the relay. A developer's own Claude Code or Codex session in a terminal or IDE is outside Buzz unless it is launched through `buzz-acp` (inference from the README; Block does not say this).
- "Would it accept an outside entry format?" Not without an upstream kind registration, and Block has not engaged publicly with any outside record, export or encryption proposal. A sidecar can still publish into Buzz without permission by using kinds Buzz already accepts (messages, kind 40008 diffs, NIP-34 patches) as an agent with its own NIP-OA-authorized key.

### Gaps
- No Block talk or engineering post after the July launch was found that states plans for durable harness capture, approvals or encryption; secondary coverage conflicts on approval status.
- Which code path is current for gated workflow runs (failed versus skipped) was not tested.
- Buzz's hosted service (buzz.xyz) terms, retention and operator access were not read.
- Whether Block maintainers discuss these topics in a private channel (Discord, internal repos such as `squareup/sprout-releases`) is unknown; only public GitHub was read.

## 2. OpenAI's codex-plugin-cc and Codex's importer: what do the vendor bridges record about review and delegation, and where? Is there an Anthropic counterpart?

### Takeaway
The most-used bridge between vendors records almost nothing that a team or auditor could use. codex-plugin-cc keeps an unsigned, local list of at most 50 jobs per repository and deletes older job files. Its review output has a verdict and findings but no reviewer model, no binary version and no commit reference, and users who need to know "which model reviewed which change" keep that record by hand. The delegated Codex threads land in the user's personal Codex store, where users complain they bury human work. OpenAI also imports Claude Code sessions into Codex, recorded in a local import ledger. The plugin has had no commit since 8 Jul 2026. Anthropic ships no counterpart: its official marketplace has no plugin that delegates to another vendor's agent.

### Inferences
- The bridge's record serves one developer's convenience, not evidence. Fifty local jobs, unsigned, without the reviewer model, cannot show an auditor that a different model reviewed a change. The users asking for model and binary fields are asking for exactly pitch4's "review between vendors, on the record" entry.
- Users want two things at once: the review recorded precisely, and kept out of their working history. A team ledger separate from personal session history fits both.
- OpenAI built the bridge into its own product and records the handoff in its own store, flowing toward Codex. Vendors build bridges that pull usage to themselves (as L1-1.02 inferred). Neither vendor has built a neutral record of the exchange.
- The plugin looks unmaintained since July (545 open issues, no commits). A neutral recorder would not need it maintained. A Claude Code `Stop` or `SessionEnd` hook can read its job JSON and the Codex rollout and write the cross-vendor entry.

## 3. GitHub Agent HQ: do its audit log and session logs capture third-party agents' actions?

### Takeaway
GitHub shows session logs (reasoning, tools, file changes) to anyone with access to the repository, but its audit log does not record agent sessions. Its event catalog, updated 27 Oct 2026, has only configuration events for coding agents (firewall allowlist, MCP configuration, repository enablement) and no event for a session, tool call, approval or review verdict. Claude and Codex in Agent HQ are still in public preview, run as GitHub Apps whose actions appear under ordinary audit events, cannot be steered, and are not covered when run locally in VS Code. No export or API for session logs is described.

## 5. Do the ACP and A2A specs and registries carry logging, audit or signing fields, and where are the extension points?

### Takeaway
Neither protocol defines an audit record. ACP carries the raw material (tool calls, permission requests, plans, diffs) and offers three seams: `_meta` (with W3C trace context reserved), custom `_` methods, and a draft "proxy chains" design that puts components between the client and the agent. Its draft v2 permission request explicitly anticipates clients that "proxy, store, replay, or forward permission requests". The ACP registry schema has no signing, attestation or audit fields. A2A signs only the agent card. Its traceability extension is a sample with steps, cost and tokens but no integrity or approval fields. Eight outside proposals for signed receipts or audit chains are open and none is adopted. Its September roadmap targets coding harnesses and human-in-the-loop prompts, not audit.

### Cited Findings
**ACP**
- Extensibility: "Implementations can add custom behavior without breaking peers that don't know about it. They can attach custom data in `_meta` fields, define custom methods whose names start with `_`, and advertise custom capabilities". "The following root-level keys in `_meta` SHOULD be reserved for W3C trace context ... `traceparent`, `tracestate`." "Implementations MUST NOT add any custom fields at the root of a type that's part of the specification." — [ACP extensibility](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v1/extensibility.mdx); the meta-propagation RFD is in "Completed" — [meta-propagation RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/meta-propagation.mdx)
- Proxy chains RFD (stage "Draft"; author nikomatsakis): "Enable a universal agent extension mechanism via ACP proxies, components that sit between a client and an agent. Proxies can intercept and transform messages". A "central _conductor_ component ... orchestrates messages"; "When proxies are installed, editors would not start the agent directly, but instead invoke the conductor with the configured proxy chain." Reference conductor: `sacp-conductor` (Rust). Limit: "proxies cannot access internal agent state, model parameters, or other implementation details that aren't exposed through ACP messages." — [proxy-chains RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/proxy-chains.mdx); stages from [docs.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/docs.json)
- v2 permission requests (stage "Active"; author benbrandt): every request gets a required `title`, optional `description`, and a structured `subject` (`tool_call` or `command`), plus `_meta`. "Unknown future subject types should be preserved by clients that proxy, store, replay, or forward permission requests." — [v2 permission-requests RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/v2/permission-requests.mdx)
- Other RFD stages on 1 Nov 2026: session-usage and message-id "Completed"; end-turn-token-usage "Draft"; subagents "Active"; v2 tool-call-updates and diff-file-states "Active". No RFD concerns audit, logging, telemetry or signing. — [ACP RFDs](https://github.com/agentclientprotocol/agent-client-protocol/tree/main/docs/rfds)
- Registry schema fields: `authors`, `description`, `distribution`, `icon`, `id`, `license`, `license_url`, `name`, `preview`, `repository`, `version`, `website`; no signing, attestation, provenance or audit fields (one checksum mention, for distribution). 44 agents listed. — [agent.schema.json](https://github.com/agentclientprotocol/registry/blob/main/agent.schema.json) (GitHub API, 1 Nov 2026)
- Attention: agent-client-protocol 4,560 stars; claude-agent-acp 2,716; codex-acp 502; registry 445 — (GitHub API, 1 Nov 2026)

**A2A**
- v1.0 proto: Task has `repeated Message history` and `metadata`; Message and Artifact carry `metadata` and `extensions`. The only signature is on the agent card: "JSON Web Signatures computed for this `AgentCard`" (`AgentCardSignature`, RFC 7515 JWS). — [a2a.proto](https://github.com/a2aproject/A2A/blob/main/specification/a2a.proto)
- Traceability extension (in the samples repo; last changed 21 Aug 2025): a `ResponseTrace` of `Step`s, each with `ToolInvocation` or `AgentInvocation`, `cost`, `total_tokens`, `latency`, start and end time. "Traceability information MUST be stored in the metadata for a Message or Artifact". No signature, hash or approval fields. — [traceability spec](https://github.com/a2aproject/a2a-samples/blob/main/extensions/traceability/v1/spec.md)
- Roadmap ("Last updated: Sep 15, 2026"): "A2A CLI and Coding Harness Integration (#1929): Deliver the new A2A CLI tool to bridge the adoption gap in coding harness tools"; BiDi streaming; "Elicitation & Multi-Turn Workflows ... structured human-in-the-loop interaction models". Nothing on audit or receipts. — [A2A roadmap](https://github.com/a2aproject/A2A/blob/main/docs/roadmap.md). The CLI (created 28 Jul 2026, 168 stars) ships as an Agent Skill that "teaches harnesses like Claude Code, Cursor, and Codex to delegate work to A2A agents" — [a2aproject/a2a-cli](https://github.com/a2aproject/a2a-cli)
- Extension governance: official repos use `ext-{name}`; experimental repos use `experimental-ext-{name}` and need sponsorship from an A2A maintainer; "The TSC retains oversight". — [extension governance](https://github.com/a2aproject/A2A/blob/main/docs/topics/extension-and-binding-governance.md). The four experimental extensions are `oid4vp-auth` (14 May 2026), `cratb-auth` (24 Oct), `structured-input` (26 Oct) and `media-type-schemas` (27 Oct); none concerns receipts or audit — (GitHub API, 1 Nov 2026)
- Open, unadopted outside proposals: #1718 "Bilateral signed interaction records as the trust primitive for A2A" (5 Apr 2026); #2026 "Trace Context Extension for Cross-Protocol Audit Chains (A2A ↔ MCP)" (3 Jul); #2079 "cA2A, confidential delegation (attenuated authority, peer attestation, sealed payloads, provenance)" (28 Jul); #2093 "Governed Objects (signed purpose/TTL/replay envelopes)" (31 Jul); #2132 "Trust Decision Provenance and Evaluation Assurance" (13 Aug); #2150 and #2152 "signed-receipts/v1" (19 Aug, two variants); #2254 "Intent Exchange (... dual-signed deals)" (21 Sep). All eight were open on 1 Nov 2026. — [#1718](https://github.com/a2aproject/A2A/issues/1718); [#2026](https://github.com/a2aproject/A2A/issues/2026); [#2079](https://github.com/a2aproject/A2A/issues/2079); [#2093](https://github.com/a2aproject/A2A/issues/2093); [#2132](https://github.com/a2aproject/A2A/issues/2132); [#2150](https://github.com/a2aproject/A2A/issues/2150); [#2152](https://github.com/a2aproject/A2A/issues/2152); [#2254](https://github.com/a2aproject/A2A/issues/2254) (GitHub API, 1 Nov 2026)

### Inferences
- The protocols that join vendors leave the record to the endpoints. In ACP the natural capture point is the client or a proxy in the chain. A sidecar built as an ACP proxy (or a conductor wrapper) would see every tool call, permission request and decision for any of the 44 registry agents in Buzz, JetBrains Air or Zed, without each hub's cooperation. That depends on the proxy-chains RFD moving past Draft and on clients letting an organization insert a proxy.
- The ACP v2 permission request is close to a portable approval record: title, subject (tool call or command), options, plus `_meta` for a sidecar's action digest and approver reference. Recording approvals in that shape keeps the sidecar's entry format close to the wire format.
- In A2A, receipts are a crowded, leaderless area: eight proposals in seven months and no maintainer-sponsored extension. A ninth would add noise. Sponsoring or joining one, after the IETF AUDIT decision (L1-1.06), is the cheaper path.

### Gaps
- ACP's meeting notes (`agentclientprotocol/meetings`) and the proxy-chains implementation status in Zed or JetBrains were not read.
- I did not check whether any A2A maintainer has commented on the receipt proposals or offered sponsorship.
- I did not read whether the Linux Foundation or AAIF governance covers ACP (L1-1.06 found none).

### Inferences
**Answer to the question.** Hubs are starting to capture harness actions (Buzz live, GitHub and JetBrains as session views), and none records review and delegation between vendors as durable, signed, team-readable evidence. Each stops at a different layer:
- Buzz streams and forgets, by design.
- GitHub logs what reached the repository.
- JetBrains counts sessions.
- codex-plugin-cc keeps a capped personal job list that does not name the reviewing model.
None encrypts records from its own host under the team's keys.

**What it means for "partner with Buzz".**
- It holds, as complementary layers: Buzz is the live window and coordination surface, and the sidecar is the durable, team-keyed record and the capture for sessions outside Buzz.
- The integration can be built without Block: the sidecar runs as a Buzz agent with an owner-authorized key (NIP-OA). It posts approval requests and entry summaries as ordinary messages, diffs or NIP-34 patches, and reads NIP-AO frames it is owner of, for agents launched by `buzz-acp`.
- Offering an upstream kind, an audit export (#3228) or a decision ledger (#7797) is worth trying but should not be on the critical path. Block has not answered six such outside proposals.
- The open-source role does not narrow to "a capture plug-in for Buzz" while Buzz keeps workspace content operator-readable, captures only agents it launches, and treats durable transcripts as out of scope.

**What it means for "review between vendors, on the record".**
- It holds and gains direct evidence: a user of the most-starred bridge keeps "a per-round record by hand" because the bridge does not record which model reviewed.
- The entry should carry the fields users ask for: reviewer harness, model ID, binary version, effort, sandbox, verdict and findings (codex-plugin-cc's schema can be adopted as is), round number, and the commit or change set reviewed. It should keep automated review threads out of personal histories (#282, #385).
- Block itself practises review across models ("crossfire reviews"), which supports the demand story.

**What it means for pitch4's competitor tables.**
- Buzz row: replace "over iroh" and "one vendor each". Buzz runs Claude Code, Codex, goose and nine preset harnesses through ACP. It streams every tool call to the owner live but keeps none, signs workspace events, and keeps channel content readable by the operator by design.
- Add a "vendor bridges" row: codex-plugin-cc, the Codex importer and GitHub Agent HQ carry work between vendors for free, and none keeps a signed, team-readable record of the exchange.
- JetBrains row: cross-harness policy and session counts, no action content.

**Directions this evidence supports.**
- **Lead with the durable record the hubs drop** (differentiation; confidence high): "Hubs show you agents working; the sidecar keeps the evidence." Every hub reviewed either discards harness actions (Buzz NIP-AO), logs only configuration (GitHub), keeps metadata (JetBrains) or keeps 50 local jobs (codex-plugin-cc).
- **Capture at the ACP seam** (offering; confidence medium): build the capture point as an ACP proxy or conductor wrapper, alongside hooks for non-ACP harnesses. One adapter would cover the 44 registry agents in Buzz, JetBrains Air and Zed. Record approvals in the shape of ACP v2 permission requests, with the sidecar's digest in `_meta`.
- **Ship a concrete cross-vendor review entry and a codex-plugin-cc companion** (both; confidence medium). Use the plugin's review schema plus model, binary, effort, round and commit. Fill it from Claude Code `Stop` and `SessionEnd` hooks and the Codex rollout. Keep it in the team ledger, not personal histories. This answers open issues #645 and #655 without OpenAI.
- **Make the Buzz partnership one that needs no upstream changes** (both; confidence low to medium). Use existing kinds and NIP-OA keys; offer the decision ledger and audit export as sidecar features that read and write Buzz; propose upstream only through an issue first, per Buzz's CONTRIBUTING.
- **Join an existing receipt effort rather than add a ninth** (differentiation; confidence low). Map entries to ACP `_meta` and v2 permission subjects, and pick a sponsored A2A experimental extension or the IETF AUDIT outcome for the envelope.

### Gaps
- No buyer evidence was gathered on whether teams want a shared record of review between vendors, or would pay for it (the open question c2-1.2-3 from L1-1.02 still applies).
- Codex message boards, Zed, Devin Desktop and Happy were not examined as hubs; Cursor's ACP behaviour was not opened.
- Whether hubs will let an organization insert an ACP proxy (the seam the capture direction depends on) is untested.
