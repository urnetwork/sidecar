# Would teams pay for a network identity per agent, or is fixing port and service collisions a free script? (research as of 1 Nov 2026)

Scope: this follows L1-1.02 (`L1-1.02-coordination-parallel-agents.md`). That note found the shared local environment is the pain people voice most about parallel agents: 14 people describe it directly and 6 more built workarounds. It also listed Coasts, Hyve, Boxes.dev, and Paradev, Conductor's pricing, and a star table. None of that is repeated here. This note adds:
- what happened to Claude Code #34385;
- what each harness now does per worktree;
- traction and prices for the tools that fix collisions;
- a measured proxy for how many parallel-agent setups run services per agent;
- new user voices.

Method and reading key:
- **GitHub (1 Nov 2026):**
  - Repo metadata, issues, and releases were read with `gh api`.
  - Release "asset downloads" sum `download_count` over all releases. Auto-updates inflate this for desktop apps.
  - Repo counts come from `search/repositories` with `created:>=2026-01-01`.
- **Config-file sample (my measurement):**
  - For each harness I took the top 100 GitHub code-search results ("best match", not random) for its parallel-agent setup file and kept one file per repo.
  - Files: Conductor `conductor.json` (query `filename:conductor.json setup run`), Cursor `.cursor/worktrees.json`, and Codex `.codex/environments/*`.
  - I fetched each file by blob SHA and classified it by regex:
    - **port wiring:** `CONDUCTOR_PORT`, `${PORT`, `PORT=`, `--port`, `*_PORT`, `"port":`
    - **services:** docker compose, Postgres, psql, createdb, Redis, MySQL, Mongo, Supabase, db:create/migrate/setup, prisma migrate, rails db, devcontainer, testcontainers
    - **dev-server command:** npm/pnpm/yarn/bun dev or start, next dev, vite, rails s, bin/dev, uvicorn, runserver, flask run, phx.server, foreman, overmind, turbo dev, mprocs, tilt up
  - Scripts that a config calls in other files were not followed, so the counts are lower bounds. Raw REST code-search totals are approximate and token-based, so I use them only as rough size indicators.
- **Hacker News:**
  - I ran 12 Algolia comment queries and 12 story queries (created on or after 1 Jan 2026), listed in the scratchpad script.
  - I excluded every HN id already cited in L1-1.02 and read the matches by hand.
  - Full comment text and the root story come from the HN Firebase API.
  - People promoting their own product are labeled "(vendor)" and left out of the counts. Authors of free tools are labeled "(free-tool author)" and counted.
- **Docs:**
  - Claude Code docs were read from `code.claude.com/docs/llms-full.txt`, with the source page attributed for each quote.
  - Cursor and Codex worktree docs and the vendor pricing pages were fetched as HTML on 1 Nov 2026.
  - Conductor's environment-variable reference and Docker's report were read through a fetch tool, so their quotes come back from that tool's extraction.
- **Quotes** are exact unless marked. "Earlier notes" means this project's earlier research, not re-opened today.

## 1. What share of developers running parallel agents run local services for each agent?

### Takeaway
No survey measures this. The best proxy I could build, from public setup files, says it is a minority practice except where the tool makes it easy:
- **Cursor:** about 5% of public worktree setup files start or wire any service.
- **Codex:** about 19% of public local-environment files name a dev-server command, and none wires a per-worktree port.
- **Conductor:** about half of public configs with setup and run scripts name a dev-server command. Conductor ships a run script and a 10-port block per workspace.

A Boxes.dev founder says "Very few people are doing this right now".

Those who do it run whole stacks per agent (web, frontend, Redis, Postgres) and describe it as heavy. Others avoid worktrees because of the friction.

### Inferences
- Running services per agent is a minority practice. It concentrates where the tool supplies the primitive:
  - Conductor gives a run script plus `CONDUCTOR_PORT`, and about half of its sampled configs start a dev server.
  - Cursor's setup-only `worktrees.json` almost never starts one (5%).
  - Codex sits between (19%), and none of its sampled configs wire a port.
- That pattern suggests latent demand held back by friction (sprobertson opts out; jefftk shows homemade schemes collide). It also shows that a harness vendor can capture the demand with a single environment variable.
- A very rough order of magnitude, with low confidence: about a third of agent users run several agents (Stack Overflow, in L1-1.02). If 5–20% of their setups (outside Conductor) run services per agent, that is low single-digit percent of all agent users today. Among Conductor-style users and full-stack web teams whose agents test the running app, it is much higher. Public config files are a biased proxy: open-source repos, best-match ordering, and many teams configure nothing.
- The trend runs toward more per-agent stacks. Agents now verify their work against the running app (nab's claim), and multi-copy stacks are already heavy on laptops (booty). The same pressure pushes toward cloud boxes, which do not need a local per-agent address.

### Gaps
- No survey or telemetry gives the share of parallel-agent users who run a dev server, database, or compose stack per agent. Conductor, Paradev, or Orca usage data would answer it; none is public.
- The sample covers public repos only and does not follow scripts referenced from the config files, so port wiring is undercounted.
- Docker's 2026 report and the Stack Overflow 2026 survey were not found in search. The figures above are from the fall-2024 Docker survey.
- Reddit, Discord, and the Cursor forum were not mined in this round.

## 2. Do Claude Code, Codex, Cursor, or Conductor now allocate ports, containers, or network namespaces per worktree or agent? What happened to Claude Code #34385?

### Takeaway
Harnesses and managers have converged on allocating ports. None gives each agent its own address on default ports.
- **Claude Code:** #34385 was closed by a stale bot as "not planned", with no staff reply. Claude Code now puts background sessions in worktrees automatically and gives Desktop preview servers the next free port (`autoPort`).
- **Claude Code's Linux sandbox:** it already gives each sandboxed command a private localhost. That is a network namespace for security, and it cannot reach the host's servers.
- **Conductor:** it assigns a block of 10 ports per local workspace. Its cloud workspaces get their own machine.
- **Cursor and Codex:** their worktree docs do not mention ports. Codex users have open requests for port forwarding of dev servers.

### Inferences
- **What #34385 shows.** The vendor did not treat this as a platform priority. A bot closed it, the demand signal was 4 reactions, and its duplicates had none. Anthropic then shipped the narrow version: a free port for its own preview server. The demand-side reading is that users who hit this build their own fix rather than upvote, which is what the author said he did.
- **Two harnesses now ship a port primitive, but not a network identity.**
  - Conductor ships a port block, and Claude Desktop ships next-free-port.
  - Both still change the port number, which Claude's own docs say breaks "OAuth callbacks or CORS allowlists". hotfixguru says the same about portless.
  - Both cover the HTTP dev server, not the whole stack: Postgres on 5432, Redis on 6379, compose services.
- **Claude Code already has a per-command network namespace on Linux.** It exists for security, not convenience.
  - Its macOS warning names the cross-service risk: a sandboxed command can reach "every other service listening there".
  - So a private network identity per agent is in the vendor's design vocabulary on both sides: isolation now, and possibly convenience later. It is a credible area for a harness to extend, which makes it a commoditization risk.
- **Cloud is how vendors answer this.** Each cloud workspace gets its own machine (Conductor Cloud, Boxes.dev), and Codex users ask for port forwarding rather than local isolation (#21294, #49927).

### Gaps
- I did not find whether Claude Desktop's `autoPort` or worktree isolation coordinates ports across concurrent CLI sessions, or only for its own preview server.
- I did not read Conductor's cloud docs or Codex #44385's body directly.
- Cursor's own docs show no port feature. One HN user (ninininino, [HN 47708417](https://news.ycombinator.com/item?id=47708417)) quoted a Cursor docs line that automatic worktree management "was removed in Cursor 3.0". The current docs page describes worktrees in the Agents Window, IDE, and CLI, so the claim is unverified.

## 3. What adoption, pricing, and traction do the tools that fix collisions have?

### Takeaway
Free tools hold the traction, paid tools sell compute, and the dedicated free product has stalled:
- **Local fixes are free and widely used.** Vercel's portless has 12.8k stars and 5.9M npm downloads in the last month. Conductor's local port block is free, and so is Claude Desktop's autoPort. GitHub holds a long tail of about 183 new repos in 2026 that describe worktree port tools.
- **The only paid products bundle isolation with cloud compute:**
  - Boxes.dev: $19–$249 per user per month plus hours.
  - Conductor Cloud: Pro, plus Teams at $60 per user (earlier notes).
  - Paradev cloud hours: Pro $20, Team $60, Ultra $200 per user per month.
- **The dedicated isolation product is free and quiet.** Coasts is YC-backed, "Free, OSS... no AI upsells", and has had no commits since 28 Apr 2026.
- **No customer counts or revenue for any of them were found.**

## 4. Is this a paid need or a free script, and how should pitch4 present a network identity per agent?

### Takeaway
On today's evidence it is a free script, not a paid need:
- No user in this round or in L1-1.02 says they pay to fix collisions between local agents.
- Vendor trackers show little upvoted demand, and the vendor let #34385 lapse.
- Free tools are converging on the HTTP-port case.

A private address per agent is still worth leading with for developers, as a free, daily-use reason to install the sidecar, because it covers what the free tools break: exact ports for OAuth and CORS, whole stacks (databases, Redis, compose) rather than one dev server, any harness, and other machines.

The paid line should stay on what only a team needs: reaching a teammate's or a cloud agent's stack across machines, with grants, approvals, and records. Cloud devbox vendors already charge for this bundle.

### Cited Findings
- **Paying for isolation:**
  - Among the 15 new and 20 earlier non-vendor voices, none states paying to solve local collisions. The nearest is jimmydoe's use of OrbStack, a paid commercial license, for per-worktree domains; whether he pays is unknown. — [HN 46505053](https://news.ycombinator.com/item?id=46505053)
  - booty weighs moving to the cloud instead: "We could, of course, alternatively... just run cheap shitboxes locally and have all our dev environments in the cloud." — [HN 49438090](https://news.ycombinator.com/item?id=49438090)
- **Demand signals in vendor trackers are small:** #34385 has 4 reactions and its duplicates 0. The top Codex port requests have 14 and 6 reactions and concern forwarding, not local isolation. Sources are in section 2.
- **Where port remapping fails:**
  - Claude's docs tell users to disable autoPort "when your server must use a specific port, such as for OAuth callbacks or CORS allowlists" — [code.claude.com/docs/en/desktop](https://code.claude.com/docs/en/desktop)
  - portless "doesn’t work well with oauth flows" — [HN 47971483](https://news.ycombinator.com/item?id=47971483)
  - Coasts lets only one instance hold "canonical ports" on the host at a time — [Coasts README](https://github.com/coast-guard/coasts)
- **Shared databases stay unsolved even in the dedicated tool:** Coasts leaves that choice "to the orchestration layer". — [HN 47578593](https://news.ycombinator.com/item?id=47578593)
- **Security framing already exists at the vendor:** Claude's macOS sandbox warning says a sandboxed command can reach "every other service listening there". Its Linux sandbox makes localhost "private to that command". — [code.claude.com/docs/en/sandboxing](https://code.claude.com/docs/en/sandboxing)
- **Buyer features attach to cloud compute:** Boxes.dev Teams lists "SSO, SCIM, RBAC Audit logs and spend controls" and "Custom MSA, security review". — [boxes.dev](https://boxes.dev)

### Inferences
- **Present reach to developers as everyday convenience, in the free tier.**
  - A line such as: "Every agent runs its whole stack on its default ports, at its own private address: 3000, 5432, and 6379, unchanged, in every harness."
  - This turns pitch4's first-release "IP addresses" item from a security line into something developers use every day. It matches the pain voiced most (L1-1.02) and needs no config changes, unlike `CONDUCTOR_PORT`, autoPort, or portless renaming.
  - It should not be the paid line. Every comparable local fix is free, and a harness can copy the HTTP case with one environment variable.
- **Differentiate against port remappers on four cases they leave open:**
  1. exact ports (OAuth callbacks, CORS allowlists);
  2. non-HTTP services (databases, Redis, queues);
  3. all instances holding canonical ports at once, which Coasts cannot do;
  4. one mechanism across Claude Code, Codex, Cursor, and Conductor.
  - Caveat: a different IP means a different host. OAuth redirect URIs registered for `localhost:3000` still break unless each agent has its own private `localhost` (a namespace) or the provider accepts the per-agent hostname. The demo has to show OAuth working, not just claim it. This is inference and is untested.
- **Join the halves.** The same per-agent address that ends collisions also stops agent A reaching agent B's unauthenticated localhost services, and it records which agent reached which service. That turns a daily developer feature into security evidence. It fits "one write, three readers", and it extends a risk the harness vendor already documents.
- **Put the free/paid line at the machine boundary:**
  - Free: per-agent addresses and services on one machine.
  - Team (paid): a cloud agent, or a teammate, reaching a specific agent's stack across machines, with a grant, approval, and receipt. This also covers previews shared with reviewers, and the Codex users asking for remote dev-server forwarding (#21294).
  - This competes with cloud devboxes ($19–$249 per user plus hours) by keeping compute on the customer's hardware ("the bulk of your hardware sits idle", Coasts). It does not compete with free port tools.
- **Integrate with the free tools rather than fight them.** The sidecar's "instruction-file writer" could write `conductor.json`, `.claude/launch.json` (`autoPort: false`, plus a per-agent `url`), `.cursor/worktrees.json`, and Codex local-environment setup that point each agent at its own address. It could also coexist with portless names. Adoption then rides on files developers already keep.
- **Pick design partners from full-stack web teams whose agents test running apps** (nab's trend, booty's four-stack monolith). For most parallel-agent users today, per-agent services are rare (5–19% of non-Conductor setup files), so a broad "every developer needs this" claim would overreach.

### Gaps
- Willingness to pay for cross-machine, per-agent reach is untested. No interviews or pricing tests exist. The cloud-devbox prices show what compute plus isolation sells for, not what reach alone would.
- Feasibility on macOS (where Coasts and most managers run) of giving each agent its own address on default ports without root or containers is not established in this note. Loopback aliases, utun, or a VM may be required.
- No data shows how often exact-port needs (OAuth, CORS) block port-remapping tools in practice. Two sources name it: Claude's docs and one user.
