## 1. What does each open harness send off the machine when set up for a local model, and what switches stop it?

### Takeaway
Every one of the nine harnesses contacts hosts other than the model server by default, even when pointed at a local model. The traffic falls into five groups: telemetry, model catalogs, update checks, downloads of binaries and plugins, and vendor cloud features. Eight of the nine have a telemetry or analytics client; I found none in OpenCode's core. Source confirms it is on by default in Crush, Continue, and Qwen Code. Goose asks for consent, Aider asks a 10% sample to opt in, Pi sends install telemetry, and I did not verify the defaults for Cline and Kilo. Pi has a single documented offline switch (`PI_OFFLINE`/`--offline`). Crush has two flags that cover its two hosts. OpenCode has about six separate flags but no single offline mode, and its maintainers closed two offline-mode PRs unmerged. Cline, Kilo, Continue, Goose, and Qwen Code have per-feature opt-outs, and none has a documented air-gapped mode.

### Cited Findings

#### OpenCode 2.2.5 (anomalyco/opencode)
- **Model catalog from `https://models.opencode.ai`.** `const defaultSource = "https://models.opencode.ai"`, path `/experimental/v2.0/api.json`. A bundled snapshot is the fallback: "Release builds bundle the live catalog in its place when it can be fetched", and a server comment calls it "the boot-time floor either way" — [models-dev.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/core/src/models-dev.ts); [workerd.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/server/src/workerd.ts)
  - The switches are `OPENCODE_DISABLE_MODELS_FETCH` ("Disable fetching models from remote sources"), `OPENCODE_MODELS_URL`, and `OPENCODE_MODELS_PATH` ("Load the model catalog from a local JSON file") — [cli.mdx env table](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)
  - `OPENCODE_MODELS_URL` arrived in PR #9258, merged 21 Jan 2026, "so the models.dev domain configurable for offline environments" — [#9258](https://github.com/anomalyco/opencode/pull/9258)
- **Desktop catalog polling (v1).** "The OpenCode Desktop app (`ai.opencode.desktop` v1.14.29) downloads 25–145 MB from `raw.githubusercontent.com` every ~10 minutes, 24/7, while only writing a 1.9 MB local file (`~/.cache/opencode/models.json`)." The reporter noticed it on a gateway traffic chart. Closed as not planned, 8 Jul 2026 — [#26068, 6 May 2026](https://github.com/anomalyco/opencode/issues/26068)
- **ripgrep download.** If no `rg` is on PATH, OpenCode downloads `https://github.com/BurntSushi/ripgrep/releases/download/${VERSION}/${filename}`. The v2 code checks for a system `rg` first — [ripgrep/binary.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/core/src/ripgrep/binary.ts)
- **LSP server downloads.** On by default. "You can disable automatic LSP server downloads by setting the `OPENCODE_DISABLE_LSP_DOWNLOAD` environment variable to `true`." — [lsp.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/lsp.mdx)
- **Update checks.** "You can turn off update checks and notices with the `autoupdate` option… Setting `autoupdate` to `true` or `"notify"` keeps the default behavior: you're notified, but nothing is installed until you choose to update." — [config.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/config.mdx)
  - The updater calls `https://formulae.brew.sh/api/formula/opencode.json` or the npm registry, depending on install method. `OPENCODE_DISABLE_AUTOUPDATE` also exists — [updater.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/cli/src/services/updater.ts); [cli.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)
- **npm plugin installs at startup.** "opencode installs `@opencode-ai/plugin` and any npm plugins at startup via arborist. In environments where npm registry access is restricted (corporate networks, air-gapped systems) or undesirable (immutable production containers), this fails silently or causes unexpected network calls on every run." A request for `OPENCODE_DISABLE_INSTALL` was closed as not planned on 29 Oct 2026 — [#37888, 20 Jul 2026](https://github.com/anomalyco/opencode/issues/37888)
  - Related flags: `OPENCODE_DISABLE_DEFAULT_PLUGINS` and `OPENCODE_PURE` ("Run without external plugins, like `--pure`") — [cli.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)
- **Web UI.** Now embedded. Maintainer, 26 Mar 2026: "Fixed by #19299 - The WebUI is now embedded directly in the binary, so it works fully offline without requiring any CDN assets… Note: Other non-LLM network calls (models.dev, update checks) may still require additional configuration via existing environment variables like OPENCODE_DISABLE_MODELS_FETCH." — [#18492](https://github.com/anomalyco/opencode/issues/18492)
  - `OPENCODE_DISABLE_EMBEDDED_WEB_UI` means "Disable the bundled web UI and use the remote UI fallback" — [cli.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)
- **Default model when signed out.** "Signed out, only free OpenCode models are enabled. Clients default to the first available model" (code comment). Unless a local default model is configured, the default is a hosted OpenCode model — [model.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/core/src/model.ts)
- **Title generation (small model).** In v2, `Model.small(providerID)` picks only models with `model.providerID === providerID` from the families `gpt-luna`, `gemini-flash-lite`, `gemini-flash`, and `claude-haiku` — [model.ts](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/core/src/model.ts)
  - The docs say: "By default, OpenCode tries to use a cheaper model if one is available from your provider, otherwise it falls back to y[our main model]" — [config.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/config.mdx)
  - Conflict: HN users in Sep 2026 described a cloud default for titles (L1-1.01). That may describe v1 (see Inferences).
- **Web search.** Opt-in: `OPENCODE_ENABLE_EXA` and `OPENCODE_ENABLE_PARALLEL` — [cli.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)
- **What a proposed offline switch would have blocked.** A contributor's offline-mode PR listed these: "`opencode.ai/install` auto-update check | Skipped"; "`opncd.ai` session sharing | Disabled"; "`app.opencode.ai` web UI proxy | Returns 503". - **OpenCode declined a single offline mode.**
  - PR #18235 was closed unmerged on 10 Oct 2026 with: "This branch has been upgraded to V2. We're no longer taking PRs for V1. If you think this is still relevant, please port it over and open it for V2." An earlier PR, #8130 ("add offline mode support for air-gapped environments"), was also closed unmerged — [#18235](https://github.com/anomalyco/opencode/pull/18235); [#8130](https://github.com/anomalyco/opencode/pull/8130)
  - Issues closed as not planned: #2224 (airgapped install; 53 reactions, 26 comments) on 16 May 2026; #10416 ("not private by default"; 85 reactions) on 23 Jun 2026; #18233 (offline mode) on 15 Jul 2026 — [#2224](https://github.com/anomalyco/opencode/issues/2224); [#10416](https://github.com/anomalyco/opencode/issues/10416); [#18233](https://github.com/anomalyco/opencode/issues/18233)
  - The current docs list no `offline` key, even though a maintainer promised an `offline: true` flag in Jan 2026 (L1-1.01) — [cli.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/cli.mdx)

### Inferences
- **The leaks are the harness's own housekeeping.** Eight harnesses have telemetry clients, six of them PostHog. Catalogs, updates, and plugin or binary downloads appear in nearly all. Sidecar policy therefore has to be per harness and per version. A model-API proxy cannot see this traffic.
- **OpenCode's title-to-cloud leak is probably fixed in v2.** The code restricts the small model to the same provider, which matches the docs. The September 2026 HN reports likely describe v1. This should be checked at runtime before pitch4 cites it.
- **A local default model matters in OpenCode.** When signed out with no default configured, OpenCode picks a hosted free model. A sidecar should set a local default model, not only block egress.
- **Unlike OpenCode, Pi and Crush accepted a first-class offline mode.** Maintainers of the largest harness (OpenCode) have twice declined a single switch. That is the strongest evidence that a harness-independent layer has a role.

### Gaps
- I did not run any harness to measure traffic. The matrix is from source and docs. Runtime-built hosts and analytics-SDK defaults may add hosts I did not see.
- I did not confirm when Kilo calls `ingest.kilosessions.ai`, whether `OPENCODE_PURE` prevents the startup npm installs in #37888, or when Cline's SDK fetches models.dev.
- Continue's `main` branch shows its last commit on 20 Jul 2026, although the repository was pushed 1 Nov 2026. Active development may be on another branch.

## 2. What breaks when that traffic is blocked?

### Takeaway
Blocking without stubs breaks real work in four harnesses. It breaks search and skills in OpenCode and Kilo (ripgrep), setup or startup in Kilo, Cline, and older OpenCode and Crush, and MCP configuration in Cline. Elsewhere the effects are softer: slower or noisy starts in Aider, lost model discovery in Pi, and warnings in the Continue CLI. Maintainers often close these reports as not planned. ## 3. How widely do harness users use OS firewalls and sandboxes, and what do those tools and the harnesses' own sandboxes record about network attempts?

### Takeaway
OS firewalls are popular in general but rare in the coding-agent context. On HN, about a dozen people over 22 months describe running Little Snitch, OpenSnitch, or LuLu on an AI coding tool or local model. LuLu's 18k Homebrew installs a year compare with tens of millions of monthly npm downloads for harnesses (downloads are not users). OS firewalls see the harness's own traffic, but they key on processes, prompt per connection, and do not know which host is telemetry and which is the model server. Built-in sandboxes (Claude Code, Codex, Anthropic's sandbox-runtime) fence only the agent's commands, and their violation records are short-lived. nono already writes a per-session network audit that can be listed as JSON and signed. Greywall and Watch.ly are building "Little Snitch for agents".

### Cited Findings

### Inferences
- **Overlap with OS tools.** OS firewalls already see and block the harness's own traffic, which the harnesses' sandboxes do not. That is real overlap with "keep the harness's traffic local". OS firewalls do not:
  - know per harness version which host is the model server, a catalog, or telemetry
  - stub catalogs or provision binaries, so blocking breaks things (section 2)
  - tie connections to an agent run, approval, or model
  - produce a signed, shareable, team-readable report
  - avoid prompt fatigue
  
  So the sidecar would run alongside OS tools, or drive them, rather than replace them.
- **Overlap with sandboxes.** nono, srt, and Greywall overlap most with "enforce and record" on one machine, and they are free and open source. The sidecar should not try to win on single-machine capture. It can add harness manifests, team keys and signing across machines, and binding to runs and approvals. Integrating their logs (nono's JSON audit, srt's violation events) may be cheaper than rebuilding them.
- **The users are few, but signal is high.** People who run OS firewalls are the ones who discover undocumented traffic (guessmyname on Codex telemetry; the OpenCode #12770 reporter). They are a natural early-adopter and evangelist segment, not a revenue segment.

### Gaps
- There is no direct measure of how many harness users run OS firewalls or sandboxes. HN counts measure who talks about it. Reddit (r/LocalLLaMA) was not accessed.
- I did not check whether LuLu or Little Snitch can export connection logs or rules in a form a sidecar could import.
- Codex's local default network policy and any network log were not documented on the pages I could fetch.

## 5. Does enforcement in the request path survive the single-point-of-failure objection, and what fail-open designs exist?

### Takeaway
The objection holds when the sidecar proxies model calls: in-path egress proxies do break work, as Anthropic's Cowork allowlist bugs show. It does not hold if enforcement sits in the OS or sandbox layer with a direct allow rule to the model server, so that the sidecar only configures rules and records denials. Then a sidecar crash leaves inference running and leaks still blocked. Precedents for scoped fail-open and fail-closed choices exist: Claude Code's `failIfUnavailable` and LiteLLM's `allow_requests_on_db_unavailable`. The HN debate itself split: OTEL-only advocates argued against proxies, while others argued that untrusted clients are exactly where proxies belong.

### Cited Findings
- **The objection.** "I would argue you should not use a proxy to do this because the end result is a single point of failure direct in the line of your productivity." — [CharlieDigital, HN 50151130, 19 Oct 2026](https://news.ycombinator.com/item?id=50151130). The reply subtree has 14 comments by 8 authors.
  - "OTEL… out-of-process + buffered by default… A failing/mis-configured OTEL endpoint/collector isn't going to stop you from getting w[ork done]" — [CharlieDigital, HN 50156016](https://news.ycombinator.com/item?id=50156016)
  - "You can build a proxy setup that is not a SPOF." — [lokar, HN 50155646](https://news.ycombinator.com/item?id=50155646)
  - "a key place for proxies is resource access where the client is not fully trusted (or for any reason it may fail to log correctly). AI agents seem like a pretty clear case of this." — [lokar, HN 50156389](https://news.ycombinator.com/item?id=50156389)
  - "Wouldn't a fair criticism of OTEL be that you only see what these harnesses are willing to show you?… Maybe the argument should be that all harnesses should be sandboxed and monitored for all networking." — [ProjectBarks, HN 50153072](https://news.ycombinator.com/item?id=50153072)
  - "The proxy's are generally inconvenient and yet another point of failure." — [chopete3, HN 50147725](https://news.ycombinator.com/item?id=50147725)
  - eBPF-based collection was mentioned as an option — [JustFinishedBSG, HN 50154600](https://news.ycombinator.com/item?id=50154600)
- **In-path egress proxies breaking work** (anthropics/claude-code):
  - "[BUG] Cowork network egress allowlist not working - custom domains blocked with 403 blocked-by-allowlist" (59 reactions, 76 comments, open) — [#30112, 2 Mar 2026](https://github.com/anthropics/claude-code/issues/30112)
  - "Cowork macOS: MITM egress proxy blocks all non-API domains regardless of allowlist settings" (23 reactions) — [#30861](https://github.com/anthropics/claude-code/issues/30861)
  - Two more allowlist bugs, with 21 and 30 reactions — [#34690](https://github.com/anthropics/claude-code/issues/34690); [#38984](https://github.com/anthropics/claude-code/issues/38984)
  - Sandbox network breakage: "macOS sandbox blocks Security.framework TLS verification, breaking Go binaries" (70 reactions) — [#23416](https://github.com/anthropics/claude-code/issues/23416); "SOCKS5 proxy requires authentication that BSD nc cannot negotiate, breaking SSH git operations" — [#70684](https://github.com/anthropics/claude-code/issues/70684)
  - A request to reach local servers: "Sandbox: allow outbound connections to localhost" (80 reactions) — [#28018](https://github.com/anthropics/claude-code/issues/28018)
- **Fail-open and fail-closed choices in shipped tools:**
  - Claude Code: fails open when the sandbox can't start, unless `sandbox.failIfUnavailable` is `true`; with it set, commands are refused with "Sandbox is required but failed to initialize" — [sandboxing](https://code.claude.com/docs/en/sandboxing) (via fetch tool)
  - LiteLLM: `allow_requests_on_db_unavailable: True`, with "WARNING: Only do this if you're running LiteLLM on VPC". On Prisma connection errors, "Requests proceed with a restricted `INTERNAL_USER` fallback identity, never admin"; query errors are "Treated as fail-closed because the database is reachable"; "LiteLLM Pods will start even if the database is down or unreachable" — [LiteLLM production docs](https://docs.litellm.ai/docs/proxy/prod) (via fetch tool)
  - srt on Windows blocks the sandbox account's outbound connections at the kernel (WFP) "except loopback to the proxy port range" — [srt README](https://github.com/anthropics/sandbox-runtime/blob/98a4016d27/README.md)
  - nono: "direct outbound connections are blocked and traffic must go through the proxy", which fails closed — [networking.mdx](https://github.com/nolabs-ai/nono/blob/f9f58b77ad/docs/cli/features/networking.mdx)
  - Goose tried to make telemetry consent fail closed and dropped it as "too complex for the uncommon failure it addresses" — [PR #11102](https://github.com/aaif-goose/goose/pull/11102)
- **OpenCode's own proxy caution.** "The TUI communicates with a local HTTP server. You must bypass the proxy for this connection to prevent routing loops." — [network.mdx](https://github.com/anomalyco/opencode/blob/97a71f0cc6/packages/web/src/content/docs/network.mdx)

### Inferences
- **A split design answers the objection.** It has three parts:
  1. Model traffic goes directly to the model server's IP and port under an OS-level allow rule, with no user-space hop.
  2. All other egress from the harness's process tree is denied at the kernel or sandbox layer (seatbelt, bwrap or netns with nftables, WFP).
  3. The sidecar sets the rules, records denials from sandbox and kernel logs, and writes the report.
  
  If the sidecar dies, inference continues and leaks stay blocked. Only the report has a gap, and the next run can state that gap, which matches pitch4's "each run states what the record could not see".
- **Domain filtering may need a local proxy for non-model traffic.** Kernel rules cannot see hostnames, which is why srt and nono use a proxy. Under the split design that proxy is not on the productivity-critical path.
- **Pitch4's first-release "model access" forward is a different case.** It does put the sidecar in the request path for remote model servers. For a LAN or same-host model, the direct allow should be the default. For remote reach, the forward needs a stated failure behavior (high availability, or a policy that permits a direct fallback).

### Gaps
- I did not test whether out-of-path enforcement can be applied per harness process tree without root on macOS, Linux, and Windows, or whether it survives harness auto-updaters and background daemons (for example, Codex's daemon, L1-1.01).
- I found no public fail-open design from an agent-egress vendor (nono, Greywall, Watch.ly) describing what happens when its proxy crashes.

## 6. What this means for pitch4

### Takeaway
Local-only proof should be a strong first-release feature for open-weight teams, but not the lead product on its own. Capture and blocking on one machine are already free (nono, Greywall, srt, LuLu, OpenSnitch). Developers who care already use those tools, and they are few. Four things are not covered by anything found here:
- a maintained per-harness egress manifest, with stubs that keep harnesses working offline
- verification that opt-outs held
- a signed, team-readable "what left" record across machines, tied to runs and approvals
- enforcement designed to stay out of the model path

Together these make slide 4's "nothing has to leave your control" checkable.

### Cited Findings
- Pitch4 slide 4: "Open source, so no one has to take our word for it. With open-weight models, nothing has to leave your control." Slide 1: "Local models leave no log. No vendor keeps one." Slide 6: "Hooks fail open, so each run states what the record could not see." Slide 6 also schedules the air-gapped install for "Last" — [pitch4.html](/Users/brien/urnetwork/sidecar/pitch4.html)
- Harnesses send telemetry to their vendors even with local models (section 1). nono, Greywall, and Watch.ly keep local logs of agent egress (section 3).

### Inferences
- **Rewrite slide 1's "Local models leave no log. No vendor keeps one."** Two facts undercut it. Harnesses send telemetry to their vendors (PostHog, Alibaba RUM) even with local models, which is the opposite of "no vendor keeps" anything. And single-machine tools already keep local logs. A more accurate claim: "Local-model sessions leave no record your team controls."
- **Restate slide 4 in checkable form:** "Nothing leaves except what your run report lists". The report should show allowed connections (the model server) and denied attempts (catalogs, telemetry, updates), against the published manifest for that harness version.
- **Move offline and air-gapped operation earlier** for single users, as L1-1.01 also recommended. Stubs (catalog snapshots, ripgrep and LSP provisioning, an npm mirror) are what make it usable.
- **Sell the cross-machine part.** Keep single-machine local-only enforcement and reports free; it builds adoption among OS-firewall users. The paid part is the cross-machine team ledger, client-facing egress packets, and policy managed centrally.

### Gaps
- Willingness to pay for verified egress reports is untested.
- Whether harness maintainers would cooperate on manifests is unknown.
