## 1. Is ACP's proxy-chains design moving past Draft? (RFD stage, PRs, meetings, sacp-conductor and symposium-acp)

### Takeaway
Proxy chains is still Draft on 1 Nov 2026. The maintainers' own notes say "ACP Proxies remain in Draft" (29 Oct). Even so, it moved more in the last week than in the ten months before:
- **30 Oct:** the lead maintainer revised the RFD and merged unstable `proxy/initialize` and `proxy/successor` messages for both ACP v1 and v2. A release PR (open, 31 Oct) would publish them in schema crate 1.15.0.
- **Reference conductor:** it moved from the Symposium `sacp-conductor` prototype (no release since 16 Mar 2026) into the official Rust SDK as `agent-client-protocol-conductor` 3.6.0 (28 Oct 2026). That crate had about 9,000 downloads in 90 days and five dependent crates, all small.
- **Companion RFD:** MCP-over-ACP moved to Active on 29 Oct.
- **Editors:** none implements the conductor or the RFD's "install proxies like MCP servers" vision. A code search of Zed found no use of the new messages.

### Inferences
- **Direction of travel.** Proxy chains is moving toward Active: the schema is in, the conductor lives in the official SDK, and the maintainers list it as "in progress". The next stage needs an owner with bandwidth and a PR. No date has been stated. Getting editors to ship "install a proxy" UI is a separate, later step, and nothing found shows Zed or JetBrains working on it.
- **The protocol is not a prerequisite for a recorder.** A single recording proxy does not need proxy chains. Any process that speaks ACP on stdin and stdout and spawns the real agent works today wherever a client launches the agent from a configurable command (section 2). Proxy chains matters for two things: composing several proxies (a recorder plus others) and editor-managed install. For pitch4, "first release" capture should not wait on it.
- **The reference conductor fails open.** Its documented policy, "Graceful degradation by bypassing failed components", is the "hooks fail open" problem pitch4 criticizes, moved into the conductor. A recorder that sits in a chain needs the opposite policy: fail closed, or record that it was bypassed.
- **Reach of the prototypes.** The Symposium prototypes reached a few hundred downloads, and the successor conductor has five small dependents. There is no sign of a proxy ecosystem a sidecar would compete with or ride on yet.

### Gaps
- ACP's Zulip discussions were not read. The reasons proxies stayed in Draft, and any target date for Active, are unknown.
- No August 2026 meeting notes exist in the repository. Whether meetings happened without notes is unknown.
- Whether JetBrains (which ships ACP clients and attends the meetings) plans conductor support was not found.
- I did not trace which crates pull `sacp` (99k downloads in 90 days), so its remaining users are unknown.

## 2. Can a user or admin set a wrapper or conductor as the agent command in each ACP client today?

### Takeaway
Yes, in every client examined. Each launches the agent from a command the user (or, in JetBrains and Buzz, an admin or host) can set:

| Client | Where the command is set | Wrapper evidence |
|---|---|---|
| Zed | `agent_servers` custom agent: `command`, `args`, `env` | Open-source recorder already does this |
| JetBrains AI Assistant | `~/.jetbrains/acp.json` | Same recorder |
| JetBrains Air (local tasks) | `acp.json` | (none found) |
| Air Governance | Organization custom agents from registry-format JSON with any command | (none found) |
| Buzz | Custom harness JSON; host-controlled `BUZZ_ACP_LAUNCH_PREFIX` | Prefix merged 30 Sep 2026 for a sandbox launcher |
| CodeCompanion | Per-adapter `commands` | (none found) |
| agent-shell | Command variables plus `agent-shell-command-prefix` | (none found) |
| marimo | User runs `npx stdio-to-ws "<agent command>"` | (none found) |

The recorder is the open-source `acp-devtools`: it "sits in the middle of that stdio pipe — neither side knows it's there". The limits:
- In Zed a registry-installed agent cannot be re-pointed. The wrapper has to be a separate custom entry.
- Agents in JetBrains Air Teams cloud tasks run where no local wrapper can sit.

### Inferences
- **Insertion works today, client by client.** Every client takes a wrapper; acp-devtools shows it working in Zed and JetBrains without either side noticing. The work is per-client setup: write `agent_servers` or `acp.json`, set Buzz's prefix, CodeCompanion's commands or agent-shell's prefix. It is not protocol work.
- **Zed's registry path bypasses the recorder.** Zed's registry entries cannot be wrapped in place, so a developer who installs "Claude Agent" from the registry runs it unrecorded. The sidecar has to add a sibling custom entry (for example "Claude Agent (recorded)") and rely on the developer choosing it.
- **The only adoption signal is debugging.** One debugging proxy has 5 stars and 22 downloads a month; one policy benchmark has no results. Nobody has turned ACP capture into a durable or team record. Capture itself is also easy (acp-devtools is MIT-licensed), so it cannot be the moat.
- **Buzz already has a slot for a launcher.** Its prefix was built for a sandbox launcher and is reserved against user settings. A sidecar recorder that preserves stdin and stdout fits that slot unchanged.

### Gaps
- Zed release notes were not read item by item. I relied on the docs (last changed 19 Sep 2026) and source on `main`.
- Devin Desktop, VS Code ACP extensions, avante.nvim, Toad and Obsidian clients were not examined.
- I did not test any of the configurations. Whether JetBrains' org custom-agent JSON accepts a `binary` or `npx` distribution that launches a wrapper (as opposed to a known agent) is documented as "accepted as is" but unverified in practice.
- Remote setups were not examined: Zed remote projects, JetBrains Remote Development, dev containers. Where the wrapper must run in each is unconfirmed. A third-party guide says JetBrains Remote Development runs AI Chat on the remote host — [fast.io](https://fast.io/resources/devin-ai-intellij/) (search summary, secondary).

## 3. Does any client lock the agent's launch path, and can an organization make the wrapper mandatory?

### Takeaway
No client stops a developer from wrapping their own agent. Two clients give an organization a lock, and both locks can work in the sidecar's favour:
- **JetBrains (Business and Enterprise plans):** an admin can turn off "Custom ACP agents" (default enabled), switch off "All available agents" so only listed agents run, and add an organization custom agent whose command is anything. That makes "recorded agents only" enforceable inside JetBrains IDEs. Registry agents are auto-added and cannot be deleted, but they can be left out of a policy.
- **Buzz:** a trusted host can set a launch prefix that user settings cannot override and that fails closed.

Zed gives admins nothing here. Zed Business admin controls "don't cover ... External Agents", registry entries cannot be re-pointed, and the registry URL is a constant. In Zed, capture is opt-in and easy to bypass.

### Cited Findings
- JetBrains policy, AI Assistant card on the Tools tab: "Custom ACP agents | Determines whether users and service accounts can use their own local agents via the Agent Client Protocol (ACP), beyond those configured at the organization level. This is separate from agents configured for the policy on the Agents tab. Default value: enabled." — [Air Governance, Configure AI policies](https://www.jetbrains.com/help/air/ai-policies-configure.html) (fetched 1 Nov 2026; no page date found)
- JetBrains Agents tab:
  - "When All available agents is off, only the agents listed in the Agents table are available."
  - "In the default policy, All available agents is on initially".
  - "Agents added to your organization later are not automatically available to principals under existing policies where All available agents is turned off."
  - Each row shows "Whether the agent is sourced from the global agent registry or added manually at the organization level as a custom agent."

  — same page
- Precedence: when custom policies conflict, "the more restrictive value applies", and "If an agent is disabled in at least one custom policy, it is not available to principals, even if another policy enables it." — [Air Governance, AI policies](https://www.jetbrains.com/help/air/ai-policies.html) (dated 21 Oct 2026; fetch-tool extraction)
- Defaults and registry agents:
  - "The default policy initially makes all agents from this list available to everyone with AI access, so agents work out of the box until you configure policies to restrict them."
  - "If a new agent appears in the global registry, it is automatically added to the Agents table."
  - "Users can also add ACP-compatible agents locally in their IDEs if the relevant AI policy allows it."

  — [Air Governance, Agents](https://www.jetbrains.com/help/air/ai-agents.html) (08 Oct 2026). The same page says registry-sourced agents "cannot be deleted from the list" (fetch-tool extraction).
- The IDE side confirms the lock: if the organization manages AI through JetBrains IDE Services or JetBrains Central, "an administrator can control which agents are available to you and whether you can add your own"; some agents "might be disabled, and you might not be able to add a custom agent." — [AI Assistant help, ACP](https://www.jetbrains.com/help/ai-assistant/acp.html) (07 Oct 2026; fetch-tool extraction)
- MCP is not locked the same way: "Users can also add MCP servers locally in their IDEs and JetBrains Air. The servers they can add locally are not limited to the ones configured at the organization level." — [Configure AI policies](https://www.jetbrains.com/help/air/ai-policies-configure.html)
- Buzz: the host must "reserve this key against user-supplied environment settings and apply the trusted prefix after merging user environment. Desktop's shared reserved-key filter covers saved persona/agent settings and local/remote launch environments." Malformed prefixes "fail launch with no direct fallback". Custom harness `env` cannot override Buzz-reserved keys ("always stripped and cannot be overridden"). — [buzz-acp README](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md)
- Zed Business: "Most controls apply server-side to anything that routes through Zed's infrastructure." "These controls don't cover bring-your-own-key (BYOK) configurations, gateways, local or self-hosted models, External Agents, Terminal Threads, or third-party extensions, since those work independently of Zed's servers." The listed controls are Collaboration, Zed Model Provider, Edit Prediction and Agent Thread Feedback. — [Zed docs, Admin Controls](https://github.com/zed-industries/zed/blob/main/docs/src/business/admin-controls.md) (last changed 4 Jun 2026; public at [zed.dev/docs/business/admin-controls](https://zed.dev/docs/business/admin-controls))
- Zed's registry agents carry no `command` override, and the registry URL is a compile-time constant (section 2 sources).
- The ACP maintainers discussed promoting "creating your own filtered registry" (17 Sep 2026); `acpr` already accepts `--registry <file>`. — [2026-09-17](https://github.com/agentclientprotocol/meetings/blob/main/core-maintainers/2026-09-17.md); [acpr](https://github.com/agentclientprotocol/acpr)
- The Claude adapter honours managed policy: `managed-policy.ts` "Applies the managed-policy tier's env vars to `process.env` before any SDK call", including "MDM sources on macOS and `HKLM`/`HKCU` on Windows". — [claude-agent-acp managed-policy.ts](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/managed-policy.ts) (GitHub API, 1 Nov 2026)

### Inferences
- **JetBrains is the one ACP client where a security buyer can make the sidecar mandatory with the client vendor's own controls.** The recipe:
  1. Add an organization custom agent whose command is the sidecar wrapper launching the real agent.
  2. Turn "All available agents" off and list only wrapped agents.
  3. Turn "Custom ACP agents" off.

  This is untested. JetBrains warns it does not validate commands, and enforcement is client-side under the organization's JetBrains licence. A developer can still run Claude Code in a terminal outside the IDE, so the claim is "inside JetBrains IDEs", not "everywhere".
- **Buzz is the second.** The host that packages Buzz controls the prefix. For pitch4 that means a deployment note ("set `BUZZ_ACP_LAUNCH_PREFIX` to the sidecar") rather than any change upstream.
- **Zed is opt-in.** A recording claim there depends on developer discipline or device management of `settings.json` (not researched). A private registry would be the natural enterprise path, but Zed cannot point at one today.
- **An adapter-level path may be stronger.** Claude Code's managed settings reach the adapter, so an organization could require Claude Code hooks or permission rules through MDM in every ACP client at once. That captures at the agent, not the wire. It is a complement to the wire recorder, and those decisions are invisible to an ACP recorder (section 4).

### Gaps
- Whether JetBrains enforces "Custom ACP agents = off" against a hand-edited `~/.jetbrains/acp.json`, and from which IDE version, is not documented on the pages read.
- Whether Air Teams cloud tasks can run an organization custom agent (versus registry agents only) is not stated.
- Zed's support for organization-managed or read-only settings files was not researched.
- No client was found that pins a registry agent to a verified binary hash at launch, beyond the registry's optional `sha256` on archives.

## 4. Would such a proxy see the approval decision as well as the request?

### Takeaway
For every permission exchange that crosses ACP, yes. The request (`session/request_permission`, with its options and tool-call subject) and the client's answer (`selected` plus an `optionId`, or `cancelled`) travel on the same stdio pipe, so a wrapper sees both and can pair them by JSON-RPC id. Four limits keep this from being "every decision, and who made it":

1. **ACP carries no approver identity.** The response is just an outcome and `_meta`, and it does not distinguish a person from a client rule. Zed sends external-agent requests to a human prompt; Buzz's harness answers `allow_once` automatically.
2. **Agents decide many calls before ACP is involved.**
   - Claude Code applies its mode and settings rules first, and "always allow" writes a rule to local settings so later matching calls never cross ACP.
   - Codex's default ACP mode is "Auto review", which asks only "for actions detected as potentially unsafe".
   - "Full access" never asks.
3. **ACP v2 removes the client's file and terminal methods,** so a proxy sees the agent's own report of edits and commands, not the operations themselves.
4. **Requests that come from agent hooks or sandboxes** inside the agent are outside the wire.

### Cited Findings
**Wire shape**
- `RequestPermissionResponse`: `"outcome"` is "The user's decision on the permission request", plus `_meta`. `RequestPermissionOutcome` is one of two shapes. `cancelled` means "The prompt turn was cancelled before the user responded" (and on `session/cancel` the client "MUST respond to all pending `session/request_permission` requests with this `cancelled` outcome"). `selected` means "The user selected one of the provided options" and carries `optionId` and `_meta`. There is no field for who selected it. — [schema/v1/schema.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/schema/v1/schema.json) (GitHub API, 1 Nov 2026)
- ACP v2: "ACP v2 will remove the standard Client filesystem and terminal execution surface." It removes `clientCapabilities.fs`, `clientCapabilities.terminal`, `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/release` and `terminal/wait_for_exit`. (RFD stage: Active, in the v2 group.) — [v2 client-filesystem-terminal-capabilities RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/rfds/v2/client-filesystem-terminal-capabilities.mdx); [docs.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/docs.json)
- acp-policy-bench's unverified hypothesis: "Some agents may use a native shell instead of the client's terminal, so terminal policies never see the call." — [acp-policy-bench](https://github.com/harshanacz/acp-policy-bench)

**Clients: who answers**
- Zed. External-agent requests go through `handle_v2_request_permission` to `AcpThread::request_permission`:
  - That function validates the options, upserts the tool call ("The protocol applies a tool call subject exactly like a `tool_call_update`, before the prompt is shown, so the request can anchor to the tool call it describes"), and emits `AcpThreadEvent::ToolAuthorizationRequested`.
  - It waits on a channel that `select_permission_option` resolves. A dropped channel becomes `Cancelled`.
  - In this path I found no rule-based auto-answer.

  The docs are vaguer: for external agents, "Zed ACP/tool forwarding permissions may apply". — [agent_servers/src/acp.rs](https://github.com/zed-industries/zed/blob/main/crates/agent_servers/src/acp.rs); [acp_thread/src/acp_thread.rs](https://github.com/zed-industries/zed/blob/main/crates/acp_thread/src/acp_thread.rs) (around line 6584); [External Agents](https://zed.dev/docs/ai/external-agents) (GitHub API, 1 Nov 2026)
- Zed's own agent has rule-based approval (`tool_permissions` with `always_allow`, `always_deny`, `always_confirm` and `default`), and its prompts offer "Allow once / Deny once", "Always for <tool>" and "Always for <pattern>". The docs tie these to Zed Agent; whether they reach external agents is the "may apply" above. — [Zed docs, Tool Permissions](https://zed.dev/docs/ai/tool-permissions)
- JetBrains AI Assistant: the ACP page does not mention permission requests, auto-approval or a "brave mode" (fetch-tool extraction, 07 Oct 2026). — [AI Assistant help, ACP](https://www.jetbrains.com/help/ai-assistant/acp.html)
- Buzz: on `main`, the harness auto-approves `session/request_permission` with `allow_once` (L2-2.06, citing [acp.rs](https://github.com/block/buzz/blob/main/crates/buzz-acp/src/acp.rs)). A recorder under Buzz would record the harness's automatic choice.

**Adapters: what is decided inside the agent**
- `claude-agent-acp`, `canUseTool`. The adapter forwards asks with `this.client.requestPermission(params, signal)`. A source comment explains which asks reach it: "Do not auto-allow here based on the session's advertised mode. Claude Code applies bypassPermissions before invoking canUseTool; a request that still reaches this callback is deliberately bypass-immune (for example a safety check, a tool requiring user interaction, or an explicit ask rule). Re-applying bypass in the host would erase that provider safety decision." So calls allowed by mode or settings rules are decided inside Claude Code and never produce an ACP permission request. — [acp-agent.ts](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/acp-agent.ts) (around lines 10377 and 10786; GitHub API, 1 Nov 2026)
- `claude-agent-acp`, "always allow". The options are `allowOnce` (`kind: "allow_once"`), `allowWithUpdates` (`kind: "allow_always"`) and `reject` (`kind: "reject_once"`). The "always" option applies the CLI's suggested update, which `exactLocalAllowRule` expects to be `type: "addRules"`, `behavior: "allow"`, `destination: "localSettings"`. After that, matching calls are allowed by the rule inside Claude Code. The adapter withholds the "always" option when "the user's own ask rule forced the prompt" or when the CLI marks the rule as broader than the ask (`suppressAlwaysAllowRule`). — [permissions/options/shared.ts](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/permissions/options/shared.ts); [acp-agent.ts](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/acp-agent.ts)
- `codex-acp`, forwarding. `CodexApprovalHandler` forwards command approvals, file-change approvals and a third request type to the client through `acp.methods.client.session.requestPermission`, then maps the selected `optionId` back to a Codex decision. If the decision set is incomplete it cancels ("Cancelling command approval without a complete authoritative decision set"). "A v2 client may answer with a custom outcome instead of 'cancelled'; only 'selected' carries an `optionId`". — [CodexApprovalHandler.ts](https://github.com/agentclientprotocol/codex-acp/blob/main/src/permissions/CodexApprovalHandler.ts) (GitHub API, 1 Nov 2026)
- `codex-acp`, decisions. They include `accept` ("Yes, proceed", `allow_once`), `acceptForSession`, `decline` and `cancel`. Two more persist a policy:
  - `acceptWithExecpolicyAmendment` adds an exec-policy rule.
  - `applyNetworkPolicyAmendment` is offered as `allow_always` or `reject_always`.

  — [permissions/options.ts](https://github.com/agentclientprotocol/codex-acp/blob/main/src/permissions/options.ts)
- `codex-acp`, modes:
  - "Read-only" ("Requires approval to edit files and access the internet.", `on-request`).
  - "Workspace access" (`on-request`).
  - "Auto review": "Only ask for actions detected as potentially unsafe". It is `on-request`, with the value `auto_review` where the other modes have `user`.
  - "Full access": "Unrestricted access to the internet and any file on your computer", approval `never`, sandbox `danger-full-access`.
  - `static DEFAULT_AGENT_MODE = AgentMode.Agent;`, which is "Auto review".
  - Only JetBrains Air receives the mode kind: "Only AIR gets the mode kind, in `_meta.jetbrains.air.kind`."

  — [AgentMode.ts](https://github.com/agentclientprotocol/codex-acp/blob/main/src/AgentMode.ts) (GitHub API, 1 Nov 2026)
- From L2-2.06: Buzz issue #7582 reports that with the Claude adapter, "`plan`, `dontAsk` and `acceptEdits` end up behaving like `bypassPermissions` unless the adapter happens to enforce them internally." — [block/buzz #7582](https://github.com/block/buzz/issues/7582)

### Inferences
- **What a recorder does see.** An ACP recorder reliably sees three things:
  - every approval a person makes in Zed or a JetBrains IDE for a Claude or Codex session, with the full request: title, tool-call subject, offered options, and the chosen `optionId` and its `kind`;
  - the session's mode (mode updates and config options cross ACP);
  - every tool call the agent reports.
- **What it can say about calls that ran without a prompt.** It can label each such call as one of: allowed by an earlier "always" decision it recorded, run under a no-ask mode (bypass, "Full access"), or decided inside the agent by rule or Codex auto review. It cannot see the rule or the reviewer's reasoning.
- **What it cannot know.** Who clicked. ACP has no field for it. A local sidecar can attribute a decision to the OS user and the developer's key on that machine, which is honest for single-user editors. In a multi-user client (Buzz), attribution needs the client to put the approver in `_meta`, or the decision will look human when it was automatic.
- **Consequence for pitch4's line.** "Records who clicked Allow" holds for prompts shown in the editor, as long as the sidecar binds the decision to the local identity. For all actions it does not hold, especially under Codex's default "Auto review" and Claude Code's "always allow" rules. The pitch needs a coverage line, for example: "decisions made in the editor are recorded with who made them; decisions the agent made by its own rules are recorded as such".
- **v2 weakens the proxy as an enforcement point.** Once v2 lands, a proxy can still approve or refuse permission prompts and record the agent's reports, but it can no longer watch or block file and terminal operations through the client. Evidence of what actually changed on disk has to come from the sidecar's own file and git capture (pitch4's change sets), not from the wire.

### Gaps
- No measurement was found of what share of tool calls in real Claude Code or Codex sessions over ACP produce a permission request versus being decided internally. acp-policy-bench plans this but has no results.
- JetBrains' handling of ACP permission requests (any auto-approve or "brave" setting for external agents) is undocumented on the pages read.
- How Codex's `auto_review` reviewer decides, and whether its verdicts are visible anywhere (Codex logs, rollouts), was not checked.
- Whether Zed's `tool_permissions` rules apply to external agents through another code path (the docs' "may apply") was not resolved.

## 5. What this means for pitch4's differentiation and product offering

### Takeaway
Pitch4 can claim approval capture across ACP clients in the first release, but only as a qualified claim. The supportable parts:
- A sidecar shipped as a transparent ACP wrapper can be inserted today in Zed, JetBrains IDEs, the Air app, Buzz, CodeCompanion, agent-shell and marimo without waiting for proxy chains.
- It records both the request and the decision for every prompt that crosses ACP.
- Organizations can make it mandatory in JetBrains (policy) and Buzz (host prefix), but not in Zed.

The claim must not say "every decision" or "who clicked" from the wire alone:
- ACP carries no approver identity.
- The two most-used adapters decide many calls internally. Codex's default ACP mode is "Auto review".

Capture itself is commodity (acp-devtools, MIT). The differentiation is in four places:
1. Binding each decision to a person's key.
2. Labelling what was not asked.
3. Failing closed.
4. Keeping the result as a signed, team-keyed record across clients.

### Inferences
**Answer to the question.**
- **Insertion:** yes, today, in every ACP client examined. It is per-client configuration, not a protocol feature.
- **Proxy chains:** still Draft but moving. Schema and an official conductor landed in the last week, and no editor supports it yet.
- **Locks:** JetBrains and Buzz let an organization make a wrapper the only path. Zed does not.
- **Decisions:** a proxy sees the decision for every prompt that crosses ACP, but not who made it, and not the decisions agents make internally.

**What changes in pitch4's first page.**
- "Nothing records who clicked Allow" stays true of the market. Clients only keep debug logs (Zed's ACP log view; JetBrains' `llm.agent.extended.logging`, which warns it captures chat contents). acp-devtools keeps a local SQLite file for debugging, and Buzz drops the frames.
- The sidecar's promise should be: "Every approval made in your editor is recorded with who made it, and every action the agent took without asking is marked as unasked."

**Directions this evidence supports.**
- **Ship the ACP recorder as a plain stdio wrapper in release 1, with setup writers per client** (offering; confidence high on feasibility, medium on value). Targets: Zed custom agent, JetBrains `acp.json` and org custom-agent JSON, Air `acp.json`, Buzz launch prefix, CodeCompanion commands, agent-shell prefix, marimo command. Do not wait for proxy chains, and do not depend on `sacp`. Add a `proxy/initialize` mode later from the Rust SDK conductor so the recorder can also sit inside a chain.
- **Make "who decided, and what was never asked" the differentiator** (differentiation; confidence medium):
  - Bind each `selected` outcome to the developer's key and device.
  - Record the session mode and the offered options with each decision.
  - Mark tool calls that ran without a prompt as allowed by a recorded rule, by the agent's internal rule or auto review, or by a no-ask mode.
  - Pair the wire record with the sidecar's own file and git change sets, since ACP v2 drops client file and terminal methods.

  No client, adapter or existing proxy does any of this.
- **Fail closed where pitch4 says hooks fail open** (differentiation; confidence medium). The reference conductor bypasses failed components. Buzz's prefix refuses to launch without its wrapper. The sidecar should copy Buzz: if the recorder cannot write, the agent does not start, or the gap is entered in the ledger. That turns the "hooks fail open" critique into a concrete product property.
- **Sell enforcement where the client vendor provides the lock** (offering, aimed at security buyers; confidence medium-low until tested):
  - A documented JetBrains recipe: an org custom agent that wraps Claude Agent or Codex, "All available agents" off, and "Custom ACP agents" off.
  - A Buzz host-prefix recipe.

  For Zed, state that capture is opt-in until Zed extends admin controls to external agents or supports private registries.
- **Propose a decision-source convention upstream rather than a new protocol** (both; confidence low). Suggest a `_meta` convention on the permission response, for example decision source (human, client rule, auto) and approver reference, through an RFD or issue. Any client that fills it improves the record. The RFD process allows a Draft with only an elevator pitch, and proxies already preserve `_meta` across hops.

### Gaps
- No buyer evidence was gathered on whether "approval capture inside JetBrains IDEs only" or "opt-in in Zed" is enough to change a purchase.
- The JetBrains enforcement recipe and the Buzz prefix recipe are untested.
- The share of risky actions that never reach an ACP prompt (Codex "Auto review", Claude rules) is unmeasured. That share decides how strong the approval claim can be.
