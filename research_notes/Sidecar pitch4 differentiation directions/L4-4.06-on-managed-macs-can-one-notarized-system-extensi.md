# On managed Macs, can one notarized NetworkExtension system extension run alongside fleet SSE, VPN and EDR clients, and attribute each flow to a harness's process tree? (research as of 1 Nov 2026)

Scope: this follows L3-3.04, which concluded that egress control on macOS that survives updaters and daemons needs an MDM-pushed "fleet mode" system extension, and flagged coexistence with corporate VPN and ZTNA clients as unverified. It does not repeat 3.04's material on entitlements, notarization, MDM SystemExtensions payloads, `sourceProcessAuditToken`, the Codex daemon or Tailscale's MDM steps. This note adds:
- Apple's rules for several network extensions at once;
- what each fleet client actually installs on macOS;
- the documented and reported conflicts;
- the mechanism (and limits) of process-tree attribution;
- whether the SSE clients' own per-app policies give the sidecar a way in.

Method and reading key:
- **Docs and source only, no lab tests.** Everything was read on 1 Nov 2026.
  - Apple developer docs came through Apple's JSON doc endpoints (`developer.apple.com/tutorials/data/documentation/...json`), which return the text the doc pages render. The URLs below are the human-readable pages.
  - Apple Developer Forums sit behind a bot check, so `curl` failed. They were read with WebFetch, which returned the DTS replies as quoted text. The forum shows only month and year for posts.
  - help.zscaler.com and two cisco.com pages did not load (empty page, or HTTP 403). Every Zscaler and Cisco-site claim is a **search excerpt** and is labelled that way.
  - GitHub issues, code search and raw files were read with `gh api` or raw.githubusercontent.com.
- **MDM profiles** on GitHub are third-party or vendor-engineer samples. They show which NetworkExtension (NE) provider types each client registers. They are not vendor documentation.
- "(inference)" marks my reasoning. Quotes are exact.
- **Vocabulary:**
  - CF = content filter (NEFilterDataProvider or NEFilterPacketProvider);
  - TP = transparent proxy (NETransparentProxyProvider, an app proxy);
  - PT = packet tunnel (NEPacketTunnelProvider, managed by NETunnelProviderManager);
  - ES = Endpoint Security;
  - sysext = system extension.

## 1. What Apple allows: several network extensions at once, who sees a flow first, and a second VPN

### Takeaway
- **Content filters compose.** Several content filters from different vendors can run at once. Each flow passes through every filter, and it is blocked if any filter blocks it. Filters with the `firewall` grade see traffic before `inspector`-grade filters. The order within a grade is undefined.
- **Transparent proxies chain.** A flow passes from one proxy to the next. Their order is undefined unless MDM sets an `Order` value, and Apple's DTS (Developer Technical Support) says it "changes from Mac to Mac and OS release to OS release". A proxy that re-originates a flow must attach the original flow's metadata, or every provider after it sees the proxy as the source.
- **Packet tunnels do not stack.** "Only one enterprise VPN configuration can be enabled on the system at a time". Starting a second packet tunnel stops the first.
- **Packaging is not the problem.** One sysext can hold several NE providers and an ES client, each enabled independently. Coexistence, not packaging, is the constraint.

### Cited Findings
**Content filters**
- **Multiple filters, and what wins.** Asked whether two vendors' content filters can run together when one blocks a port the other allows, Quinn "The Eskimo!" (DTS, Sep 2022): "Yes." "The system runs the flow through each filter and blocks it if _any_ of the filters blocks it." "Note that it calls the filters in order, but the specific order is currently unspecified." Footnote: "This is in contrast to other NE providers, which can transform the content, and thus the order is important." — [Apple Developer Forums 716388](https://developer.apple.com/forums/thread/716388)
- **Filter grade (MDM WebContentFilter payload, key `FilterGrade`):** "The system uses this value to derive the relative order of content filters. Filters with a grade of `firewall` see network traffic before filters with a grade of `inspector`. However, the system doesn't define the order of filters within a grade. Available: macOS 10.15+" — [Apple WebContentFilter](https://developer.apple.com/documentation/devicemanagement/webcontentfilter)
- **The same setting in code:**
  - `NEFilterManager.grade` (macOS 10.15) is "The grade of the filter, which determines when it acts relative to other filters." "The default grade is NEFilterManager.Grade.firewall." — [Apple NEFilterManager.grade](https://developer.apple.com/documentation/networkextension/nefiltermanager/grade-swift.property)
  - The grades: `firewall`, "A grade for filters that act as firewalls, blocking some network traffic"; `inspector`, "A grade for filters that act as inspectors of network traffic." — [Apple NEFilterManager.Grade](https://developer.apple.com/documentation/networkextension/nefiltermanager/grade-swift.enum)
- **One filter configuration per app, holding both provider kinds.**
  - "Each app is allowed to create a single filter configuration." — [Apple NEFilterManager](https://developer.apple.com/documentation/networkextension/nefiltermanager)
  - "On macOS, using both providers at the same time is supported", meaning `NEFilterDataProvider` and `NEFilterPacketProvider` — [TN3120](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers) (revised 2025-07-22)
- **Filters cannot modify traffic.** "Filter providers cannot modify traffic, but simply provide a filter verdict to the system, either to allow or drop the flow." — [WWDC25 session 234 transcript](https://developer.apple.com/videos/play/wwdc2025/234/)
  - Quinn (May 2026): "A transparent proxy can _modify_ the flow; a content filter cannot." "Once a transparent proxy has accepted a flow, it must proxy that flow until the flow ends. A content filter can examine part of the flow and, once it's satisfied, return an `.allow()` verdict. At that point the flow's traffic no longer comes to the filter, so it's out of the loop." — [Forums 827106](https://developer.apple.com/forums/thread/827106)

**Transparent proxies**
- **Chaining and order.** Quinn (Mar 2026), asked how macOS handles several vendors' transparent proxies with overlapping rules:
  - "Generally, traffic in transferred from one proxy to the next to the next, but there are a couple of things to watch out for."
  - "First, the order in which transparent proxies load isn't specified unless the proxies are configured by the device manager with an `order` property."
  - "Second, each flow received by the proxy has a `metadata` value. If your proxy wants to ascribe a network connection to that flow — so that subsequent subsystems in the chain understand that this network connection is 'owned' by the original application — it must apply that metadata to the flow."
  - Asked whether order can be influenced outside MDM: "No." "And, in practice, the order you get is very much an implementation detail, one that changes from Mac to Mac and OS release to OS release."
  - Source: [Forums 820632](https://developer.apple.com/forums/thread/820632)
- **The MDM order key.** The `VPN.TransparentProxy` dictionary has `Order` ("A positive integer."), and `ProviderBundleIdentifier` is required "If the VPN provider uses a system extension" — [Apple VPN.TransparentProxy](https://developer.apple.com/documentation/devicemanagement/vpn/transparentproxy-data.dictionary)
- **Attribution through two proxies (Matt Eaton, DTS, 2021):**
  - Apr 2021: "I enabled two NETransparentProxyProvider's that will handle TCP connections from Safari… NETransparentProxyProvider One picked it up and proxied the flow, while NETransparentProxyProvider Two did see the flow but did not recognize the flow as a Safari flow that needed to be proxied."
  - On whether the second provider can learn the true source: "You may be running into a limitation here or a bug. I am not sure."
  - Jun 2021, on any tool or API that reports the order: "To my knowledge, no."
  - Source: [Forums 677357](https://developer.apple.com/forums/thread/677357)
- **The metadata fields.** `NEFlowMetaData` carries `filterFlowIdentifier` ("The identifier of the content filter flow corresponding to this flow"), `sourceAppSigningIdentifier` and `sourceAppAuditToken`. "This metadata is only present for data flowing through per-app VPN providers, that is, app proxy providers and packet tunnel providers in per-app VPN mode" — [Apple NEFlowMetaData](https://developer.apple.com/documentation/networkextension/neflowmetadata)
- **Transparent proxies ignore the VPN routing switches.** "NETransparentProxyManager doesn't support this property", said of both `includeAllNetworks` and `enforceRoutes` — [includeAllNetworks](https://developer.apple.com/documentation/networkextension/nevpnprotocol/includeallnetworks); [enforceRoutes](https://developer.apple.com/documentation/networkextension/nevpnprotocol/enforceroutes)

**Packet tunnels and a second VPN**
- **One enterprise VPN.** "VPN configurations created using NETunnelProviderManager are classified as regular enterprise VPN configurations (as opposed to the Personal VPN configurations created by `NEVPNManager`). Only one enterprise VPN configuration can be enabled on the system at a time. If both a Personal VPN and an enterprise VPN are active on the system simultaneously, the enterprise VPN takes precedence, meaning that if the routes for the two VPNs conflict then the routes for the enterprise VPN will take precedence." — [Apple NETunnelProviderManager](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager)
- **Starting a second tunnel stops the first.** Matt Eaton (Aug 2021), asked about several packet tunnels from different apps on macOS:
  - "For `NEPacketTunnelProvider`, No. If you start `NEPacketTunnelProvider` A and then start `NEPacketTunnelProvider` B, then `NEPacketTunnelProvider` A will stop because you can only have one Enterprise VPN running on the system at one time."
  - "Kext based VPNs are not a recommended path."
  - On creating a utun outside NE: "This is something you will need to research on your own. This is not something I would recommend or provide help with either as it is way off the beaten path of what is considered to be supported."
  - He points to SCDynamicStore for discovering other tunnels' configuration.
  - Source: [Forums 687862](https://developer.apple.com/forums/thread/687862)
- **Full tunnel and route enforcement.**
  - `includeAllNetworks`: "If this property is true, the system routes network traffic through the tunnel except traffic for designated system services necessary for maintaining expected device functionality." — [Apple](https://developer.apple.com/documentation/networkextension/nevpnprotocol/includeallnetworks)
  - `enforceRoutes` (macOS 11): "the system scopes the included routes to the VPN and the excluded routes to the current primary network interface. This property supersedes the system routing table and scoping operations by apps." — [Apple](https://developer.apple.com/documentation/networkextension/nevpnprotocol/enforceroutes)
  - Without these, "the system routing table supersedes the `includedRoutes` and `excludedRoutes` properties", and an app's interface "scoping… supersedes the system routing table." — [Apple: Routing your VPN network traffic](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic)
- **How the switches work (Quinn, Jun 2025):**
  - "`includeAllNetworks` represents a giant switch, which effectively disables destination IP routing. This setting is implemented using NECP."
  - "`enforceRoutes` lets you continue using destination IP routing but prevents apps from bypassing that."
  - "`NEPacketTunnelFlow` doesn't support re-injecting packets."
  - "Many macOS VPN products predate Network Extension framework, and thus were implemented using a variety of ad-hoc techniques. These days we have NE and thus DTS no longer supports such shenanigans."
  - Source: [Forums 786651](https://developer.apple.com/forums/thread/786651)
- **WWDC25 on route precedence:** "On macOS, the routing table could be modified outside of your app by an administrator or another process. More precise routes could interfere with your VPN routes. Network Extension lets your app enforce its VPN routes to ensure they take precedence and are honored at all times." — [WWDC25 234](https://developer.apple.com/videos/play/wwdc2025/234/)
- **What a packet tunnel is for.**
  - TN3120: "Do not use a packet tunnel provider to selectively claim traffic for the packet tunnel and proxy all other traffic elsewhere… The recommended alternative is to implement a NETransparentProxyProvider on macOS." Also "Do not use a packet tunnel provider to implement a network content filter." — [TN3120](https://developer.apple.com/documentation/technotes/tn3120-expected-use-cases-for-network-extension-packet-tunnel-providers)
  - WWDC25: "NEPacketTunnelProvider operates at the IP layer, and will not receive flow or application level metadata needed to do other things, like proxying DNS requests or content filtering." — [WWDC25 234](https://developer.apple.com/videos/play/wwdc2025/234/)
- **PF is not an alternative.** "Do not use Packet Filter in a software product that you distribute to a wide audience", because rules "might clash with those installed by… Other third-party products" — [TN3165](https://developer.apple.com/documentation/technotes/tn3165-packet-filter-is-not-api)

**Packaging**
- **One sysext, many providers, plus ES.** Quinn (May 2026): "you can combine different sysex types into a single sysex. For example, folks often combine an ES client and NE providers into one sysex." "My general advice is that you use as few sysexen as possible." "If your sysex has multiple providers, you can enable and disable them independently by enabling or disabling each provider configuration using its corresponding `NEXyzManager` type." — [Forums 827106](https://developer.apple.com/forums/thread/827106)
- **Sysexts run without a user.** "System extensions run in a global context, completely independent of the logged in user." All three provider types ship as Developer ID system extensions from macOS 10.15, with no "managed device" restriction on macOS — [TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment). WWDC19: a personal firewall must protect the Mac "even if there's no user logged into the system." — [WWDC19 714](https://developer.apple.com/videos/play/wwdc2019/714/)

**Fragility when products are stacked**
- **macOS 15.** LuLu's developer opened a DTS thread after reports that NE products broke on macOS 15 (it names LuLu and Microsoft Defender; the original post cites CrowdStrike, ESET, Defender and VPNs). Quinn (Sep 2024): "in general, NE products that use the API correctly should work on macOS 15. There has been no overarching change, like the NKE-ectomy on macOS 10.15." "However, both the "correctly" and the "should" in the above are 'load bearing'." No fix version is confirmed in the thread — [Forums 763864](https://developer.apple.com/forums/thread/763864)
- **No documented precedence for iOS filters (search excerpt, thread not opened).** A DTS engineer answered "We do not" when asked whether Apple documents precedence among multiple iOS content filters, and pointed to an enhancement request (FB18723200) — [Forums 792165](https://developer.apple.com/forums/thread/792165)

### Inferences
- **The content filter is the coexistence-safe enforcement point.** Its verdicts combine as AND: any block wins. A sidecar filter's "deny except granted ranges, for this harness tree" therefore holds whatever Zscaler, GlobalProtect, Cisco or Falcon filters decide, provided the sidecar's filter sees the original app flow. Grading the sidecar `firewall` puts it ahead of inspector-grade filters such as CrowdStrike's (section 2). It still lands at an undefined position among other firewall-grade filters (GlobalProtect, Cisco). Because a block is final, that order only matters for which product logs the block.
- **A sidecar transparent proxy is the risky choice on SSE fleets.** Its position in the proxy chain is undefined without MDM `Order`, and outside MDM the order shifts by Mac and by OS release. If an SSE's proxy is upstream and does not apply metadata, the sidecar sees the SSE's extension as the source of agent traffic, as in Eaton's 2021 test. Even when the sidecar is upstream, it must call `setMetadata` on every re-originated connection, or the SSE's own per-app policies attribute agent traffic to the sidecar.
- **A sidecar packet tunnel cannot sit beside another enterprise VPN.** Apple allows one enabled enterprise VPN configuration; starting the second stops the first. On a Mac whose corporate client uses an NE packet tunnel, a sidecar tunnel for per-agent addresses would knock out the corporate VPN, or be knocked out by it. Where the corporate client builds its tunnel some other way, the risks become route and address-range conflicts and `includeAllNetworks` or `enforceRoutes` capture (section 2).
- **One notarized sysext can hold CF + TP + PT + ES and enable each separately.** The design question is therefore which providers to turn on per fleet, not how many extensions to ship.

### Gaps
- No Apple document states whether content filters see a flow before or after transparent proxies, or whether a filter sees both the app's original flow and the proxy's re-originated connection. `filterFlowIdentifier` suggests filters see the original flow first; that is my inference, not documentation.
- I found no Apple statement on whether per-app VPN configurations (`NETunnelProviderManager.forPerAppVPN()`) count against the "one enterprise VPN" limit on macOS.
- Matt Eaton's "only one" reply is from Aug 2021 (macOS 11–12). The NETunnelProviderManager doc text is current, but I found no newer DTS restatement for macOS 15 or 26.
- The forum thread "Managing the order of Transparent Proxies from MDM Profile" ([796810](https://developer.apple.com/forums/thread/796810)) surfaced in search but was not read.

## 2. What the fleet clients install on macOS, and the coexistence matrix

### Takeaway
- **What each client installs:**
  - Netskope: a transparent proxy (app-proxy sysext).
  - GlobalProtect and Cisco Secure Client: firewall-grade content filters, plus transparent proxies (GlobalProtect per a user report, Cisco per a university IT page) and DNS proxy components (Cisco).
  - CrowdStrike Falcon: an inspector-grade content filter in the same sysext as its ES client.
  - Cloudflare's client (formerly WARP): system extensions of an undocumented type.
  - Zscaler: a system extension whose provider type I could not confirm from Zscaler's own pages.
- **What the vendors document:** route, DNS and address conflicts between tunnels, but not filter-on-filter conflicts. Every SSE vendor tells admins to split routing and DNS, and to exclude each other's ranges.
- **Reported problems with stacked filters:** chaining bugs (LuLu with SentinelOne or Defender); an OS-level limit on macOS 14 and earlier that Jamf documents for EDR firewall extensions; and macOS 15 regressions.
- **Net verdict:**
  - Content filter: likely to coexist (by Apple's rules), but not vendor-tested.
  - Transparent proxy: conflict risk.
  - Packet tunnel: conflicts or unknown nearly everywhere.

### Inferences
- **The vendors' documented conflicts are tunnel conflicts.** Overlapping routes and subnets, full tunnels capturing each other, DNS ownership, and CGNAT ranges (Tailscale's 100.64/10; Netskope's reported 100.127.100.0/24 VIF) account for every vendor-documented conflict. None of the vendors documents a filter-on-filter conflict. Those come from field reports (LuLu, Jamf, DNSFilter) and from Apple's own grading scheme. A sidecar that ships only a content filter (plus ES, section 3) stays out of the most-documented class of conflict.
- **Per-agent addresses through a sidecar packet tunnel are not viable on SSE fleets:**
  - every packet-tunnel cell is a conflict, a risk or unknown;
  - Apple permits one enabled enterprise VPN;
  - the obvious overlay range (CGNAT) is already taken by Tailscale and reportedly Netskope;
  - corporate full tunnels (`includeAllNetworks`) and `enforceRoutes` capture whatever routes the sidecar adds.

  For per-agent *local* addresses, a root helper adding lo0 aliases (3.04's LaunchDaemon option) avoids VPN machinery entirely. Remote reach can ride the sidecar's existing userspace transport, or go through the SSE where the customer requires it.
- **Every cell needs a lab result before a sales claim.** Order within a grade is undefined; proxy order "changes from Mac to Mac and OS release to OS release"; macOS 15.0 regressed NE products and Cloudflare told customers to wait for 15.4. A coexistence claim is therefore a per-OS-release test result, not a design property. A published compatibility matrix, re-run in CI against each SSE client and macOS beta, is a product artifact security buyers will ask for.
- **The Microsoft statement most likely describes Defender's own constraint, or the macOS 14-era limit that Jamf documents.** Apple's API has supported multiple filters since 10.15 (that is what `FilterGrade` exists for). Buyers will still read Microsoft's sentence, so a sidecar filter needs a written answer to it.

### Gaps
- Zscaler's own pages did not load. I could not confirm whether ZCC on macOS uses a content filter, a transparent proxy, a packet tunnel or a root-daemon utun, so the Zscaler row is the weakest.
- I could not confirm whether GlobalProtect's, Cisco's or Cloudflare's tunnels are NE packet tunnels (subject to "one enterprise VPN") or utun interfaces created by root daemons.
- I found no vendor (Zscaler, Netskope, Palo Alto, Cisco, Cloudflare, CrowdStrike) page that tests coexistence with a *third-party content filter* on macOS. Netskope's CrowdStrike line does not say which OS was tested.
- The Jamf Protect quote came through a community reply; the Jamf page itself did not render.
- I found no MacAdmins Slack archive or Jamf Nation thread that tests three or more NE products together on macOS 15 or 26.

## 3. Can the extension attribute each flow to a harness's process tree, including daemons reparented to launchd?

### Takeaway
- **With NetworkExtension alone: no.** NE gives each flow the audit token of the source app and of the creating process (pid, pidversion, uid). DTS says "NE does not provide a direct mechanism for you to get the responsible process for a flow." `sourceAppIdentifier` is not even listed for macOS.
- **With an Endpoint Security client in the same sysext: yes for fork and exec descendants**, including daemons reparented to launchd. The ES client must be running before the harness starts. The mechanism: ES fork and exec events, `es_process_t.original_ppid` ("stays constant, even if the process' parent changes"), `parent_audit_token` and `responsible_audit_token`, keyed to NE's audit tokens.
- **Uncertain for work handed to launchd jobs, XPC services or system daemons.** Their original parent is launchd, and only `responsible_audit_token` or NE's app-versus-process delegation gives a partial link.
- **The cost:** Apple must grant the ES entitlement, and MDM must grant Full Disk Access.

### Cited Findings
- **Responsible process (Quinn, Jan 2024).** The question: a developer found that `sourceAppAuditToken` gave the WebKit helper rather than Safari.
  - "Responsible process tracking is a tricky business. NE does not provide a direct mechanism for you to get the responsible process for a flow. If you'd like to see that change, I encourage you to file an enhancement request".
  - "It's common for macOS NE filter providers to be paired with an Endpoint Security client… If so, you can use the ES client to track process responsibility via its `responsible_audit_token` property."
  - On identity: "Don't use the bundle ID to identify a program in a security context. You can't trust it". He recommends the code-signing designated requirement (TN3127).
  - The asker filed FB13511360 and said getting the ES entitlement for production was uncertain.
  - Source: [Forums 743812](https://developer.apple.com/forums/thread/743812)
- **NE identity fields on macOS:**
  - `sourceAppAuditToken` (macOS 10.15): "The audit token of the source application of the flow." `sourceAppIdentifier` lists only "iOS 11.0, iPadOS 11.0, Mac Catalyst 13.1, visionOS 1.0", not macOS — [NEFilterFlow](https://developer.apple.com/documentation/networkextension/nefilterflow); [sourceAppIdentifier](https://developer.apple.com/documentation/networkextension/nefilterflow/sourceappidentifier)
  - `sourceProcessAuditToken` (macOS 13): differs from the app token when "a system process creates the connection on behalf of a source app" (in 3.04).
  - Proxies get `sourceAppSigningIdentifier`, which for apps "signed in the standard way using Xcode… is identical to the app's bundle identifier" — [NEFlowMetaData.sourceAppSigningIdentifier](https://developer.apple.com/documentation/networkextension/neflowmetadata/sourceappsigningidentifier)
  - Matt Eaton resolved a flow's source with `SecCodeCopySigningInformation` on "the signature of the app that generated the flow" ([677357](https://developer.apple.com/forums/thread/677357)).
- **Endpoint Security process fields:**
  - `original_ppid`: "The original parent process ID." "This field stays constant, even if the process' parent changes." — [Apple es_process_t.original_ppid](https://developer.apple.com/documentation/endpointsecurity/es_process_t/original_ppid)
  - `responsible_audit_token`: "The audit token of the process responsible for this process." "The responsible process may be this process itself, if there's no responsible process or the responsible process already exited." "This field is only available if the message version is `4` or greater." — [Apple](https://developer.apple.com/documentation/endpointsecurity/es_process_t/responsible_audit_token)
  - `parent_audit_token`: "The audit token of the parent process." (message version 4 or greater) — [Apple](https://developer.apple.com/documentation/endpointsecurity/es_process_t/parent_audit_token)
  - `es_process_t` also carries `signing_id`, `team_id`, `cdhash`, `session_id` and `group_id`. "You can extract values such as the process identifier (`PID`), user identifier (`UID`), and group identifier (`GID`) from the audit_token field by using functions defined in `libbsm.h`." — [Apple es_process_t](https://developer.apple.com/documentation/endpointsecurity/es_process_t)
- **The ES gate.** "You must request this entitlement from Apple." Without it, "es_new_client(_:_:) fails with the result ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED." — [Apple com.apple.developer.endpoint-security.client](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.endpoint-security.client)
- **Precedents for NE + ES in one sysext:** Quinn says "folks often combine an ES client and NE providers into one sysex" ([827106](https://developer.apple.com/forums/thread/827106)). CrowdStrike ships exactly that: one `com.crowdstrike.falcon.Agent` with types "Network, Endpoint security" ([FileWave](https://kb.filewave.com/books/software-deployment-recipes-macos/page/crowdstrike-falcon-protection-macos)). Defender uses "endpoint security and network system extensions" ([Microsoft](https://learn.microsoft.com/en-us/defender-endpoint/mac-sysext-policies)).

  - Sources: [Apple NEAppRule.matchTools](https://developer.apple.com/documentation/networkextension/neapprule/matchtools); [NEAppRule](https://developer.apple.com/documentation/networkextension/neapprule)

- **Races and per-user attribution (search excerpts, threads not opened):**
  - DTS explains ESRCH errors when converting a flow's audit token: the process "probably terminated between the point after it triggered the network request that invoked your provider but before your provider actually ran" — [Forums 738848](https://developer.apple.com/forums/thread/738848)
  - For per-user attribution DTS points to `audit_token_to_ruid()` — [Forums 677517](https://developer.apple.com/forums/thread/677517)
- **The daemon pattern this must cover.** Codex's daemon is "reparented to PID 1", runs from a copied binary and updates itself hourly (3.04, [openai/codex #48195](https://github.com/openai/codex/issues/48195)).

### Inferences
- **The mechanism, step by step:**
  1. One sysext runs an NE content filter (firewall grade) and an ES client subscribed to fork, exec and exit notifications.
  2. When the sidecar starts a harness, it registers the root process's audit token (pid plus pidversion) as an agent session.
  3. ES fork and exec events extend the session to every descendant. Each process is keyed by audit token, not pid, so reuse is safe.
  4. For each new flow, the filter reads `sourceAppAuditToken` and `sourceProcessAuditToken`, looks up the session, and allows or blocks against that agent's grants.
- **Reparented daemons stay attributed.** A double-fork or `setsid` daemon was seen at fork time, and `original_ppid` stays constant, so it remains in the session after it becomes a child of PID 1. A Codex-style daemon is covered. Copied binaries are covered too, because lineage, not path or signing ID, carries the identity.
- **Escapes, and how far each can be closed:**
  - **launchd jobs** (LaunchAgents a harness registers, `launchctl submit`, SMAppService), **XPC services**, and apps started with `open` are children of launchd from birth. ES may link them through `responsible_audit_token`, but responsibility is a TCC-style notion and not guaranteed for every launch path. Mark as uncertain until tested.
  - **System daemons acting on the harness's behalf:** `nsurlsessiond` downloads appear with the app as `sourceAppAuditToken` (covered by delegation). DNS lookups run in `mDNSResponder` and are not attributable per agent; the sidecar should enforce by IP after resolution, or proxy DNS itself.
  - **Processes already running before the ES client started** have no fork history. LuLu-style heuristics (ppid, the private responsible-pid call) are only a fallback.
  - **Short-lived processes** can exit before the filter resolves them (ESRCH). The ES exec record keeps the identity anyway.
- **An alternative key that survives everything:** run each harness under a dedicated macOS user (uid). The audit token carries the uid, so every flow from that account's processes stays attributable, including launchd jobs in that user's domain, with no lineage tracking. This mirrors Codex's Windows "dedicated lower-privilege sandbox users" and srt's `srt-sandbox` account (3.04). Its costs: file-permission friction on the repo, a keychain and TCC state per user, and admin rights to create accounts. Fleets already grant admin through MDM, so it is a fit for fleet mode, not the free tier. (Inference; not tested.)
- **Signing ID alone is not a process-tree key.** Harness children are `node`, `python`, `git`, `curl` and `docker`, signed by others or ad hoc. Apple's own app-rule lineage (`matchTools`) is "app plus its helper tools", and for a CLI harness started in Terminal or VS Code the "app" is the terminal, not the harness. Policies keyed on signing ID or process name (section 4) therefore attribute to the terminal or to the tool, never to "agent session 7".

### Gaps
- I found no Apple documentation on how `responsible_audit_token` is assigned for launchd-submitted jobs, SMAppService agents or XPC services started by a CLI tool. That decides whether "uncertain" can become "yes".
- I did not verify whether an unprivileged process can create a new audit session (asid), which would be a cheaper inherited tag than ES lineage.
- No public source shows Apple granting or refusing the ES entitlement for a non-EDR purpose such as agent attribution. The forum asker called production approval "uncertain".
- I did not test whether NE audit tokens for flows from Codex's daemon or Claude Code's background tasks resolve as expected.

## 4. If the sidecar can't do it alone, do the SSE and EDR clients' per-app or per-process policies offer an integration path?

### Takeaway
Only weakly.
- **What exists:**
  - Netskope: steering exceptions by *process name* (exact or regex; no path), which bypass Netskope and leave no transaction record.
  - Zscaler: process-based bypass that its docs tie to Windows WFP, plus an "Application Bypass" for macOS on Z-Tunnel 2.0 (search excerpts).
  - Cloudflare: split tunnels by IP and domain.
  - Defender's macOS network protection: domains via TLS SNI and indicators, not processes.
- **What none of them offers:** none can express "this agent's process tree may reach only these ranges", and none is configured locally. They are bypass or steering switches in each vendor's admin console.
- **The integration that works:** the sidecar enforces locally (content filter plus ES) and composes with the SSE. It does not try to drive the SSE's per-app rules.

### Cited Findings
- **Netskope** (fetched):
  - "If you want to bypass web traffic from certain applications from the Netskope cloud, you can add them as a custom certificate pinned application."
  - "Exact: Enter the exact process name for matching… Netskope doesn't support input quotes or the absolute path. Enter only the process name, such as googleefs.exe."
  - "RegEx: Enter the Perl Compatible Regular Expression (PCRE) to use wildcard formats for process names such as python*.exe".
  - Source: [Netskope: Creating a custom certificate pinned application](https://docs.netskope.com/en/creating-a-custom-certificate-pinned-application/)
  - A community Q&A (search excerpt): "no transaction records will be available on the Netskope tenant for bypassed traffic due to certificate pinned applications steering exception" — [Netskope community 7815](https://community.netskope.com/steering-configuration-77/general-q-a-certificate-pinned-application-steering-exceptions-7815)
- **Zscaler** (search excerpts; pages did not load):
  - Process-based bypass covers "Zscaler Tunnel (Z-Tunnel) 1.0 and Z-Tunnel 2.0 when using the Filtering Platform (WFP)", and "you must enable Install WFP Driver in App Profiles to use Process-Based Application Bypass". The fields are labelled "Windows Process Based Applications" — [Zscaler: Adding process-based applications to bypass traffic](https://help.zscaler.com/unified/adding-process-based-applications-bypass-traffic)
  - A separate "Application Bypass" feature "is only applicable for Windows and macOS App Profiles and if you use Z-Tunnel 2.0" — same source family (search excerpt)
- **Cloudflare:** VPN coexistence is configured with "Split Tunnel Exclude" entries by IP address or domain (the docs show the selectors "IP Address" and "Domain") — [Cloudflare vpn-ip-traffic partial](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/partials/cloudflare-one/warp/vpn-ip-traffic.mdx)
- **Microsoft Defender for Endpoint, macOS network protection:** "In processes other than Microsoft Edge, network protection determines the fully qualified domain name for each HTTPS connection by examining the Transport Layer Security (TLS) handshake… The HTTPS connection must use TCP/IP instead of User Datagram Protocol (UDP) or Quick UDP Internet Connections (QUIC), and the ClientHello message must not be encrypted." Policies are web threat protection, custom indicators, web content filtering and Defender for Cloud Apps — [Microsoft: Network protection for macOS](https://learn.microsoft.com/en-us/defender-endpoint/network-protection-macos)
- **GlobalProtect:** split tunnel on macOS (including by domain) needs the system extensions — [GP 6.3 user guide](https://docs.paloaltonetworks.com/globalprotect/user-guide/6-3/globalprotect-app-for-mac/use-the-globalprotect-app-for-mac). I did not read the admin docs that define the include and exclude keys (gap).
- **Agent-aware products from SSE vendors (earlier notes; vendor claims):** Netskope Client AI Discovery and Agent Action Control; Zscaler AI Endpoint Security for VS Code, Cursor and Windsurf (record_feature_benchmark.md). These are separate products, not per-process egress rules.

### Inferences
- **Name-based exceptions are spoofable bypasses.** Netskope's process-name exception and Zscaler's app bypass let anything named, say, `sidecar` skip the SSE: an absolute path is not accepted, and a name is not an identity. A security buyer would not accept "add our process name to your bypass list" as the integration. They delete the SSE's record of that traffic, which is the opposite of pitch4's promise.
- **The right integration has four parts:**
  1. **Do not bypass the SSE.** Agent egress that the sidecar allows still leaves through the SSE's steering, so the SSE's DLP and logs stay intact. The sidecar adds per-agent attribution and a deny overlay *before* the SSE (block wins).
  2. **Use destination exceptions only for the sidecar's own transport,** for example the relay or exit the customer runs: Netskope "Destination Network" exceptions, Cloudflare split-tunnel excludes, a GlobalProtect exclude list. These are keyed on IP or domain, which the customer controls.
  3. **When the sidecar must proxy, apply `NEFlowMetaData`** so that the SSE's own per-app policies still see the original app (Quinn's metadata advice, section 1).
  4. **Feed the SSE and the SIEM,** not the reverse. The sidecar's signed per-agent flow records go to the SIEM (OCSF, per earlier notes) and become the "which agent session" join key that SSE logs lack. SSE logs know the device, the user and, at best, the process name.
- **"Drive the existing SSE's policies" is not a fallback that delivers pitch4's claim.** The best available keys are a process name (Netskope, Zscaler on Windows) or a destination. Neither gives per-agent or per-tree identity. The design should not move to "configure Zscaler or Netskope" as its enforcement plan.

### Gaps
- I could not read Zscaler's macOS App Profile docs, so whether "Application Bypass" on macOS keys on bundle ID, signing ID or process name is unknown.
- I did not verify Cisco Secure Client's Per App VPN on macOS, or GlobalProtect's split-tunnel-by-application keys (path, process name or bundle ID).
- I found no Microsoft page offering per-process outbound rules for macOS in Defender or Intune.

## 5. What this means for pitch4

### Takeaway
pitch4 can keep "agents reach only granted ranges" for managed Macs only in this form:
- a firewall-grade content filter plus an Endpoint Security client in one notarized sysext;
- composing with the SSE (any block wins) rather than replacing or bypassing it;
- with a lab-tested coexistence matrix per macOS release.

It should not promise "a permanent private address for each agent" on managed Macs by way of a packet tunnel. Apple allows one enterprise VPN, SSE and VPN clients already claim routes and CGNAT ranges, and every vendor's documented conflicts are of exactly that kind. Per-agent local addresses should come from a root helper (lo0 aliases) or a Linux VM per stack. Process-tree attribution, the security pitch's real differentiator, depends on Apple granting the ES entitlement.

### Cited Findings
- **Sources** for each claim are in sections 1–4:
  - one enterprise VPN ([Apple](https://developer.apple.com/documentation/networkextension/netunnelprovidermanager));
  - filter verdicts compose ([716388](https://developer.apple.com/forums/thread/716388));
  - filter grades ([Apple](https://developer.apple.com/documentation/devicemanagement/webcontentfilter));
  - proxy order is undefined and changes by OS release ([820632](https://developer.apple.com/forums/thread/820632));
  - NE gives no responsible process ([743812](https://developer.apple.com/forums/thread/743812));
  - `original_ppid` ([Apple](https://developer.apple.com/documentation/endpointsecurity/es_process_t/original_ppid));
  - the ES entitlement must be requested ([Apple](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.endpoint-security.client));
  - Netskope's exceptions are name-only bypasses ([Netskope](https://docs.netskope.com/en/creating-a-custom-certificate-pinned-application/)).
- **pitch4's current lines:** "A permanent private address for each agent and service, plus subnets you choose to route." "Agents reach only granted ranges, and leave only through exits you run." (pitch4.html, read 1 Nov 2026)

### Inferences
- **Directions supported by the evidence:**
  1. **Fleet mode is a content filter plus ES, not a VPN.**
     - Ship one notarized sysext with an NE content filter (`firewall` grade, socket level) and an ES client. Include a transparent proxy in the bundle, but enable it only where MDM can set `Order` and the customer has no SSE proxy.
     - Pitch it as "a deny overlay that composes with your SSE": the SSE keeps steering, DLP and logging; the sidecar adds "which agent, which grant".
  2. **Rewrite the per-agent address line by platform.**
     - Linux: per-agent addresses stay free, as before.
     - macOS: "a private localhost per agent" via a root helper (lo0 aliases) in fleet mode, or a Linux VM per stack.
     - Never "a VPN per agent" on managed Macs.
     - Choose address ranges outside 100.64/10, which Tailscale uses and Netskope reportedly uses for its VIF.
  3. **Make process-tree attribution the Assured-tier differentiator,** and name its mechanism: ES lineage keyed to NE audit tokens, covering daemons reparented to launchd. No SSE offers it; their keys are process names or destinations. Ask Apple for the ES entitlement early. It is a schedule risk for the first paid release, and the fallback (a dedicated uid per harness) should be designed now.
  4. **Publish a compatibility matrix as a product, re-tested per macOS beta.** Cover Zscaler, Netskope, GlobalProtect, Cisco, WARP, Falcon and Defender. Keep the test harness open source. Apple says proxy order "changes from Mac to Mac and OS release to OS release", and macOS 15.0 regressed NE products, so the matrix doubles as an approval-kit item (3.04) and a trust signal.
  5. **Ship SSE coexistence kits, not SSE bypasses:**
     - destination exceptions for the customer's own exits and relays (Netskope Destination Network, Cloudflare split-tunnel exclude, GlobalProtect exclude list, Zscaler trusted-network notes);
     - `NEFlowMetaData` passed through on any proxied flow;
     - OCSF exports so the SIEM can join SSE logs to agent sessions.

     Decline name-based bypasses in writing, because they erase the SSE's record.
  6. **Keep the Linux VM per stack as the strict-fleet fallback.** It needs no host network extension for addresses. Its cost is that host-side attribution sees only the VM process (3.04), so it still needs the in-VM sidecar for per-agent records.

### Gaps
- No lab evidence yet for any matrix cell; all verdicts are documentary.
- Whether security buyers accept a second content filter and an ES client from a small vendor on fleets that already run Falcon and an SSE client is unmeasured. Endpoint teams may cap the number of NE products per Mac.
