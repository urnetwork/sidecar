## 1. Vanta: what can be pushed, with which fields, how often, and what do auditors see?

### Takeaway
- **Vanta accepts pushed data three ways:**
  1. **Resources** through the Build Integrations API (`PUT /v1/resources/<type>`).
  2. **Evidence files** uploaded to "documents".
  3. **Customer-authored Custom Tests** that turn custom resources into pass/fail evidence.
- **Constraints that matter for a change list:**
  - **Custom resources and Custom Tests work only in a customer's own *private* integration.** A marketplace (partner) integration may push only 11 built-in types, and **none of them is a code change, pull request or build**.
  - Custom Tests can be created only by hand in the dashboard ("no API to create them"), and "may require a plan upgrade or add-on".
  - Custom fields must be flat scalars: `boolean`, `int32`, `string`, `timestamp`.
  - Each sync replaces the whole set ("state of the world"). A type's full set must arrive **in one request of at most 10,000 records and 10 MB**.
- **Cadence:** syncs are "typically hourly", and Custom Tests re-run on every sync.
- **Auditor visibility:**
  - Auditors see test results across the observation window.
  - They can receive immutable **test snapshots** that carry the raw JSON of every record tested.
- **Vanta's own code-change population** (pulled from GitHub, GitLab, Bitbucket and Azure DevOps and exposed to audit firms since at least May 2026):
  - It holds only title, PR number, forge, repository, opened and closed dates.
  - It has **no author, approver or AI field**, and outside data cannot be added to it.
- **Vanta's per-PR test** checks only that the approver is someone other than the author, and treats bot-authored PRs like human ones.

### Cited Findings
**Which API does what, and who may use it**
- **Partners are limited to one API.** The Build Integrations API "is the **only** Vanta API available to partners"; "**Partners cannot use the Manage Vanta or Auditor APIs at all.**" — [Vanta, Integrations in Vanta](https://developer.vanta.com/docs/concepts/integrations.md) [downloaded]; [Build Integrations overview](https://developer.vanta.com/reference/build-integrations/overview.md) [downloaded]
- **The admin API cannot push.** "A Manage Vanta automation script **cannot** push resources or upload evidence on a customer's behalf. That lives in the Build Integrations API." — [Integrations in Vanta](https://developer.vanta.com/docs/concepts/integrations.md) [downloaded]
- **Private versus public.**
  - Private integrations are single-tenant: "They never get published; the integration only exists inside your tenant."
  - Publishing a public integration requires "becoming a Vanta partner and a marketplace review".
  - Source: [Integrations in Vanta](https://developer.vanta.com/docs/concepts/integrations.md) [opened]
- **Credentials do not cross API types.** "A Build Integrations `access_token` **cannot** call Manage Vanta or Auditor endpoints, and vice versa." — [Integrations in Vanta](https://developer.vanta.com/docs/concepts/integrations.md) [downloaded]

**Resource push: endpoint, types, semantics, limits** — [Build Integrations overview](https://developer.vanta.com/reference/build-integrations/overview.md) [downloaded; page undated]
- **Endpoint:** `PUT /v1/resources/<type>`: "Idempotent upsert by `uniqueId`. Push the full set of resources you own on a periodic schedule (typically hourly)."
- **Full replacement:** "`PUT` is a 'state of the world' sync — any resource you previously pushed but omit from a later `PUT` is treated as deleted. There is no separate `DELETE` endpoint."
- **One request per type:** "Each `PUT` must carry the full set of resources for its type in a single request; a follow-up `PUT` replaces the previous payload rather than appending to it."
- **Built-in types (complete list):** `user_account`, `macos_user_computer`, `windows_user_computer`, `vulnerable_component`, `package_vulnerability_connectors`, `api_endpoint_vulnerability_connectors`, `static_analysis_code_vulnerability_connectors`, `background_check_connector`, `user_security_training_status`, `security_task`, `secret`, `custom_resource`.
  - A search of the downloaded page for "pull request", "code change", "change management" and "commit" found no matches.
- **Partner restriction:** "Public marketplace integrations are restricted to the built-in resource types in this table, excluding `custom_resource`."
- **Size limits:** "Maximum resources per `PUT` | 10,000"; "Maximum request body size | 10 MB".
  - "every resource you want Vanta to retain for a given `resource_type` must arrive in a **single** request".
  - "You can split work *across* resource types (a separate `PUT` per type), but not *within* one."
  - If a payload nears either cap, "scope the sync down to fewer resources".
- **Rate limits:** "Build Integrations endpoints | 10 / minute per access token"; OAuth "25 / minute". Vanta sends no `Retry-After` header.
- **Scheduling advice:** "Schedule it. Run the sync hourly from cron, a Lambda, or your CI runner." — [Vanta quickstart: Build a custom integration for compliance data](https://developer.vanta.com/docs/quickstart/build-private-integration.md) [downloaded]

**Custom resources: the fields allowed** — [Vanta, Resources in Vanta](https://developer.vanta.com/docs/concepts/resources.md) [downloaded]
- **Default properties:** every custom resource has `displayName`, `uniqueId` and `externalUrl`.
- **Custom properties:** "Currently supported types: `boolean`, `int32`, `string`, `timestamp`."
- **Flat only:** "Custom properties must be **top-level, flat fields** on the resource. Nested properties — objects, arrays, or sub-objects inside a property — are not supported by Custom Tests and cannot be referenced in pass/fail rules."
- **Private only:** "Custom resources are a private-integration feature. They are only available to direct Vanta customers building against their own tenant. Public marketplace integrations cannot define or sync custom resources on a customer's behalf."
- **Passive without a test:** "Without a custom test, a custom resource is just a passive data record — it won't contribute evidence to controls."
- **Test cadence:** "Build custom tests that evaluate the synced data and produce pass/fail evidence against your controls. Vanta re-runs them on every sync."

**Custom Tests**
- **Authoring and plan:** "Custom Tests are authored in the Vanta Dashboard under **Tests → + Create custom test**. There is no API to create them, and the feature may require a plan upgrade or add-on". — [Vanta, Tests in Vanta](https://developer.vanta.com/docs/concepts/tests.md) [downloaded]
- **Private only:** "Custom Tests are a **private-integration feature only** … not available to public integrations". — same page [downloaded]
- **Two-resource joins:** "A Custom Test can pull data from up to **two resource types** — a primary resource plus one secondary — and correlate them with a join condition you define (for example, `User.email == GitHubMembership.user_email`). The secondary resource can come from the same integration as the primary or from a different one." — same page [downloaded]
- **Help article** (last updated 1 Apr 2026) — [Vanta Help, Creating Custom Tests](https://help.vanta.com/hc/en-us/articles/28012720726036-Creating-Custom-Tests) [opened]:
  - Tests "can't be edited after they're created", and copying a test does not carry over its control mappings.
  - Control mapping "is not automatic".
  - "you cannot currently create a custom test that is not tied to an integration".
  - Join fields must be scalar, matching is type-strict, and "null or missing values never match".
  - It does not say how often tests run or what auditors see.
- **Not through MCP either:** "The MCP server (and the Manage Vanta API) can query existing Custom Tests and their results, but cannot create or edit them." — [Vanta MCP server docs](https://developer.vanta.com/docs/vanta-mcp.md) [downloaded]

**Evidence files**
- **Upload flow:** "This guide attaches an evidence file to a Vanta document with `POST /v1/documents/{documentId}/uploads` and submits it for review with `POST /v1/documents/{documentId}/submit` on the Manage Vanta API."
  - Required scope: `vanta-api.documents:upload`.
  - "Re-uploading evidence on a recurring schedule (e.g. quarterly access reviews)? Wire this flow into a cron job or CI step".
  - Source: [Vanta guide, Upload a document](https://developer.vanta.com/docs/guides/upload-a-document.md) [downloaded]
- **Upload fields:** a multipart `file`, a `description`, and `effectiveAtDate` ("Date indicating when the document is effective from."). — [Upload file for document](https://developer.vanta.com/api-reference/documents/upload-file-for-document.md) [downloaded]
- **Partners can upload files.** The Build Integrations scope `self:write-document` exists to "Upload file-based evidence on a customer's behalf." — [Build Integrations overview](https://developer.vanta.com/reference/build-integrations/overview.md) [downloaded]
- **Intended use:** "Upload documents and evidence (`PDF`, screenshots, exports) directly to Vanta. Useful for any workflow that produces a periodic report or evidence collected in a file format." — [Integrations in Vanta](https://developer.vanta.com/docs/concepts/integrations.md) [downloaded]

**What auditors see (Auditor API, for audit firms)**
- **Who may use it:** the Auditor API "is for **audit firms** conducting audits of their customers' Vanta tenants", and requires a registered Vanta Audit Partner. — [Auditor API overview](https://developer.vanta.com/reference/audits/overview.md) [opened]
- **`listCodeChanges`** — [Vanta Auditor API TypeScript SDK, audits reference](https://github.com/VantaInc/vanta-auditor-api-sdk-typescript/blob/main/docs/sdks/audits/README.md) [GitHub]:
  - "Retrieves code changes population data for an audit. This endpoint provides access to code change records (pull requests) visible to auditors during an audit engagement."
  - Filter by `sourcesMatchesAny` ("accepted values: github, gitlab, bitbucket, azuredevops") and by closed-date range.
  - "Only Controlled Audit View (CAV) audits are supported. Full Audit View audits are rejected with 403. Returns 403 if the customer has not made this population page visible to auditors."
  - "Rate limit: 10 requests / minute."
- **The `CodeChange` record has eight fields:** `id`, `codeChange` ("Code change title (e.g. PR title)"), `segmentIds`, `identifier` ("e.g. PR number"), `service`, `repository`, `openedAt`, `closedAt`.
  - It carries **no author, reviewer, approver, check or AI field**.
  - The model first appears in a commit dated 21 May 2026 (SDK 0.6.2) and was last regenerated 13 Oct 2026 (0.9.35).
  - Sources: [CodeChange model](https://github.com/VantaInc/vanta-auditor-api-sdk-typescript/blob/main/docs/models/components/codechange.md) [GitHub]; commit history via `gh api` [GitHub]
- **Evidence types an information request accepts:** `"UPLOADED_DOCUMENT" | "OBSERVATION" | "LINK" | "VANTA_DOCUMENT" | "VANTA_POLICY" | "VANTA_TEST" | "VANTA_TEST_SNAPSHOT"`. — [InformationRequestSupportedEvidenceType](https://github.com/VantaInc/vanta-auditor-api-sdk-typescript/blob/main/docs/models/components/informationrequestsupportedevidencetype.md) [GitHub]
- **Test snapshots** — [audits reference](https://github.com/VantaInc/vanta-auditor-api-sdk-typescript/blob/main/docs/sdks/audits/README.md), [VantaTestSnapshotEvidence](https://github.com/VantaInc/vanta-auditor-api-sdk-typescript/blob/main/docs/models/components/vantatestsnapshotevidence.md) [GitHub]:
  - "A snapshot is an immutable record of all files (workpapers, raw data, etc.) generated during a single test execution". Each carries `testRunExecutedAt`.
  - Snapshot detail includes "the raw test data captured at snapshot time, and the resources that were excluded from the test (out-of-scope resources)".
  - "For structured snapshots, the `rawTestData` array contains one row per resource the test ran against; each row carries `resourceId`, `resourceType`, and the raw JSON for that resource."
- **Help article "Auditor visibility into test data"** (last updated 1 Dec 2025) — [Vanta Help](https://help.vanta.com/en/articles/11345526-auditor-visibility-into-test-data) [opened]:
  - Auditors see "Test results within the audit's observation window (the period from audit start to end date)", "Overall test statuses based on SLA deadlines", and "Issues discovered and remediated during the observation window".
  - Not visible to auditors: "Raw API request and response data".
  - Failing items fixed before the window began are not visible.
- **Audit features shipped in 2026 (vendor log)** — [Vanta product updates](https://help.vanta.com/en/articles/11345422-product-updates) [opened]:
  - "Control Assessments in Audits" (week of 12 Jul 2026);
  - "Bulk Export of Audit Information Request List and Evidence" as "a structured ZIP file" (week of 26 Jul 2026);
  - "Multi-framework Audits" (week of 23 Aug 2026).

**Vanta's own change-management test (what a sidecar record would sit beside)** — [Vanta Help, GitHub integration guide](https://help.vanta.com/en/articles/14845240-github-integration-guide) (last updated 4 Jun 2026) [opened]
- "Only PRs merged to the production or default branch are evaluated."
- Each merged PR is checked to confirm "it was either approved by someone other than the author" "or has a documented justification for why it was merged without approval".
- "Bot-authored PRs (such as those from Dependabot or Renovate) are evaluated under the same rules as human-authored PRs."
- Sync: "Vanta fetches PRs incrementally"; "Changes take up to 24–48 hours to reflect in Vanta."
- The guide never mentions AI, Copilot, Claude or agents.

### Inferences
- **A per-change record with agent fields can live in Vanta only as the customer's own custom resource,** with a Custom Test the customer builds by hand.
  - It cannot be added to the code-change population that audit firms pull through `listCodeChanges`. That population is native-only (four forges) and lacks even author and approver columns.
  - So pitch4 cannot truthfully say "your auditor sees the agent records in Vanta's change population". It can say the auditor sees them as **a mapped test, with per-record snapshots, across the observation window**.
- **Vanta keeps only the current set, so the sidecar must push the whole audit period every time.** It should push the cumulative set of changes for the open audit period on every sync, not just what is current.
  - At the 10,000-record cap, a 100-engineer team merging about one PR per engineer per working day fills one type in about 100 working days (my arithmetic).
  - Larger or agent-heavy teams must therefore split the population across several custom resource types, for example one per quarter or per repository group.
- **Flat scalars push logic into the sidecar.**
  - Lists such as reviewers must be flattened into strings.
  - The test logic must ride on booleans the sidecar computes: `agent_authored`, `approver_is_sponsor`, `reconciled_to_forge`, `justification_present`.
  - **Consequence:** the GRC platform only checks values that the sidecar asserts. The integrity of those values has to be proven outside Vanta, through a signed export plus a verifier.
- **A reconciliation test inside Vanta may be possible.** A two-resource Custom Test could join sidecar records to Vanta's own GitHub data, for example "every merged PR has a sidecar record". This works only if Vanta exposes pull requests as a testable resource kind, which is unverified.
- **The weakness in Vanta's own test is exactly what the sidecar fixes.**
  - Vanta's PR test passes whenever approver ≠ author, and treats bot authors like humans.
  - When a coding agent opens the PR under a bot or app identity, the engineer who directed the agent can approve it and the test passes.
  - Only a record that names the sponsoring human can flag this.

### Gaps
- **Which Vanta plans include Custom Tests and private integrations** is not stated ("may require a plan upgrade or add-on"). The pricing page was not checked.
- **Not documented:** whether Vanta exposes GitHub pull requests as a resource kind a Custom Test can join.
- **Not documented:** whether Custom Test results on custom resources appear in the Controlled Audit View like built-in tests, or only when attached as snapshots to information requests.
- **Not documented:** how long Vanta keeps test-run history.

## 2. Drata: what can be pushed, with which fields, how often, and what do auditors see?

### Takeaway
- **Drata's "Custom Connections and Tests" takes arbitrary JSON records** under a schema you supply or one Drata infers. The help article sets 5 MB per payload and 500 requests a minute.
- **Pushes can be batched into "sessions".** Completing a session makes it the full current set and permanently deletes everything not in it.
- **Custom tests:**
  - built in a Test Builder or an Advanced editor, and run daily in Drata's classic interface;
  - each run produces a PDF "test evidence" file listing failures and exclusions;
  - drafts are "not auditor-facing".
- **Separate Evidence API for files:** it accepts files including `.json`, `.csv`, `.zip` and `.log`, with a filed date, a renewal schedule and control mappings.
- **Plans:** custom connections and tests require the Advanced or Enterprise plan.
- **Audit Hub** pulls "the evidence for your audit period", lets auditors "pick sample data", and freezes point-in-time packages.
- **Drata's own code-review test reads branch settings, not individual pull requests.**

### Cited Findings
- **Help article "Custom Connections and Tests"** (last updated 9 Jun 2026) — [Drata Help](https://help.drata.com/en/articles/11117161-custom-connections-and-tests) [opened]:
  - What it is: "you can send structured JSON data from any source, whether cloud-based, on-premises, or proprietary".
  - Plans: "Custom Connections and Tests are available on the Advanced and Enterprise plans."; "This is not a standard integration."
  - Limits: "Maximum JSON size: 5 MB"; "Rate limit: 500 requests/min per source IP"; "Avoid top-level arrays."
  - Nesting: complex nested arrays "may require" the advanced test editor.
  - Cadence: "The cadence and how data is pulled and pushed into Drata is determined and manually initiated by the customers."
  - Upsert by ID: "If the record ID is found, the record will be updated (200)." "If the payload does not include an ID, a new record will be created."
- **API v2, Custom Connections** — [Drata API reference](https://developers.drata.com/openapi/reference/v2/tag/Custom-Connections/) [opened; undated]:
  - "CUSTOM connections push arbitrary JSON evidence records using a user-defined schema."
  - Create supports provider types "CUSTOM, MDM, HRIS". MDM and HRIS use "a fixed common model". **There is no version-control or change common model.**
  - Every endpoint requires the "Custom Connections and Tests" feature; otherwise the API returns 402.
- **API v2, Custom Data Records** — [Drata API reference](https://developers.drata.com/openapi/reference/v2/tag/Custom-Data-Records/) [opened]:
  - "Upsert Custom Data Records": "Records with matching IDs will be updated; new records will be created."
  - Sessions: "Insert or update Custom Data records in batches using Session Management"; "Records remain inactive until the session is completed via the session action endpoint."
  - Completing a session "permanently deletes all data that is not part of the session."
  - Records carry `createdAt` and `updatedAt`. Sessions carry the states `IN_PROGRESS`, `ACTIVE`, `CANCELED` and `ARCHIVED`.
  - No maximum batch size is stated, and there is no record versioning.
- **Help article "Create and Publish Custom Tests"** (last updated 21 May 2026) — [Drata Help](https://help.drata.com/en/articles/13401776-create-and-publish-custom-tests) [opened]:
  - Authoring: a Test Builder, or the "Advanced editor to write complex queries". Custom connections are a qualifying data source.
  - Cadence (classic interface): "All custom published or draft tests are run by Autopilot daily." The new interface gives no frequency.
  - Drafts are "not auditor-facing". Only published tests can be mapped to controls and generate audit evidence.
  - Classic evidence: a downloadable PDF, "Raw Evidence and Event Details", with exclusions, the test logic in JSON, and the raw JSON response.
  - Limits: the new interface needs "A Drata Advanced plan or higher". A maximum number of custom tests exists; the number is not given.
- **Help article "Evidence overview"** (last updated 21 May 2026) — [Drata Help](https://help.drata.com/en/articles/13404035-evidence-overview) [opened]:
  - "When a monitoring test runs, Drata generates a test evidence PDF." It "lists failed resources along with any exclusions for that test."
  - Evidence "can be mapped to one or more controls, updated over time, and reused across frameworks."
  - Only the current version affects readiness; past versions remain viewable.
- **API v2, Evidence Library** — [Drata API reference](https://developers.drata.com/openapi/reference/v2/tag/Evidence-Library/) [opened]:
  - These are "the legacy single-artifact endpoints; new integrations should use the Evidence endpoints".
  - Fields: name (≤191 characters), description (≤30,000); an artifact as a file, Base64, URL, ticket URL or S3 key; `filedAt`; a renewal schedule (1, 2, 3, 6 or 12 months, custom, or none); `ownerId`; `controlIds`.
  - Accepted file types: .pdf, .docx, .odt, .doc, .xlsx, .ods, .pptx, .odp, .gif, .jpg, .jpeg, .png, .json, .csv, .md, .markdown, .txt, .html, .log, .zip, .msg, .mp4.
  - Responses carry a `versions` array.
- **Audit Hub** (product page, undated) — [Drata Audit Hub](https://drata.com/product/audit-hub) [opened; vendor]:
  - "Drata automatically pulls in the evidence for your audit period to the hub".
  - "Auditors can pick sample data, request documents, and tag you in action items".
  - "Review the pre-audit and control evidence packages automatically generated as a point-in-time snapshot."
  - "agree upon when you'll freeze samples and finalize packages".
  - "an auditor view accessible only to authorized parties".
- **Test history:** a History tab with run events and a monthly pass/fail summary, each linking to raw test evidence. — [Drata Help, monitoring test details](https://help.drata.com/en/articles/11592978-monitoring-manage-individual-test-details) [search summary]
- **Drata's code-review test (Test 8)** (last updated 5 Aug 2026) — [Drata Help, Test: Formal Code Review Process](https://help.drata.com/en/articles/4776886-test-formal-code-review-process) [opened]:
  - "Drata reads branch configurations for all in-scope repos in your version control system".
  - It fails when "branch configurations allow code changes merged by the same user into the main branch".
  - Providers: AWS CodeCommit, Azure DevOps Repos, Bitbucket, GitHub, GitLab.
  - It does not mention bots, AI or agents, or describe per-PR evidence.
- **Drata MCP** (last updated 23 Sep 2026) — [Drata Help, MCP setup and usage](https://help.drata.com/en/articles/13379899-drata-mcp-setup-usage-guide) [opened]:
  - "Some scopes allow write and delete actions."
  - It can create, update and delete evidence; create and update controls; and create user documents, which work only when paired with evidence.
  - It lists no tool for creating custom data records.
  - Clients named: Claude, ChatGPT, Cursor, Microsoft Copilot.

### Inferences
- **Drata is the best structural fit for a per-change population.**
  - Records are nested JSON, not flat scalars.
  - Session batching avoids Vanta's one-request cap.
  - A daily test produces a PDF that lists the failing records, the form auditors already consume.
  - The Evidence API can carry the sidecar's signed bundle as `.zip` or `.json`, with `filedAt`, a renewal schedule and `controlIds`.
- **Like Vanta, Drata keeps the current set only.** Completing a session deletes everything not in it, so the sidecar must re-send the period's full population each time.
- **Drata's own change test leaves the per-change gap open.** Test 8 inspects branch-protection settings, so Drata holds **no per-change approval evidence of its own**. A sidecar record with sponsor ≠ approver fills that gap. It would not duplicate a Drata feature.
- **Plan gating narrows the Team-tier route.** Custom connections need the Advanced or Enterprise plan, so 5–150-engineer customers on entry plans may only be able to upload files.

### Gaps
- **Not documented:** whether custom-connection records can be selected as a *sampling population* in Audit Hub, or only appear through test-evidence PDFs.
- **Not stated:** the run cadence for custom tests in Drata's new interface, the maximum number of custom tests per plan, and the maximum session size.
- **Not found:** any public Drata partner program for third parties to push custom-connection data into customer tenants. Every path found is customer-run with the customer's API key.

## 3. Secureframe: what can be pushed, with which fields, how often, and what do auditors see?

### Takeaway
- **Custom Integrations** (Complete plan only) accept JSON through the API, or a CSV upload.
  - Secureframe infers a schema, normalizes personnel, devices, cloud resources and training records, and files everything else as "Custom".
  - Files such as PDFs cannot be sent through custom integrations.
- **Custom Automated Tests (CAT)** run against any integration resource. Their evidence can be inspected as JSON and exported. The entry plan includes one.
- **The hosted MCP server (launched 5 Aug 2026) has 112 tools.** It can **publish custom-integration data, create tests, and attach evidence files to tests (up to 32 MB)**, so Secureframe exposes write paths that Vanta's MCP lacks.
- **Upload tests** take periodic evidence on monthly, quarterly or annual intervals. Expired evidence stays in history and stays visible to auditors when it falls within the observation window.
- **Auditors** have read-only access to tests, evidence, controls and comments.

### Cited Findings
- **Help article "Create custom integrations"** (last updated 17 Sep 2026) — [Secureframe Support](https://support.secureframe.com/en/articles/15111548-create-custom-integrations) [opened]:
  - Purpose: "connect systems that Secureframe does not cover with a native integration"; "this feature is available for customers on our Complete Plan."
  - Input: "Send structured JSON payloads using our public API", or "Upload CSV files from the custom integration or schema pages".
  - Schema: "Secureframe will automatically infer the appropriate source and target fields". "All other ingested resource types appear as Custom."
  - Logging: a Request logs tab "keeps a record of batches of data processed or pushed through the API."
  - No files: "Secureframe currently does not support uploading manual evidence, such as PDFs or screenshots, through Custom Integrations."
  - API limits: "You can only update objects already existing in Secureframe through the API." Custom Integrations, by contrast, let you "create and map custom resources".
  - Key ownership: the key "is owned by the logged-in company user who created the connection and is scoped to that custom integration."
  - The page does not say whether pushes replace or append, or how often they run.
- **Help article "Custom Automated Tests (CAT)"** (undated: "Updated over a week ago") — [Secureframe Support](https://support.secureframe.com/en/articles/15111245-custom-automated-tests-cat) [opened]:
  - "Secureframe supports CAT across all integration resources", including the Custom Data Platform.
  - Current scope options: Cloud Resources (AWS) and Assets (Devices, Repositories, Tickets).
  - "View evidence, inspect json, and export evidence just like Secureframe's default tests."

## 4. Can each platform take in a full list of changes with completeness data (period, counts, signature), or only documents?

### Takeaway
- **All three accept a pushed list of records *and* files.**
  - **None has first-class fields for an audit period, record counts, a reconciliation, or a signature, and none verifies signatures.** These must be pushed by the sidecar as ordinary fields (a manifest record) and as a signed file.
- **They hold pushed lists as current state, not history.**
  - Vanta's sync replaces everything; Drata's completed session deletes everything not in it.
  - So the sidecar must push the **cumulative period population**, and history lives in each platform's test runs and snapshots.
- **Each platform's native change population comes only from its own forge integrations** and contains no AI attribution.

### Inferences
**Completeness data travels in three parts on every platform:**
1. **The per-change records,** with computed booleans the tests can check: `agent_authored`, `approver_is_sponsor`, `reconciled_to_forge`, `emergency_with_post_approval`.
2. **A manifest record per period:**
   - `period_start` and `period_end` (timestamps);

   - `ledger_checkpoint_id` and `export_sha256` (strings);

3. **The signed export file,** uploaded as document or test evidence with its effective date, for the auditor to check with the sidecar's open verifier.
   - This keeps the evidence for IPE completeness (period, count, reconciliation, integrity), which L2-2.10 showed auditors test, in front of the auditor. It does not depend on the GRC tool keeping history.

**"Only documents" is the fallback for buyers on entry GRC plans.** A dated, signed CSV or JSON population plus its manifest, uploaded quarterly, works on all three.

- **Secureframe:** whether CAT keeps a test history.

## 7. What the answer means for pitch4's differentiation and offering

### Takeaway
- **The integration route is real but narrower than pitch4 can currently claim.**
  - The sidecar can feed all three platforms. Doing so relies on custom-data features tied to higher plans (Drata Advanced or Enterprise; Secureframe Complete; Vanta "may require" an add-on).
  - For change records it needs the customer's own private integration, since none can go through a Vanta marketplace app.
  - Auditors then see the records as tests across the observation window, not inside the platforms' own change populations.
- **The stronger position is "the evidence source they cannot collect".**
  - Vanta's change population lacks even author and approver fields.
  - Vanta's PR test passes whenever approver ≠ author, and Drata's test reads branch settings.
  - Neither can tell who directed an agent. The sidecar's per-run sponsor and run-to-commit link fill a hole the platforms cannot reach.
- **Drata's AI Agent Governance is the bundling threat to watch,** not Vanta's GrantGuard.

### Cited Findings

- Pitch4 currently offers "exports" in Team and "a visible audit member … compliance mappings" in Assured. It says "December 2027 Draft SOC 2 criteria … apply" and "The moat is time and service". — `/Users/brien/urnetwork/sidecar/pitch4.html` [read locally]

### Inferences
1. **Reword the claim.**
   - **Not:** "auditors see the records in Vanta or Drata".
   - **Instead:** "Feeds Vanta, Drata and Secureframe through your own integration. Your auditor reviews the agent-change tests across the audit window, and can verify the signed export themselves." Name the plan dependency in the FAQ.

   - Drata custom connections using sessions;
