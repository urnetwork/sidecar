# What share of coding-agent sessions run in surfaces the sidecar does not launch, can supported configuration put the sidecar in their launch or tool path, and can an organization make it mandatory? (research as of 1 Nov 2026)

Scope: this follows L3-3.04 (unprivileged enforcement covers only process trees the sidecar launches) and L3-3.07 (ACP wrappers work in every ACP client; JetBrains has an org lock, Zed does not). Neither is repeated. New here: per-surface launch and insertion paths for the Claude Code, Codex, Cursor, Copilot, Cline, Roo, Kilo and OpenCode surfaces; vendor managed-settings and policy-hook systems; Zed's settings layers read from source; JetBrains YouTrack items; the Codex daemon's start mechanism read from source; and a computed people-level share estimate from the Stack Overflow 2026 raw data.

Method and reading key:
- **Docs:** fetched 1 Nov 2026 with a script (HTML stripped to text), or through vendor Markdown endpoints (`.md` suffix on code.claude.com, learn.chatgpt.com and code.visualstudio.com; the docs.github.com article API). Quotes are exact.
- **Source:** GitHub files and searches read with `gh api` on 1 Nov 2026 from default branches. GitHub code search indexes only default branches.
- **YouTrack:** read through JetBrains' public REST API on 1 Nov 2026. Vote counts are as of that day.
- **Install and download counts:** VS Code Marketplace `extensionquery` API, Open VSX API and npm downloads API, all queried 1 Nov 2026. npm "last month" covers 30 Sep to 29 Oct 2026.
- **Stack Overflow 2026:** the same public CSV as L2-2.11 (SHA-256 prefix `ad520b4d5d71f240`; 30,903 rows), downloaded from the StackExchange/Survey archive on 1 Nov 2026. Cross-tabs were computed by me, unweighted, on the 11,739 respondents who named at least one product in `AICodeAgentHaveWorkedWith`. These are counts of people, not sessions.
- No configuration was tested in a lab. "(inference)" marks my reasoning.

## 1. Surface by surface, can the sidecar be put in the launch or tool path through supported configuration, without patching?

### Takeaway
Supported insertion exists on almost every surface, but it comes in four different strengths:

1. **Launch wrapper (the sidecar becomes the agent's parent process):**
   - Claude Code's VS Code extension (`claudeProcessWrapper`) and JetBrains plugin ("Claude command").
   - Every ACP client (L3-3.07).
   - Cursor's CLI and its self-hosted worker, which the sidecar can start itself.
   - Codex's IDE extension has only an executable override documented as "Development only".
2. **Per-command wrapper (every shell command the agent runs passes through the sidecar):**
   - Claude Code's `CLAUDE_CODE_SHELL_PREFIX` wraps Bash tool calls, hooks, status-line commands and stdio MCP server startup, in every Claude surface that reads settings.
   - Pre-tool hooks that can rewrite a command: Claude Code `updatedInput`, Codex `updatedInput`, and Cursor `updated_input`.
   - VS Code has a terminal-profile setting for chat terminal commands.
3. **Hooks only (capture, and block or allow):**
   - Claude Desktop's Code tab, which "runs its own copy of Claude Code".
   - The ChatGPT desktop app that now hosts Codex.
   - Cursor's IDE agent.
   - Copilot in VS Code, which runs in a dedicated "Agent Host" process.
   - Cline and Kilo, through in-process plugins.
4. **MCP everywhere:** this only adds the sidecar's own tools. It does not see the agent's built-in tool calls.

Desktop apps and IDE-native agents have no wrapper slot at all. On those surfaces, capture rests on vendor hooks, and enforcement rests on per-command wrapping or privileged fleet mode.

### Cited Findings
**Claude Code: VS Code extension**
- **The wrapper setting.** `claudeProcessWrapper`: "Executable used to launch the Claude process. The bundled binary path is passed as an argument when present. Set this to a separately installed `claude` binary if the extension build doesn't include one for your platform."
- **Side effects of setting it.**
  - With the wrapper set, the extension skips the "still open somewhere else" check and "opens the conversation directly".
  - It does not restore plan mode on resume.
  - "Conversations missing with `claudeProcessWrapper` set: update the extension to version 2.1.304 or later."
- **Environment.** `environmentVariables`: "Set environment variables for the Claude process."
- **Auto-install.** "If you run `claude` in a VS Code integrated terminal, Claude Code reinstalls the extension automatically."
- Source: [code.claude.com, VS Code](https://code.claude.com/docs/en/vs-code)

**Claude Code: JetBrains plugin**
- "The plugin runs the `claude` command in your IDE's integrated terminal and connects to it. It does not bundle its own copy of the CLI".
- "**Claude command**: specify a custom command to run Claude, for example `claude`, `/usr/local/bin/claude`, or `npx @anthropic-ai/claude-code`".
- "When using JetBrains Remote Development, you must install the plugin on the remote host".
- Source: [code.claude.com, JetBrains](https://code.claude.com/docs/en/jetbrains)

**Claude Desktop, Code tab**
- **Its own copy of Claude Code.** "In a local session, the **Code** tab runs its own copy of Claude Code, which has its own version number. The desktop app downloads and updates that copy, so it can differ from the `claude` command in your terminal, and updating one doesn't update the other."
- **Settings.** "The desktop app reads the same settings files as the CLI." Desktop sets `API_TIMEOUT_MS` and `ANTHROPIC_BASE_URL`, "among others", itself.
- **No documented wrapper setting.**
- Source: [code.claude.com, Desktop](https://code.claude.com/docs/en/desktop)
- **Launch environment.** "When the Claude Desktop app or a self-hosted environment runner starts the session, the launch environment it builds takes precedence instead: Claude Code ignores an `env` value from any settings file for a variable the launch environment already sets." — [settings reference](https://code.claude.com/docs/en/settings-reference)
- **No login shell.** "Desktop doesn't start Claude Code through a login shell." — [monitoring](https://code.claude.com/docs/en/monitoring-usage)

**Claude Code: per-command wrapper**
- **What it wraps.** `CLAUDE_CODE_SHELL_PREFIX`: "Command prefix that wraps shell commands Claude Code spawns: Bash tool calls, hook commands, status line commands, and stdio MCP server startup commands. PowerShell hooks and exec-form hooks run without the prefix. Useful for logging or auditing."
- **What the wrapper receives.** "For Bash tool calls, `$1` contains the full shell invocation Claude Code assembles, including environment setup, not only the command Claude ran".
- **Choice of shell.** `CLAUDE_CODE_SHELL` accepts only a `bash` or `zsh` path.
- Source: [env vars](https://code.claude.com/docs/en/env-vars)
- **Command rewriting.** For `PreToolUse`, "`updatedInput` directly under `hookSpecificOutput` replaces a tool's arguments before it runs" — [hooks](https://code.claude.com/docs/en/hooks)

**Claude Code: telemetry already labels the surface**
- `app.entrypoint` is "How the session was launched, such as `cli`, `sdk-cli`, `sdk-ts`, `sdk-py`, `claude-vscode`, or `claude-in-slack`". It is off by default (`OTEL_METRICS_INCLUDE_ENTRYPOINT`).
- `service.name` is "`claude-code` for terminal sessions, `claude-code-desktop` for local sessions started from the Code tab".
- The Desktop entrypoints are "`claude-desktop`, `claude-desktop-3p`, or `local-agent`".
- Source: [monitoring](https://code.claude.com/docs/en/monitoring-usage)

**Cursor**

### Inferences
- **Wrapper slots exist only where the vendor's client spawns a separately addressable CLI:** Claude's VS Code extension and JetBrains plugin, ACP clients, and Cursor's CLI and worker. Desktop apps and IDE-native agents (Cursor's agent, Copilot's Agent Host, Codex's IDE extension in supported use, Claude Desktop) give no supported way to become the parent process. So "a subprocess any harness launches" is false for them.
- **`CLAUDE_CODE_SHELL_PREFIX` is the strongest unprivileged lever found.** Deployed through managed settings (section 2), it could put the sidecar in front of every Bash command and stdio MCP server in every Claude surface on the machine, including Desktop's Code tab, which has no wrapper slot. Two limits:
  - It does not wrap the agent's own network calls: model traffic, WebFetch and connectors.
  - Whether a managed `env` value takes effect for this variable in each surface is untested.
- **Pre-tool rewrite (`updatedInput`) offers a second per-command path** for Claude Code, Codex and Cursor. The rewritten command would be "run this inside the sidecar's sandbox". Two weaknesses: the hook path fails open on timeouts, and the model sees the change. Copilot documents no equivalent.
- **MCP gives coordination and claims.** It gives neither capture of built-in tools nor enforcement.

### Gaps
- I did not establish how the ChatGPT desktop app starts its local Codex runtime (embedded app-server, a bundled binary, or the daemon).
- Whether VS Code's `chat.tools.terminal.terminalProfile.<platform>` applies to Copilot-harness sessions or only to the Local harness is not stated.
- Whether Cursor CLI sessions run the same `hooks.json` hooks is not stated on the hooks page.
- I found no hook surface for Zed's native agent or for Roo Code.
- None of the wrapper, prefix or rewrite paths was tested.

## 2. Can an organization make that configuration mandatory (Zed managed or read-only settings, JetBrains' "Custom ACP agents" policy, MDM)?

### Takeaway
- **What can be made mandatory:** the hook and environment layer, through each vendor's own policy system:
  - Claude Code managed settings (MDM plist, HKLM registry or system file), which reach the terminal, both IDE extensions, Desktop's Code tab and Agent SDK sessions, and therefore the ACP adapter.
  - Codex `requirements.toml` (managed hooks, `allow_managed_hooks_only`, MDM key).
  - Cursor enterprise `hooks.json` at a system path.
  - Copilot root-owned policy hooks and enterprise-managed settings.
- **What cannot:** I found no way to lock any wrapper or executable-path setting. Local administrators can edit every managed file.
- **Zed:** no managed or read-only layer. Its only extra layer, `global_settings.json`, sits in the user's config directory, below user settings. A community PR that would have added required ACP sandboxing was closed unmerged.
- **JetBrains:** has the policy, but the docs do not say whether it disables an `acp.json` that already exists. Custom ACP agents in Air cloud tasks are implemented through an environment variable, per YouTrack, but not documented.
- **VS Code:** Copilot enterprise-managed settings switch off the Claude and Codex harnesses entirely. A managed VS Code fleet is funnelled into Copilot's own harness.

### Cited Findings
**Claude Code managed settings**
- **Every local surface reads them.** "Surfaces: on the developer's machine, the terminal, the VS Code and JetBrains extensions, the desktop app's Code tab, and Agent SDK sessions read all of these sources. Agent SDK sessions load managed settings even when `settingSources` excludes the user, project, and local files."
- **Delivery.**
  - macOS: "the `com.anthropic.claudecode` managed preferences domain".
  - Windows: `HKLM\SOFTWARE\Policies\ClaudeCode`.
  - Files: `managed-settings.json` and `managed-settings.d/` in `/Library/Application Support/ClaudeCode/`, `/etc/claude-code/` or `C:\Program Files\ClaudeCode\`.
  - Timing: MDM is "Read at startup and checked for changes every 30 minutes".
- **Limits.**
  - "Local admin rights: a developer who is an administrator on the machine can edit the managed source itself".
  - "Other tools: managed settings bind Claude Code only."
  - "On WSL, `/etc/claude-code` is user-writable as well".
  - A server-managed change to "a hook or an `env` variable, waits for the developer to accept the dialog in an interactive session".
- **Embedding hosts.** These can pass "parent settings", but "By default, Claude Code ignores parent settings whenever an admin source is present".
- Source: [managed settings](https://code.claude.com/docs/en/managed-settings)
- **Desktop.**
  - Device policies (`com.anthropic.claudefordesktop`; `SOFTWARE\Policies\Claude`; root-owned `/etc/claude-desktop/managed-settings.json`) include "enabling or disabling the Claude Code feature, controlling auto-updates".
  - `disableDesktopLocalSessions` turns "off Code sessions that run on the device, leaving SSH sessions to other hosts and cloud sessions available".
  - Desktop reads `allowManagedHooksOnly`, `strictPluginOnlyCustomization` and `disableAllHooks` for its SSH command entries.
  - Source: [Desktop](https://code.claude.com/docs/en/desktop)
- **The ACP adapter.** `claude-agent-acp` applies "the managed-policy tier's env vars ... including MDM sources on macOS and `HKLM`/`HKCU` on Windows" (L3-3.07). — [managed-policy.ts](https://github.com/agentclientprotocol/claude-agent-acp/blob/main/src/managed-policy.ts)

**Codex `requirements.toml`**
- **Enforcement.** Requirements are "admin-enforced constraints that users can't override".
- **Managed hooks.**
  - "To enforce managed hooks even for users who turned hooks off locally, pin `[features].hooks = true` alongside `[hooks]`. To skip user, project, session, and plugin hooks while still allowing managed hooks, set `allow_managed_hooks_only = true`."
  - "The local runtime enforces the hook configuration from `requirements.toml`, but it doesn't distribute the scripts in `managed_dir`."
  - "a `PreToolUse` callback error, timeout, or malformed response can fail the hook without blocking the tool."
- **Layers.** `/etc/codex/requirements.toml` (Unix) or `%ProgramData%\OpenAI\Codex\requirements.toml`; the cloud bundle; legacy `managed_config.toml`; and "macOS managed preferences (MDM) delivered through `com.openai.codex:requirements_toml_base64`".
- **Self-hosted configuration** reaches "Codex CLI and the desktop app".
- Source: [managed configuration](https://learn.chatgpt.com/docs/enterprise/managed-configuration)
- **Feature pins and update controls.**
  - "Use `[features]` in `requirements.toml` to pin runtime feature flags by the same canonical keys that `config.toml` uses".
  - `features.in_app_updates` can be set "to `false` in `requirements.toml` to disable in-app updates".
  - `check_for_update_on_startup` can be enforced.
  - Source: [config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- **`daemon_auto_start` is one of those feature keys.** It appears in `codex-rs/features/src/lib.rs` and `core/config.schema.json` (GitHub code search, 1 Nov 2026).
- **Managed requirements reach JetBrains' Codex.** YouTrack LLM-28454 (5 Jun 2026, resolved; title only): "[ACP] Codex "failed to reload config: Failed to load cloud requirements (workspace-managed policies)"".

**Cursor**
- **MDM policies.** The list covers only `AllowedExtensions`, `AllowedTeamId`, `ExtensionGalleryServiceUrl`, `NetworkDisableHttp2`, `UpdateMode` and `WorkspaceTrustEnabled`. - **The policy.** "Custom ACP agents: Determines whether users and service accounts can use their own local agents via the Agent Client Protocol (ACP), beyond those configured at the organization level." — [Configure AI policies](https://www.jetbrains.com/help/air/ai-policies-configure.html)
- **Air cloud, documented position.** "Agents added through acp.json are not available in Air Teams". "Cloud tasks and automation runs always use the JetBrains AI provider". — [Air supported agents](https://www.jetbrains.com/help/air/supported-agents.html)
- **Air cloud, implemented position.** YouTrack AIR-6457, "Ability to run Custom ACP agent in the Cloud" (22 Jul 2026; state "Ready for test"). A JetBrains developer, 29 Jul 2026:
  - "Implementation is done ... The agent needs to be installed in the workspace image via `.air/cloud/startup.sh` setup script"
  - "An environment variable `FLEET_WORKSPACE_CUSTOM_ACP_AGENTS` needs to be added containing the agent launch config. The schema is the same as in `acp.json`".
  - Source: [AIR-6457](https://youtrack.jetbrains.com/issue/AIR-6457)
- **Demand for finer controls.**
  - [LLM-26701](https://youtrack.jetbrains.com/issue/LLM-26701) (open, 19 votes): "Add Separate Controls to Disable JetBrains AI Assistant While Keeping ACP Agents Enabled for Organization". A commenter (Ara_Jerahian, 30 May 2026): "our IT dept. has shortsightedly disabled AI Assistant completely".
  - [LLM-20519](https://youtrack.jetbrains.com/issue/LLM-20519) (open, 11 votes): "Add the option to disable AI Agents in AI Assistant".
  - Two distinct requesters, counted by login, in the opened comments asked to distinguish agent types.

### Inferences
- **Mandatory capture is achievable where a vendor ships a managed hook system.** That is Claude Code, Codex, Cursor and Copilot (CLI and the VS Code Copilot harness). It needs one policy artifact per vendor (plist or JSON, `requirements.toml`, `hooks.json`, `policy.d`) plus MDM-delivered scripts. It is fleet work, not "nothing to change".
- **Mandatory enforcement is not achievable unprivileged.** No wrapper setting is lockable. Locks bind only the vendor's own tool ("managed settings bind Claude Code only"). Admins on their own machines can edit policy.
- **In VS Code, Copilot managed settings decide the harness.** A fleet with Copilot managed settings loses the Claude and Codex harnesses in VS Code. Their sessions move to the Copilot harness (hooks fail open on timeouts) or to the separate Claude and Codex extensions, which do take a wrapper (Claude) or managed hooks (both). A sidecar sold to Copilot-managed fleets inherits that funnel.
- **Zed stays opt-in.** Its "global" layer is user-writable and below user settings, so neither MDM nor read-only settings exist. Device management could only overwrite the user's `settings.json`, which the user can edit again.
- **JetBrains is the one IDE vendor lock that names custom agents.** Whether it holds against a hand-edited `acp.json` is still undocumented. AIR-6457 suggests a cloud path for an organization's wrapped agent (a workspace image plus an environment variable), but it is undocumented and "Ready for test".

### Gaps
- **JetBrains' lock was not verified.** I found no documentation or YouTrack item on whether "Custom ACP agents = off" disables entries already in `~/.jetbrains/acp.json`.
- **Claude Code's wrapper settings lack a documented lock.** I found no way to lock `claudeCode.claudeProcessWrapper` or the JetBrains "Claude command". VS Code's policy reference lists only built-in policies.
- **Copilot in other IDEs.** Copilot's managed-settings table does not mention JetBrains, Visual Studio, Xcode or Eclipse. I did not find whether those clients honour policy hooks.
- **Copilot-managed fleets are unmeasured.** No source says how many fleets deploy Copilot managed settings, and so lose the Claude and Codex harnesses in VS Code.

## 3. What share of coding-agent sessions run in surfaces the sidecar does not launch?

### Takeaway
No vendor publishes session shares by surface. Anthropic's telemetry already labels each session's entrypoint (`app.entrypoint`), but no distribution has been published. The best measurable proxy is people. In the Stack Overflow 2026 raw data (computed), among 11,739 coding-agent users:
- **83.5%** used at least one IDE- or app-native agent product that the sidecar cannot launch;
- **20.7%** used only such products;
- **16.2%** used only CLI-first harnesses (Claude Code, Codex, OpenCode, Pi, Aider, Mistral Vibe);
- **62.9%** used both.

In 20–99-person companies the figures are 81.1% (any IDE- or app-native product) and 15.8% (only such products); in 100–499-person companies, 84.2% and 18.3%. Even among Claude Code users, 80.4% also use an IDE-native agent, 61.9% use VS Code regularly and 41.7% use a JetBrains IDE.

So a launcher-only sidecar can see every agent session for at most about one agent user in six. Most sessions most likely run where only hooks or managed settings reach them (inference, low reliability for sessions).

## 4. L3-3.04's open items: is Codex's macOS daemon started through launchd, and do Cursor, Copilot or OpenCode run persistent daemons or detached updaters?

### Takeaway
- **Codex:** its daemon is not a launchd job. On Unix it is "a pidfile-backed detached process" started with `setsid()`; on Windows it is started with `DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB`. Its updater loop is "not reboot-persistent". Later sessions attach to it and share "the environment inherited when the daemon started".
- **Cursor:** its CLI auto-updates by default. The app ships an updater process. Its self-hosted worker is a long-lived process that the user (or the sidecar) starts.
- **Copilot in VS Code:** runs agents in a long-lived Agent Host utility process that outlives windows.
- **OpenCode:** runs no daemon and "Updates are never installed automatically".

### Cited Findings
- **Codex daemon README.**
  - Purpose: it "backs the machine-readable `codex app-server` lifecycle commands used by remote clients such as the desktop and mobile apps. It is intended for Codex instances launched over SSH".
  - Start: it "starts app-server as a pidfile-backed detached process. It launches a detached updater loop when automatic updates are enabled".
  - Persistence: "the updater loop is not reboot-persistent; a managed start after reboot starts it again".
  - Environment: "Shared clients use the environment inherited when the daemon started ... per-client environment isolation is not provided."
  - Bypass: "An invocation that sets `CODEX_EXEC_SERVER_URL` skips implicit daemon attachment".
  - Windows: "Windows startup requires a non-elevated terminal whose host permits detached child processes."
  - Updater preference: `CODEX_HOME/app-server-daemon/settings.json` holds `"updater": { "autoUpdateEnabled": false, ... }`.
  - Source: [codex-app-server-daemon README](https://github.com/openai/codex/blob/main/codex-rs/app-server-daemon/README.md) (last changed 27 Oct 2026, #57533)
- **Codex daemon source.**
  - Unix: `command.pre_exec(|| { if libc::setsid() == -1 ...`.
  - Windows: `command.creation_flags(CREATE_NO_WINDOW | DETACHED_PROCESS | CREATE_BREAKAWAY_FROM_JOB)`, with the comment "Never retry inside the parent's Job Object".
  - Source: [pid_start.rs](https://github.com/openai/codex/blob/main/codex-rs/app-server-daemon/src/backend/pid_start.rs)
  - Code search for "LaunchAgents" in openai/codex returned 0 hits. "launchd" appears only in Windows-sandbox files and a PID-identity test (1 Nov 2026).
- **Cursor.**
  - "Cursor CLI will try to auto-update by default" — [installation](https://cursor.com/docs/cli/installation)
  - The Windows app includes `inno_updater.exe` — [endpoint security](https://cursor.com/docs/enterprise/endpoint-security)
  - The `UpdateMode` MDM policy can "disable updates" — [deployment patterns](https://cursor.com/docs/enterprise/deployment-patterns)
  - The worker holds "a long-lived outbound HTTPS connection" — [Self-Hosted Machines](https://cursor.com/docs/cloud-agent/self-hosted)
- **Copilot.**
  - "For sessions managed by desktop VS Code on your machine, keep the application running"; the Agent Host can also run standalone through `code agent host` — [Agent Host](https://code.visualstudio.com/docs/agents/concepts/agent-host)
  - Copilot CLI's README lists Homebrew, WinGet and npm installs. I found no auto-update statement — [copilot-cli README](https://github.com/github/copilot-cli/blob/main/README.md)
- **OpenCode.**
  - "OpenCode checks for new versions and shows a notice when one is available. Updates are never installed automatically." — [OpenCode config](https://opencode.ai/docs/config/)
  - `opencode serve` runs a headless server only when it is invoked explicitly — [OpenCode server](https://opencode.ai/docs/server/)

### Inferences
- **`setsid()` changes the session and process group.** It does not remove a Seatbelt profile, a Linux namespace or a cgroup, so a daemon started inside the sidecar's sandbox stays inside it (OS semantics, inference).
- **The real escapes for Codex are architectural.**
  - Sessions attach to whichever daemon exists over its socket. A sidecar-wrapped `codex` can therefore hand its turns to an unwrapped daemon, and an unwrapped session can use a sandboxed one.
  - On Windows, `CREATE_BREAKAWAY_FROM_JOB` leaves a Job Object that permits breakaway.
- **Three supported mitigations for Codex:**
  1. The sidecar starts and owns the daemon.
  2. `CODEX_EXEC_SERVER_URL` is set per launch.
  3. `daemon_auto_start` is pinned off through `requirements.toml` `[features]` (an untested pin of a documented feature key).
- **The other harnesses add only long-lived processes the sidecar cannot parent.** Cursor and VS Code agents run inside the app (Agent Host or extension host), and their updaters are app-level and configurable by MDM. The process-tree problem there is "never launched by the sidecar", not "detached".

### Gaps
- Whether the ChatGPT desktop app starts or attaches to the same daemon on a local machine is not documented.
- Whether Copilot CLI self-updates was not established.
- Cursor's IDE-side persistent helpers (beyond the extension host) are undocumented.

## 5. Per-surface table, and what it means for pitch4's differentiation and offering

### Takeaway
pitch4's "Nothing to change: a subprocess any harness launches" holds only for terminal CLIs, Claude's VS Code and JetBrains integrations, ACP clients, and Cursor's CLI and worker. Those cover all of the agent work of only about one agent user in six. For everyone else:
- **Capture** can be made complete and mandatory only through per-vendor managed hooks: Claude Code, Codex, Cursor and Copilot.
- **Unprivileged enforcement** reaches commands, not agent processes. This works through Claude's shell prefix or hook rewrites, and fails open where hooks do.
- **"Governed egress for every agent"** needs privileged fleet mode on IDE and desktop surfaces.

The first release should be scoped and claimed accordingly.

### Inferences
**What changes in pitch4**
- **Developer claim.** Change "Nothing to change: a subprocess any harness launches" to something like: "Captures every session from the harness's own hooks, deployed once per machine; adds launch-path control where the harness allows a wrapper." Capture via hooks is the only mechanism that reaches the about 84% of agent users with IDE or desktop sessions, and it needs managed deployment to be complete.
- **Security claim.** "Every way your agents reach the outside world is ... approved" needs a coverage qualifier:
  - commands can be routed through the sidecar unprivileged on Claude, Codex and Cursor (shell prefix or rewrite);
  - agent-process egress (model calls, fetch, connectors) on IDE and desktop surfaces is governed only in fleet mode (L3-3.04: NetworkExtension, a root helper or WFP).
- **First-release scope.** Ship a "policy pack" per vendor before shipping more wrappers:
  - Claude Code managed settings with hooks and `CLAUDE_CODE_SHELL_PREFIX`;
  - Codex `requirements.toml` with managed hooks, `allow_managed_hooks_only` and a daemon pin;
  - Cursor enterprise `hooks.json` with `failClosed`;
  - Copilot `policy.d` and managed settings.
- **The coverage record is the differentiator.** The record should state, per session, how it was captured: wrapper, managed hook, shell prefix, ACP wire or not at all. Anthropic's `app.entrypoint` and `service.name` already label Claude surfaces, so the sidecar can report coverage by surface. That answers "what did the sidecar not see", which no vendor console does across harnesses.
- **Fail-closed where it exists.** Cursor (`failClosed`) and Copilot policy hooks run outside the sandbox but fail open on timeouts. The sidecar should use `failClosed` where offered and log hook-timeout gaps elsewhere, which matches L3-3.07's fail-closed direction.

### Gaps
- No buyer evidence on whether one MDM policy pack per vendor is acceptable to 5–150-engineer companies that may have no MDM.
- No lab confirmation that the shell prefix and `updatedInput` rewrites survive auto, bypass and "Full access" modes, or the Desktop launch environment.
- Session-level shares by surface remain unknown. Design-partner telemetry (Claude OTel `app.entrypoint`, Codex and Copilot metrics) is the only route.
