# What can the sidecar do on a developer's machine without admin rights, and what approvals would a managed fleet need for the rest? (research as of 1 Nov 2026)

Scope: this follows L2-2.15 (per-agent network identity) and L2-2.14 (local-only egress). Those notes found that port remapping breaks "OAuth callbacks or CORS allowlists" (Claude Desktop docs, portless users), that Claude Code's Linux sandbox already gives each command a private localhost, and that a split design (enforcement outside the request path, per process tree) is the answer to the "proxy as single point of failure" objection. None of that is repeated. This note adds what each OS lets an unprivileged process do, what the OAuth providers and browser specs actually say, how harness daemons and updaters escape process-tree rules, and what Apple, MDM and EDR require for the rest.

Method and reading key:
- **Docs and source only, no lab tests** (per the brief). All pages were fetched on 1 Nov 2026 with a script (HTML stripped to text) unless marked "search excerpt". Apple developer pages were read through Apple's JSON doc endpoints (`developer.apple.com/tutorials/data/documentation/...json`), which return the same text the doc pages render.
- **GitHub** issues, source and rule files were read with `gh api` on 1 Nov 2026. Reaction counts are totals on that day. anthropics/sandbox-runtime (srt) was read at commit 98a4016d27 (25 Oct 2026).
- **Local man pages** (`ifconfig(8)`, `sandbox-exec(1)`) were read on the macOS machine running this research (Darwin 27). They are Apple's shipped documentation, not a test.
- **Hacker News user evidence:** HN Algolia API, 10 comment queries (for example "our IT tailscale", "IT department ngrok", "work laptop tailscale", "crowdstrike ngrok", "zscaler tailscale"), comments created on or after 1 Jan 2024. That gave 235 unique comments. A regex filter (workplace terms plus a tunnel-tool name) left 36, which I read by hand. I kept people who state a workplace restriction on installing or using tunnel tools, counted by username.

## 1. Can the sidecar give each agent its own address on default ports, on macOS, Linux and Windows, while the developer's browser and Playwright still reach a chosen agent's stack?

### Takeaway
- **Linux:** yes, without root. Each agent gets a user and network namespace, so it has its own private localhost on default ports. Unprivileged forwards on 127.0.0.N let the browser reach it. One exception: Ubuntu 24.04 and later block this by default until someone with sudo installs an AppArmor profile.
- **macOS:** not for processes running natively on the Mac. There are no network namespaces. Extra loopback addresses need root ("Only the super-user may modify the configuration of a network interface"). Seatbelt can filter only "localhost" or "*" as the host. Addresses from a NetworkExtension need a notarized system extension that the user, or MDM, approves. The only rootless route is to run each agent's stack in a lightweight Linux VM (Apple's `container`, or Lima with vzNAT), where every container gets an IP the host can reach.
- **Windows:** there are no per-process network namespaces. Per-agent stacks have to live inside WSL2, where the Linux mechanisms apply.
- **All three OSes:** a per-agent IP on a shared host still needs every service told to bind that IP. Postgres, Redis and Vite all default to localhost. So "nothing to change" holds only for a private localhost per agent, not for a per-agent IP.

### Cited Findings
**macOS**
- **Root for extra loopback addresses.** `ifconfig(8)` on macOS: "Only the super-user may modify the configuration of a network interface." (local man page, Darwin 27). A secondary source shows the failure and the fix: `rails -b 127.0.0.2` → "Can't assign requested address - bind(2) for 127.0.0.2:3000 (Errno::EADDRNOTAVAIL)"; "Mac OSX will disable all loopback addresses other than 127.0.0.1 by default, but they can be enabled with ifconfig"; `sudo ifconfig lo0 alias 127.0.0.2 up` — [Hashrocket TIL](https://til.hashrocket.com/posts/94a6225fad-loopback-to-different-127-ips-mac-osx) (secondary, undated). A HashiCorp support article on aliases for multiple Vault instances appeared in search, but the page did not load (it returned 69 characters).
- **Making a root change persistent means installing a LaunchDaemon.** Apple: "In macOS 13 and later, use SMAppService to register and control LoginItems, LaunchAgents, and LaunchDaemons as helper executables for your app… For SMAppServices initialized as LaunchDaemons, the register() and unregister() methods provide a replacement for installing property lists in /Library/LaunchDaemons." — [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)
- **Low ports and hosts files on macOS** (portless README, a tool that already handles this boundary):
  - "Ports below 1024 normally need root, so portless elevates with `sudo` to bind 443 or 80."
  - "macOS lets a non-root process bind a port below 1024 only on the wildcard address, so the proxy binds `0.0.0.0` and `::` instead of the loopback addresses and then refuses every connection whose peer is not loopback itself".
  - Its unprivileged mode is for "a managed laptop, a CI runner, or an agent session with no terminal to type a password into". It "never writes the hosts file either, since that needs root". "`.localhost` names resolve in browsers without it. For Safari or a custom TLD, run `portless hosts sync` once yourself".
  - "On a Mac with the application firewall turned on, the first wildcard bind shows an 'allow incoming connections' prompt for Node."
  - Source: [vercel-labs/portless README](https://github.com/vercel-labs/portless/blob/main/README.md)
- **Seatbelt cannot partition localhost or name hosts.** srt's macOS profile generator comments: "Seatbelt only accepts "localhost" or "*" as the host token". With `allowLocalBinding` it emits `(allow network-bind (local ip "*:*"))` and `(allow network-outbound (remote ip "localhost:*"))`. Otherwise outbound is allowed only to `localhost:${httpProxyPort}` and `localhost:${socksProxyPort}` — [srt macos-sandbox-utils.ts @98a4016d27](https://github.com/anthropics/sandbox-runtime/blob/98a4016d27/src/sandbox/macos-sandbox-utils.ts). `sandbox-exec(1)` itself is marked "DEPRECATED" (local man page).
- **NetworkExtension routes** (each needs an entitlement, and outside the App Store a system extension):
  - The entitlement lists separate Developer ID variants: "The APIs you use to proxy TCP and UDP connections, when signed with a Developer ID profile"; "The filter APIs you use to allow or deny network connections created by other apps on the system, when signed with a Developer ID profile"; "The APIs you use to tunnel IP packets to a remote network… when signed with a Developer ID profile" — [Apple NE entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension)
  - System extensions: "The system grants these extensions a high level of privilege"; "You must either distribute your app and extension through the Mac App Store, or notarize them." — [Apple SystemExtensions](https://developer.apple.com/documentation/systemextensions)
  - Tailscale's three macOS builds show the trade-off:
    - Standalone (system extension): such extensions "run with root privileges but remain within a sandbox".
    - App Store: "both the Tailscale app and its Network Extension are sandboxed and running as the local user, there are a number of limitations".
    - Open-source `tailscaled`: "uses the kernel utun interface… only recommended for unattended installs managed by experienced macOS system administrators".
    - Sources: [Tailscale macOS variants](https://tailscale.com/kb/1065/macos-variants). The `tailscaled` route installs as root: `sudo tailscaled install-system-daemon` "copies the binary to `/usr/local/bin` and installs a plist in `/Library/LaunchDaemons/com.tailscale.tailscaled.plist`" — [Tailscale wiki](https://github.com/tailscale/tailscale/wiki/Tailscaled-on-macOS)
- **VM per stack, no root (Apple `container`).**
  - "Every container gets an IP address on its network, always reachable by that IP from the host and from other containers on the same network."
  - Names cost one admin step: `sudo container system dns create test`. "Enter your administrator password when prompted. This writes a resolver file to `/etc/resolver/`".
  - The API server "is a launch agent", so it runs as the user.
  - On macOS 15: "The vmnet framework in macOS 15 can only provide networks where the attached containers are isolated from one another", and separate isolated networks need macOS 26.
  - Sources: [apple/container networking.md](https://github.com/apple/container/blob/main/docs/networking.md); [technical-overview.md](https://github.com/apple/container/blob/main/docs/technical-overview.md)
- **VM per stack, no root (Lima).**
  - Default user-mode networking: the guest "IP address is not accessible from the host by design. Use vzNAT or managed networks".
  - "For VZ instances, the vzNAT network is easier to set up, as it needs neither socket_vmnet nor the sudoers file." socket_vmnet must be installed "into a secure path only writable by root".
  - The host's loopback is reachable from the guest as `host.lima.internal` unless `hostLoopback: false` (Lima v2.3).
  - Sources: [Lima managed networks](https://lima-vm.io/docs/config/network/managed/macos/); [Lima user-mode network](https://lima-vm.io/docs/config/network/user/)
- **OrbStack (vendor docs):**
  - "You can also connect to containers by IP, directly from Mac!" Containers have `container-name.orb.local` domains, with automatic HTTPS.
  - "Container domains currently depend on the direct IP access feature, so make sure 'Allow access to container domains & IPs' is enabled in Settings → Network." — [OrbStack network](https://docs.orbstack.dev/docker/network); [OrbStack domains](https://docs.orbstack.dev/docker/domains)
  - Privileges, from the release notes: v0.16.1 (17 Aug 2023) "Helper tool to avoid asking for password more than once" and "Option to stop requesting admin privileges"; v1.8.1 (10 Nov 2024) "Support for symlinking /var/run/docker.sock when running as non-admin user" — [OrbStack release notes](https://docs.orbstack.dev/release-notes)
  - A maintainer in 2023: "We'll add a privileged helper tool"; "in the future there will likely be more lost functionality as we add more privilege-dependent features" — [orbstack/orbstack #281](https://github.com/orbstack/orbstack/issues/281)
- **Docker Desktop:** each container "receives its own internal IP address", but host reach goes through published ports: "Docker Desktop's backend process listens on the specified host port". Outbound, "Docker Desktop's backend process receives the traffic and creates standard TCP/IP connections using the same networking APIs as other applications." — [Docker Desktop networking](https://docs.docker.com/desktop/features/networking/)
- **Coasts gives each worktree its own runtime, not its own host address.**
  - "Check out one coast at a time to bind canonical ports to your host, and use dynamic ports to peek into the progress of any worktree."
  - It needs Docker and socat. "Linux development works, but canonical ports below `1024` require host setup before `coast checkout` can bind them."
  - Source: [coast-guard/coasts README](https://github.com/coast-guard/coasts/blob/main/README.md)

**Linux**
- **The whole 127.0.0.0/8 range is usable on lo without configuration.** Practical evidence: systemd-resolved listens on "the IP addresses 127.0.0.53 and 127.0.0.54 on the local loopback interface" — [systemd-resolved.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-resolved.service.html)
- **Unprivileged namespaces with forwards to chosen addresses (pasta).**
  - pasta is "Unprivileged user-mode network connectivity for network namespaces", working "without requiring any capabilities or privileges".
  - Its `-t` spec is `[address[%interface]/]ports`: "Optionally, a specific listening address and interface name (since Linux 5.7) can be specified."
  - Source: [passt/pasta man page](https://passt.top/builds/latest/web/passt.1.html)
- **Ubuntu blocks this by default.**
  - "Ubuntu now sets `kernel.apparmor_restrict_unprivileged_userns=1` by default, which blocks network namespace operations (including loopback setup) for unprivileged processes" ("bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted"). The workaround is a sudo-installed AppArmor profile — [srt #74, 18 Dec 2025, 11 reactions](https://github.com/anthropics/sandbox-runtime/issues/74)
  - Claude Code docs: "On Ubuntu 24.04 and later, the default AppArmor policy prevents bubblewrap from creating the user namespaces it needs for isolation", followed by `sudo tee /etc/apparmor.d/bwrap` — [code.claude.com sandboxing](https://code.claude.com/docs/en/sandboxing)
  - Codex docs give the same sudo steps, and as a last resort `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` — [Codex sandboxing](https://learn.chatgpt.com/codex/sandboxing)
- **It keeps breaking in 2026:**
  - Claude Code #43454 ("apply-seccomp fails on Linux - cannot write /proc/self/setgroups", Ubuntu 25.10; 4 Apr 2026; 58 reactions, 29 comments, open) — [link](https://github.com/anthropics/claude-code/issues/43454)
  - Claude Code #105194 (26 Oct 2026): Ubuntu 26.04's `bwrap-userns-restrict` profile "runs bwrap's child processes under 'unpriv_bwrap', which denies all capabilities" — [link](https://github.com/anthropics/claude-code/issues/105194)
  - Codex #38715 (15 Aug 2026): "Documented AppArmor remediation breaks bubblewrap when another vendor's profile is already installed" — [link](https://github.com/openai/codex/issues/38715)
  - Further open issues titled after the same failure: srt #428 and #429 (28 Jul 2026), Claude Code #93130 (9 Sep 2026), #101946 (14 Oct 2026), and Codex #48681 (27 Sep 2026) (GitHub search, 1 Nov 2026).

**Windows**
- **Claude Code:** "On native Windows, Claude Code runs commands unsandboxed. To use the sandbox on a Windows machine, run Claude Code inside a WSL2 distribution." — [code.claude.com sandboxing](https://code.claude.com/docs/en/sandboxing)
- **WSL2:** by default a Linux app's server is reachable from a Windows browser "using localhost (just like you normally would)". Mirrored mode (Windows 11 22H2+) changes the architecture. For the Hyper-V firewall: "Run the following command in PowerShell window with admin privileges to Configure Hyper-V firewall settings to allow inbound connections" — [Microsoft WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)
- **Codex's no-admin Windows sandbox (MXC) shares the host's loopback.** "MXC permits connections to and from services on host loopback" and "Remaining child processes stop when the foreground command exits. Test workflows that rely on detached development servers." MXC was "introduced… in Windows 11 24H2 (build 26100.9278) and 25H2 (build 26200.9278)" — [Codex Windows](https://developers.openai.com/codex/windows)

**Default bind addresses, which decide whether per-agent IPs need configuration**
- Postgres `listen_addresses`: "The default value is localhost" — [PostgreSQL docs](https://www.postgresql.org/docs/current/runtime-config-connection.html)
- Redis default config: `bind 127.0.0.1 -::1` — [redis.conf](https://github.com/redis/redis/blob/unstable/redis.conf)
- Vite `server.host`: "Default: 'localhost'" — [Vite server options](https://vite.dev/config/server-options)

**Browser and Playwright reach**
- Chromium does not proxy loopback: "Requests to certain hosts will not be sent through a proxy… localhost, *.localhost, [::1], 127.0.0.1/8". The pattern `<-loopback>` "*Subtracts* the implicit proxy bypass rules… generally only needed for test setups. Beware of the security implications to proxying localhost." — [Chromium net/docs/proxy.md](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)
- Playwright: "You can configure pages to load over the HTTP(S) proxy or SOCKSv5. Proxy can be either set globally for the entire browser, or for each browser context individually." — [Playwright network](https://playwright.dev/docs/network)
- Node ignores `HTTP_PROXY` by default. Built-in proxy support (added v24.5.0 and v22.21.0, "Stability: 1.1 - Active development") applies only "if the NODE_USE_ENV_PROXY environment variable is set to 1 or --use-env-proxy is enabled" — [Node.js http docs](https://nodejs.org/api/http.html)

### Inferences
- **A per-agent IP and a per-agent localhost are two different products.**
  - With a per-agent IP on a shared host, each service must bind that IP, because Postgres, Redis and Vite all default to localhost. That is a change in every service config, against pitch4's "Nothing to change".
  - With a per-agent private localhost (a namespace or a VM), each stack keeps its defaults (3000, 5432, 6379 on localhost), and the sidecar adds a forward from outside.
  - Only the second matches the 2.15 promise of "default ports, unchanged".
- **Linux: the free tier can do this today, with no root.**
  - Recipe: a user and network namespace per agent; the harness and its stack inside it; a pasta forward from host 127.0.0.N:port into the namespace.
  - The developer's browser can then open `http://127.0.0.N:3000`, which is still a secure context (section 2).
  - Ubuntu 24.04 and later need one sudo step (an AppArmor profile), so "no admin rights" is false on the most common developer distro unless IT ships the profile.
- **macOS: no rootless per-agent address exists for processes running natively on the Mac.** The choices:
  - root (lo0 aliases, kept across reboots by a LaunchDaemon);
  - an approved system extension (NE packet tunnel addresses on a utun);
  - a Linux VM per stack (Apple `container` or Lima vzNAT, no root; DNS names need sudo once).

  The VM route changes how developers work: Linux binaries, file sharing into the VM, and no macOS-only toolchains. It is closer to OrbStack or Coasts than to "a subprocess any harness launches".
- **Userspace stacks (tsnet, tailcat) give an identity to the overlay, not to the OS.** Unmodified dev servers cannot bind an address that exists only inside another process. Clients reach that address only through a proxy, and Node ignores proxies unless a flag is set. So a userspace stack suits reach across machines (pitch4's forwards), not same-machine default ports.
- **The developer's browser and Playwright can both reach a chosen agent without root:**
  - Option A: open the agent's 127.0.0.N address (Linux), or its VM IP (macOS).
  - Option B: give each agent its own browser context, routed through that agent's proxy with `<-loopback>`, so that `http://localhost:3000` in that context means that agent's stack.
  - Option B is the one that keeps OAuth and CORS (section 2). It is a test-setup pattern by Chromium's own description, so the sidecar should confine it to per-agent Playwright contexts and dedicated browser profiles.

### Gaps
- I found no first-party Apple document stating that macOS configures only 127.0.0.1 on lo0. The evidence is the super-user rule in `ifconfig(8)` and a secondary TIL post.
- I did not verify whether native Windows lets an unprivileged process bind 127.0.0.N (N ≠ 1), whether creating an AppContainer profile needs admin, or what networking MXC gives beyond "host loopback".
- I did not establish whether macOS allows a sidecar packet tunnel to run alongside a corporate VPN or ZTNA client. This is critical for managed fleets.
- OrbStack's docs pages I read do not say which features its privileged helper is for, beyond the docker.sock symlink.
- I did not read the tsnet or gVisor netstack docs this round. The userspace point rests on 2.02's tailcat evidence and on how sockets work.

## 2. Does a per-agent address keep OAuth redirect URIs and CORS allowlists working, or must each agent get its own private localhost?

### Takeaway
A different IP or hostname breaks exact-match OAuth redirects and CORS allowlists registered for `localhost:PORT`.
- The loopback leniency in the standards covers native apps on 127.0.0.1 or [::1] with any port. It does not cover 127.0.0.2, and it does not cover web-app clients.
- Google rejects `.localhost` and `.test` hostnames outright.
- CORS compares scheme, host and port exactly.

So keeping OAuth and CORS with "nothing to change" requires each agent to have its own private localhost, plus a browser context routed into it. Per-agent 127.0.0.N addresses do have two real advantages over port remapping: they stay secure contexts, and they isolate cookies.

### Cited Findings
- **RFC 8252 (native apps):**
  - Loopback redirects are "http://127.0.0.1:{port}/{path}" for IPv4, and "http://[::1]:{port}/{path}" for IPv6. "The authorization server MUST allow any port to be specified at the time of the request for loopback IP redirect URIs."
  - "the use of localhost is NOT RECOMMENDED".
  - It also warns: "Loopback IP-based redirect URIs may be susceptible to interception by other apps accessing the same loopback interface on some operating systems."
  - Source: [RFC 8252 §7.3, §8.1, §8.3](https://www.rfc-editor.org/rfc/rfc8252.txt)
- **RFC 9700 (Security BCP):** "authorization servers MUST utilize exact string matching except for port numbers in localhost redirection URIs of native apps" — [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.txt)
- **Google:**
  - Web clients: "Redirect URIs must use the HTTPS scheme, not plain HTTP. Localhost URIs (including localhost IP address URIs) are exempt from this rule." "Hosts cannot be raw IP addresses. Localhost IP addresses are exempted from this rule." "Host TLDs… must belong to the public suffix list." — [Google OAuth web server](https://developers.google.com/identity/protocols/oauth2/web-server)
  - Installed apps: "http://127.0.0.1:port or http://[::1]:port", which "start an HTTP listener on a random available port" — [Google OAuth native](https://developers.google.com/identity/protocols/oauth2/native-app)
- **Google rejects per-agent hostnames under `.localhost` (portless #58).**
  - Google's error: "Invalid Redirect: must end with a public top-level domain (such as .com or .org)."
  - Users: "localhost:3000 works with 127.0.0.1:3000. But with portless, google oauth doesn't recognize `.localhost` TLD" (risonsimon), and "I also tried using the `test` TLD… but Google also blocks that" (yangshun).
  - The fix was a custom TLD on a domain you own. The team-wide pain stayed: "each dev is accessing with different URLs, and each URL would need to be added to the google oauth callbacks" (zwily). Multi-segment TLDs standardise "the URL by convention (per-machine `/etc/hosts` sync), not a shared network address" (Railly).
  - The issue opened 27 Feb 2026 and closed as completed on 5 Apr 2026, with 10 reactions and 15 comments.
  - The README now says: "Strict OAuth providers (Google, Apple) reject `.localhost` and `.test` redirect URIs but accept a real domain".
  - Sources: [portless #58](https://github.com/vercel-labs/portless/issues/58); [README](https://github.com/vercel-labs/portless/blob/main/README.md)
- **portmap's answer is to avoid hostnames.** "Unlike Portless, portmap doesn't hijack your localhost with subdomain routing or break OAuth flows. It simply scans your ports, lets you name them". The repo is now vibber-ai/portmap: 26 stars, created 29 Mar 2026, last pushed 2 Jul 2026 — [vibber-ai/portmap](https://github.com/vibber-ai/portmap). Its author's HN pitch is in 2.15.
- **GitHub:**
  - "For the http://127.0.0.1/path callback URL, you can use this redirect_uri if your application is listening on port 1234: http://127.0.0.1:1234/path".
  - With wildcard matching, "the redirect URL's host (excluding subdomains) and port must exactly match the callback URL"; without it, "the redirect URL must exactly match the callback URL".
  - "Apps that had a single callback URL enabled prior to August 3, 2026 have wildcard matching enabled for that callback URL."
  - Source: [GitHub authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)
- **Microsoft Entra:**
  - "the port component (for example, :5001 or :443) is ignored for the purposes of matching a localhost redirect URI… This is only true for localhost redirect URIs."
  - "The IPv6 loopback address ([::1]) isn't currently supported."
  - "use the IP literal loopback address 127.0.0.1 in your redirect URI instead of localhost". An http redirect on 127.0.0.1 requires editing `replyUrlsWithType` in the manifest.
  - "Do not register multiple localhost redirect URIs where only the port differs. The login server picks one arbitrarily".
  - Source: [Entra redirect URI restrictions](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)
- **Auth0:** "For production environments, verify that the URLs do not point to localhost" — [Auth0 application settings](https://auth0.com/docs/get-started/applications/application-settings). Also: "a login confirmation prompt may still appear when the application uses a non-verifiable callback URI (such as localhost or a custom URI scheme)" — [Auth0 consent](https://auth0.com/docs/get-started/applications/confidential-and-public-applications/user-consent-and-third-party-applications). An Auth0 community thread asking for wildcard ports under RFC 8252 appeared in search, but I did not open it.
- **Okta (2022, current status not verified):** asked about ephemeral loopback ports, Okta's Developer Support replied "At this time, Okta does not support this RFC." (staff, 19 Oct 2022) — [Okta devforum 22197](https://devforum.okta.com/t/22197)
- **CORS and origins:** "Two URLs have the same origin if the protocol, port (if specified), and host are the same for both." — [MDN same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)
- **Cookies are not port-isolated.** "Cookies do not provide isolation by port. If a cookie is readable by a service running on one port, the cookie is also readable by a service running on another port of the same server." — [RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265.txt)
- **Secure contexts:** a host in "127.0.0.0/8 or ::1/128" is "Potentially Trustworthy", as are "localhost" and names ending in ".localhost" — [W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/)

### Inferences
- **Per-agent 127.0.0.N addresses break the common case.** A web app registered `http://localhost:3000/callback` with Google, GitHub, Auth0 or Okta, and an API allowlisted `http://localhost:3000` for CORS. Both are exact host matches. Entra's port leniency does not help, because the host changes.
  - Whether Google's "localhost IP addresses" includes 127.0.0.2 is undocumented (gap).
  - RFC 8252's leniency names only 127.0.0.1 and [::1], and covers native clients.
- **Port remapping (Conductor, autoPort, portless) breaks the same allowlists and also shares cookies across agents.** RFC 6265 says cookies on localhost do not isolate by port, so agents' apps in one browser can overwrite each other's session cookies. Per-agent hosts (127.0.0.N, or `*.localhost` names) do isolate cookies. This is an advantage of per-agent addresses that 2.15 did not record.
- **Avoid non-loopback per-agent addresses** (CGNAT 100.64/10 from tailnet-style overlays, or 10/8) for browser work. `http://100.64.x.y:3000` is not a secure context, so Secure cookies, service workers and similar features fail over plain HTTP. Keep per-agent addresses inside 127.0.0.0/8 (Linux), or use VM IPs only behind the proxy pattern.
- **The design that keeps OAuth, CORS and cookies has three parts:**
  1. a private localhost per agent (namespace or VM);
  2. agents' own browser tests in per-agent Playwright contexts proxied into that localhost (Chromium `<-loopback>`), so origins stay `http://localhost:3000`;
  3. the developer's everyday browser getting real `localhost:3000` for one agent at a time, as a "checkout" (Coasts' model). The sidecar can switch the host forward without root on Linux, and through the VM's port publishing on macOS.

  Native-app loopback flows (CLIs doing OAuth on 127.0.0.1:random) work unchanged inside a namespace, because the redirect returns to the same namespace's loopback.
- **RFC 8252 warns about interception on shared loopback.** A private localhost per agent closes that hole, which gives the sidecar a security reason to offer this, not only a convenience reason.

### Gaps
- No provider page says whether 127.0.0.N (N ≠ 1) counts as "localhost" or loopback in redirect URIs (Google, Entra, GitHub, Okta, Auth0, Apple).
- Okta's current docs were not found (the developer.okta.com URLs I tried returned 404). The only evidence is a 2022 staff reply.
- How often OAuth or CORS exact-match needs block parallel agents in practice remains unmeasured. 2.15 has two sources; portless #58 adds 10 reactions and about 10 distinct commenters.

## 3. Can the sidecar block all egress by default for each harness's process tree, except what is allowed, in a way that survives auto-updaters and daemons?

### Takeaway
Without admin rights, yes, but only for process trees the sidecar itself launches:
- **macOS:** Seatbelt (a deprecated API, localhost-proxy-only).
- **Linux:** a namespace, Landlock (port-only) or seccomp (all-or-nothing). Ubuntu needs the AppArmor step.
- **Windows:** only Codex-style MXC on recent Windows 11 builds.

It does not survive harness daemons and updaters that start outside the tree. Codex's CLI now starts a persistent daemon that is reparented to PID 1, runs from a copied binary, updates itself hourly, and "pins the environment" (including `HTTPS_PROXY`) of whichever session started it. Enforcement that does survive needs privilege: a NetworkExtension content filter keyed on the signing identity (macOS), cgroup BPF or nftables (Linux), or WFP filters (Windows, admin).

### Inferences
- **Process-tree rules cover what the sidecar launches; they fail in four ways:**
  1. A daemon outlives the session that started it. Codex's daemon is reparented to PID 1, and its turns are served for later sessions.
  2. Environment-based routing (`HTTPS_PROXY`) is pinned to the first session.
  3. The binary moves: Codex runs from a copied directory, and Claude Code from `versions/<v>`. That breaks path-keyed rules, though not rules keyed on a signing identity.
  4. Updaters do their own egress. Codex checks hourly and has downloaded 1.3 GB. The harness's own telemetry and catalogs, covered in 2.14, are another source.

  Desktop apps and IDE extensions started by launchd or the IDE never pass through the sidecar's wrapper at all.
- **What survives updaters and daemons, without admin:**
  - The sidecar owns the daemon: it sets `daemon_auto_start=false`, or starts the daemon itself inside the sandbox, through its "instruction-file writer".
  - The sidecar records version and updater events in the run's record.
  - Neither is enforcement. Both are configuration plus evidence, and the "what left this machine" report must state what was outside the tree.
- **What survives, with privilege:**
  - On macOS, an NE content filter or transparent proxy that keys rules on the code-signing identity of the process creating the flow (`sourceProcessAuditToken`) and follows parent-process chains.
  - On Linux, cgroup-scoped nftables or BPF rules applied by a root helper. systemd's per-user manager cannot do this.
  - On Windows, WFP filters keyed on application ID or user SID (admin), or Codex's dedicated-account design.

  All of these are fleet features that need approval (section 4).
- **Landlock is attractive but port-only.** It can say "only connect to the sidecar's proxy port". It cannot say "only connect to the team's inference server". The kernel layer can enforce a deny-by-default rule plus a proxy exception; host and IP policy has to live in the proxy. That confirms 2.14's split design, but on macOS and Landlock systems the model-server traffic must also go through the local proxy, unless it is on loopback or allowed by a privileged rule. That is the in-path dependency 2.14 wanted to avoid.
- **VM-based per-agent stacks (the only rootless macOS route in section 1) move attribution inside the VM.** On the host, every agent's traffic looks like the VM backend process. The sidecar would need an in-VM component or a per-VM proxy to keep per-agent records.

### Gaps
- I found no public source on whether Codex's daemon on macOS is started through launchd (which escapes Seatbelt), or how it behaves under Codex's own Seatbelt profile.
- I did not check whether Cursor, Copilot or OpenCode run comparable persistent daemons or detached updaters.
- I found no documentation on whether an NE content filter can reliably attribute flows from processes reparented to launchd to the harness that started them. The audit token identifies the process, not its original tree.
- I did not verify Windows defaults for unprivileged AppContainer creation, or MXC's network-policy granularity (allowlists versus on/off).

## 4. Where root, a system extension or a driver is needed, what do MDM, notarization and EDR policies require, and who approves?

### Takeaway
On macOS, a filter or tunnel built on a system extension must be notarized (or come from the App Store), signed with Developer ID NetworkExtension entitlements, and approved:
- either by the user in System Settings, which needs an administrator to authenticate if no profile manages the extension;
- or silently through an MDM-pushed SystemExtensions payload (team ID) together with a VPN or web-content-filter payload. "macOS enforces that a payload with system scope can only be deployed by an MDM server."

Intune, Jamf, JumpCloud and Iru (formerly Kandji) all support this.

Separately, public detection content now flags the shape of the sidecar's reach features:
- Sigma rates "PUA - Ngrok Execution" as high, and has cloudflared tunnel rules.
- Elastic added "Potential Tunneling via Tailscaled" (29 Jul 2026), which fires on exactly the userspace SOCKS and HTTP-proxy flags.
- MITRE T1572 now cites an intrusion where "the adversary instructed Claude Code to connect to the victim devices through SSH tunnels."

Developers report that managed laptops forbid Tailscale and ngrok. For a fleet, endpoint approval is a gate that comes before any vendor review.

- **A fleet-grade sidecar on macOS needs:**
  - a notarized Developer ID app with NE system-extension entitlements;
  - an MDM profile containing a SystemExtensions payload (team ID), and a WebContentFilter or TransparentProxy VPN payload;
  - optionally a LaunchDaemon helper through SMAppService for loopback aliases.

  This is the Tailscale and Little Snitch class of deployment. On unmanaged Macs, users can approve it themselves, but approval needs an administrator account. Users without admin rights, who are common on managed fleets, cannot.
- **The detection gate is real and recent.** Rules written in 2026 match userspace SOCKS and HTTP-proxy relays and tunnel binaries. A sidecar that opens relays, SOCKS listeners or tunnels from developer laptops will trip T1572 and T1090 content unless it is signed, inventoried and allowlisted. The "no admin, runs in userspace" pitch is exactly what Tela's author used to get around a ban, and what Elastic now hunts. In a managed fleet, a no-admin design does not avoid approval; it changes approval into a detection exception.
- **For managed fleets the first gate is endpoint approval.** Someone must allowlist the team ID or extension, add EDR and NGFW exceptions, and push the MDM profile. That person is the IT or endpoint owner. In 5–150-engineer companies this may be the same person who runs the SOC 2 tooling. The public evidence shows the restriction (8 people), not who lifts it.
- **The ledger can turn "a tunnel" into "an approved, receipted grant".** That is the counter-story to T1572: every connection maps to a grant the security team approved, with the signing identity and process recorded. Detection engineers already write "verify the user and host are authorized" into their false-positive notes. The sidecar can be the system that answers that question.

- I found no first-party CrowdStrike, SentinelOne or Microsoft Defender documentation naming built-in detections for Tailscale or cloudflared. The evidence is public rule sets (Sigma, Elastic, Splunk), MITRE, a 2025 Defender user report and ngrok's FAQ.
- I found no public thread showing who approves such tools in small companies (5–150 engineers), how long it takes, or whether IT treats an open-source binary differently.
- Apple's macOS 15+ behaviour for network-extension approval (where it appears in System Settings, how removal works) was read only through the payload keys, not in a user-facing Apple support article.
- I did not check vendor certification paths for allowlisting (CrowdStrike Store, Microsoft partner programs, Jamf Marketplace).

## 5. Matrix by OS, and what it means for pitch4

### Takeaway
pitch4's first-release line "A permanent private address for each agent and service" and its developer line "Nothing to change: a subprocess any harness launches" hold only on Linux and WSL2, and even there Ubuntu needs one sudo step.
- **On macOS:** a per-agent address for native processes needs root or an approved system extension, and the rootless option means running stacks in a Linux VM.
- **Process-tree egress enforcement:** unprivileged mode does not survive harness daemons. Surviving enforcement needs the same approvals.
- **Recommended shape for the first release:**
  - a free, unprivileged "private localhost per agent" mode, with checkout and per-agent browser contexts;
  - a notarized, MDM-deployable "fleet mode" (system extension or helper);
  - endpoint approval treated as the first sales gate, with an approval kit, not SOC 2 alone.

### Cited Findings
Matrix (sources are in sections 1–4; "(inf)" marks an inference).

**macOS**

| Mechanism | Privilege needed | What it enables | What breaks |
|---|---|---|---|
| lo0 alias 127.0.0.N, made persistent with a LaunchDaemon | Root (`ifconfig(8)`); the daemon through SMAppService or /Library/LaunchDaemons | Per-agent loopback IPs; secure contexts; separate cookies | Every service must bind its IP (Postgres, Redis, Vite default to localhost); OAuth and CORS registered for localhost fail; names need /etc/hosts (root) or `.localhost` (Safari needs hosts; Google rejects it) |
| Seatbelt (`sandbox-exec`) as srt and Claude Code use it | None | Deny-by-default per process tree, except localhost proxy ports; inherited by children | Deprecated; host tokens only "localhost" or "*"; no private localhost (with local binding, every localhost service is reachable); tools that ignore proxies fail (Node unless `NODE_USE_ENV_PROXY=1`); daemons and launchd-started processes outside the tree (inf) |
| Userspace stack with SOCKS or HTTP proxy (tsnet, tailcat, Cursor's tailscaled recipe) | None | Overlay identity, cross-machine reach, egress through a proxy | Cannot give dev servers OS addresses (inf); Chromium bypasses proxies for loopback without `<-loopback>`; Elastic flags tailscaled's SOCKS and HTTP-proxy flags (T1090/T1572) |
| NetworkExtension packet tunnel (utun addresses) or transparent proxy | Developer ID entitlement, notarization, user or admin approval, or MDM SystemExtensions plus VPN payload | Per-agent addresses on utun (inf); per-flow proxying | Approval friction; MDM-only silent install; coexistence with corporate VPN/ZTNA unknown |
| NE content filter (NEFilterDataProvider) | Same, plus a WebContentFilter payload | System-wide per-process allow and deny keyed on signing identity and audit token; survives updaters and daemons (inf) | Same approvals; mapping a flow to a process tree is not documented |
| `tailscaled`-style utun daemon | Root (`sudo … install-system-daemon`) | Kernel utun without Apple's approval flow | Root daemon; "only recommended for unattended installs managed by experienced macOS system administrators" |
| Linux VM per stack (Apple `container` on macOS 26, Lima vzNAT, OrbStack) | None for the container API server (a launch agent) or Lima vzNAT; sudo for `container` DNS names; OrbStack's helper is optional | A true private localhost per agent; IP reachable from the host; checkout or proxy for the browser | Stack must run as Linux; macOS 15 limits; host sees only the VM process (attribution moves inside the VM) |

**Linux**

| Mechanism | Privilege needed | What it enables | What breaks |
|---|---|---|---|
| 127.0.0.0/8 on lo | None | Bind 127.0.0.N without configuration; host forwards per agent | Per-service bind config if stacks share the host namespace |
| User and network namespace (bwrap `--unshare-net`, pasta, slirp4netns, rootless Podman) | None in the kernel; Ubuntu 24.04+ needs a sudo-installed AppArmor profile; 26.04's `bwrap-userns-restrict` breaks srt and Claude Code | Private localhost per agent on default ports; pasta forwards `127.0.0.N/3000:3000`; deny-by-default egress except a proxy socket | AppArmor breakage (#43454, 58 reactions); nested user namespaces inside containers; processes outside the namespace |
| Landlock (ABI 4 TCP, ABI 10 UDP) | None | Irrevocable port-level connect and bind limits for the tree | Ports only, no IP or host; older kernels |
| seccomp (as Codex uses it) | None | Block all network syscalls (including io_uring bypass) | All or nothing |
| cgroup BPF or nftables per cgroup (systemd `IPAddressDeny=`, `NFTSet=`) | Root, or CAP_BPF/CAP_NET_ADMIN; NFTSet and IP accounting are system-manager only | IP allowlists per cgroup that survive daemons placed in the cgroup (inf) | Needs a privileged helper; user daemons outside the cgroup escape |

**Windows**

| Mechanism | Privilege needed | What it enables | What breaks |
|---|---|---|---|
| WFP filters or Windows Firewall per app or SID | Admin (or Network Configuration Operators) | Per-app or per-account enforcement that survives updates (srt's `srt-sandbox` account) | Needs admin or IT provisioning |
| AppContainer | Not verified (gap) | Network capabilities per process (Internet, intranet, server) | Loopback blocked by default; exemption needs admin and a running CheckNetIsolation; no host allowlist |
| MXC (Windows 11 24H2/25H2, build .9278 and later) | None | Codex's recommended no-admin sandbox with network permissions | Shares host loopback (no private localhost); child processes killed when the foreground exits, which hurts detached dev servers; new builds only |
| Codex-style elevated sandbox (dedicated users plus firewall rules) | Admin-approved setup, IT can pre-provision | Strong network isolation | Admin |
| WSL2 | None to run (installing WSL2 itself not checked) | Linux namespaces inside; NAT localhost forwarding to the Windows browser | Hyper-V firewall changes need admin; WSL1 unsupported for bwrap |

### Inferences
- **Change "IP addresses" to "a private localhost for each agent" in the developer pitch.** Offer per-agent IPs only where they are free (Linux 127.0.0.N, VM IPs). This is the version that keeps "default ports, unchanged", OAuth redirects, CORS allowlists and separate cookies, which no free tool does today:
  - portless needs sudo for 443 and the hosts file, and its `.localhost` names fail Google OAuth;
  - Coasts gives canonical ports to only one checkout at a time;
  - Claude Code's private localhost is Linux-only and cannot be reached from the host;
  - Codex's MXC shares host loopback.
- **Make the developer message honest per OS.**
  - Linux and WSL2: "no admin rights; one sudo step on Ubuntu, or IT ships the profile".
  - macOS: "per-agent stacks run in a lightweight Linux VM, or with an admin-approved helper".
  - "Nothing to change" stays true for session capture (MCP or stdio). It does not hold for network identity on macOS.
- **Split enforcement into two products.**
  - *Wrap mode* (free, no admin): Seatbelt, namespaces, Landlock or MXC, plus a local proxy, for trees the sidecar launches. It records what it could not see.
  - *Fleet mode* (Team and Assured): a notarized NE content filter or transparent proxy on macOS, a root helper with cgroup rules on Linux, and a WFP service on Windows. All are keyed on signing identity, so they survive updaters and daemons, and are deployed by MDM.

  The second is what a security buyer means by "every way out is governed". It is also what forces enterprise packaging into the first paid release.
- **Treat endpoint approval as the first sales gate, before SOC 2.** Ship an approval kit:
  - Apple team ID and bundle IDs, plus ready `.mobileconfig` files (SystemExtensions, WebContentFilter or TransparentProxy);
  - Intune, Jamf and Iru guides;
  - EDR exclusions keyed on signer and command line;
  - notes on the Sigma and Elastic rules the sidecar's reach features resemble (T1572, T1090).

  Design the transport so it does not look like a covert relay: no generic SOCKS listener flags, a signed binary, registered in inventory. Every tunnel should map to a grant in the ledger.
- **Manage harness daemons explicitly.** The instruction-file writer should set daemon and updater options per harness (for example Codex `daemon_auto_start=false`, or a daemon owned by the sidecar inside the sandbox), and pin harness versions per run. The record should log updater egress and the binary each turn actually ran, which matches the "execution receipt" a #48195 commenter asked for.

### Gaps
- Whether a single notarized macOS system extension can deliver both per-agent addressing and per-process-tree enforcement, alongside common corporate VPN, ZTNA and EDR filters, is unverified.
- No survey or thread measures how many target developers lack local admin rights, or how long IT approval takes in 5–150-engineer companies.
- The matrix's Windows rows rest mainly on Codex's and Microsoft's docs. MXC's network granularity and unprivileged AppContainer creation are unverified.
