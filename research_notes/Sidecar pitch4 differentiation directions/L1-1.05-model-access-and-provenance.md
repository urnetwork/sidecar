# Model access and provenance: AI gateways, model signing, attested inference, and pitch4's "signed receipt of which weights served" (L1-1.05)

Researched 1 November 2026. GitHub star counts come from the GitHub REST API and PyPI download counts from the pypistats.org API (`/api/packages/<name>/recent`), both fetched on 1 November 2026. Hacker News threads were read in full through the Algolia items API. Claude Code issues were found with `gh search issues`. Labels used below:
- **[vendor claim]**: the vendor's own statement about itself.
- **[secondary]**: an aggregator, press piece or competitor blog, not the primary source.
- **[search summary]**: seen only in a search-result summary; the page itself was not opened.
- **[not opened]** or **[403]**: the page was not read, or refused the fetch.

Context from earlier rounds, not repeated here: Aperture's record fields, Coder's and Cloudflare's portals, transparency logs (Tessera, Rekor v2), SCITT (RFC 9942 and 9943), in-toto agent predicates and commit signing. All are in `research_notes/Agent work record gaps and features/` (`record_feature_benchmark.md`, `verifiable_record_tech.md`). Those notes put hardware attestation under "Later, if ever". This round finds attested inference in production at several vendors, which changes that judgment (see Q2 and Q4).

## Q1. Who ships AI or LLM gateways for agent traffic, with what features, self-hosting, pricing and adoption? Does any keep logs under customer-held keys, or end-to-end encrypted?

### Takeaway
Gateways are crowded and commoditizing, and in 2026 they are being absorbed by security platforms:
- Palo Alto Networks bought Portkey. Mintlify bought Helicone. Envoy AI Gateway became Agent Router under the Agentic AI Foundation (AAIF).
- Anthropic now ships its own self-hosted gateway inside the `claude` binary.
- Open-source LiteLLM gives virtual keys, budgets and request logging away for free.
- Tailscale Aperture and NetFoundry already route agents to self-hosted llama.cpp, vLLM and Ollama servers over a private network. That is pitch4's "model access" reach item, at par.

No gateway found signs per-request receipts or binds the served weights. Every one logs a model-name string, and the operator can read and alter that log. "Customer-held keys" exist only in weak forms: Cloudflare encrypts *exported* logs to a customer RSA public key, and Portkey's hybrid mode keeps logs in the customer's own database under a key management service (KMS) the customer brings. In both, the gateway operator still processes plaintext. The only end-to-end designs found are attested-inference gateways (Q2). They protect prompts from the provider, not the team's record.

**Customer-held keys, end-to-end encryption, signing**
- **Cloudflare.** Logpush can encrypt AI Gateway logs to a customer RSA key: "an AES key is generated for each log", and "We encrypt this key with the recipient's RSA public key". The only advice is "Keep the private key secure, as it will be used to decrypt the logs".
  - Logpush exports "whether or not logging is enabled for the gateway". Limits: four jobs per account and 1 MB per log.
  - The page says nothing about dashboard copies or about the plaintext the gateway sees in transit — [Cloudflare AI Gateway Logpush](https://developers.cloudflare.com/ai-gateway/observability/logging/logpush) (updated 26 Oct 2026).
- **Portkey hybrid.** "Your LLM logs explicitly reside in your databases; the control plane has no access to them". Metrics still go to Portkey's ClickHouse. Hybrid and air-gapped installs can "Bring your own KMS (AWS KMS, Azure Key Vault, GCP KMS) for envelope encryption" [vendor claim] — [Portkey hybrid architecture](https://portkey.ai/docs/self-hosting/hybrid-deployments/architecture); [Portkey security](https://portkey.ai/docs/enterprise/security.md) [search summary].
- **Self-hosted open source** (LiteLLM, agentgateway, Agent Router, Kong OSS, NetFoundry). Logs sit wherever the operator stores them. No end-to-end encryption against the operator is documented. Aperture documents no encryption at rest or customer-held keys (Aperture docs, above; also the earlier round).
- **Signed, hash-chained gateway logs** exist only in small open-source projects.
  - AIR Blackbox: "ML-DSA-65 signed, HMAC-SHA256 chained" records per call; airblackbox/airblackbox has 25 stars — [pkg.go.dev](https://pkg.go.dev/github.com/airblackbox/gateway) [search summary].
  - Wardin: hash-chained receipts; wardin-verify has 1 star.
  - Model Witness on PyPI — [Model Witness](https://pypi.org/project/model-witness/0.5.4/) [search summary].
  - None of them binds weights, because they see only the model name in the request and response.

**Gateways as concentrated targets**
- **LiteLLM PyPI compromise.** Malicious `litellm==1.82.7` and `1.82.8` were "live on March 24, 2026 from 10:39 UTC for about 40 minutes". The payload was a credential stealer that scanned environment variables, SSH keys, cloud credentials, Kubernetes tokens and database passwords.
  - The official Docker image was not affected. The fix was a new CI/CD pipeline and v1.83.0 (30 Mar 2026), with Mandiant engaged for forensics — [LiteLLM security update](https://docs.litellm.ai/blog/security-update-march-2026).
  - One aggregator claims more than 2,500 organizations were affected [secondary, unverified] — [OECD AI incident](https://oecd.ai/en/incidents/2026-08-11-8e67).
- **CVE-2026-42208 (CVSS 9.3).** A pre-authentication SQL injection in LiteLLM's Bearer-token check affected versions 1.81.16 through 1.83.6. It was "observed under targeted exploitation just 36 hours and seven minutes after" indexing.
  - The proxy database holds virtual keys, upstream provider credentials ("can hold an OpenAI organization key", Bedrock IAM credentials, Azure secrets) and configuration secrets.
  - Read-write access permits destroying "audit and usage records" — [CSA research note, 28 Apr 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-litellm-pre-auth-sqli-20260428/).

### Inferences
- **Reach to model servers is at par.** "Agents reach only the inference servers you run" is no longer distinctive. Aperture and NetFoundry already route to self-hosted vLLM, Ollama and llama.cpp over private overlays. LiteLLM, agentgateway and Agent Router do the same when self-hosted. pitch4 rates reach "at par" elsewhere, and model access belongs there too. Only the receipt and the team-keyed record are new.
- **The gateway field is turning into security-platform inventory.** Portkey sits inside Prisma AIRS, Anthropic bundles its own gateway, and AAIF hosts Agent Router and agentgateway. All of them inspect plaintext by design. That supports pitch4's incentive argument: vendors built on reading the data will not ship a record they cannot read. The open-source gateways could add signed receipts cheaply, though. The lasting gap is the record kept under team keys, linked to agent actions, not signing as such.
- **pitch4 can say something new against gateways.** A gateway's own log sits in a mutable database that the operator and attackers can rewrite. CVE-2026-42208 allowed exactly that. A per-request receipt signed beside the model server and stored outside the gateway is evidence a gateway compromise cannot quietly rewrite. That is a concrete, sourced reason to sit beside a gateway instead of being one.
- **The sidecar should complement gateways, not compete with them.** Teams already run LiteLLM or Agent Router for budgets and keys. A sidecar that signs receipts and verifies attestations alongside an existing gateway avoids fighting free virtual keys and budgets.
- **"No vendor sits in the path" is a real contrast with Aperture**, whose traffic passes through Tailscale's gateway and Vercel AI Gateway (per Vercel's own case study). It holds only while the sidecar's model path really is sidecar-to-sidecar.
- **"Local models leave no log. No vendor keeps one."** (pitch4 page 1) needs a qualifier. No *model vendor* keeps one, but a gateway such as LiteLLM, Aperture or NetFoundry can log local-model traffic, in a form its operator can read.

### Gaps
- Aperture and TrueFoundry list prices were not confirmed from primary pages. Kong's are unpublished.
- Whether Portkey's open-source gateway is still maintained after May 2026 is not confirmed. There have been no public pushes since 25 May 2026.
- I found no adoption numbers for agent traffic specifically (as opposed to all LLM traffic) for any gateway.
- Whether Cloudflare's dashboard keeps readable copies when Logpush encryption is on is not stated in its docs.

## Q2. What is production-ready in 2026 for model provenance (signing, hashes, BOMs, runtime identity) and for attested inference?

### Takeaway
Signing model files at rest works but is thinly adopted:
- The OpenSSF Model Signing (OMS) library (`model-signing`) reached v1.0 in April 2025.
- NVIDIA signs every NVIDIA-published model in NGC, and Kaggle has integrated it.
- Its last release was October 2025. It has 249 stars and about 19,000 PyPI downloads a month.
- Hugging Face Hub signing is unconfirmed.

Nothing standard records serving-time identity: the engine, its version, the parser, the chat template, the quantization and any adapters.

Attested inference is production-grade at the hardware layer, with NVIDIA Blackwell confidential computing at single-digit overhead. Several services expose it to customers:
- Tinfoil binds a dm-verity Merkle root of the weights into its attestation.
- NEAR AI signs every response with a key held in a trusted execution environment (TEE).
- Phala/Dstack publishes an open "Attested Confidential Inference" (ACI) spec with signed per-request receipts.
- Apple PCC (now also on Google Cloud), Google Private AI Compute, Chutes, Privatemode and OpenPCC do similar work.

An IETF individual draft (AIR) defines a COSE receipt that binds `model_hash` to request and response hashes. Zero-knowledge proofs are not yet practical at coding-model scale.

### Cited Findings

**Signing model files at rest**
- **Library release.** The `model-signing` v1.0 Python library was released on 4 April 2025. It supports Sigstore, self-signed certificates and key pairs — [Sigstore blog](https://blog.sigstore.dev/model-transparency-v1.0); [PyPI model-signing](https://pypi.org/project/model-signing/).
  - Latest GitHub release: v1.1.1 (10 Oct 2025). sigstore/model-transparency has 249 stars (GitHub API).
  - PyPI downloads: 19,297 in the last month (pypistats).
- **NVIDIA NGC.** "NVIDIA has been signing all NVIDIA-published models in the NGC Catalog" since March 2025 with OMS.
  - Each version gets a detached bundle: a manifest of per-file hashes, optional metadata and a signature.
  - Users verify with `model_signing verify ... --certificate_chain` against NVIDIA's public certificate.
  - The post does not mention verification at serving time (NIM, Triton, vLLM) or attestation — [NVIDIA Technical Blog, 28 Jul 2025](https://developer.nvidia.com/blog/bringing-verifiable-trust-to-ai-models-model-signing-in-ngc).
- **Kaggle.** OMS was "integrated into major model hubs such as NVIDIA's NGC and Google's Kaggle" — [OpenSSF case study](https://openssf.org/?p=8650) [search summary]. A July 2026 OpenSSF podcast cites Kaggle, NVIDIA and "the path to PyTorch" — [OpenSSF podcast, 14 Jul 2026](https://openssf.org/podcast/2026/07/14/whats-in-the-soss-podcast-65-s3e17-signing-the-future-securing-ai-and-ml-artifacts-with-mihai-maruseac/) [search summary].
- **Red Hat.** `rh-model-signing` is a Red Hat "Tech Preview" that signs OCI model images and attaches signatures through the OCI 1.1 Referrers API — [PyPI rh-model-signing](https://pypi.org/project/rh-model-signing/) [search summary]. Signing Red Hat AI ModelCar images is a planned, unshipped effort — [Red Hat Jira AIPCC-1490](https://issues.redhat.com/browse/AIPCC-1490) [search summary].
- **Load-time check pattern.** sigstore/model-validation-operator (32 stars) is "a proof of concept". A webhook injects an init container that validates a model's Sigstore, PKI or public-key signature "before they are picked up by actual workload", with optional periodic re-validation through a native sidecar — [README](https://github.com/sigstore/model-validation-operator) (GitHub API).
- **Hugging Face (status unclear).**
  - The author of huggingface_hub issue #4021 (1 Apr 2026, closed 29 Apr 2026 with no comments) asserts that "HuggingFace signs uploaded models with Sigstore". The same author asks for signed attestations linking quantized GGUF, AWQ and GPTQ files to their source model: "source model hash, quantization tool + version, method" — [huggingface_hub #4021](https://github.com/huggingface/huggingface_hub/issues/4021).
  - I could not confirm Hub-wide signing in any Hugging Face document. A third-party page says Sigstore signing is "essentially unadopted on Hugging Face today" [secondary] — [ModelVet space](https://dfrokido-modelvet.static.hf.space/index.html).
- **Why quantized files need provenance.** "Mind the Gap" (ICML 2025) built malicious GGUF quantizations that look benign in full precision. The effect was Δ=88.7% on insecure code generation, Δ=85.0% on content injection and Δ=30.1% on benign refusal, across three LLMs and nine GGUF types — [PMLR v267](https://proceedings.mlr.press/v267/egashira25a.html); [arXiv 2505.23786](https://arxiv.org/abs/2505.23786) [abstract via search summary]. The insecure-code result bears directly on coding agents run on local quantizations.

**Runtime identity in serving stacks**
- **Ollama** stores models as content-addressed blobs with SHA-256 digests in manifests. Its create API takes "file name and SHA256 digest of each GGUF file" and of safetensors files — [Ollama API docs](https://github.com/ollama/ollama/blob/main/docs/api.md) (raw file read 1 Nov 2026).
- **vLLM's "Weight Checker"** has `POST /weight_checker` with `checksum`, `reset` and `compare` actions. "It hashes each model parameter with SHA-256" across data-, pipeline- and tensor-parallel shards. It is meant for verifying RL weight updates.
  - It needs `VLLM_SERVER_DEV_MODE=1`. It does not check "Buffers, draft models, and LoRA adapters".
  - "Hashing copies every weight to CPU, so it's costly on latency-sensitive paths." There is no signing or attestation — [vLLM docs, latest](https://docs.vllm.ai/en/latest/training/weight_checker/).
- Tailscale Aperture and the OpenAI-compatible servers identify a model only by the `id` from `/v1/models` (Q1).

**Bill-of-materials standards (descriptions at rest)**
- CycloneDX ML-BOM "Represents datasets, models, and configurations for AI and machine learning systems" and "Documents provenance and ethical considerations for datasets". The page does not cover quantization, inference engines or serving configuration. CycloneDX Attestations (CDXA) is a separate capability — [CycloneDX ML-BOM](https://cyclonedx.org/capabilities/mlbom/).
- SPDX 3.0 added an AI profile (an AI model class with hyperparameters, architecture and model-card references) and a Dataset profile [secondary] — [MONOist, Sep 2026](https://monoist.itmedia.co.jp/mn/articles/2609/11/news021_2.html).
- The OWASP AIBOM generator maps 17 of 29 fields (59%) exactly to the SPDX 3.0 AI profile — [OWASP AIBOM mapping](https://huggingface.co/spaces/GenAISecurityProject/OWASP-AIBOM-Generator/blob/main/docs/AI_SBOM_Fields_Mapping_Reference.md) [search summary]. I found no adoption metrics for either standard.

**Attested inference: hardware**
- NVIDIA lists confidential computing on "NVIDIA Blackwell GPUs, including the NVIDIA RTX PRO 6000, HGX B200, and HGX B300", with multi-GPU support up to 8 GPUs over NVLink encryption. The NVIDIA Remote Attestation Service (NRAS) checks GPU evidence combined with CPU TEE (AMD SEV-SNP or Intel TDX) measurements against a reference manifest — [NVIDIA blog, 2 Jul 2026](https://developer.nvidia.com/blog/hardware-rooted-ai-security-that-wont-slow-you-down/) [vendor claim].
  - "The attestation handshake is typically a one-time startup event."
  - On HGX B300 running Qwen3.5-397B-A17B-FP8 with SGLang, throughput fell between 1.0% and 7.5%, depending on concurrency and sequence length.
  - The post does not say the loaded weights are measured into attestation. Weights are protected by releasing "model decryption keys" into the confidential VM after verification.

**Attested inference: platforms**
- **Apple PCC on Google Cloud.** Apple is bringing Private Cloud Compute to Google Cloud, working with Google and NVIDIA [secondary press of Apple's announcement] — [Help Net Security, 10 Jun 2026](https://www.helpnetsecurity.com/2026/06/10/apple-private-cloud-compute-google-cloud-expansion/).
  - It uses NVIDIA Confidential Computing, Intel TDX and Google's Titan chip.
  - Apple keeps a "cryptographically verifiable, append-only ledger" of the hardware. Components require "at least two separate roots of trust from independent vendors". All binaries will be published.
  - apple/security-pcc has 1,334 stars (GitHub API).
- **Google Private AI Compute** (November 2025) uses bi-directional attestation over Noise. It runs on AMD SEV-SNP for CPUs and a "Titanium Intelligence Enclave" for TPUs [secondary press] — [The Hacker News, Nov 2025](https://thehackernews.com/2025/11/google-launches-private-ai-compute.html).
- **Azure.** Confidential inferencing with Azure OpenAI Whisper is still marked "Preview" in a 2026 Confidential Computing Summit deck [search summary; PDF not opened] — [Russinovich, CC Summit 2026](https://hosted-files.sched.co/ccsummit2026/e8/Mark%20Russinovich%20-%20Confidential%20Computing%20Summit%202026%20-%20v2.pdf).
- **Anthropic.** "Confidential Inference via Trusted Virtualization" (18 Jun 2025) is "just a sketch of our research". It uses a trusted loader and a TPM root, with attestation used internally to release keys. It does not describe customer-visible proof of which model served — [Anthropic research](https://www.anthropic.com/research/confidential-inference-trusted-vms).
  - A crypto-news outlet reports an Anthropic Responsible Scaling Policy "moonshot" on "provable inference": signing outputs so they are "attributable to specific model weights". The Phase 1 deadline was moved to 30 Sep 2026 [secondary, unverified; RSP page not opened] — [Forkast, 30 Sep 2026](https://forkast.news/anthropics-provable-inference-deadline-arrived-today-the-company-has-not-said-a-word/).

**Attested inference: startups and open source**
- **Tinfoil, "Modelwrap"** (3 Feb 2026). Weights are hashed in 4 KB blocks into a Merkle root via dm-verity. The root goes on the kernel command line, so "the enclave measurement includes the kernel command line". A block that does not match returns an I/O error.
  - "Once the model is loaded into GPU memory, dm-verity is out of the path."
  - Overheads: about 0.8% extra image size. Cold-cache loading takes "~80% longer". Kimi K2 (554 GB) took 13 m 25 s to build.
  - Anyone can rebuild the root from the same Hugging Face commit — [Tinfoil blog](https://tinfoil.sh/blog/2026-02-03-proving-model-identity).
  - Tinfoil runs "Intel TDX/AMD SEV-SNP with H200/B200 GPUs configured to run in Nvidia Confidential Computing mode". The client SDK compares the attested measurement to one pinned on Sigstore at every connection — [Tinfoil team member FrasiertheLion on HN, 21 Feb 2026](https://news.ycombinator.com/item?id=47105022). The commenter writes "our previous blog"; their exact role is not verified.
  - tinfoilsh/modelwrap is MIT, with 19 stars. tinfoilsh/cvmimage is AGPL-3.0, with 31 stars.
  - Tinfoil is a Y Combinator company. Its Launch HN, titled "Tinfoil (YC P25): Verifiable Privacy for Cloud AI", drew 146 points (15 May 2025, HN API). Listings disagree on the batch name, and no 2026 funding round was found.
- **NEAR AI Cloud.** Clients verify gateway attestation, model-attestation candidates and "a completion's signature after the request" — [NEAR AI verification docs](https://docs.near.ai/cloud/verification). The detail pages were not retrieved (one returned 404).
  - A third-party crate describes the signature as covering `{model}:{sha256(req)}:{sha256(resp)}`, using EIP-191 ECDSA recoverable to the TEE signing address [secondary] — [bitrouter-attestation](https://docs.rs/bitrouter-attestation).
- **Phala/Dstack: Attested Confidential Inference (ACI) v1 draft, Apache-2.0.** It lets a service "prove **what workload is serving its API**". It defines three artifacts: an attestation report, a per-request inference receipt and an attested session for aggregators.
  - A receipt is "a signed, per-request event log" with `request.received`, `request.forwarded`, `upstream.verified` and `response.returned` body hashes, "hashed inside the TEE and signed with an attested receipt key" (ed25519).
  - It is "one self-contained file a client can archive and re-verify offline", but "Receipts are retained for a bounded, implementation-defined period".
  - ACI v1 does **not** define "canonical model identifiers". `model` is "the model id the client asked for" — [ACI spec](https://github.com/Dstack-TEE/private-ai-gateway/blob/main/spec/aci.md).
  - The reference gateway, Dstack-TEE/private-ai-gateway (44 stars, created 19 May 2026), ships a `pap` CLI and says "Use `pap` for coding agents and provider access" — [README](https://github.com/Dstack-TEE/private-ai-gateway).
- **Chutes** offers TEE inference on "Intel TDX and NVIDIA GPUs". It warns: "Do not upgrade a parsed evidence response into a cryptographic attestation claim unless DCAP validation actually ran". Part of its GPU attestation is proprietary [vendor docs, search summary] — [Chutes security architecture](https://chutes.ai/docs/core-concepts/security-architecture).
- **Privatemode (Edgeless Systems).** The app and proxy verify backend attestation before sending data. It runs on AMD SEV-SNP and H100 in an EU data center [vendor, search summary] — [Edgeless press release](https://www.edgeless.systems/press-release-edgeless-systems-to-launch-privatemode-ai).
- **OpenPCC (Confident Security)** is "An open-source framework for verifiably private AI inference" modeled on Apple PCC. openpcc/openpcc is Apache-2.0 with 956 stars; its Show HN drew 433 points (5 Nov 2025, HN API).
- OpenRouter routes some traffic to Phala GPU TEEs [vendor claim, April 2025] — [Phala blog](https://phala.com/posts/GPU-TEEs-is-Alive-on-OpenRouter). I found no OpenRouter-documented attestation filter.

**Receipt formats and drafts**
- **IETF AIR.** draft-tsyrulnikov-rats-attested-inference-receipt-02 (5 Jul 2026, individual, Informational, "not endorsed by the IETF") is a COSE_Sign1 and CWT/EAT profile binding:
  - `model_hash` ("SHA-256 of the model artifact set"), `model_id` and `model_version`;
  - `request_hash` and `response_hash`;
  - `attestation_doc_hash` and enclave measurements (Nitro PCRs, TDX MRTD/RTMR);
  - `policy_version` and `security_mode`.
  - It is "Attester-signed Evidence, not an appraisal verdict".
  - Software-only receipts may be "a signed log of application-layer claims", and such receipts must not be presented as TEE evidence. GPU confidentiality is out of scope — [IETF datatracker](https://datatracker.ietf.org/doc/draft-tsyrulnikov-rats-attested-inference-receipt/).
- **draft-sharif-ai-model-lifecycle-attestation-01** (26 Aug 2026, individual) is "Cryptographic Attestation for AI Model Lifecycle: From Training Data to Inference Output" — [IETF](https://datatracker.ietf.org/doc/html/draft-sharif-ai-model-lifecycle-attestation-01) [search summary].
- **arXiv 2608.00801** (1 Aug 2026): an agent's signed action record "alone cannot answer" whether "a specific model version produced the output on unmodified hardware". It proposes binding a model-artifact measurement in an attested quote. The demo used an emulated TPM — [arXiv](https://arxiv.org/abs/2608.00801).

**Non-TEE verification research**
- **Cai et al. (NeurIPS 2025)** on substitution, including quantization:
  - Text classifiers were "near 50%" at telling quantized from full-precision models.
  - Benchmarks sat within about one standard deviation.
  - Log-probability tests were swamped by nondeterminism across frameworks and GPUs. Greedy-decoding agreement across provider APIs for Gemma-2-9B was "below 5%".
  - The authors recommend GPU confidential computing plus a CPU TEE. On Llama-3-8B with one H100 and vLLM, time to first token rose 9.23–16.18% and throughput fell 2.88–15.38% — [arXiv 2504.04715](https://arxiv.org/html/2504.04715v2).
- **Rank-based uniformity test** (Zhu et al., June 2025) catches a 4-bit Gemma-2-9b substitution with better statistical power — [arXiv 2506.06975](https://arxiv.org/pdf/2506.06975v1) [search summary].
- **TOPLOC** (Prime Intellect) "can detect unauthorized modifications to models, prompts, or precision" with "100% accuracy" in its own evaluations. It needs "only 258 bytes of storage per 32 new tokens" — [arXiv 2501.16007](https://arxiv.org/abs/2501.16007) (v2, 30 May 2025). PrimeIntellect-ai/toploc has 63 stars.
- **zkML.** DeepProve reports "1855 tokens per minute" with distributed proving [paper, search summary] — [IACR ePrint 2026/1112](https://eprint.iacr.org/2026/1112). Lagrange claims working examples on GPT-2 and Gemma-3, with "Llama-class models in progress" [vendor claim] — [Lagrange blog, 3 Jun 2026](https://lagrange.dev/blog/deepprove-is-now-open-source).

### Inferences
- **Ready today for a sidecar.**
  1. Verify OMS signatures where they exist (NGC, Kaggle) and hash files where they do not (Ollama digests, safetensors and GGUF SHA-256).
  2. Record a runtime manifest of the serving stack.
  3. Sign per-request receipts in a format close to AIR or ACI.
  4. Verify third-party attestation and receipts from Tinfoil, NEAR, Phala/Dstack, Chutes and Privatemode, as a client.
- **Not ready.** Proving weights without a TEE (statistical tests are weak, and zk is not at coding-model scale), and binding weights *in GPU memory* to attestation. Even Modelwrap stops at load: "Once the model is loaded into GPU memory, dm-verity is out of the path."
- **The earlier round's "hardware attestation: Later, if ever" is too cautious.** The sidecar need not run TEEs itself. Verifying other parties' attestations and storing their receipts under team keys is cheap and available now.
- **The format slot is open.** ACI explicitly leaves "canonical model identifiers" undefined, and AIR's `model_hash_scheme` is optional. A small open spec for a "weights + runtime manifest" (file digests, the OMS bundle reference, engine and version, parser, template hash, quantization, adapters) is unclaimed. URnetwork could propose it, preferably inside AIR or ACI, not as a rival.

- No primary Hugging Face document confirms or denies Hub-side Sigstore signing of uploads.
- The exact format of NEAR AI response signatures was not read from primary docs (404).
- The status of Anthropic's "provable inference" moonshot was not verified on the RSP page.
- Azure confidential inferencing GA status was not verified from a primary page.
- I found no measurements of how often OMS signatures are verified at load in production.

## Q3. Is there demand for proof of model identity?

### Takeaway
Yes, but the strongest demand concerns **third-party hosts of open-weight models** and **silent model switching in hosted harnesses**, not teams' own servers:
- Moonshot built two vendor verifiers because hosts served Kimi badly. Its own K2 table shows self-hosted vLLM and SGLang well below the official API on tool-call schema accuracy.
- OpenRouter now ranks providers by tool-call telemetry.
- Artificial Analysis found a 13-point AIME spread on gpt-oss-120b across hosts.
- Hacker News threads on the topic drew 310 and 69 points.
- On Claude Code, 19 distinct issue authors reported that the model serving them was not the one selected or shown.

Causes are mostly **runtime, not weights**: engine versions, tool-call parsers, chat templates and decoding parameters. OpenRouter found no measurable effect from quantization alone. Auditors ask for the model version per output, at least in one draft (HITRUST); I found no rule that requires cryptographic proof.

**Model makers and routers**

  - The proof has value for a *third party*: a client, an auditor, or a platform team serving many developers.

K2VV's own table shows self-hosted vLLM at 76% schema accuracy against the official 100%. A receipt that proves "the right weights" alone could certify a badly served model.

## Q4. What would a credible "signed weights receipt" need, and where is the whitespace for the sidecar?

### Takeaway
Existing designs agree on the parts of a credible receipt:
- a canonical digest of the weights (OMS manifest, dm-verity root or `model_hash`);
- request and response hashes over the exact bytes;
- a signer whose key is bound to something verifiable;
- an honest statement of what that binding proves.

Without a TEE, a signature by the server's own sidecar is an operator assertion: in AIR's words, "a signed log of application-layer claims", not proof. HN skeptics and Cai et al. say the same.

The evidence adds runtime identity (engine, parser, template, quantization, adapters) and a conformance check, because these drive quality more than weights do.

The whitespace is not the receipt itself, since ACI, NEAR and AIR exist. It is the **customer-side** part no one ships:
- a verifier and collector that works across self-hosted servers *and* attested providers;
- that keeps receipts beyond the provider's retention, under team keys;
- that links them to agent actions and commits ("which weights wrote this change");
- with trust tiers labeled honestly.

### Cited Findings
- **What existing designs bind:**
  - **ACI receipts:** request-received, forwarded and returned body hashes, the upstream verification result, the keyset digest and an ed25519 signature by an attested key. They are re-verifiable offline but held for "a bounded, implementation-defined period", and ACI leaves "canonical model identifiers" undefined — [ACI spec](https://github.com/Dstack-TEE/private-ai-gateway/blob/main/spec/aci.md).
  - **AIR:** `model_hash`, `model_id`, `model_version`, `request_hash`, `response_hash`, `attestation_doc_hash`, enclave measurements and `policy_version`, in COSE_Sign1 with Ed25519. Software-only use is permitted only as "a signed log of application-layer claims" — [AIR draft-02](https://datatracker.ietf.org/doc/draft-tsyrulnikov-rats-attested-inference-receipt/).
  - **Tinfoil:** the weights' Merkle root sits in the attested kernel command line and is checked on every connection — [Tinfoil](https://tinfoil.sh/blog/2026-02-03-proving-model-identity).
  - **NEAR AI:** a per-response signature from a TEE key [search summary] — [NEAR docs](https://docs.near.ai/cloud/verification).
  - **OMS:** a detached bundle with per-file hashes plus a signature — [NVIDIA](https://developer.nvidia.com/blog/bringing-verifiable-trust-to-ai-models-model-signing-in-ngc).
- **What breaks a weights-only receipt:**
  - Old vLLM commits ignored `reasoning_effort` on Azure — [Willison](https://simonwillison.net/2025/Aug/15/inconsistent-performance/).
  - Tool-call parsers are "the actual culprit" — [OpenRouter](https://openrouter.ai/blog/announcements/auto-exacto/).
  - Decoding parameters were misused — [Kimi](https://www.kimi.com/en/blog/kimi-vendor-verifier).
  - K2VV pins engine versions and a Hugging Face commit, and recommends guided decoding — [K2VV](https://github.com/MoonshotAI/K2-Vendor-Verifier).
  - vLLM's in-memory hashes skip "draft models, and LoRA adapters" — [vLLM](https://docs.vllm.ai/en/latest/training/weight_checker/).
  - KV-cache quantization and kernels change outputs (HN: wongarsu, KeplerBoy — [HN 47098172](https://news.ycombinator.com/item?id=47098172), [HN 47838703](https://news.ycombinator.com/item?id=47838703)).
  - A malicious GGUF can hide insecure-code behavior that full precision does not show — [ICML 2025](https://proceedings.mlr.press/v267/egashira25a.html).
- **Root-of-trust limits:**
  - "the hardware assembles the attestation through mechanisms that it cannot control" (julesdrean, HN).
  - Without one, "what stops an inference provider from giving you a hash of whatever they want" (LoganDark, HN) — [HN 47098172](https://news.ycombinator.com/item?id=47098172).
  - Software-only checks are unreliable, and TEEs give "provable cryptographic guarantees of model integrity with only a modest performance overhead" [authors' claim] — [Cai et al.](https://arxiv.org/html/2504.04715v2).
  - Hardware overhead on Blackwell: −1.0% to −7.5% throughput [vendor claim] — [NVIDIA](https://developer.nvidia.com/blog/hardware-rooted-ai-security-that-wont-slow-you-down/).
- **Gateway logs are mutable and attackable:** read-write SQL access through CVE-2026-42208 permits destroying "audit and usage records" — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-litellm-pre-auth-sqli-20260428/).
- **Coding-agent access to attested providers already exists:** Dstack's `pap` CLI is offered "for coding agents and provider access" — [private-ai-gateway](https://github.com/Dstack-TEE/private-ai-gateway).
- **pitch4's current claims to test:**
  - Model access: "Proves: The sidecar beside the model server signs which weights it serves."
  - The comparison table: "What the record can prove … Also which weights, quantization, and runtime".
  - "Which agents, harnesses, and models, down to the weights, touched which repos" — [pitch4.html](/Users/brien/urnetwork/sidecar/pitch4.html) pages 3 and 4.

### Inferences

**Minimum contents of a credible receipt (synthesis from the designs above)**
1. **Weights identity.** A canonical digest over every file the server loads: safetensors or GGUF shards, tokenizer, config, chat template.
   - If an OMS signature exists, record its bundle digest and the verification result.
   - For quantized derivatives, record the source model's commit and the quantizer's tool and version. The hub does not (HF #4021), and the GGUF attack makes it matter.
2. **Runtime identity.** Engine and exact version or commit, launch arguments (quantization including KV-cache dtype, tensor parallelism, max context), tool-call and reasoning parser, chat-template hash, speculative or draft model, LoRA adapters, and any enforced sampling constraints. Every item maps to a documented cause of provider variance.
3. **Per-request binding.** Requested model, served model, request and response hashes over the exact bytes including SSE framing (as ACI and NEAR do), timestamp, sequence number and the signer's key id. Content stays out; only hashes go in, which fits the vault-and-ledger split.
4. **Trust tier, stated in the receipt.**
   - (a) **Observed**: a hosted provider's own `model` field. No proof.
   - (b) **Operator-signed**: the server-side sidecar's key. It proves what that sidecar saw and that the record was not altered later, not that the operator was honest.
   - (c) **Hardware-attested**: a TEE quote with a weights root such as dm-verity (Modelwrap) or AIR-style measurements. Only (c) can honestly be called "proves which weights".
5. **Conformance evidence.** A periodic canary in the KVV or Exacto style against the reference API or reference outputs, with scores written to the ledger. This turns "right weights" into "served correctly".
6. **Portability.** Encode as COSE_Sign1 (AIR) or an ACI receipt, or wrap as in-toto or SCITT (earlier round). Receipts must verify offline without URnetwork's software.

**Where the whitespace is**
- Gateways (Q1) log model-name strings in operator-readable, mutable stores. Attested-inference providers (Q2) sign receipts but keep them themselves, for bounded periods, per provider, with no link to agent actions. Standards (AIR, ACI, OMS) each cover one piece.
- No product found collects receipts across a team's mixed fleet into a customer-keyed, append-only record linked to agent sessions and commits. The fleet means self-hosted vLLM, SGLang, Ollama or llama.cpp, attested providers and hosted APIs. pitch4's existing ledger is that record. The receipt work is mostly integration and a manifest spec.
- The likeliest closers are Phala/Dstack, if ACI gains a team-side store, Tailscale Aperture, if it adds signing (it already routes to self-hosted servers), and Anthropic, if its "provable inference" work ships for Claude. All are inferences from current offerings, not announced plans.

**Directions for pitch4 (inference)**
- **D1, honest tiers.** Replace "signs which weights it serves" with a tiered claim: "Records which weights and runtime served each call, signed by the server's sidecar; proven by hardware attestation where the server or provider supports it." This keeps credibility with the skeptics quoted above and with AIR's rule against passing software receipts off as TEE evidence.
- **D2, weights plus runtime plus conformance.** Make the receipt cover runtime and a conformance score, and sell it as "your self-hosted model, served as well as the reference", backed by K2VV's self-hosted gap. This is a stronger offer for open-weight teams than identity alone.
- **D3, verified open weights wherever they run.** Widen model access from "only your own servers" to "your servers, plus attested hosts such as Tinfoil, NEAR, Phala/RedPill, Chutes and Privatemode". The sidecar is the verifying client that fails closed and keeps the receipts under team keys.
  - This answers the "11% of spend" and GPU-operations objections: teams get open-weight privacy without running GPUs.
  - It is differentiated because no attested provider keeps a team record, and Dstack's `pap` stops at verification.
- **D4, served-model record for hosted models.** Add "served-model record" across all harnesses, flagging a served model that differs from the configured one (19 Claude Code reporters). It is cheap, honest (tier (a)) and reaches hosted-model teams.
- **D5, beside the gateway.** Position as "the receipt layer beside your gateway", not a gateway. Integrate with LiteLLM, Agent Router or agentgateway callbacks and the Claude apps gateway's OTLP output, and cite gateway-database compromise as the reason receipts must live elsewhere. Do not fight free virtual keys and budgets.
- **D6, weights supply-chain check at load.** Verify OMS signatures, or pin digests and record quantization provenance, before a server may answer agents. Model access stays closed until verification passes. This follows the model-validation-operator pattern and is backed by the GGUF insecure-code attack.
- **D7, propose the manifest spec.** Propose the "weights + runtime manifest" as an open extension to ACI or AIR, not a URnetwork format. Neither defines canonical model identity, so a small contribution could make URnetwork the reference implementation, which supports the "open all the way down" story.

### Gaps
- No evidence yet that auditors or clients accept operator-signed (non-TEE) receipts as evidence. This decides whether tier (b) sells.
- The feasibility and cost of capturing runtime identity from vLLM, SGLang, Ollama and llama.cpp without patching them was not tested. vLLM's weight checker is dev-mode and costly.
- I found no data on how many open-weight coding-agent teams self-host versus use third-party hosts, or which hosts offer attestation to them.
- Interoperability between ACI, NEAR, Tinfoil and AIR receipts, and which one will dominate, is unknown.
