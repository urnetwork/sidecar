## 1. Which formats do SIEMs and auditors ingest or accept today for AI-agent activity?

### Takeaway
No SIEM or security lake documents support for the OCSF releases that carry AI-agent fields (1.8, March 2026) or signed-record fields (1.9, August 2026). Amazon Security Lake caps custom sources at OCSF 1.3. Google SecOps's OCSF parser maps only v1.0.0-rc.3 and v1.1.0 classes. Splunk converts 9 source types to OCSF, none AI-related. Datadog runs 38 OCSF pipelines without stating a version. CrowdStrike converts OCSF to its ECS-based parsing standard. Microsoft Sentinel skips OCSF and instead ships its own GA "Agent Event" schema in ASIM, which has no approval or integrity fields. The OCSF schema itself is moving fast toward agent harnesses: `ai_status` and `ai_capability` landed after 1.9, a Cisco-authored "AI Agent Activity" class is in draft, and one practitioner has mapped about 27,000 live Claude Code and Codex events to OCSF. I found no auditor, framework or regulator that names SCITT or COSE receipts as acceptable evidence; auditors ask for tamper evidence without naming a format.

### Cited Findings
**OCSF itself: when the AI and integrity fields arrived, and what changed after 1.9**
- The AI fields are recent. OCSF 1.8.0 (18 Mar 2026) "Added `ai_operation` profile with essential attributes for AI operation event mapping", plus `ai_model` (`name`, `ai_provider`, `version`) and `message_context` with token counts. OCSF 1.9.0 (3 Aug 2026) added `record_integrity`, `attestation`, `delegation`, `ai_agent`, `prompt_text` and `response_text`. No OCSF release before 1.8 has an AI profile — [OCSF 1.8.0 release](https://github.com/ocsf/ocsf-schema/releases/tag/1.8.0); [OCSF 1.9.0 release](https://github.com/ocsf/ocsf-schema/releases/tag/1.9.0) (GitHub API, 1 Nov 2026)
- On `main` after 1.9, the `ai_operation` profile carries `ai_agent`, `ai_capability`, `ai_model`, `delegation`, `message_context` and `ai_status`. At the 1.9.0 tag it carried only `ai_agent`, `ai_model`, `delegation` and `message_context`. `ai_status` holds "Per-operation outcome scalars for this operation, such as the stop reason and the permission check result". `ai_capability` is "The AI capability invoked in this operation: a tool, resource, or prompt, in the sense of the MCP primitives" — [ai_operation.json on main](https://github.com/ocsf/ocsf-schema/blob/main/profiles/ai_operation.json); [at 1.9.0](https://github.com/ocsf/ocsf-schema/blob/1.9.0/profiles/ai_operation.json) (GitHub API, 1 Nov 2026)
- `record_integrity`: "adds one or more cryptographic attestations over the event itself, providing integrity, authenticity, and non-repudiation independent of any domain-specific content. It is domain-agnostic and may be applied to any event class." Multiple signers of one attestation, "such as a producer plus a co-signature, notary, or witness", go in that attestation's `signatures`. The `attestation` object has `authority_uid`, `chain_uid`, `fingerprint`, `prev_event`, `signatures` and `uid` — [record_integrity.json](https://github.com/ocsf/ocsf-schema/blob/main/profiles/record_integrity.json); [attestation.json](https://github.com/ocsf/ocsf-schema/blob/main/objects/attestation.json)
- `ai_agent` is "An autonomous AI agent that performs tasks under delegated authority. Distinguished from the OCSF agent object (which describes security sensors such as EDR and DLP tools) and from human principals." The `ai_model` object has only `ai_provider`, `name`, `uid` and `version`: there is no weights digest, quantization or serving-runtime field — [ai_agent.json](https://github.com/ocsf/ocsf-schema/blob/main/objects/ai_agent.json); [ai_model.json](https://github.com/ocsf/ocsf-schema/blob/main/objects/ai_model.json)
- No OCSF milestone (and so no 1.10 date) is published — [ocsf-schema milestones](https://github.com/ocsf/ocsf-schema/milestones) (GitHub API, 1 Nov 2026)
- **A practitioner has mapped coding-agent harnesses to OCSF.** Issue #1736 ("Map Agent Harness Behavior to OCSF", opened 20 Aug 2026, open, 6 comments): "I mapped agent harness behavior (Claude Code, Codex) to OCSF and ran it against live traffic for a few days, about 27k events." Choices it asks the schema team to confirm:
  - Prompts as API Activity (6003) with text in `message_context`.
  - Permission-mode changes as Authorize Session (3003) / Assign Privileges.
  - Approvals through the Security Control profile: "Is `disposition_id` `1` (Allowed) vs `8` (Approved) the intended way to separate auto-approved by policy from approved by a human?"
  - Harness telemetry often lacks the host identity that OCSF requires on File System, Process and Script Activity. Claude Code's OTLP resource "reported a hostname on 0 of 7,888 events. Codex managed 3,814 of 19,110."
  - Later comments agree on shell commands as Process Activity Launch/Terminate, joined by a uid derived from the tool-call ID. A denied command is a Launch with action Denied and disposition Blocked, with no Terminate. MCP and remote tool calls are API Activity "Invoke" with the capability in `ai_capability` — [ocsf-schema #1736](https://github.com/ocsf/ocsf-schema/issues/1736) (GitHub API, 1 Nov 2026)
- **A dedicated agent class is in draft.** PR #1754, "[draft] Add `AI Agent Activity` event class" (opened 8 Sep 2026 by `davemcatcisco`; "This is work-in-progress."), adds "AI Agent Stop Information" and "AI Agent Tool Use Information" objects. A reviewer argued that agent actions already representable in OCSF "should be duplicated - because really they're two different things" (a tool-use activity plus the process it creates) — [ocsf-schema #1754](https://github.com/ocsf/ocsf-schema/pull/1754)
- Other open OCSF items in the window: #1755 (`is_final` on `attestation`, "producer-declared end of an append-only chain"), #1741 (`causal_link` / `caused_by` on base_event), #1739 (delegation lineage via `parent_uid`), #1724 ("agent trust-base inventory, applying record_integrity per emission"), #1727 (OTel-based observability categories) — [ocsf-schema issue search](https://github.com/ocsf/ocsf-schema/issues?q=ai+updated%3A%3E2026-08-03) (GitHub API, 1 Nov 2026)

### Inferences
- **"SIEM-ready" has to mean "ingestible today", not "OCSF 1.9".** The common denominator is OCSF 1.1–1.3 core classes: API Activity 6003, Process Activity 1007, Authorize Session 3003, Network Activity 4001, HTTP Activity 4002, plus File System Activity 1001 where the target accepts it. The AI and integrity fields would ride along as extra fields that the lake stores but no vendor content uses. Security Lake's one-class-per-source rule means a sidecar export is about five or six custom sources, not one.
- **Sentinel needs its own path.** ASIM `AgentEvent` is GA and is where Microsoft's agent detections will look. A sidecar would ship an `ASimAgentEvent<vendor><Product>` KQL parser over a custom table, with approvals, coverage and signature references in `AdditionalFields`, because ASIM has no place for them.
- **No SIEM can verify a signed record today.** OCSF `record_integrity` can carry a signature to a lake, but nothing in the six products documents verifying it. Verification stays with the sidecar's own tools and with standard COSE or in-toto verifiers. pitch4 should sell "signed at the source, verifiable offline, exported to your SIEM", not "your SIEM verifies it".
- **The harness telemetry gap is a selling point.** The #1736 numbers (Claude Code hostname on 0 of 7,888 events) show that vendor OTLP alone fails OCSF validation for file and process events. A sidecar on the machine can supply the device identity, the approval decision and the denial-without-execution case that the mapping needs.
- **The schema slot for agent events is still open but filling.** Cisco is drafting the OCSF agent class, Microsoft has ASIM `AgentEvent`, and the AAIF WG's chair is also from Cisco (L1-1.06). Publishing open, tested mappings from six harnesses to OCSF and ASIM, starting from #1736's conventions, is a contribution that could be adopted. A new schema would not be.

- Splunk's and Datadog's OCSF versions are not stated in their docs; I did not find Splunk's OCSF-to-CIM add-on version.
- I did not confirm what Security Lake's Glue crawler does with OCSF 1.8/1.9 attributes in a 1.3-declared custom source (kept as columns or dropped).
- Google SecOps's OCSF page was only partly read (100k of 474k characters); a later section could list more classes.
- No primary source dates Microsoft's ASIM Agent Event launch beyond the 16 Sep 2026 ms.date, and I did not find which first-party sources (Copilot Studio, Foundry) its parsers cover.
- No evidence was found either way on auditors accepting SCITT/COSE receipts.

## 2. Which signed-record and receipt envelopes have implementations and working-group momentum?

### Takeaway
COSE is the IETF-side envelope, and it is the only one built on finished standards. The SCITT RFCs are published, SCRAPI waits in the RFC Editor queue, and the proposed AUDIT charter names SCITT, RATS and vCon as its building blocks. Agent-specific records are another matter. Before the 17 Nov BoF, AUDIT is a charter under heavy debate: about 280 list messages from about 53 senders in September and October, a contested choice between vCon and new formats for interaction records, no posted agenda, and no adopted draft. VACR has not moved since 31 August. DSSE/in-toto has the largest production base through GitHub and Sigstore, but about ten agent predicates sit unmerged, and in-toto maintainers have not engaged on #588. ACI has running code and steady commits but little adoption. AIR has been quiet since July, and the AUDIT charter excludes inference from scope, so model-serving receipts will not come out of AUDIT.

### Inferences
- **COSE wins the signature layer.** Every IETF agent-record candidate (VACR, AAC, draft-gilda's WIMSE variant, AIR) and the AUDIT charter's building blocks (SCITT, RATS) are COSE. Choosing COSE_Sign1 with RFC 9995 hash-envelope payloads for each ledger entry carries little regret: it matches whichever AUDIT data model wins, and the payload can stay content-free.
- **DSSE wins the developer-tooling layer.** GitHub artifact attestations, Sigstore bundles and nono's per-session bundle are DSSE/in-toto. A per-run in-toto Statement (subjects = commit or tree digests) is cheap to derive from the ledger at run end. It should use a URnetwork-namespaced predicate type until one agent predicate merges; none will soon, judging by the empty maintainer engagement on #588.
- **The AUDIT data model will not be settled for at least a year.** No WG exists, the charter is still contested, the vCon base is unfinished, and the list mostly carries small-vendor drafts announcing "running code". The safe position is to emit SCITT-shaped statements now and add whichever AUDIT profile is adopted. pitch4 should not wait for AUDIT, and should not claim AUDIT compliance.
- **The charter's verifiability bar matters for pitch4's design.** "Verifiable by a party that trusts neither the agent nor its operator" is not met by a team-keyed signature alone, because the team is the operator. Meeting it needs an independent log or witness. URnetwork's host-blind relay could co-sign hashes it cannot read (OCSF `record_integrity` and RFC 9942 receipts both carry a witness). This could be a paid "Assured" feature rather than a promise every tier makes.
- **Model receipts have a different home.** AUDIT excludes inference, so the sidecar's "which weights served this call" receipt should copy AIR's field set (COSE/CWT, `model_hash`, request and response hashes) and verify ACI receipts from attested providers. It should label its own software-only receipts as AIR requires (L1-1.05). ACI is the one with momentum (steady commits, a Privatemode upstream). AIR is the one with an IETF shape.

## 5. Recommended composition, and the claims pitch4 can make today

### Takeaway
Build the entry from finished IETF pieces and export into what SIEMs already ingest. Each ledger entry is a small, content-free JSON or CBOR record. It uses OTel GenAI names, is signed as COSE_Sign1 over a hash-envelope payload, and is shaped as a SCITT Signed Statement, with RFC 9942 receipts from a team log and an optional independent witness. Each run also yields a DSSE/in-toto attestation over the commits it produced. The "admins answer" export ships in four dialects: OCSF core classes at 1.1–1.3 level with optional 1.9 AI and integrity fields, a Sentinel ASIM `AgentEvent` parser, OTLP, and JSON for Splunk HEC. Releases get CycloneDX/SPDX attribution mappings, and model calls get AIR-shaped receipts. pitch4 can claim records built on IETF Proposed Standards, verifiable offline with open tools and exportable to six named SIEMs. It cannot claim a standard agent-record format, OCSF 1.9-native SIEM support, SIEM-side signature checks, or any AAIF or IETF endorsement.

**Claims pitch4 can make today (as design statements, since nothing has shipped)**
- Can claim:
  - "Every entry is a signed statement in the IETF SCITT format (RFC 9943, RFC 9942, RFC 9995). Anyone can verify it offline with open-source tools, without URnetwork."
  - "Each run can be exported as an in-toto attestation in a DSSE envelope, the format GitHub artifact attestations use."
  - "Exports to OCSF and OpenTelemetry. It loads into Amazon Security Lake as an OCSF custom source, Google SecOps through its OCSF parser, Microsoft Sentinel through an ASIM Agent Event parser, Splunk through HEC, CrowdStrike through its Security Lake connector, and Datadog through OCSF pipelines." Each item needs a tested mapping before launch.
  - "Records say what they could not see, and record denials as well as approvals."
  - "Release SBOMs in CycloneDX and SPDX that name the AI tool and model per file, built from run-to-commit links."
- Must not claim:
  - "a standard agent audit record", "IETF AUDIT-compliant" or "AAIF-standard" (no WG or adopted draft exists, and the AAIF WG does not write formats);

  - "your SIEM verifies our signatures" (none documents it, and ASIM has no integrity fields);

### Gaps
Open questions for the next level (at most five):
1. What will the 17 Nov AUDIT BoF decide: a WG or not, and is the interaction record vCon-based, VACR or new? This decides the vault's conversation export and whether "AUDIT profile" can enter pitch4 in 2027.

4. Will the AAIF WG take an outside-the-harness capture tool's baselines as comparison evidence, and who will own #40 and #46 once PR #60 is decided? This decides whether the AAIF is a credible distribution route for pitch4 before the end-of-November draft.
