## 1. What does each incumbent record, who can read it, what does it cover, and what does it cost?

### Takeaway
Every incumbent now records per-request or per-session agent activity with a user identity and a model-name string. None records a weights digest. Approvals appear only in fragments:
- GitLab's approve and deny events are stream-only and cover only Duo sessions.
- Aperture's node-provisioning approval happens in a browser flow, not as a record field.
- Prisma AIRS records the delegating user, not per-action approval.

Who can read the records splits by deployment:
- **Self-hosted** (GitLab Self-Managed, Coder, LiteLLM, the Claude apps gateway): the customer's own admins read plaintext rows in the customer's own database. The vendor never sees them.
- **Hosted** (Aperture, Tailscale flow logs and PAM, Cloudflare, Prisma AIRS): the vendor stores the records.

Coverage of laptops and other harnesses has jumped. GitLab 19.5 (15 Oct 2026) pulls Claude Code, Cursor and Codex sessions from developer machines into an AI Governance dashboard (beta, Premium and Ultimate). Coder's AI Gateway can now run standalone, outside its workspaces.

#### Tailscale

**Aperture** (docs "Last validated Oct 1, 2026")
- **Identity.** "Every metric record includes the login name and device ID". For tagged devices, "Aperture sorts the device's tags alphabetically and joins them with commas".
- **Model and headers.** "Aperture extracts the model name from the request body". Upstream auth headers are redacted, but "Other headers, including client-supplied custom headers, remain in plaintext in local captures".
- **Integrity.** The only integrity statement is "Every connection to a tailnet carries cryptographic proof of identity". It concerns who connects, not the records.
- **Readers.** "Users access only their own sessions and usage in the web portal." "Admins can filter organization-wide views by user in the admin dashboard."
- **Not mentioned.** Encryption at rest, signing, attestation and approvals.
- Source: [Tailscale, How Aperture works](https://tailscale.com/docs/aperture/how-aperture-works)

**Aperture GA post** (26 Aug 2026; vendor claims)

**Agent node provisioning through MCP** (search summary)
- The built-in Tailnet connector's `provision_node` tool returns an authorization link. Once the user approves it, the tool returns a single-use auth key.
- Timing: the user must approve within 15 minutes, and the agent must collect the key within 10 minutes of approval.
- "every provisioned node still needs its own approval".
- Setup needs an Owner or Admin to create an OAuth app.
- Sources: [Aperture MCP server proxying](https://tailscale.com/docs/aperture/mcp-server); [Built-in connectors](https://tailscale.com/docs/aperture/connectors/built-in-connectors)

**Network flow logs** (page "Last validated Jan 23, 2026")
- **Plans.** "This feature is available for the Premium and Enterprise plans." "Only nodes using Tailscale v1.34 or later can send networking telemetry to the Tailscale logs service."
- **Fields.** Each message has `nodeId`, `logged`, `start`, `end`, `srcNode`, `dstNodes`, `virtualTraffic`, `subnetTraffic`, `exitTraffic` and `physicalTraffic`. Traffic counters carry protocol, source and destination address:port, and packet and byte counts. Node objects carry name, addresses, OS, user and tags.
- **Identity.** The `user` field "is not populated if the node is tagged". "The user authenticated on a source or destination host is not logged."
- **Content.** "Tailscale does not log the actual contents or data of the network traffic."
- **Integrity.** "Tailscale cannot guarantee the delivery or integrity of the client logs." "It is possible for malicious nodes to spoof this information." Only the NodeID is verified by the logs service.
- **Generation.** "Network logging is performed client-side." "Tailscale only logs successful connects."
- **Storage and readers.** "Network flow logs are available for the most recent 30 days." "Tailscale centrally stores network logs and lets you export them." Readers are Owner, Admin, Network admin or IT admin. Logs can be streamed to a SIEM.
- Source: [Tailscale, Network flow logs](https://tailscale.com/kb/1219/network-flow-logs)

**Codex Cloud as tagged nodes** (6 Oct 2026)
- OpenAI's setup uses a Reusable and Ephemeral auth key. The post recommends tagging it `tag:codex` so each VM gets the tag's rules, not the key creator's access.
- Flow logs (Premium, Enterprise) are the way to see what agents reach. Device approval applies to devices "if they are not associated with an auth key".
- Cursor is not mentioned.
- Source: [Tailscale blog, Codex Cloud](https://tailscale.com/blog/codex-cloud-tailscale)

## 2. Does any incumbent sign per-request or per-action records, bind them to approvals or to the weights served, or keep them under keys only the customer holds?

### Takeaway
No. None of the seven documents signing, hash-chaining or external anchoring of agent-activity records. None binds a record to the weights served. None binds a person's approval to the action it allowed in a signed record. The only customer-key mechanisms are:
- Cloudflare's per-log encryption of *exports* to the customer's RSA key;
- Prisma AIRS's rotatable keys over scan data (ownership not stated);
- Portkey's hybrid bring-your-own-KMS mode (earlier round);
- Anthropic's CMEK, which the vendor uses (earlier round).

In all of them the vendor or operator still processes plaintext. The integrity-related signals that do exist are internal or weak:
- Anthropic signs its internal token traffic and checks outputs against specific weights, but only inside Anthropic.
- GitLab offers an "immutable copy" download.
- The Claude apps gateway hashes its config file.
- Tailscale disclaims the integrity of flow logs outright.

A record whose content the operator's admins cannot read without the developer, whose integrity a third party can check, and which joins approval, action, reach grant and served model into one entry across harnesses.

### Gaps

## 4. Does Tailscale welcome tsnet-based partners, and should reach be built, run over Tailscale, or dropped from the first release?

### Takeaway
Tailscale openly invites products to embed it:
- tsnet "any app ... as its own node";
- a Tailnets API pitched for "one tailnet per customer";
- tailcat, which uses its data plane without its control plane;
- the line "Whether you're building with Tailscale, on it, or both".

It welcomed Codex's integration even though there was no partnership agreement. It has a general Technology Partners track, but no tsnet, OEM or ISV program. The Tailnets API is alpha and limited.

Its own records cannot say which agent run reached what, or on whose approval. So the evidence favours running reach over the customer's Tailscale (or Headscale, tailcat or iroh) and selling the signed, run-bound reach receipt, not building a new overlay. The receipt is what Tailscale lacks.

## 5. What this means for pitch4's "Ours" and "No one" rows and the "why the gap stays open" argument

### Takeaway
pitch4's core rows survive, but only in narrower wording:
- **"A record of agent work you can read and we cannot: No one."** True only for hosted services. Self-hosted GitLab, Coder, LiteLLM and the Claude apps gateway already keep records their vendors cannot read.
- **"Vendor record of agent work: Each vendor's, for its own product."** No longer accurate: GitLab records three other vendors' agents.
- **"Why the gap stays open."** Its incentive story misses GitLab. GitLab is neither harness owner nor gateway, and earns by being the system of record for every harness.

The defensible claims are the ones none of the seven makes:
1. Signed and verifiable without trusting the operator, including against a compromised gateway or database.
2. Developer-private content under separate keys.
3. Approval, action, reach grant and served model bound per run across harnesses.
4. Weights and runtime receipts for self-hosted open weights.

### Cited Findings
- **pitch4 lines tested:**
  - "Vendor record of agent work: Each vendor's, for its own product / None, so the record is the one you keep".
  - "Anthropic's Compliance API and OpenAI's compliance logs cover their own products."
  - "Proves: The sidecar beside the model server signs which weights it serves."
  - "A record of agent work you can read and we cannot: No one. Harness vendors bind it to their runtime; gateways and recorders read it. / Ours."
  - "Sessions and actions under separate keys ... Ours."
  - "Why the gap stays open: harness owners earn when work stays on their runtime, and gateway and recorder vendors are built on reading the data. ... Tailscale's and Cloudflare's roadmaps are the first to watch."
  - Source: [pitch4.html](/Users/brien/urnetwork/sidecar/pitch4.html)
- **GitLab records three other vendors' harnesses:** "connect Externally Connected Agents (ECAs) like Claude Code, Cursor, and Codex to GitLab AI Governance" — [19.5 release notes](https://docs.gitlab.com/releases/19/gitlab-19-5-released/)
- **Self-hosted incumbents keep records away from their vendor:**
  - "The gateway's own data plane sends nothing to Anthropic infrastructure unless the Anthropic API is a configured upstream" — [Claude apps gateway](https://code.claude.com/docs/en/claude-apps-gateway).
  - Coder writes records to the customer's own deployment database (earlier round) — [Coder setup](https://coder.com/docs/ai-coder/ai-gateway/setup).
  - Duo Self-Hosted AI logs stay in the installation (search summary) — [GitLab docs](https://docs.gitlab.com/administration/gitlab_duo_self_hosted/logging).
- **None documents record signing, approval binding or weights binding** (Q2 sources).
- **Tailscale's records disclaim integrity** — [Network flow logs](https://tailscale.com/kb/1219/network-flow-logs).
- **Anthropic verifies weights only internally** — [RSP roadmap](https://www.anthropic.com/responsible-scaling-policy/roadmap).

### Inferences (directions for pitch4)
1. **Rewrite the "No one" row** (differentiation; high confidence). Suggested wording: "Signed, append-only, and readable by the developer and team only — not by us, and not silently rewritable by an admin or a compromised gateway." Concede that self-hosted platforms (GitLab, Coder, LiteLLM) already keep records their vendors cannot read.
2. **Change the "Vendor record" row and the watch list** (differentiation; high).
   - Hosted column: "GitLab now records Claude Code, Cursor and Codex sessions (beta); harness vendors record their own."
   - Watch list: lead with GitLab AI Governance and Coder's standalone gateway, then Tailscale and Anthropic. Cloudflare's 2026 AI Gateway work is identity and analytics.
   - Restate the incentive argument as: "platforms that hold the record also administer it, so none has a reason to make it unreadable to admins or verifiable by outsiders."
3. **Make approval binding the lead security claim** (differentiation; high). No incumbent records who approved which action under which grant in a durable, verifiable entry; GitLab's approve and deny events are stream-only and cover Duo only. "Every allow has a name, a grant and a run" is concrete and testable.
4. **Feed incumbents instead of replacing them** (offering; medium). Emit signed entries as GitLab audit events (ECA source), LiteLLM callbacks, Coder structured logs and OCSF or OTLP. Sell verification ("prove this record was not altered since it was written") as the paid layer. That avoids competing with $29 GitLab Premium bundles and free LiteLLM.
