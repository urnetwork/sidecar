# WebGPU puts Gemma on desktops, not phones

As of November 2026 a web page can run a local language model only by bringing its own engine onto WebGPU, and for URnetwork that engine is LiteRT-LM's JavaScript SDK. It is the only engine that loads the same Gemma 4 `.litertlm` files the apps use, and a static scan of its package shows it fits the key origin's CSP as written: it needs no `eval`, no `blob:` worker and no SharedArrayBuffer, provided its wasm and the model are served from `sidecar.ur.io` and it runs in a classic Worker. What does not carry over is reach. Google says Gemma 4 E2B "requires around 4GB of free ram when running in the browser, and it won't work on iOS" ([LiteRT-LM #2368](https://github.com/google-ai-edge/LiteRT-LM/issues/2368)); iPhone tabs are killed at about 2 GiB, about 94% of Snapdragon Adreno 7xx phones cap a GPU buffer binding at 128 MiB, and Firefox's WebGPU decodes at 1–10 tokens per second. That leaves desktop Chrome, Edge and Safari on macOS Tahoe with several gigabytes of free GPU or unified memory, decoding at about 45% of native speed (73 against 160 tokens/s for E2B on an M4 Max). The apps' safeguards do not carry over either. Their SHA-256 check must be rebuilt as an incremental hash, since WebCrypto cannot stream, `fetch` integrity buffers the whole body, and LiteRT-LM's web `hf://` check compares Hugging Face's metadata rather than the bytes. Chromium refuses `persist()` to the framed key origin, so its storage stays evictable and a 2–4 GB model would share one eviction unit with every network's keychain. No shipped browser feature verifies that the served loader, Worker or engine matches the signed release. Browser-provided models are no substitute: Chrome's Prompt API is desktop-only, callable only from a window, unversioned and without tool calling, and Mozilla and WebKit oppose it. The strongest move for the design is to let the page reach a model outside itself, on a device that already runs the native engine with its pins and sandbox. Every page user has such a device, because a consented device must admit the page Worker. In-page LiteRT-LM can follow as a capability-gated desktop tier, in a Worker that holds no keys.

The table sets each of the apps' practices beside its web counterpart; the sections that follow give the evidence.

| The apps today | On the web | What breaks |
|---|---|---|
| LiteRT-LM's native engine (C API, Kotlin or Swift) | `@litert-lm/core` 0.20.0, labeled "early preview", WebGPU only | single-threaded wasm; a classic Worker; no JSON-schema constraint or `tool_choice` |
| Gemma 4 E2B or E4B, 2.3–3.7 GB, on phones and desktops | the `-gpu.litertlm` files, 2.34 and 3.31 GB, on desktops | iPhones and most Android phones cannot hold them; decode at about 45% of native |
| each file's SHA-256 checked before load | an incremental hash the page computes itself | no streaming WebCrypto digest; `fetch` integrity buffers 2–4 GB |
| files in the app's own storage | origin storage the browser evicts whole | `persist()` refused to the frame in Chromium; keychains evicted with the model |
| a signed binary | code served by `sidecar.ur.io` | no browser verifies served code (the design's EX7) |
| on desktop, a confined `ur-engine` helper with no keys and no network | a sibling Worker with no keys and `connect-src 'self'` | the same renderer process; a GPU process shared with every tab |
| a foreground app | a tab that browsers freeze, discard or suspend | long jobs must checkpoint and resume |

## WebGPU reaches about 85% of browsers, but memory decides who can run a model

WebGPU is the only accelerator a page can count on. WebNN, the API that would reach NPUs, has shipped nowhere. Chrome disabled its origin trial on 2026-03-27 over "more release blocking issues", and in May its owner asked for the trial to be removed. Edge's trial has closed, and WebKit has taken no position ([blink-dev](http://www.mail-archive.com/blink-dev@chromium.org/msg16537.html); [Chrome Status](https://chromestatus.com/feature/5176273954144256); [WebKit #486](https://github.com/WebKit/standards-positions/issues/486)). WebGPU is on by default for **86.83% of global browser usage plus 3.32% partial**, by caniuse's count of 2026-11-24. Web3D Survey's probes found a working adapter in **82.89%** of reports, but only **69.8% on Android, 18.03% on Linux and 59.16% in Firefox** ([caniuse](https://caniuse.com/webgpu); [Web3D Survey](https://web3dsurvey.com/webgpu)). Whether a device qualifies depends more on its GPU vendor and OS version than on its browser.

| Browser and OS | WebGPU on by default | Excluded or limited | Fit for a multi-GB model |
|---|---|---|---|
| Chrome and Edge, Windows x64 | since 113 (May 2023), on D3D12 | D3D11-only adapters; vendors other than AMD, Intel, Microsoft and NVIDIA | yes, VRAM permitting |
| Chrome and Edge, macOS | since 113 | CPU adapters | yes on Apple Silicon |
| Chrome and Edge, Linux | Intel Gen12+ with Mesa 22+ (144); NVIDIA 535.183.01+ on Wayland (147) | AMD and older Intel need flags | a narrow slice |
| Chrome, Android | 121, on Android 12+ with Qualcomm, ARM or Intel GPUs; Imagination from Android 16 (139) | Samsung Xclipse "planned, date TBD"; Android below 12 | small models; most Adreno 7xx bind at most 128 MiB |
| Safari, macOS | 26, only on macOS 26 Tahoe or later | older macOS (Sequoia, Sonoma) | yes on Tahoe |
| every browser on iOS and iPadOS (WebKit) | 26 | 1 GiB per buffer; about 2 GiB per tab process | models of about 0.4 GB or less |
| Firefox, Windows and Apple Silicon macOS | 141 on Windows; 145 on Tahoe and 147 on all macOS | no `shader-f16` in MDN's data; Intel Macs in Nightly only | no: about 1 ms per dispatch |
| Firefox, Linux and Android | Nightly or a flag only | — | no |

Sources: [gpuweb implementation status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status); [Chromium WebGPU blocklist](https://github.com/chromium/chromium/blob/main/gpu/config/webgpu_blocklist_impl.cc); [caniuse](https://caniuse.com/webgpu); [MDN compatibility data](https://unpkg.com/@mdn/browser-compat-data/data.json). Two points are contested. For Windows on Arm, the gpuweb wiki says WebGPU needs a flag, while Chromium's main branch enables it by default for one Adreno part with a recent driver. For Firefox, MDN lists no `shader-f16`, while Web3D Survey reports it on 93.7% of Firefox adapters ([Web3D Survey](https://web3dsurvey.com/webgpu/features/shader-f16)).

The key origin's layout gets WebGPU without help from ur.io. The spec exposes `navigator.gpu` to windows and workers in secure contexts and defines no Permissions-Policy feature. The dedicated Worker inside the `sidecar.ur.io` frame therefore needs no `allow=` attribute and no COOP or COEP ([WebGPU spec source](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)). Dedicated workers have WebGPU in every browser that ships it, and Chrome added service and shared workers in 124 ([Chrome 124](https://developer.chrome.com/blog/new-in-webgpu-124)). The missing cross-origin isolation matters elsewhere. Without it there is no SharedArrayBuffer, so wasm runs single-threaded in every browser. Chromium's Document-Isolation-Policy (desktop 137, Android 146) would let the frame isolate itself without ur.io sending anything. Safari supports neither that policy nor COEP `credentialless`, so threads there need ur.io itself to send COOP and `require-corp` ([MDN compatibility data](https://unpkg.com/@mdn/browser-compat-data/data.json); [DIP explainer](https://github.com/WICG/document-isolation-policy)). For language models this makes the web **GPU or nothing**. LiteRT-LM's shipped web builds are single-threaded whatever the isolation, and its CPU path took **3.4–5.2 seconds to embed one 440-token text** with a 270M-parameter model, with thread settings making no difference ([LiteRT-LM #4786](https://github.com/google-ai-edge/LiteRT-LM/issues/4786)).

Adapter limits break models that fit in RAM. The limit that matters for weight tensors, `maxStorageBufferBindingSize`, is at least 2 GiB on 99% of Windows reports. It sits at the 128 MiB floor on about **94% of Snapdragon Adreno 7xx phones**, the most common modern Android class ([Web3D Survey limits](https://web3dsurvey.com/webgpu/limits/maxStorageBufferBindingSize)). WebKit's code caps every buffer on iOS at **1 GiB** whatever the RAM ([WebKit HardwareCapabilities.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm)). Exceeding a limit need not raise an error. On an Adreno 750, LiteRT-LM bound a 148 MiB embedding table as one buffer: "Dawn rejects the bind group and engine creation continues with no error", and the model produced garbage ([LiteRT-LM #3866](https://github.com/google-ai-edge/LiteRT-LM/issues/3866)). Half-precision shaders (`shader-f16`) are present on only 28% of Adreno 6xx reports. Subgroups reach Safari only in the 27.3 beta of 2026-11-16 ([Web3D Survey shader-f16](https://web3dsurvey.com/webgpu/features/shader-f16); [Safari 27.3 beta notes](https://developer.apple.com/documentation/safari-release-notes/safari-27_3-release-notes)).

Process memory decides the rest, and iOS is the hard wall. System logs from an iPhone 17 Pro on iOS 26.5 show Safari's WebContent process killed at an **"ActiveHard" limit of 2,097,154 KiB**, about 2 GiB, with the same limit in Worker mode. An 805 MB model died while loading until the loader stopped holding two copies of it ([llama-web-bridge #257](https://github.com/leehack/llama-web-bridge/issues/257)), and Transformers.js on an iPhone 16 Pro Max hit the same 2048 MB limit ([transformers.js #1827](https://github.com/huggingface/transformers.js/issues/1827)). Moving the model into a Worker buys nothing, because the Worker counts against the same process. GPU timeouts add a second constraint. Windows resets a GPU that fails to respond within its 2-second default TDR, and Chromium has its own watchdog ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys); [Corentin Wallez](https://lists.w3.org/Archives/Public/public-webapps-github/2021Dec/0233.html)). A Transformers.js issue quotes WebKit arming a 3-second watchdog per committed command buffer on iOS ([transformers.js #1836](https://github.com/huggingface/transformers.js/issues/1836)). Every forward pass, long prefills included, therefore has to be split.

A privacy product meets one more gap: hardened browsing turns the platform off. Apple's Lockdown Mode explicitly disables WebGPU, and a WebKit bug filed against iOS 17.4, still unresolved at its last update, says it blocks WebAssembly even for sites the person exempts ([WebKit commit](https://lists.webkit.org/pipermail/webkit-changes/2024-May/301532.html); [WebKit bug 273824](https://bugs.webkit.org/show_bug.cgi?id=273824)). Chromium's main branch enables a feature that blocks WebGPU under Android Advanced Protection, and Edge is testing a Lockdown Mode that blocks WebGPU ([gpu_finch_features.cc](https://github.com/chromium/chromium/blob/main/gpu/config/gpu_finch_features.cc); [BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-tests-new-edge-lockdown-mode-that-disables-gpu-apis/)). Chrome's enterprise JIT policy "may also disable parts of JavaScript including WebAssembly" ([Chrome policy](https://github.com/chromium/chromium/blob/main/components/policy/resources/templates/policy_definitions/ContentSettings/DefaultJavaScriptJitSetting.yaml)). Sidecar's users probably turn these modes on more often than most, and under Lockdown Mode `sidecar.wasm` itself may not load. Eligibility therefore belongs at run time. If `requestAdapter()` resolves to `null` or a fallback adapter, there is no local model. Only two browser identities are worth acting on: Firefox, whose adapters work at unusable speed, and WebKit on iOS, whose memory ceiling no adapter limit reveals.

## Browsers decode at about 45% of native speed, and phones hold only half-gigabyte models

Google publishes the only vendor numbers for Gemma 4 in a browser, all from an M4 Max MacBook Pro. LiteRT-LM's web build of E2B, the 2,341 MB `gemma-4-E2B-it-gpu.litertlm`, prefills at **4,853 tokens/s and decodes at 73 tokens/s, with a 1.09 s time to first token**, using about 1.8 GB of GPU memory. Native LiteRT-LM on the same GPU does 7,835 and **160.2**, with 0.1 s ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)). E4B on the web does 1,590 and **44** against 2,560 and **101.1** natively, using about 3.3 GB ([E4B card](https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm)). The browser thus keeps about 45% of native decode and 62% of native prefill. It still decodes 1.6–1.75 times faster than LiteRT-LM's native CPU path on the same machine. Most of the web's time to first token is fixed overhead: prefilling the benchmark's 1,024 tokens at 4,853 tokens/s takes about 0.2 s of the 1.09 s. Discrete GPUs do better; an RX 7900 XT in Edge 158 decodes E2B at **118 tokens/s** ([LiteRT-LM #4784](https://github.com/google-ai-edge/LiteRT-LM/issues/4784)).

The overhead lies in dispatching GPU work, and it explains the spread between browsers. A February 2026 study measured each sequential compute dispatch at 32.8–66.5 µs in Chrome and 31.7 µs in Safari, but about **1,040 µs in Firefox on every platform**, "consistent with rate-limiting". In short runs, WebLLM then decoded Qwen2.5-0.5B at 46.4 tokens/s in Chrome on an M2 and at 9.6 in Firefox ([arXiv 2604.02344](https://arxiv.org/html/2604.02344v1)). The author's follow-up concludes that at batch size 1 the number of dispatches, not kernel quality, is the bottleneck ([arXiv 2608.08730](https://arxiv.org/abs/2608.08730)). That is why 0.5B and 1.5B models decode at similar speeds, and why for small models the engine matters more than the parameter count. Safari's gap depends on the engine. On an M3, llama.cpp's WebGPU backend decoded at 47.4 tokens/s in Chrome and 25.6 in Safari, and WebLLM at 42.1 and 40.3. Transformers.js crashed in Safari as its memory grew ([WebKit bug 311598](https://bugs.webkit.org/show_bug.cgi?id=311598)).

Phones collapse on both speed and size. The one cross-device study ran llama.cpp's WebGPU backend on 16 GPUs from 8 vendors. It put the iPhone 17 Pro Max, the iPhone 15, Adreno 7xx, Mali and PowerVR in a low cluster that decodes at **4–17 tokens/s** and fits only its four smallest models, files of **0.23–0.40 GB**. Mali and PowerVR devices crashed at a 2,048-token KV depth, and Gemma 4 E2B "did not run on an iPhone with a tight tab-memory cap" ([Llamas on the Web](https://arxiv.org/html/2605.20706v1)). Natively, the same E2B model decodes at 52 tokens/s on a Galaxy S26 Ultra GPU and 56.5 on an iPhone 17 Pro ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)). By this rough, not like-for-like comparison, the browser cuts the largest model a phone can load about sixfold, on top of most of its speed. Vendor-specific code paths still matter. A Pixel 10 Pro's PowerVR GPU generated 2.5 tokens/s through stock WebGPU, slower than its CPU, and 38 after a vendor-specific rewrite ([wllama #307](https://github.com/ngxson/wllama/issues/307)). Android flagships are the gray zone: Google ran E2B in its web demo on a Pixel 9, "although native performance is better" ([LiteRT-LM #2368](https://github.com/google-ai-edge/LiteRT-LM/issues/2368)). Sustained use cuts further. Natively, an iPhone 16 Pro lost nearly half its throughput within two iterations, and a Galaxy S24 Ultra hit an OS-enforced GPU frequency floor that ended inference; no study measures this in a browser ([arXiv 2603.23640](https://arxiv.org/abs/2603.23640)).

On desktops the cliff is dedicated VRAM. In one practitioner's test on a 6 GB RTX 3050 laptop, E4B spilled into shared memory and fell to about **1.8 tokens/s**. The same report notes that Chrome can route WebGPU to the integrated GPU on NVIDIA Optimus laptops ([DEV Community](https://dev.to/jpablortiz96/5-production-patterns-for-running-gemma-4-in-the-browser-what-the-docs-dont-tell-you-2ai1)). No API reports free GPU memory. Adapter heap sizes sit behind a developer flag, and `navigator.deviceMemory` is Chromium-only and saturates at 8 on Android ([Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121); [blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/vXtAmrVZeDk)). The tiers below therefore combine coarse signals with a probe, which loads the tier's model, times a fixed prefill and about 32 decoded tokens, and persists the result and any reload. They are a synthesis of the measurements above, not a published recommendation.

| Device class | Evidence | Default local model |
|---|---|---|
| Desktop high: Chrome or Edge (or Safari 26+ on Tahoe, unmeasured) on M3–M5 with 16 GB or more, or a dGPU with 8 GB+ | E2B 73–118 tokens/s; E4B 44 tokens/s | Gemma 4 E4B (`-gpu`, 3.31 GB), or E2B where latency matters |
| Desktop mid: 8 GB Macs, Intel or AMD integrated GPUs, dGPUs of 6 GB or less | an M2 in Chrome at 36–46 tokens/s on 0.5–1.5B models; E4B spills at 6 GB | Gemma 4 E2B (`-gpu`, 2.34 GB) at 4–8K context, after a probe |
| Android flagship: Chrome 121+, `shader-f16`, bindings of 512 MiB or more | the Galaxy S24 in the study's mid cluster; E2B ran on a Pixel 9 | 0.6–1.7B models at 2–4K context; E2B only after a probe |
| Android mid and low: most Adreno 6xx and 7xx, Mali, PowerVR | 4–17 tokens/s; 0.40 GB or less; crashes at a 2K KV depth | models of 0.4 GB or less at 2K context or less, or none |
| iPhone and iPad, any browser | about 2 GiB per tab; E2B "won't work on iOS" | models of 0.4 GB or less at 0.5–2K context, or the native app |
| Firefox, any device | 1–10 tokens/s | none |

Inside a tier, model choice turns on tool use and memory. Vendor-reported agentic scores fall steeply below 2B. Qwen3.5-4B reports BFCL-V4 50.3 and TAU2-Bench 79.9, Qwen3.5-2B reports 43.6 and 48.8, and Qwen3.5-0.8B 25.3 and 11.6 ([Qwen3.5-4B card](https://huggingface.co/Qwen/Qwen3.5-4B); [Qwen3.5-2B card](https://huggingface.co/Qwen/Qwen3.5-2B)). Gemma 4 reports Tau2 averages of **24.5% for E2B and 42.2% for E4B** ([Gemma 4 model card](https://gemma.ai/models/gemma-4/model-card/)). The harnesses differ, so these numbers rank models only loosely. Even so, the phone tier is fit for classification, extraction and short rewrites, not for agent loops. Gemma 4's architecture is unusually frugal for long contexts under browser ceilings. Its 512-token sliding window and shared KV layers keep E2B's KV cache to about **30 MiB at 4K tokens and 200 MiB at 32K**, by arithmetic on its published config. Dense Qwen3-4B needs about 576 MiB and 4.5 GiB ([Gemma 4 E2B config](https://huggingface.co/unsloth/gemma-4-E2B-it/blob/main/config.json); [Qwen3-4B config](https://huggingface.co/Qwen/Qwen3-4B/blob/main/config.json)). The saving holds only in an engine that implements the window; WebLLM's Gemma 3 1B record sets `sliding_window_size: -1` ([web-llm config.ts](https://raw.githubusercontent.com/mlc-ai/web-llm/main/src/config.ts)).

The download dominates the first visit. At May 2026's global median mobile speed of 113 Mbps, E2B's 2.34 GB file takes about 2.8 minutes and E4B's 3.31 GB about 3.9; at 25 Mbps they take 12.5 and 17.7 minutes ([Statista](https://www.statista.com/statistics/896779/average-internet-connection-speed-worldwide/)). Kernel compilation adds 1–5 seconds to the first forward pass ([Llamas on the Web](https://arxiv.org/html/2605.20706v1)). No source measures load time from a warm cache, and Google's time-to-first-token figures exclude loading.

## LiteRT-LM is the one engine that runs the apps' files and fits the CSP

Five engines run language models inside a page or Worker today. Their npm tarballs were scanned on 2026-11-25 for the code paths a CSP cares about, which shows what each statically contains rather than what fires at run time. Popularity and fit point in opposite directions. ONNX Runtime Web and Transformers.js drew 8.06 million and 4.55 million downloads that week, against 194,909 for WebLLM and 24,630 for `@litert-lm/core` ([npm](https://registry.npmjs.org/@litert-lm/core)). Yet one of the least used fits sidecar best.

| Engine (latest) | Runs the apps' Gemma 4 files | Fit under the key origin's CSP | Tools and constraints | Main risk |
|---|---|---|---|---|
| LiteRT-LM JS `@litert-lm/core` 0.20.0 (2026-11-23), "early preview" | yes: `.litertlm`, with `-gpu` builds for the web | fits: no `eval`, no `blob:` workers, single-threaded; self-host the wasm; a classic Worker until a packaging fix ships | OpenAI-like messages and `tool_calls`, `clone()`, image and audio input; a tool-syntax constraint only | open faults in cancel and device loss; broken npm releases |
| Transformers.js 4.3.2 on ONNX Runtime Web 1.31.1 | different files: onnx-community's Gemma 4 E2B q4f16, 3.38 GB | fits if `wasmPaths` is self-hosted and `useWasmCache` is off; the WebGPU glue holds an embind `new Function` to test | tools rendered into templates, parsing left to the app; experimental structured output | ORT's GitHub repository returned 404 on 2026-11-25 |
| WebLLM 0.2.89 (2026-11-17) | different files: MLC's Gemma 4 E2B only, plus a compiled model library | fits if model libraries and weights are self-hosted | JSON schema through XGrammar; tools only for five Hermes builds | model libraries are executable code |
| wllama 4.0.0 (2026-11-22), llama.cpp | GGUF | **does not fit**: always starts its worker from a `blob:` URL | the fullest OpenAI feature set | effectively one maintainer |
| MediaPipe `tasks-genai` 0.10.30 | `-web.task` | fits; works in module workers | no chat, tool or constraint API | maintenance mode; requires `shader-f16` and about 500 MB bindings |

Sources: npm tarballs of [@litert-lm/core](https://registry.npmjs.org/@litert-lm/core/-/core-0.20.0.tgz), [@huggingface/transformers](https://registry.npmjs.org/@huggingface/transformers/-/transformers-4.3.2.tgz), [onnxruntime-web](https://registry.npmjs.org/onnxruntime-web/-/onnxruntime-web-1.31.1.tgz), [@mlc-ai/web-llm](https://registry.npmjs.org/@mlc-ai/web-llm/-/web-llm-0.2.89.tgz), [@wllama/wllama](https://registry.npmjs.org/@wllama/wllama/-/wllama-4.0.0.tgz) and [@mediapipe/tasks-genai](https://registry.npmjs.org/@mediapipe/tasks-genai/-/tasks-genai-0.10.30.tgz); [microsoft/onnxruntime](https://github.com/microsoft/onnxruntime).

One rule decides most of the fit. With no `worker-src` or `child-src`, worker creation falls back to `script-src`, then `default-src` ([MDN worker-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/worker-src)). `script-src 'self' 'wasm-unsafe-eval'` therefore allows same-origin workers, `importScripts`, dynamic `import()` and wasm compilation, and blocks `blob:` and `data:` workers and any `eval` that runs. wllama 4.0.0 always constructs its worker as `new Worker(URL.createObjectURL(new Blob([workerCode])))`, so it cannot run without a fork. Transformers.js fetches ONNX Runtime's wasm from jsDelivr by default and, with its wasm cache on, turns ORT's factory script into a `blob:` URL. ORT's WebGPU glue also contains embind's `new Function` caller. One project enforcing `script-src 'self' 'wasm-unsafe-eval'` saw no violation while a model ran on WebGPU, but that is a single report, not a vendor statement ([QSMPC #70](https://github.com/Quantum-Daemons/QSMPC-QKD-QHE-AI-Hybrid/issues/70)). WebLLM evaluates no strings as code but downloads each model's compiled library from `raw.githubusercontent.com`. Four of the five default to a third-party host, and all can be pointed at self-hosted copies. WebGPU, OPFS, the Cache API and IndexedDB lie outside CSP's reach; only the downloads pass through `connect-src`.

LiteRT-LM fits with the least change. Its glue contains no `eval` or `new Function`, its shipped builds contain no pthread or SharedArrayBuffer code, and `loadLiteRtLm('/v1/…/wasm/')` replaces its jsDelivr default ([@litert-lm/core 0.20.0](https://registry.npmjs.org/@litert-lm/core/-/core-0.20.0.tgz)). Its source already probes whether a SharedArrayBuffer can be posted, so a threaded build may follow ([wasm_feature_detect.ts](https://github.com/google-ai-edge/LiteRT-LM/blob/main/js/packages/core/src/wasm_feature_detect.ts)); that build would need the cross-origin isolation the frame lacks. The loader picks one of four wasm builds by feature test. The JSPI build with relaxed SIMD is **22.60 MB (7.13 MB gzipped)**. The Asyncify build, **34.75 MB (10.10 MB gzipped)**, was added after the JSPI-only build failed on iOS Safari ([LiteRT-LM #2616](https://github.com/google-ai-edge/LiteRT-LM/issues/2616)). One condition remains. The engine loads its glue with `importScripts`, which module workers expose but refuse ("Module scripts don't support importScripts()"). The upstream fix is not in `@litertjs/wasm-utils` 2.6.0, the newest on npm, so for now the engine must run in a **classic Worker** ([LiteRT-LM #4080](https://github.com/google-ai-edge/LiteRT-LM/issues/4080)). It is also the only engine that runs the apps' artifacts, though not every file of them. The E2B card, updated 2026-11-20, says "Web on LiteRT-LM uses a specially optimized model (gemma-4-E2B-it-gpu.litertlm)": the 2.34 GB `-gpu` file, which supports up to 128K context, rather than the 2.00 GB `-web` file ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)). The name suggests it is the build native GPU backends load, which would let one SHA-256 pin serve both. Google documents neither how it differs from the `-web` file nor which file an `hf://` URI selects. Other builds can fail outright with "model lacks WebGPU artifacts" ([LiteRT-LM #2322](https://github.com/google-ai-edge/LiteRT-LM/issues/2322)).

The JavaScript SDK keeps the native API's shapes. It takes OpenAI-like messages, returns `tool_calls` whose arguments arrive as objects, and offers an `AutoToolChat` helper, `clone()` to fork a conversation without re-prefilling, and image and audio input since v0.19.0 ([v0.19.0](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.19.0)). Its `EngineSettings` expose `activationDataType`, the setting whose FP32 value cures FP16 digit corruption on some GPUs natively, though no source tests it on the web. Its gaps against the C API matter for a harness. The web SDK has no JSON-schema or regex constraint and no `tool_choice`, even though the llguidance grammar engine is compiled into its wasm ([LiteRT-LM #4785](https://github.com/google-ai-edge/LiteRT-LM/issues/4785)). Its tool-syntax constraint costs about **950 ms per new conversation and cuts tool-call decoding from 118 to 53 tokens/s** ([LiteRT-LM #4784](https://github.com/google-ai-edge/LiteRT-LM/issues/4784)). The other engines trade differently. WebLLM offers JSON-schema decoding through XGrammar but tool calling only for Hermes builds of 7–8B models. Transformers.js renders tools into chat templates and leaves parsing to the app ([transformers.js 4.2.0](https://github.com/huggingface/transformers.js/releases/tag/4.2.0)). wllama embeds llama-server's full feature set but cannot run under this policy ([wllama v3 guide](https://github.com/ngxson/wllama/blob/master/guides/intro-v3.md)).

Every engine has open web faults, and LiteRT-LM's sit on exactly the paths an agent uses. Against 0.20.0, and reproduced by Google: after `cancel()`, "the conversation can no longer be used" ([#4783](https://github.com/google-ai-edge/LiteRT-LM/issues/4783)). After a reply fails on a lost GPU device, `createConversation()`, `conversation.delete()` and `engine.delete()` never return, "the page's thread itself is blocked", and the reporter's only remedy was to reload the runtime ([#4782](https://github.com/google-ai-edge/LiteRT-LM/issues/4782)). A failed streaming send closes with zero chunks, and deleting a clone breaks the original ([#4779](https://github.com/google-ai-edge/LiteRT-LM/issues/4779); [#4810](https://github.com/google-ai-edge/LiteRT-LM/issues/4810)). npm releases have shipped broken: 0.16.0 contained only `package.json`, and 0.18.1 shipped the next version's wasm, so `Engine.create` always failed ([#3364](https://github.com/google-ai-edge/LiteRT-LM/issues/3364); [#4051](https://github.com/google-ai-edge/LiteRT-LM/issues/4051)). WebLLM has Adreno device-loss failures, and one regression produced a `DXGI_ERROR_DEVICE_HUNG` that survived page reloads until the browser restarted ([#836](https://github.com/mlc-ai/web-llm/issues/836); [#844](https://github.com/mlc-ai/web-llm/issues/844)). The pattern that follows is to treat the engine as disposable. It gets its own dedicated Worker. A cancelled turn continues from a pre-turn `clone()` or from re-prefilled history. After a device loss the Worker is terminated and respawned, never cleaned up in place.

Go cannot call these engines as libraries. They are JavaScript built on promises, streams and callbacks around their own wasm instances, and `syscall/js` blocks the event loop while a wrapped Go function runs. Calling "any async JavaScript API ... will cause an immediate deadlock" unless the Go side starts a goroutine ([syscall/js](https://pkg.go.dev/syscall/js)). The workable shape is a small JavaScript adapter that exposes `load`, `generate` with a chunk callback, `cancel` and `unload`, and exchanges JSON strings with `sidecar.wasm` so that no objects cross. Weights are never copied into Go whole: `js.CopyBytesToGo` would double memory, the very failure that kills iPhone tabs. The adapter and engine belong in a sibling Worker that the frame document creates and links to the key Worker with a `MessageChannel`. A worker is governed by the CSP on its own script response, not its creator's ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)), so the key origin can serve that Worker a narrower policy with `connect-src 'self'` alone. It would hold no key, no token and no IndexedDB handle. That is the browser analogue of the desktop `ur-engine` helper, which holds none of `ur`'s keys and has no network ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §6.5). Only one tab should run an engine, because a second would duplicate 2–3 GB of GPU memory. LiteRT-LM's model cache already coordinates downloads with a Web Lock per model ([model_cache.ts](https://github.com/google-ai-edge/LiteRT-LM/blob/main/js/packages/core/src/model-cache/model_cache.ts)). An origin-wide engine lock beside the page Worker's per-network lock, with requests relayed over a BroadcastChannel as the design already relays views, gives inference the same shape ([DESIGN.md](../../DESIGN.md) §18.8).

## Chrome's built-in Gemini Nano cannot be pinned, labeled or called from a Worker

Chrome's Prompt API shipped on the open web in Chrome 148 (stable 2026-05-05). It runs Gemini Nano with no download by the site, but only on Windows 10/11, macOS 13+, Linux and Chromebook Plus; Android, iOS and WebView are unsupported ([Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api); [Chrome 148](https://developer.chrome.com/release-notes/148)). The device needs "strictly more than 4 GB of VRAM", or 16 GB of RAM and 4 cores, plus 22 GB free on the profile's volume and an unmetered connection for the first download ([get started](https://developer.chrome.com/docs/ai/get-started)). Every site then shares that download, about 4 GB for the GPU build and 2.7 GB for the CPU build ([adsm.dev](https://adsm.dev/posts/prompt-api/)). One developer measured **35–48 tokens/s on a GPU and 15 on a CPU**, with about 100 ms to the first token ([adsm.dev](https://adsm.dev/posts/prompt-api/)). Sessions take text, image and audio input and return text. They support `responseConstraint` with a JSON Schema or regular expression, and `clone()`. Developers measured the context window at **9,216 tokens**, a figure Chrome does not document ([Ar9av](https://github.com/Ar9av/gemini-nano-chrome); [chrome-ai-dev-preview-discuss](https://groups.google.com/a/chromium.org/g/chrome-ai-dev-preview-discuss/c/wdx5knkJW5M)). Tool calling has not shipped. The spec marks it experimental, and Chrome's function-calling entry has had only an intent to prototype since 2025 ([Prompt API spec](https://webmachinelearning.github.io/prompt-api/); [Chrome Status](https://chromestatus.com/feature/5085580563841024)).

Its placement rules collide with the key origin's layout. `LanguageModel` is exposed only to windows, and Chrome says it "isn't available in Web Workers for now" ([Chrome Prompt API](https://developer.chrome.com/docs/ai/prompt-api)). Calls would have to come from the frame's document, and decrypted text would have to cross from the Worker to it. The API is a policy-controlled feature whose default allowlist is `'self'`. The `sidecar.ur.io` frame can use it only if ur.io, which Cloudflare serves, adds `allow="language-model"` to the iframe ([Prompt API spec](https://webmachinelearning.github.io/prompt-api/)). Creating the first session, which starts the model download, requires user activation, and since activation does not propagate into cross-origin frames, the gesture probably has to happen inside the frame; no test confirms this.

The model also has no identity a catalog can record. JavaScript cannot read its version. Chrome picks a larger or smaller Gemini Nano, or a CPU build, per device. It hot-swaps updates, so "a prompt running at the exact moment of the swap" can fail, and it may purge the model "at any time, even mid-session" ([model management](https://developer.chrome.com/docs/ai/understand-built-in-model-management)). Chrome's Reilly Grant summed up the design: "The browser picks the model" ([blink-dev](https://mail-archive.com/blink-dev@chromium.org/msg16440.html)). That breaks the compute design's rule that every model has one canonical name ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §6.3), and the apps' practice of loading only SHA-256-pinned files. The most an honest label could say is "browser-provided model (Chrome: Gemini Nano, version not exposed)". Locality is a vendor promise. Chrome says "No data is sent to Google or any third party when using the model". The specification, however, lets a browser delegate to "user-agent-provided cloud-based services" and gives pages no way to require or verify on-device execution ([Writing Assistance APIs spec](https://webmachinelearning.github.io/writing-assistance-apis/)). The spec calls the shared model's download status a fingerprinting vector, and Chrome documents masking it only for the Translator ([Translator API](https://developer.chrome.com/docs/ai/translator-api)).

Elsewhere, ordinary pages do not get the API at all. On 2026-11-19 Edge replaced Phi-4-mini with Aion Instruct, a 2.3B-parameter, MIT-licensed model with a 32,768-token context. It moved its Prompt API to an origin trial, so pages without a token cannot use it. It needs 3 GB of VRAM, and from Edge 158 its unconstrained output carries an invisible watermark ([Edge blog](https://blogs.windows.com/msedgedev/2026/11/19/hybrid-intelligence-on-the-web-introducing-aion-instruct-and-prompt-api-in-microsoft-edge/); [Edge docs](https://learn.microsoft.com/en-us/microsoft-edge/web-ai/prompt-api); [Aion card](https://huggingface.co/microsoft/Aion-1.0-Instruct-2.3B)). Firefox offers pages nothing, and Mozilla reaffirmed in April 2026: "We continue to oppose this API" ([mozilla/standards-positions #1213](https://github.com/mozilla/standards-positions/issues/1213)). WebKit set its position to oppose on 2026-05-27, and Apple says its Foundation Models framework "doesn't provide any JavaScript interface" ([WebKit #495](https://github.com/WebKit/standards-positions/issues/495); [Apple forums](https://developer.apple.com/forums/thread/833716)). The specifications remain Community Group drafts, and the TAG closed its review with "lack of consensus" ([TAG #1093](https://github.com/w3ctag/design-reviews/issues/1093)). Of Chrome's task APIs, only Summarizer, Translator and Language Detector have shipped, in Chrome 138 on desktop; Writer, Rewriter and Proofreader are back in developer trial ([Built-in AI APIs](https://developer.chrome.com/docs/ai/built-in-apis)). Their output deserves the same suspicion as any model's. Mozilla showed Chrome's Translator turning `<scripte>…</scripte>` into a valid `<script>` tag ([mozilla #1015](https://github.com/mozilla/standards-positions/issues/1015)). Mint Security built two small agents on the Prompt API; a single malicious blog comment could make one send money from a bank tab and the other leak open tabs ([Mint Security](https://www.mint.security/blog/beware-of-the-tiny-agents-in-your-browser-a-chrome-prompt-api-case-study)). For decrypted mail, the built-in model would read attacker-written text, could not be named, and could not call tools.

## A multi-gigabyte model needs OPFS, an incremental hash and its own eviction unit

The three storage APIs share one per-origin quota and one default bucket, and browsers evict an origin "all-or-nothing" ([MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Chrome's storage team recommends the Cache API for models and calls IndexedDB "the worst place to store large models" ([Chrome: cache models](https://developer.chrome.com/docs/ai/cache-models)). LiteRT-LM's built-in cache follows that advice. It stores each model as one Cache API entry, written atomically and guarded by a per-model Web Lock so other tabs wait rather than download twice ([model_cache.ts](https://github.com/google-ai-edge/LiteRT-LM/blob/main/js/packages/core/src/model-cache/model_cache.ts)). WebKit makes single-entry storage dangerous. Its Cache Storage holds an entry's whole body in the WebContent process, so a single 767.5 MiB `cache.put` peaked at **2,331 MB** in macOS Safari 27; the fix was to store 16 MiB parts ([llama-web-bridge #257](https://github.com/leehack/llama-web-bridge/issues/257)). OPFS is the better home. It is the only one of the three that writes at an offset, which resumable downloads need. Its `getFile()` yields a disk-backed `Blob`, and LiteRT-LM has read Blob models with random access since October 2026 ([LiteRT-LM commits](https://github.com/google-ai-edge/LiteRT-LM/commits/main/js/packages/core)). Safari 26 added the writable-stream API that OPFS lacked there ([Safari 26 notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes)).

The framed key origin changes the quota and persistence picture. Chrome keys the frame's storage by its origin and the top-level site, the same key as a direct visit to `sidecar.ur.io`, and allows up to 60% of the disk ([MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria); [storage partitioning](https://privacysandbox.google.com/3pcd/storage-partitioning)). Firefox caps best-effort storage at the smaller of 10% of the disk or 10 GiB for all of `*.ur.io` together. WebKit gives cross-origin frames a separate partition at 10% of the main frame's quota, which may cover this same-site frame and needs a device test ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Persistence is the sharper problem. Chromium's permission code says "Durable is only allowed to be granted to the top-level origin" and denies any other requester without a prompt ([persistent_storage_permission_context.cc](https://github.com/chromium/chromium/blob/main/chrome/browser/storage/persistent_storage_permission_context.cc)). `navigator.storage.persist()` called from the `sidecar.ur.io` frame therefore **always resolves `false` in Chrome and Edge**, whatever the site's engagement. The design has the frame call `persist()` to protect every network's keychain, MLS state and token ([DESIGN.md](../../DESIGN.md) §18.8). In Chromium that call achieves nothing, and a 2–4 GB model in the same bucket would share the keychains' fate: whatever evicts the model evicts them too. A grant obtained in a top-level `sidecar.ur.io` context, where Chrome grants it to installed web apps and the profile's ten most important sites, probably covers the frame's storage as well, since Chrome keys both the same way; no test confirms it. Safari's tracking prevention also deletes script-writable storage, the Cache API included, after seven days of Safari use without interaction on the site, exempting Home Screen web apps for their first party only ([WebKit](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). Storage Buckets, in Chromium since 122, let a non-persisted `models` bucket, with its own `caches` and OPFS directory, be evicted alone. Firefox is positive about them but has not implemented them, and WebKit has given no signal ([Chrome Status](https://chromestatus.com/feature/5739224579964928)). Outside Chromium, separating the model from the keys means keeping it in another origin's storage and passing the `Blob` across, or accepting the coupling.

Hugging Face works as a source, at the cost of the CSP's narrowness. A browser download observed on 2026-11-25 went from a `huggingface.co` `/resolve/` URL by a 302 redirect to a signed `us.aws.cdn.hf.co` URL that expired after exactly one hour. The CDN served Range requests with 206 and `access-control-allow-origin: *`, and the redirect exposed the file's SHA-256 as `X-Linked-ETag` ([E2B repository](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)). Anonymous clients get 3,000 resolves and 500 API calls per IP per five minutes, so users behind carrier NAT share one budget ([HF rate limits](https://huggingface.co/docs/hub/rate-limits)). The CDN host has changed more than once since early 2025, so `connect-src` would need something like `https://huggingface.co https://*.hf.co`. The research found no Hugging Face terms covering apps whose users download multi-gigabyte files anonymously. Gemma 4's Apache-2.0 license permits mirroring. Serving the pinned files from the key origin itself, at a path such as `/v1/models/<sha256>.litertlm`, keeps `connect-src` at `'self'` and removes CORS, preflights, rate limits and host churn. The download should run in a dedicated Worker that streams each response into OPFS at its offset, records the committed offset, and resumes with `Range` and `If-Range`. Like Chrome's own model, the first multi-gigabyte download should wait for an explicit choice or an unmetered connection. Background Fetch, which survives a closed tab, is Chromium-only, refuses requests that need a CORS preflight, and restarts a dropped file from zero ([Background Fetch](https://developer.chrome.com/blog/background-fetch)). Each browser profile downloads its own copy. Nothing shipped lets it share the native app's file, and Cross-Origin Storage, which would key a shared copy by SHA-256, has no milestone ([Chrome Status](https://chromestatus.com/feature/5163371507875840)).

Checking the apps' SHA-256 pin is harder than it looks. WebCrypto's `digest()` needs its whole input in memory. A streaming proposal sits at the pull-request stage, with engine developers saying "we are not going to implement it immediately" ([Igalia hackfest notes](https://github.com/Igalia/webengineshackfest/wiki/2026-Web-Cryptography-API)). With `integrity`, `fetch` implementations "put the entire response in memory, check the integrity, and then feed you a stream backed by memory instead of network" ([whatwg/fetch discussion](https://lists.w3.org/Archives/Public/public-webapps-github/2021Feb/0665.html)), which no tab can afford at 2–4 GB. The engines do not fill the gap. LiteRT-LM's web `hf://` resolver compares Hugging Face's recorded SHA-256 and size with the caller's pin before downloading. Its JavaScript, however, contains no `crypto.subtle` or digest call, so it trusts the Hub's metadata and cannot detect a compromised CDN or a corrupted transfer ([hugging_face.ts](https://github.com/google-ai-edge/LiteRT-LM/blob/main/js/packages/core/src/model-cache/hugging_face.ts)). Native LiteRT-LM, by contrast, verifies a SHA-256 for each section of the `.litertlm` header as it writes ([model_sync.cc](https://github.com/google-ai-edge/LiteRT-LM/blob/main/sync/model_sync.cc)). WebLLM's integrity option covers its config, model library and tokenizer, not its weight shards ([integrity.ts](https://github.com/mlc-ai/web-llm/blob/main/src/integrity.ts)). The answer is an incremental SHA-256, fed each chunk as it is written. Go's standard `crypto/sha256` inside `sidecar.wasm` can do this, taking 16 MiB at a time so the file is never held whole. The file is published only when the digest equals the release's pin. Resuming means either saving the hasher's state with the offset or re-reading the written prefix once, and a published per-chunk manifest would let parallel ranges verify on arrival. Cached copies are untrusted on later loads; a Mozilla bug opened this month proposes re-verifying cached models when they load from OPFS ([Bugzilla 2091099](https://bugzilla.mozilla.org/show_bug.cgi?id=2091099)). No source measures wasm SHA-256 throughput on multi-gigabyte files, so the cost of re-verifying at every load is unknown.

A tab is a worse home than an app for long work. In desktop Chrome, a hidden tab's Worker and its WebGPU work keep running unless the tab is frozen or discarded. Freezing needs Energy Saver plus five minutes hidden and silent plus heavy CPU use; Memory Saver or memory pressure discards tabs ([Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api); [freezing on Energy Saver](https://developer.chrome.com/blog/freezing-on-energy-saver)). Holding a Web Lock blocks every Chromium freezing type, which the page Worker's instance lock already relies on ([cannot_freeze_reason.h](https://github.com/chromium/chromium/blob/main/components/performance_manager/public/freezing/cannot_freeze_reason.h)). No source says a lock prevents a discard, which kills the renderer, the Worker and the GPU device without firing an event. Android Chrome freezes background renderers after a five-minute grace period, the OS kills them first under memory pressure, and iOS suspends Safari's processes shortly after the person leaves it ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/NKtuFxLsKgo); [WebKit bug 169824](https://bugs.webkit.org/show_bug.cgi?id=169824)). On iOS a GPU out-of-memory may never reach JavaScript at all. WebKit reverted its change that turned out-of-memory into device loss, and pages under memory pressure are killed and reloaded in a loop ([WebKit bug 280929](https://bugs.webkit.org/show_bug.cgi?id=280929); [WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782)). Inference state must therefore be checkpointable. The conversation lives encrypted in IndexedDB, the weights stay in OPFS for re-upload after `device.lost`, and a long agent turn resumes on the `resume` and `visibilitychange` events.

## The browser verifies no served code, so the engine must never hold a key

In-page inference changes the security model in four places: whose code runs, what a model file can do, what the GPU exposes, and what reaching outside the page opens.

### Served code still rests on the origin, not the release

No shipped browser feature can prove that a top-level page, a frame's document or a Worker's script matches a signed or publicly logged release. Subresource Integrity, Integrity-Policy (Chrome 138, partial in Firefox 145 and Safari 26) and signature-based SRI (Chrome 141, per its intent to ship) all take the expected hash or key from HTML that the same origin serves. They defend against a third-party host, not against the origin itself ([MDN Integrity-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Integrity-Policy); [blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/R6isgRnE1j4)). WAICT would close that gap with a manifest, a transparency log and a browser preload list, but it exists only as draft specs and an "early prototype" behind a Firefox Nightly pref ([Mozilla Hacks](https://hacks.mozilla.org/2026/05/trustworthy-javascript-for-the-open-web/); [Cloudflare](https://blog.cloudflare.com/improving-the-trustworthiness-of-javascript-on-the-web/)). Isolated Web Apps, which sign a whole app with a key kept offline, install only on managed ChromeOS ([Chrome IWA](https://developer.chrome.com/docs/iwa/introduction)). An independent evaluation of five client-side code-integrity tools found over a dozen bugs that let secrets be exfiltrated, 18 disclosed in all ([CISPA](https://cispa.de/en/research/publications/213253-trust-on-reload-securing-browser-based-end-to-end-encryption); [SecureDrop](https://securedrop.org/news/webcat-update-independent-evaluation-waict-and-a-growing-team/)). The design already records this as EX7: the loader pins `sidecar.wasm`'s SHA-256 from the release's signed `SHA256SUMS`, anyone can compare the served bytes, and no browser checks them on load ([DESIGN.md](../../DESIGN.md) §2.8, §18.8). An engine lengthens that pin list, adding 22–35 MB of engine wasm and the model's hash, without changing its root. Whoever controls `sidecar.ur.io`'s responses controls the engine, the hasher and the expected hash together. The engine's glue arrives through `importScripts`, which takes no integrity metadata at all. In the apps, the release signature covers the engine; on the web, it covers nothing the browser enforces.

### Model files are data, except WebLLM's, which are code

WebLLM's model libraries are compiled code. Each is a 6–12 MB WebAssembly module with embedded WGSL kernels, built per model by MLC and Apache TVM and downloaded from GitHub by default ([WebLLM paper](https://arxiv.org/html/2412.15803v1); [binary-mlc-llm-libs](https://github.com/mlc-ai/binary-mlc-llm-libs/tree/main/web-llm-models/v0_2_87/base)). Loading one inside the key origin is equivalent to shipping third-party code there. The other formats are data, but memory-unsafe C++ compiled to wasm parses them. GGUF's parser alone had crafted-file heap overflows in 2024, which Cisco Talos said can lead to code execution (CVE-2024-21825; CVE-2024-21802 at CVSS 8.8), and an integer overflow in 2025 (CVE-2025-53630) ([Talos](https://talosintelligence.com/vulnerability_reports/TALOS-2024-1912); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-53630)). In a browser, such an exploit stays inside one wasm instance's linear memory unless it chains a second bug. That memory, though, holds the prompt and the output, and the JavaScript around it can reach every host in its `connect-src`. Chat templates and tokenizers ride inside the files too, and a malicious template could silently rewrite prompts. Pinning every file's hash in the release, self-hosting it, and running the engine in a Worker with no key and `connect-src 'self'` limits a bad file's reach to the plaintext of the one request it was given.

### WebGPU moves plaintext into a shared, less-sandboxed process

The gpuweb explainer says "GPU processes are less sandboxed than content processes, and they are typically shared between multiple origins" ([gpuweb explainer](https://gpuweb.github.io/gpuweb/explainer/)). The WebGPU stack inside them is a steady source of memory-safety bugs. Chrome's Dawn had a run of use-after-free CVEs through 2026. Google said one of them, CVE-2026-5281, was exploited in the wild before Chrome 146 fixed it, and CISA listed it on 2026-04-01 ([Help Net Security](https://helpnetsecurity.com/2026/04/01/google-chrome-zero-day-cve-2026-5281)). Firefox's WebGPU component had its own 2026 CVEs ([Red Hat](https://bugzilla.redhat.com/show_bug.cgi?id=2455902)). Direct cross-origin reads are not known. WebGPU zero-initializes resources and bounds-checks shader access, which is why browser GPU frameworks "appear not to be currently impacted" by LeftoverLocals, the attack that recovered LLM responses from leftover GPU local memory natively ([Trail of Bits](https://blog.trailofbits.com/2024/01/16/leftoverlocals-listening-to-llm-responses-through-leaked-gpu-local-memory/)). Timing is another matter. The spec concedes that one site can observe another's GPU work through contention, and that cross-origin isolation "does not provide isolation of device/queue-timeline timers" ([W3C WebGPU](https://www.w3.org/TR/webgpu/)). A GPU cache attack mounted from WebGPU recovered inter-keystroke timing with an F1 score of 82–98% on NVIDIA GPUs ([TU Graz](https://www.gruss.cc/files/WebGPUAttacks.pdf)). Local inference therefore moves decrypted text and its activations into a process every tab shares, and lets other pages see when, and roughly how fast, the model is generating. A separate exposure predates inference. Chromium groups same-site frames into site-keyed agent clusters, so ur.io's page and the `sidecar.ur.io` frame may share a renderer process. A renderer exploit delivered by Cloudflare-altered script would then reach the Worker's memory and keys ([agent_cluster_key.h](https://chromium.googlesource.com/chromium/src/+/HEAD/content/browser/agent_cluster_key.h); [process model](https://chromium.googlesource.com/chromium/src/+show/main/docs/process_model_and_site_isolation.md)). A key origin on a different registrable domain would get desktop Site Isolation, an inference worth testing. On the device, an extension with host access can inject scripts into every frame, `chrome.debugger` can attach to workers, IndexedDB and OPFS are not encrypted at rest, and Chrome's crash reports may include "memory contents at the time of the crash" ([content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts); [chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger); [Chrome Help](https://support.google.com/chrome/answer/14746339)). Weights can sit in plaintext because they are public. Any persisted conversation, KV cache or embedding must be encrypted under the Worker's keys.

### Reaching outside the page buys the native engine for a prompt

The browser vendors' own choice is telling. Mozilla moved Firefox's on-device features from wasm to a native ONNX runtime for "significantly better performance" ([Ziadé](https://blog.ziade.org/2025/12/05/two-years-of-ai-at-mozilla/)). It has since built a sandboxed `HWInference` process that runs llama.cpp for text generation when its pref is on, and content processes can request only a task-specific identifier, never name a model file ([HWInference](https://firefox-source-docs.mozilla.org/toolkit/components/ml/HWInference.html)). Chrome's built-in model is native too. Neither vendor runs its own language models as page-level wasm.

A page can reach a daemon on the same machine in Chromium, behind a prompt. Chrome 142 introduced the Local Network Access prompt, and Chrome 145 split out a separate `loopback-network` permission. Once it is granted, `fetch` with `targetAddressSpace: 'loopback'` exempts an `http://127.0.0.1` target from mixed-content blocking. A cross-origin frame needs `allow="local-network; loopback-network"` from its embedder plus a delegating `Permissions-Policy` header on the top-level document, and service and shared workers cannot raise the first prompt ([Chrome LNA guide](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access); [blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/Zl3P6NHhMBw)). Edge enforces the same rules from 143, and Firefox is rolling out a prompt from 151. Safari still blocks `http://` loopback from https pages as mixed content, under a WebKit bug that remains open ([Edge](https://learn.microsoft.com/en-us/deployedge/ms-edge-local-network-access); [Firefox policy](https://firefox-admin-docs.mozilla.org/reference/policies/localnetworkaccess/); [WebKit bug 171934](https://bugs.webkit.org/show_bug.cgi?id=171934)). For sidecar, ur.io would have to delegate the permission. Cloudflare could withhold it, which would deny service but reveal nothing. The key origin's `connect-src` would have to list the loopback origin. The daemon would also need a new listener, because its loopback gateway rightly refuses any request that carries an `Origin` header or a `Sec-Fetch-Site` other than `none` ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §8). A browser-facing listener must not rely on CORS. It needs an exact Origin allowlist, and a Host check against DNS rebinding, the flaw behind Ollama's CVE-2024-28224 and NemoClaw's 2026 model-poisoning bug ([NCC Group](https://www.nccgroup.com/research/technical-advisory-ollama-dns-rebinding-attack-cve-2024-28224/); [Cyera](https://www.cyera.com/research/nemoclaw-one-website-visit-to-hijack-your-ai-agent)). It also needs authentication, ideally a paired key exchange, so that plaintext crosses the loopback socket only encrypted to a key the daemon has proved it holds. The extension needs none of this, because the design already gives it native messaging to `ur daemon` ([DESIGN.md](../../DESIGN.md) §18.8). The host-to-extension message cap of 1 MB is ample for streamed tokens ([native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)).

Reaching the person's other devices has product precedent but no web precedent. LM Studio's LM Link, launched with Tailscale on 2026-02-25 as a preview, carries prompts end to end encrypted between a person's devices over `tsnet`, including from an iPhone app to a desktop. Prompts and responses are "never seen, either by Tailscale or LM Studio's backend service" ([Tailscale](https://tailscale.com/blog/lm-link-remote-llm-access)). Tether's QVAC offers peer-to-peer delegated inference, with blind relays for devices behind NAT ([QVAC](https://raw.githubusercontent.com/tetherto/qvac/main/README.md)). WhatsApp Web used the phone as its source of truth until 2021 ([Meta Engineering](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)). Every modern example is native at both ends, because a page cannot join a tailnet; a browser version needs a relay and its own end-to-end encryption. Sidecar starts from unusual footing. Every page Worker is admitted by a consented device of the same member, which must be online at admission ([DESIGN.md](../../DESIGN.md) §18.8). So every web user owns at least one native sidecar that can run LiteRT-LM natively, at full speed, with the apps' files, pins and sandbox. The design's enclave attach already defines the wire shape: Pi's RPC protocol, with replay from a sequence number on reconnect ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §7.10). The costs are availability and transport. The phone apps run their sidecar only while open, and phones throttle under sustained load. The page Worker speaks HTTPS long-polls until the C4 WebSocket carrier arrives, which would make streamed tokens arrive in bursts.

## Six approaches trade reach against trust

The options differ along three axes: which browsers they reach, whether the model keeps the apps' identity and pins, and whose code the person must trust.

| Approach | Reaches | Model identity and pins | Code the person trusts | Main costs |
|---|---|---|---|---|
| A. No browser-local model: the design's plan, with no compute on the page Worker at launch and a remote-only Harness on the extension's Worker later | every browser, for remote models, once a browser Worker has a compute surface | the remote catalog's labels | the attested provider, through the broker | credit; data leaves the device for a TEE or provider; no free local inference on the web |
| B. Delegate to the member's own device (desktop `ur daemon`, or the app while open) over sidecar's end-to-end encrypted transport | every browser, Firefox and iOS Safari included | the native files and SHA-256 pins, unchanged | the signed native install | the device must be online; phones only while the app is open, and throttled; bursty streaming until C4; a new label for "your own device" |
| C. Loopback to the same machine's daemon | Chrome and Edge, Firefox from 151; not Safari | native | the signed native install | an LNA prompt; ur.io must delegate; a new authenticated browser listener; loopback in `connect-src` |
| D. In-page LiteRT-LM with Gemma 4 `-gpu.litertlm`, in a keyless engine Worker | desktop Chrome and Edge, and Safari 26+ on Tahoe, with 4–8 GB of free GPU or unified memory | the same family; the same pin if the native GPU path loads the `-gpu` file | `sidecar.ur.io`'s served code (EX7) | about 45% of native decode; a 2.3–3.3 GB download per browser profile; early-preview faults; eviction coupled to the keys outside Chromium; plaintext in the shared GPU process |
| E. In-page small models: classifiers, embedders, language models of 0.4 GB or less | most WebGPU devices, phones included; plain wasm for the tiniest | different models (Prompt Guard 2, EmbeddingGemma 2, Qwen3-0.6B) | the same served code | no agent work; Prompt Guard 2 carries the Llama 4 Community License; browser latency unmeasured |
| F. The browser's own model (Chrome's Prompt API; Edge by origin trial) | desktop Chrome 148+ above its hardware gate | none: unnamed, unversioned, hot-swapped | the browser vendor | window-only; `allow="language-model"` from ur.io; about 9K tokens of context; no tools; locality only a vendor promise |

Approach A, the design's current plan ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §7.14, Q-HARN-3), adds no surface but leaves web users without free, private inference. Of the rest, the evidence favors delegation first. Approach B is the only one that reaches every browser, and it carries over everything the apps already have. It brings the native engine at full speed, 160 rather than 73 tokens/s on an M4 Max, along with the SHA-256-checked files and the `ur-engine` sandbox that holds no keys and has no network. The key origin gains only a client for the streaming carrier the design already plans (C4). B's costs are a label and a transport. The catalog's local/remote split has no name for "on your own other device", where data leaves the browser yet no server sees it in plaintext ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §6.3). And streaming wants the C4 WebSocket carrier. Approach C is worth building only as a latency optimization on Chromium desktops after B. B already reaches the same daemon through the network's ciphertext relay, in every browser and Safari included, with no prompt and no new local listener.

Approach D serves members with no device online, on desktops only. It should follow a spike that settles what the research could not. The spike would check whether LiteRT-LM runs in a classic Worker under the key origin's CSP without a single `securitypolicyviolation`, and whether the narrower engine-Worker CSP holds in every browser. It would check whether the `-gpu` file loads from an OPFS `Blob` in Chrome and in Safari 26 and 27 without Safari's single-entry memory peak. It would measure what LiteRT-LM's Asyncify build costs Safari to compile, given reports that Safari spends seconds and hundreds of megabytes compiling ONNX Runtime's ([transformers.js #1835](https://github.com/huggingface/transformers.js/issues/1835)). And it would test how the engine recovers when its Worker is terminated after device loss, and what `persist()` and eviction actually do to the frame in each browser. E2B should ship first. It should be gated by a probe rather than by user agent, except to exclude Firefox and WebKit on iOS. The design's Q-INFER-1 rule should hold: a local failure offers a remote model but never silently takes one ([DESIGN-COMPUTE.md](../../DESIGN-COMPUTE.md) §6.11).

Approach E earns a place only for a named need, such as screening text for prompt injection before a remote call. Prompt Guard 2's 22M model is 72 MB quantized and supports a 512-token window ([Prompt Guard 2 22M card](https://github.com/meta-llama/PurpleLlama/blob/main/Llama-Prompt-Guard-2/22M/MODEL_CARD.md); [gravitee-io ONNX](https://huggingface.co/gravitee-io/Llama-Prompt-Guard-2-22M-onnx)). It can run on ONNX Runtime's plain wasm build, the one variant whose glue contains no `new Function`, with no WebGPU at all; for encoders that small, wasm has beaten WebGPU in a single benchmark ([webai-bench](https://github.com/Sallamhamza/webai-bench/blob/main/docs/spikes/sp3-findings.md)); no browser latency for it has been published. Approach F should not touch decrypted data. A model that cannot be named, pinned, verified as local or called from the Worker fails the catalog's rules before its quality is even considered. The extension, Later in the design, changes little here. Its offscreen document's Worker gets WebGPU just as the page's does. Its real advantages are native messaging to the daemon and, eventually, a place to verify the key origin's served code.

## Conclusion

Porting the engine is the easy part. LiteRT-LM's JavaScript SDK runs the same model family with the same JSON shapes, and the pins carry over as values. What the web lacks are the guarantees the apps inherit from their platforms: code verified before it runs, storage the app owns, a process the engine can be confined to, and a foreground that keeps running. The file check survives as an incremental hash, and a site can approximate the last three guarantees: owned storage with a separate Storage Bucket (in Chromium only), confinement with a keyless Worker under its own CSP, and a foreground with checkpointing. It cannot rebuild the first, verified code, at all until something like WAICT ships in Chrome and Safari. That reframes local inference on the web for sidecar. The question is less which engine than which device. Because the design requires a consented native device to admit every page Worker, the web surface always has a native engine within the person's own trust boundary, and the browser can serve as the window rather than the engine. Mozilla and Google made the same choice for their own features: Firefox moved its inference from wasm to native code, and Chrome's built-in model runs natively.

The picture would change on a handful of triggers, none of them dated. iOS lifting the roughly 2 GiB WebContent ceiling would open iPhones. WAICT shipping in Chrome and Safari would give the key origin, and any in-page engine with it, a code root a browser can check. Storage Buckets in Firefox and Safari would decouple a model from the keychains. LiteRT-LM's web SDK binding its already compiled llguidance constraints, and leaving early preview, would make in-page agents practical. Safari 27.3 shipping subgroups and Memory64 would narrow Safari's gap. Until then, in-page inference is a desktop enhancement, and the person's own native device is the web's real local model.
