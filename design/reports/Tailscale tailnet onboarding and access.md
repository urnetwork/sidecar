# Reproducing tailnet onboarding on a blind network

Tailscale makes joining a private network feel like signing into a SaaS app — install the client, run one command, click once through your identity provider, and the device is working; on a managed fleet the touch count drops to zero — and it buys that ease with a central **coordination server that sees everything it needs to think for you**. That server is passwordless and delegates authentication to any OIDC identity provider (**never SAML**), can ingest a company's user/group directory over SCIM, enforces seven admin roles, gates new users and devices behind approval, mints auth keys and OAuth clients for headless joins, and compiles one deny-by-default HuJSON policy of **grants** (GA since **2025-05-29** and now the recommended model over legacy ACLs) — with tags, autogroups, and device posture — into per-node packet filters it pushes to every client. The price of those ergonomics is visibility: to resolve "who is this user, what groups and tags do they carry, which peers may they reach, is their device healthy," the coordination server must hold the **entire identity/group/policy graph in plaintext** — device public keys, identity↔device mappings, connection metadata, posture attributes, per-user PII, and a 90-day identity-attributed audit log. **Tailnet Lock** narrows this for one thing only — membership *authenticity*, so a malicious server cannot inject rogue nodes — but changes nothing about what the server *sees*, and **Headscale**, the open-source control server, simply relocates that same all-seeing role onto hardware you operate. recURd's defining constraint inverts Tailscale's bargain: its coordination network and relays carry only ciphertext, so it cannot host the plaintext graph that earns Tailscale its ease of use. The one genuinely hard problem is therefore *not* SSO or one-command join — those live at the client and the IdP and can stay off the coordination network entirely — but reproducing the **central resolver**: group/tag/ACL/posture resolution and the approval gates must move to a **customer-held key authority** whose signed, encrypted decisions the blind network transports but never reads. recURd already holds the seed of that design in the one Tailscale primitive it must generalize — Tailnet Lock — extended from signing node keys to signing the whole policy and identity graph.

## Executive summary

**What Tailscale gives.** A near-frictionless join (≈3 interactive actions to add a client to an existing tailnet; zero on an MDM fleet), passwordless enterprise SSO over OIDC with optional SCIM directory sync, a seven-role admin model, user and device approval gates, several headless-join credentials (auth keys, OAuth clients), a single deny-by-default policy language (grants/ACLs with tags, autogroups, and posture) compiled centrally and enforced locally, and a full automation surface (REST admin API, official Terraform provider, signed webhooks, always-on audit logging). Every one of these is mediated by a coordination server that can read the identity and policy graph.

**The one hard problem for recURd.** Tailscale's ergonomics come from letting the control plane be an omniscient broker. recURd's coordination network sees only ciphertext, so it cannot be that broker. The decisive engineering task is to relocate *policy and identity resolution* — group membership, tag ownership, ACL/grant compilation, approval, posture — into a **customer-held, client-verifiable key authority** (a generalization of Tailnet Lock), and to let the blind network move the resulting **signed, encrypted** artifacts without understanding them. Where Tailscale already resolves centrally and enforces locally, recURd must resolve *under customer keys* and enforce locally. The SSO click, the one-command join, the QR flow, and the automation API are comparatively easy because they already belong to the client, the IdP, or a customer-side admin plane; the resolver and its gates are where the design is won or lost, and device posture plus a *metadata-blind* audit record are where recURd must accept explicit trade-offs.

## How Tailscale turns install-plus-one-click into a working client

### Identity: passwordless OIDC sign-on that Tailscale only brokers

Tailscale has **no passwords and no email sign-up**; all authentication is delegated to an external identity provider over **OpenID Connect — SAML is not supported anywhere in the product** ([Supported SSO identity providers, last validated Jan 5 2026](https://tailscale.com/kb/1013/sso); [Custom OIDC, last validated Dec 10 2025](https://tailscale.com/kb/1240/sso-custom-oidc)). It natively supports Apple, Google (incl. Workspace), GitHub, Microsoft (incl. Entra ID), Okta, and OneLogin, plus any custom OIDC provider that signs with ES256 or RSA ≥2048, exposes the standard `openid`/`profile`/`email` scopes, and proves domain ownership via a **WebFinger** endpoint ([kb/1013/sso](https://tailscale.com/kb/1013/sso); [kb/1240/sso-custom-oidc](https://tailscale.com/kb/1240/sso-custom-oidc)). Architecturally the control plane is "essentially an OIDC relying party": it never sees passwords or MFA factors, but it does see the IdP's authenticated assertion and stores each user's **email, display name, and (for some IdPs) a profile-photo URL** ([kb/1013/sso](https://tailscale.com/kb/1013/sso)). Only a tailnet **Owner** can configure or switch the identity provider, and all users from one domain must use the same provider ([kb/1240/sso-custom-oidc](https://tailscale.com/kb/1240/sso-custom-oidc)). MFA is enforced entirely at the IdP and simply "applies to Tailscale"; passkeys are supported for any tailnet you are authorized to join ([kb/1013/sso](https://tailscale.com/kb/1013/sso)).

On top of login sits optional **SCIM provisioning** (a paid feature — **Standard/Premium/Enterprise**) for Google Workspace, Microsoft Entra ID, and Okta, plus a **custom SCIM API (alpha)** for other IdPs ([User & group provisioning, last validated Dec 8 2025](https://tailscale.com/kb/1290/user-group-provisioning)). SCIM syncs **users and group memberships** — not roles — and synced groups become policy references of the form `group:name@domain` ([kb/1290](https://tailscale.com/kb/1290/user-group-provisioning)). Two operational gotchas recur: **SCIM and user approval are mutually exclusive** on the same tailnet, and suspending a user in the IdP does **not** instantly cut access — "a suspended user stays logged in and keeps their node access… until device keys expire and they can't reauthenticate" — so immediate offboarding requires disabling the user in the IdP ([kb/1290](https://tailscale.com/kb/1290/user-group-provisioning); [Okta SCIM, last validated Jan 5 2026](https://tailscale.com/kb/1180/sso-okta-scim)). The **seven roles** — Owner, Admin, Member (basic, all plans) and Network admin, IT admin, Billing admin, Auditor (advanced, Standard+) — govern **admin-console access only, not device-to-device traffic**, and cannot be assigned via SCIM groups ([User roles, last validated Dec 4 2025](https://tailscale.com/docs/reference/user-roles)). **User approval**, available on all plans and **on by default for tailnets created on or after 2025-05-22**, holds every new user — invited or SSO-provisioned — as "needs approval" until an Owner/Admin/IT admin approves; notably, an unapproved user can still **reach and register with the coordination server**, and approval gates only peer connectivity ([User approval, last validated Sep 25 2025](https://tailscale.com/kb/1239/user-approval)). (The current paid tiers are **Standard $8**, **Premium $18**, and **Enterprise**; "Starter" is a legacy name and the entry paid tier is **Standard** — [Pricing](https://tailscale.com/pricing).)

### Device join: from one SSO click to zero-touch fleet enrollment

For a brand-new tailnet the quickstart is a **6-step wizard**; adding a client to an *existing* tailnet is effectively **three actions** — install, run `tailscale up`, complete the SSO flow in the browser — after which the device auto-registers unless device approval is on ([Quickstart](https://tailscale.com/docs/how-to/quickstart); [CLI reference](https://tailscale.com/kb/1080/cli)). The "login" is an identity-provider flow reached through a one-time login URL, not an email magic link. **Device approval** (all plans) hard-gates a new device so it cannot pass traffic until an admin approves it, unless it joined with a pre-approved key ([Device approval](https://tailscale.com/kb/1099/device-approval)).

Headless and automated joins avoid the browser entirely. **Auth keys** ("pre-authentication keys") register a device with `tailscale up --auth-key=<key>`; they come in one-off vs. reusable flavors with optional ephemeral, pre-approved, and tagged settings and a 1–90-day validity, and a key authenticates the device **as the user who generated it** (or, if tagged, as its tags) — reusable keys are "very dangerous if stolen" ([Auth keys](https://tailscale.com/kb/1085/auth-keys)). Tailscale now steers automation toward **OAuth clients**: a non-expiring, tailnet-owned client ID+secret exchanges for a **1-hour** API token and **mints short-lived, tag-bound auth keys on demand**, so no 90-day secret sits in CI; OAuth-registered devices are tag-owned rather than user-tied ([OAuth clients](https://tailscale.com/kb/1215/oauth-clients)). At fleet scale, **MDM reached GA on 2024-02-12 for Premium/Enterprise** and can push the client plus an `AuthKey` policy to managed Intune/Jamf/Kandji/JumpCloud/SimpleMDM devices for a true **zero-touch** join ([MDM GA](https://tailscale.com/blog/mdm-ga); [Auth keys](https://tailscale.com/kb/1085/auth-keys)). The lowest-friction *interactive* path is the **QR flow**: a constrained device shows a QR code (automatically on Apple TV), you scan it with a trusted phone, authenticate there via your IdP, and the new device logs in automatically with nothing typed on it ([QR device-add](https://tailscale.com/kb/1336/device-add-qr-code)). Onboarding effort varies by platform (Linux is the easiest headless; macOS needs system-extension/VPN approval that only MDM can pre-clear; Windows needs explicit "Run Unattended" for servers), and Tailscale's own designers have called the interactive onboarding "the most horrible onboarding experience we've ever done" — which is precisely why the ecosystem leans on keys, OAuth, and MDM to bypass the browser ([SCW podcast](https://www.buzzsprout.com/1822302/9890092-tailscale-with-avery-pennarun-brad-fitzpatrick)).

### Access control: one deny-by-default policy compiled into per-node filters

A tailnet has exactly **one policy file** in HuJSON (JSON with comments and trailing commas), editable by Owner/Admin/Network admin in the console, via the API, or via **GitOps** — Tailscale recommends keeping the GitOps repo private "because the file contains PII such as user email addresses" ([Policy file syntax](https://tailscale.com/docs/reference/syntax/policy-file); [GitOps](https://tailscale.com/docs/integrations/github/gitops)). **Grants reached GA on 2025-05-29** and are the recommended successor to legacy `acls`: feature-complete with ACLs, deny-by-default, with each grant carrying `src`, `dst`, and at least one of `ip` (network layer) or `app` (application layer), plus optional `srcPosture` and `via`; matching grants are **unioned**, and `app` capabilities are **opaque JSON that the policy engine only syntax-checks while clients enforce them** ([Grants GA](https://tailscale.com/blog/grants-ga); [Grants syntax](https://tailscale.com/docs/reference/syntax/grants); [Grants vs. ACLs](https://tailscale.com/docs/reference/grants-vs-acls)). Legacy ACLs "will be supported forever" and can coexist, but only grants receive new features ([Grants GA](https://tailscale.com/blog/grants-ga)).

Identity enters policy three ways. **Tags** (`tag:`) give non-user devices — servers, ephemeral nodes, and, for recURd, agents — a durable, policy-addressable identity; they are defined by their `tagOwners`, a device's identity is the **union of all its tags**, and tag identity and user identity are **mutually exclusive on one device** ([Group devices with tags](https://tailscale.com/docs/features/tags)). **Groups** are admin- or SCIM-defined user lists (no nesting), and **autogroups** are built-in dynamic selectors — `autogroup:member`, `autogroup:self`, `autogroup:tagged`, `autogroup:owner`, `autogroup:shared`, `autogroup:internet`, and admin sub-roles (Standard+) ([Policy file syntax](https://tailscale.com/docs/reference/syntax/policy-file)). **Device posture** defines named assertions over device attributes — `node:` host info reported by the device, `ip:` geolocation **computed by the control plane** (Standard+, beta), and `custom:`/EDR-integration attributes pushed in via API or OAuth provisioning — referenced from rules via `srcPosture` and applied to the **source only** ([Device postures and attributes](https://tailscale.com/docs/features/device-posture/postures-and-attributes)). **Tailscale SSH** is governed by an `ssh` array with `accept` or **`check` (periodic re-auth through the IdP, default 12h)** rules, and requires *both* a network rule allowing port 22 and an SSH rule ([Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)). Embedded `tests`/`sshTests` run on every change and cause Tailscale to reject a policy that breaks an assertion — though there is no built-in "don't lock out the admin" safeguard beyond tests you write yourself ([Policy file syntax](https://tailscale.com/docs/reference/syntax/policy-file)).

The enforcement architecture is the crux for recURd: **the control server compiles the central policy into per-machine IP:port filter rules and distributes them via each node's network map; each node then enforces its own filter locally, at decryption time, with the coordination server not in the data path** ([How Tailscale works](https://tailscale.com/blog/how-tailscale-works); [Manage permissions using ACLs](https://tailscale.com/docs/features/access-control/acls)). Policy resolution is thus **centralized at compile time and decentralized at filter time** — a seam that recURd can exploit.

### Control plane and automation: the coordination server as omniscient broker

The coordination server is "a shared drop box for public keys" that "handles device discovery, authentication, key distribution, and policy enforcement" and "distributes routing configurations and access control policies to clients, which turn them into data plane configuration" ([Control and data planes](https://tailscale.com/docs/concepts/control-data-planes); [How Tailscale works](https://tailscale.com/blog/how-tailscale-works)). Around it sits a complete automation surface available on **all plans**: a REST **admin API** at `api.tailscale.com` authenticated by personal tokens (1–90-day) or scoped OAuth clients (1-hour tokens; scopes like `devices:core`, `auth_keys`, `logs:configuration:read`, `all`), though documented request rate limits could not be found ([Tailscale API](https://tailscale.com/docs/reference/tailscale-api); [OAuth clients](https://tailscale.com/kb/1215/oauth-clients)). An official, Tailscale-maintained **Terraform provider** (`tailscale/tailscale`) manages ACL policy, keys, DNS, device tags and settings as code ([Terraform provider](https://tailscale.com/docs/integrations/terraform-provider)). **Webhooks** (all plans, HMAC-SHA256 signed, retried hourly up to 24h, replay-protected) push node-lifecycle, `policyUpdate`, and user events including `nodeNeedsApproval`/`userNeedsApproval` ([Webhooks](https://tailscale.com/kb/1213/webhooks)). **Configuration audit logging** is always on, non-disableable, retained 90 days, and binds every administratively meaningful action to the actor's plaintext identity — but **failed logins are not recorded** (only the IdP sees those), and network flow logs (connection metadata, never content) are a separate Premium/Enterprise feature ([Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging); [kb/1203](https://tailscale.com/kb/1203/audit-logging)).

**Tailnet Lock** is the one feature that deliberately *withholds* trust from the coordination server: with it enabled, a new node's key must be cryptographically signed by one of the tailnet's own **trusted signing nodes** (2–20 of them) and verified by every peer through a **Tailnet Key Authority (TKA)**, so "even if Tailscale were malicious… attackers can't send or receive traffic in your tailnet" ([Tailnet Lock, last validated Dec 2 2025](https://tailscale.com/kb/1226/tailnet-lock)). Its guarantees are bounded by a **trust-on-first-use** bootstrap, by device-key theft (the lock key lives on the device), and by **mutual exclusivity with device approval**; it is offered on the Personal and Enterprise plans.

## What the coordination server must see, and the little it cannot

The precise trust boundary is the whole argument, so it is worth stating exactly. **To deliver SSO, approval, and ACL enforcement, Tailscale's coordination server necessarily holds, in plaintext:** every device's **public key** and certificates; the **identity↔device mapping** plus IdP-issued auth tokens and their lifecycles; **per-user PII** (email/login name, display name, photo URL) and the **domain→issuer** mapping asserted via WebFinger/DNS-TXT; the **complete identity/group/policy graph** — users, groups and their memberships (synced up to 5 levels deep for Entra), tag ownership and device→tag bindings, roles, and the full grant/ACL text — because it *compiles each node's filter from that graph*; **connection and endpoint metadata** (who may talk to whom, from where) for NAT traversal and DERP selection; **device posture attributes**, including `ip:` geolocation it computes itself and `node:`/`custom:`/EDR attributes reported or pushed to it; and a **90-day, identity-attributed, non-disableable audit log** of successful logins, re-auths, and config changes ([Control and data planes](https://tailscale.com/docs/concepts/control-data-planes); [How Tailscale works](https://tailscale.com/blog/how-tailscale-works); [kb/1290](https://tailscale.com/kb/1290/user-group-provisioning); [Device postures and attributes](https://tailscale.com/docs/features/device-posture/postures-and-attributes); [Configuration audit logging](https://tailscale.com/docs/features/logging/audit-logging)). In Tailscale's own framing the social graph, membership, and identities are visible to the control plane **by construction**.

**What the control plane cannot see is narrow:** data-plane **payloads**, because "private keys never leave the device" and traffic is end-to-end encrypted over WireGuard — the same reason a **DERP relay "can never decrypt your traffic"** even while relaying it ([How Tailscale works](https://tailscale.com/blog/how-tailscale-works); [DERP servers](https://tailscale.com/kb/1232/derp)); **MFA factors and credentials**, which live at the IdP; and **failed login attempts**, which only the IdP records. Crucially, *metadata is not in this list* — Tailscale can and does reconstruct source/destination/ports/times (that is exactly what network flow logs are), so **payload confidentiality is not metadata confidentiality**.

This distinction is where **Tailnet Lock is routinely misread**. Tailnet Lock is an **integrity/authenticity control over membership**: it stops a compromised or malicious coordination server from *injecting a rogue node* into the tailnet, by anchoring node-admission trust in customer-held signing keys rather than the server. It does **not** reduce what the server sees — policy, identities, public keys, posture, and connection metadata still flow through and are stored by Tailscale exactly as before. It is confidentiality of *admission decisions' authenticity*, not confidentiality of the *graph*. And **Headscale has no Tailnet Lock equivalent at all**: the feature appears nowhere in its official feature list, FAQ, or technical write-ups (an inference from consistent absence across authoritative sources, not an explicit "unsupported" statement), and Headscale *is* the control server you now run ([Headscale features](https://headscale.net/stable/about/features/); [Headscale FAQ](https://headscale.net/stable/about/faq/)). Self-hosting Headscale (BSD-3-Clause, single-tailnet, **v0.29.3**, "not enterprise software," with the documented limitation that **OIDC groups cannot be used in ACLs** and no SCIM/roles) changes **who operates** the all-seeing control plane — you, not Tailscale — but not **what it can see**; it even lags Tailscale on the identity features that matter most for enterprise onboarding ([juanfont/headscale](https://github.com/juanfont/headscale); [Headscale features](https://headscale.net/stable/about/features/)).

The bridge to recURd is the enforcement seam named above: Tailscale **resolves centrally and enforces locally**. recURd cannot resolve centrally in plaintext, so its design problem reduces to **moving the resolver into a customer-held key domain** and keeping enforcement local — using the blind coordination network for what Tailscale uses its coordination server and DERP for only in part: ciphertext transport and rendezvous, never graph resolution.

## Designing recURd: reproduce the ergonomics, lose the visibility

The central tension, stated plainly: **Tailscale buys its ergonomics by letting the control plane read the identity/group/policy graph; recURd must reproduce the ergonomics without that visibility.** The unifying answer is a **customer-held key authority** — a generalization of Tailnet Lock from "sign node keys" to "sign and/or encrypt the entire identity, membership, tag-ownership, policy, and approval state" — whose outputs are **signed under customer-controlled keys and/or encrypted to the clients that need them**, so that recURd's coordination network transports them as opaque ciphertext and never resolves them. Enforcement stays local on each client, exactly as Tailscale already compiles-centrally-but-filters-locally; recURd simply replaces "compiles centrally" with "compiles under customer keys, client-side or in a customer-run authority." The X25519MLKEM768 post-quantum hybrid key exchange already protects the transport; the work is to ensure the *resolution* layer rides on top of it as ciphertext.

The tables below map each Tailscale capability to (a) what it does for Tailscale, (b) the requirement it implies for recURd, and (c) how to deliver it while the coordination network stays blind. After each cluster, the prose states where this is **straightforward**, **hard**, or a **trade-off**.

### Identity and enterprise sign-on

| Capability | (a) For Tailscale | (b) recURd requirement | (c) Delivering it blind |
|---|---|---|---|
| **Native OIDC SSO** | Control plane is an OIDC relying party; stores email/name/photo-URL; IdP holds credentials/MFA | Passwordless enterprise sign-on via the customer's IdP | **Straightforward.** Make the *client* (or a customer-held admin plane) the OIDC relying party. The IdP assertion/claims are verified client-side or by the key authority; the coordination network never receives the token or the PII. |
| **SCIM provisioning** | IdP pushes the user/group directory into the control plane in plaintext (Standard+) | Sync the org directory into recURd's authorization graph | **Hard.** The SCIM endpoint must be the **customer-held authority**, not the coordination network. The resulting user/group graph is encrypted to clients (or resolved by the authority into signed per-peer grants). Directory PII must never land on a relay. |
| **The 7 roles** | IAM over admin-console access only; not traffic; not SCIM-assignable | Admin-app RBAC for who may edit policy, approve, mint keys | **Straightforward.** Roles govern a **customer-side admin app**, which is outside the blind network by definition. Implement as the admin plane's own RBAC. |
| **User approval** | "Needs approval" state in control plane gates peer connectivity; on by default since 2025-05-22 | Hold new principals out of reach until a human approves | **Hard-ish.** Approval becomes a **signed capability** issued by the authority; the coordination network admits a principal only on a valid opaque token, never by reading identity. (Tailscale lets unapproved users still register with the server — recURd must *not* leak identity at registration.) |

OIDC SSO and the roles are **straightforward** precisely because Tailscale already keeps credentials at the IdP and roles at the console — recURd just relocates the relying-party and the console to the client/customer side. SCIM and user approval are **hard** because Tailscale lands the directory and the gate state on the control plane in plaintext; recURd must stand up a customer-held authority to be the SCIM target and the approver, and must carry its decisions as ciphertext. Carry forward the researchers' offboarding warning: Tailscale's revocation is **key-expiry-bounded, not instant** — recURd should decide up front whether it accepts the same latency or invests in pushed signed-revocation lists / short-TTL authorizations to peers.

### Device join

| Capability | (a) For Tailscale | (b) recURd requirement | (c) Delivering it blind |
|---|---|---|---|
| **Device approval** | Control plane holds approve/deny; unapproved device can't pass traffic | Gate a new device before it can reach peers | **Hard-ish.** Same pattern as user approval: a **signed admission token** from the authority; peers verify the signature locally; the relay sees only an opaque token. recURd effectively runs in a **Tailnet-Lock-always-on** posture (admission is authority-signed by default). |
| **Auth keys** | Bearer secret issued by control plane; registers a device as a user/tag | One-command headless join for servers, containers, agents | **Straightforward.** Issue keys **signed under customer keys**; the device presents the key to peers, which verify the signature; the coordination network treats it as an opaque blob and learns no identity from it. |
| **OAuth clients** | Tailnet-owned, non-expiring secret mints short-lived tagged keys | Non-expiring CI/automation credential that mints disposable joins | **Straightforward.** The minting authority is the **customer-held authority**, not the blind network. Minted keys are signed, tag-bound, short-TTL. |
| **MDM zero-touch join** | Push client + `AuthKey` policy to managed fleet (Premium/Ent, GA 2024-02-12) | Zero-touch enrollment of managed machines | **Straightforward.** MDM is client-side infrastructure; push the recURd client plus an **encrypted enrollment blob / signed auth key**. Nothing about this requires the coordination network to see identity. |
| **One-command / QR join** | `tailscale up` → SSO click, or QR scanned on a trusted phone | Install → one command/scan → working client | **Straightforward.** Point the login URL/QR at the **IdP or the customer admin endpoint**, not the coordination server. The handshake authenticates to the authority; the blind network only rendezvouses ciphertext. |

The entire device-join cluster is **largely straightforward**, which is the most encouraging finding for recURd: Tailscale's own headless paths (auth keys, OAuth, MDM) already exist *to bypass the browser↔control-plane handshake*, and recURd can inherit that pattern directly by making the credential **customer-signed and relay-opaque**. The only non-trivial parts are the two approval gates, which recURd should treat as signed admission tokens verified peer-side — and which collapse neatly into recURd's always-on Tailnet-Lock posture, since the coordination network is untrusted by default rather than by opt-in. This cluster is also where recURd's first product promise lands: a one-command join that "never loses a session or edit" depends on exactly this low-friction, resilient enrollment.

### Access control

| Capability | (a) For Tailscale | (b) recURd requirement | (c) Delivering it blind |
|---|---|---|---|
| **ACLs / grants** | One HuJSON policy compiled centrally into per-node IP:port filters; deny-by-default; `app` is opaque JSON clients enforce | A single deny-by-default policy that governs each agent's reach | **Hard but tractable.** Compile the policy **client-side or in the customer authority**, sign the result, and distribute per-node filters as ciphertext. The `app`-capability model is a gift: Tailscale already has clients enforce opaque JSON the server only syntax-checks — recURd can push *all* authorization as signed opaque capabilities. |
| **Tags** | Non-user device identity via `tagOwners`; identity = union of tags | Durable, policy-addressable identity for agents (not humans) | **Hard but core.** The device→tag and tag-ownership bindings must be **vouched by the authority** (signed certificates), not stored on the relay. This is the primitive that gives each coding agent an identity. |
| **Autogroups** | Dynamic selectors (`:member`, `:self`, `:tagged`, …) resolved at compile time | "Each agent reaches only its own record," "any member," etc. | **Hard.** `autogroup:self` and friends need the **user→device ownership graph**; recURd must hold that graph client-side/authority-side (encrypted) and resolve it there, since the blind network cannot. |
| **Device posture** | Control plane *collects and evaluates* device attributes; `ip:` geolocation computed server-side | Health/compliance gating of agent hosts | **Trade-off (hardest).** `node:`/`custom:`/EDR attributes can be **self-reported and attested** to the authority, which evaluates them; but **control-plane-computed `ip:` geolocation is incompatible with a blind network** that refuses to be a central evaluator of connection metadata. recURd must either drop server-computed geolocation or accept weaker client-attested signals. |
| **Tailscale SSH** | `ssh` rules; `check` mode re-auths through the IdP every `checkPeriod` | Audited, re-authenticated access to agent hosts | **Hard.** The network filter + SSH rule compile like any grant (tractable), but **`check`-mode periodic re-auth needs a trusted authority in the loop**. recURd can route that re-auth to the customer authority/IdP client-side, but it is a live dependency, not a static signed artifact. |

Access control is **the heart of the hard problem**, but it decomposes well. The `ip`-layer filter is already enforced locally in Tailscale, so recURd inherits local enforcement for free; the work is relocating *compilation* of grants, group/autogroup resolution, and tag-ownership vouching to the customer authority and shipping the output as signed ciphertext. Tailscale's **application-capability model is the single most reusable idea here**: because `app` capabilities are opaque JSON that the policy engine merely validates and clients enforce, recURd can generalize that pattern so that *all* authorization — not just app-layer — travels as signed, opaque capability blobs the coordination network cannot interpret. **Tags are hard but non-negotiable** because they are how non-human agents get a policy identity, which is recURd's whole use case. **Posture is the clearest trade-off**: node/custom/EDR attributes can be client-attested to the authority, but Tailscale's server-computed `ip:` geolocation presumes exactly the central metadata-reading recURd forgoes, so that specific signal must be dropped or replaced with a weaker attested one — and this should be stated to buyers, not papered over. SSH `check`-mode is hard for a subtler reason: it is inherently a **live round-trip to a trusted authority**, so it cannot be reduced to a static signed artifact the way grants can.

### Automation and the trust anchor

| Capability | (a) For Tailscale | (b) recURd requirement | (c) Delivering it blind |
|---|---|---|---|
| **Admin API** | REST control of devices/policy/keys/users; scoped tokens | Programmatic admin for provisioning and policy | **Straightforward.** The API is served by the **customer-held admin plane/authority**, not the coordination network; scope it like Tailscale's OAuth clients. |
| **Terraform / IaC** | Official provider manages ACLs, keys, tags as code | Policy-as-code, GitOps review of authorization | **Straightforward.** Point the provider at the customer authority's API. (Keep the policy repo private — it contains identities, exactly as Tailscale warns.) |
| **Webhooks** | Control plane emits signed node/user/policy events | Eventing for approvals, joins, policy changes | **Straightforward.** The **authority** emits HMAC-signed events; the blind network isn't the event source because it doesn't see the events anyway. |
| **Audit log** | Always-on, 90-day, identity-attributed, server-readable | "Every agent's outward reach… on a record only their team can read" | **Trade-off → advantage.** A blind network *cannot* produce an identity-attributed log — but that is recURd's headline feature inverted: write the record **client-side, end-to-end encrypted to the team**. recURd gains confidentiality Tailscale lacks; it loses the third-party, non-disableable, independently-vouched property of a server-side log. |
| **Tailnet Lock** | Opt-in; node-key signing anchored in customer keys; authenticity only | The **foundational trust anchor** for the whole design | **Foundation, not a feature.** recURd generalizes Tailnet Lock from signing node keys to signing the **entire identity/policy/approval graph**, and runs it **always-on** rather than opt-in. Note the TOFU-bootstrap, device-key-theft, and (for Tailscale) device-approval-exclusivity limits must be engineered around. |

The automation cluster is **mostly straightforward** because it attaches to a customer-held admin plane that recURd must build anyway; the admin API, Terraform, and webhooks are then ordinary customer-side services. The **audit log is recURd's signature inversion**: Tailscale's log is powerful *because* the server reads identity, which is exactly what recURd forbids — so recURd rewrites the capability as a **client-side, end-to-end-encrypted record that only the customer's team can decrypt**, directly realizing the "record only their team can read" promise and the "one write, three readers" framing. The explicit cost to acknowledge is that a self-written encrypted record lacks the independent, third-party tamper-evidence of a server-held audit log; recURd should counter that with signed, append-only/hash-chained records under customer keys so integrity does not depend on the (blind, untrusted) network. **Tailnet Lock is the keystone**: it is the one Tailscale primitive that already anchors trust in customer keys rather than the server, and recURd's entire design is, in effect, Tailnet Lock generalized from membership authenticity to *total graph authenticity and confidentiality*, running by default.

## A pragmatic bar for "tailnet-grade" onboarding, and what to build first

To credibly claim **tailnet-grade onboarding**, recURd needs a minimum set that a Tailscale user would recognize as equivalent: (1) **install → one command/scan → working client**, including a headless one-liner and an MDM/zero-touch path; (2) **passwordless OIDC SSO** via the customer's IdP, verified client-side; (3) a **single deny-by-default policy** of grants with **tags** for agent identities, compiled under customer keys and enforced locally; (4) **device and user approval** as signed admission tokens; (5) the **customer-held key authority** (generalized Tailnet Lock) that everything signs and encrypts under; and (6) a **client-side, team-only-readable encrypted record** of each agent's outward reach. That set maps one-to-one onto recURd's two promises — never-lost sessions (frictionless, resilient join) and private/approved/team-only reach (approval gates + encrypted record + egress grants).

Ranked by build order, because later items depend on earlier ones:

1. **The customer-held key authority (generalized Tailnet Lock), first and foremost.** Everything else signs or encrypts under it; without a client-verifiable trust anchor that the coordination network cannot read, blind resolution is impossible. This is the architectural spine.
2. **One-command and headless/OIDC client-side join**, with customer-signed, relay-opaque auth-key and OAuth-equivalent credentials. This delivers the visible ergonomics and is low-risk because it mirrors Tailscale's existing browser-bypass paths.
3. **Client-enforced deny-by-default grants plus tags**, compiled from an authority-signed policy and distributed as opaque capabilities. Agents cannot have governed reach without this, and it is recURd's core security claim.
4. **Signed-token device/user approval gates**, so a principal is admitted only on a valid opaque token — recURd's always-on admission control.
5. **The client-side encrypted, team-only record.** The headline differentiator and the "record only their team can read" promise; build it once the graph and joins exist to be recorded.
6. **Then the rest, in order of leverage:** SCIM-equivalent provisioning into an encrypted directory; the admin API, Terraform, and webhooks on the customer authority; MDM zero-touch; device posture (shipping client-attested signals and explicitly dropping server-computed geolocation); and Tailscale-SSH-style `check`-mode re-auth as a live authority round-trip.

## Open questions the research could not close

The sharpest unresolved question is **the depth of recURd's blindness**. Tailscale's control plane is payload-blind but **metadata-sighted** — it reconstructs source/destination/ports/times without ever reading traffic. recURd's promise that reach is "on a record only their team can read" implies hiding the **metadata/social graph** too, which is **strictly stronger than Tailscale's guarantee** and strictly harder: it must be confirmed whether URnetwork's relays carry only ciphertext *payloads* (like DERP) or also conceal connection metadata (requiring onion-style routing or similar). Every "straightforward" verdict above assumes identity and PII stay off the relay; if metadata-hiding is also required, several items (posture geolocation, any rendezvous that reveals who-talks-to-whom) get harder.

Two recURd-specific trade-offs remain open: **control-plane-computed device posture** (notably `ip:` geolocation) cannot be reproduced on a network that refuses to be a central metadata evaluator, so recURd must choose between dropping it and accepting weaker client-attested signals; and **revocation latency** — Tailscale's is key-expiry-bounded rather than instant, and a blind network makes instant revocation harder (it likely requires pushed signed-revocation lists or short-TTL authorizations), so recURd must pick a model deliberately.

Finally, carry forward the researchers' flagged gaps on the Tailscale/Headscale side, none of which change the thesis but all of which qualify specific claims: the exact per-plan gating of **custom OIDC / "SSO with any IdP"** did not render from the pricing page; **PKCE** support status is ambiguous (a search summary and the live custom-OIDC page conflict); the plan tier that gates **log streaming to SIEM** is contradictory across sources; **admin-API request rate limits** are undocumented; the **TLK signature algorithm/curve** is not stated in the KB pages; and **Headscale's lack of a Tailnet Lock equivalent** is an inference from consistent absence across its authoritative docs, not an explicit "unsupported" statement — a direct check of the `juanfont/headscale` issue tracker would confirm it.

## Conclusion

The research reframes recURd's challenge from "build a VPN control plane that can't see traffic" — which Tailscale and even DERP already achieve — to the sharper "build a *resolver* that can't see the identity and policy graph," which Tailscale explicitly does not attempt and Headscale does not either. The decisive realization is that Tailscale has already done half of recURd's work: it **compiles policy centrally but enforces it locally**, and it already ships application-layer authorization as **opaque, client-enforced capabilities** the server only syntax-checks. recURd's design is therefore less an invention than a **relocation and generalization** — move compilation from the server to a customer-held key authority, carry its signed/encrypted output as ciphertext over the blind network, and keep enforcement on the client where Tailscale already put it. Tailnet Lock is the proof that this is philosophically compatible with the Tailscale model: Tailscale already lets customers anchor *membership* trust in their own keys rather than the server, and recURd simply extends that anchor from node-key signatures to the entire graph and makes it the default rather than an option.

The practical upshot is an encouraging asymmetry. The parts of "tailnet-grade onboarding" that users *feel* — the one-command join, the SSO click, the QR scan, the zero-touch fleet — are the parts that are **straightforward** to deliver blind, because they already belong to the client and the IdP. The parts that are **hard** (group/tag resolution, approval, SSH re-auth) are hard in a bounded, well-understood way that a customer-held authority resolves. Only two things force genuine trade-offs: server-computed posture geolocation, which recURd should drop or weaken openly, and the audit log, which recURd does not lose but *inverts* into its headline advantage — a record only the customer's team can read. If recURd ships the customer-held key authority first and treats everything else as artifacts signed and encrypted beneath it, it can credibly claim tailnet-grade onboarding while delivering a confidentiality guarantee Tailscale, by its own architecture, cannot.
