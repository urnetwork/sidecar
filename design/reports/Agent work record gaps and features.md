# Keep the session, sign the approval

URnetwork should expand "the private record of agent work across harnesses" into two linked objects that no product offers together: an encrypted vault, owned by each developer, of every agent session and of everything each run changed, whichever harness or tool path made the change; and a team-held ledger of approval receipts that binds each proposal, human decision and executed action under one ID and can be shown to a client or auditor field by field without exposing code. User evidence ranks developer pains well above compliance: across 914 participants in eleven complaint themes, the broadest are reviewing and undoing what a run changed (edits made through Bash, subagents or reverts escape every harness's checkpoints), sessions that harnesses delete or hide, and handoff across surfaces, machines and teammates, with approvals bound to what actually ran a smaller but sharper fourth. Buyers ask for less, and later, than the earlier positioning assumed: today's questionnaires, contracts and auditors ask which AI a team uses and whether a human reviews it, while "what did the agents touch" hardens only with the AICPA's proposed 2027 SOC 2 criteria, the EU AI Act's high-risk dates and most Cyber Resilience Act duties, all taking effect from December 2027. The record's first job is therefore to rescue the developer when a session or an edit goes missing, while it builds up the agent inventory and approver change log those later demands will want. Three things the earlier work leaned on do not set the product apart: tamper-evidence, which open-source signed logs, dozens of IETF receipt drafts and Anthropic's own transparency log already provide; cost per shipped change, which five measurement platforms sell; and public provenance, which is retreating now that Linux has dropped its AI tag and developers strip vendor trailers. What does set it apart is the combination of customer-held keys, capture from outside any single harness, approvals signed by humans, and selective disclosure and erasure built from mature 2025–26 standards, with no need for BBS signatures or zero-knowledge proofs. The hidden constraint is inside the team, because a record the employer can read is a monitoring system under German works-council law and draws developers' objections, so raw sessions belong under each developer's keys and only actions, approvals and hashes under the team's. The window is set by harness owners extending their own records into attribution, and by Span, whose local recorder already keeps sessions private to engineers but whose documentation mentions no customer keys, tamper-evidence or approval capture.

### Edits that bypass every harness's checkpoints

The broadest pain is not a missing audit log. It is the missing **session-scoped change set**: one view of every file a run touched. Claude Code's VS Code users want aggregated diff review (220 +1 on [#33932](https://github.com/anthropics/claude-code/issues/33932)). Codex users want the full diff before approving (241 +1 on [#2998](https://github.com/openai/codex/issues/2998)). And 52 people protested when Claude Code hid which files a run had read ([#21151](https://github.com/anthropics/claude-code/issues/21151)).

Beneath all three lies one defect that crosses products: **harness checkpoints and change lists track only edits made through the harness's own edit tools**. Claude Code's documentation says "A file that only Bash commands changed isn't tracked" ([Checkpointing](https://code.claude.com/docs/en/checkpointing)). Cursor staff wrote that a restore "only reverts files the agent edited with its own edit tools", which leaves terminal, subagent and manual edits behind ([Cursor forum](https://forum.cursor.com/t/rollback-doesn-t-restore-previous-chat-state-and-files-remain-in-git-changes/170624)).

In August 2026, Claude Code's auto mode began telling the model to edit through Bash. Since then, `/rewind` "reports success but leaves every change on disk" ([#87575](https://github.com/anthropics/claude-code/issues/87575)). One auto-mode session logged 96 Bash calls and not a single Edit or Write call, so every checkpoint was empty ([#94657](https://github.com/anthropics/claude-code/issues/94657)). For one legally blind developer, "the diff is the only channel I have to know what changed in a file" ([#87575](https://github.com/anthropics/claude-code/issues/87575)).

When Codex removed `/undo`, 490 people asked for it back ([Codex #9203](https://github.com/openai/codex/issues/9203)). The usual fallback, `git diff`, fails on the point one user named: it "pulls in any pre-existing uncommitted changes in the repo that predate the session" ([#31888](https://github.com/anthropics/claude-code/issues/31888)).

### History developers thought was safe

The second cluster is history the developer believed was safe. A repository collaborator at Anthropic confirmed that Claude Code silently deletes transcripts older than 30 days by default ([#62476](https://github.com/anthropics/claude-code/issues/62476)). Meanwhile, `history.jsonl` keeps every typed prompt forever, in plaintext ([#98575](https://github.com/anthropics/claude-code/issues/98575)). Users treat transcripts as working memory. Simon Willison wrote that "Most of my work is captured in them now" ([HN](https://news.ycombinator.com/item?id=48921792)), and another user called them "a proof of work, justifying the spend" ([#59248](https://github.com/anthropics/claude-code/issues/59248)).

Sessions also disappear behind UI and update bugs in Claude Code, Codex and Cursor, while the files remain on disk. Codex shows the opposite failure: one user found 396.5 GB of session logs kept indefinitely ([Codex #6015](https://github.com/openai/codex/issues/6015)).

Handoff draws the third-largest +1 total, led by a request for a read-only view of terminal sessions in the desktop app ([#28791](https://github.com/anthropics/claude-code/issues/28791)). These requests increasingly cross harnesses: "a cumulative history of all my agents would be nice" ([HN](https://news.ycombinator.com/item?id=48879774)). Recorders that hook into a repository miss work that starts elsewhere. One agent, launched from a parent folder, made 29 commits, and 26 of them lacked Entire's checkpoint trailer. A commenter concluded that "the actual capture boundary is the agent process, not the working tree" ([Entire #529](https://github.com/entireio/cli/issues/529); [Entire #1098](https://github.com/entireio/cli/issues/1098)).

### Smaller themes carry the sharpest requirements for a record

Approvals draw fewer people, but they produce the sharpest statements of what a record must do. One user found no way to answer "What have I authorized Claude to do in this session?" and asked for a log of every allow and deny decision ([#32904](https://github.com/anthropics/claude-code/issues/32904)). Hook decisions that should prompt the user are silently approved in auto and bypass modes, and logged as `hook_success` ([#51255](https://github.com/anthropics/claude-code/issues/51255)). Codex retired its strictest approval policy without notice ([Codex #39973](https://github.com/openai/codex/issues/39973)). And a Cursor user running in Run Everything mode lost an entire drive because "nothing was gated" ([Cursor forum](https://forum.cursor.com/t/cursor-agent-auto-ran-a-command-that-wiped-an-entire-drive-windows-powershell/175121)). The documented harm of auto modes is that the harness's own safety records go dark together: checkpoints, diffs, hooks and even `/cost`.

Requests to inspect what an agent was given tend to follow a surprise. Seventy-seven users +1'd a report that Claude Code puts the account email into the system prompt ([#81138](https://github.com/anthropics/claude-code/issues/81138)). One user pinned down the structural limit: no hook can "inspect or modify the assembled request body before it leaves" ([#44868](https://github.com/anthropics/claude-code/issues/44868)).

Complaints about secrets draw few reactions, but they describe the same failure on every harness: instructions do not keep credentials out of saved transcripts ([#44868](https://github.com/anthropics/claude-code/issues/44868); [Codex #36079](https://github.com/openai/codex/issues/36079)). Cost requests ask for spend attached to the unit of work, whether a session, a client or a pull request. They also ask for the subagent and classifier calls that `/cost` leaves out ([#55768](https://github.com/anthropics/claude-code/issues/55768); [#43945](https://github.com/anthropics/claude-code/issues/43945)).

### Four promises the record must make developers

Not every developer wants a record. The Hacker News thread on Entire's launch was mostly skeptical ("I did test it and use it and trashed it because there is very little value"). Later threads argued that "nobody wants to read someone else's conversation", and that commits should store "CHOICES… Not the whole session" ([HN](https://news.ycombinator.com/item?id=46967727); [HN](https://news.ycombinator.com/item?id=48846859); [HN](https://news.ycombinator.com/item?id=48846415)). The workarounds users build converge on two artifacts: a durable private transcript, and a short decisions file kept with the repository, such as the PROGRESS.md that Cursor staff endorsed ([Cursor forum](https://forum.cursor.com/t/agent-loses-entire-conversation-when-interrupted-mid-work/173005)).

That yields four promises to developers, in order of evidence. First, nothing a run changed is invisible or irreversible, whatever tool made the change. Second, nothing a run did is lost: retention is the owner's policy, archiving replaces deletion, and prompts and replies follow one rule. Third, any run can be picked up in another harness, on another machine or by a teammate, through a summary of its decisions rather than its full transcript. Fourth, every approval is on file and bound to what ran, whatever the permission mode. Inventory, cost and telemetry are what admins ask the record to supply, and far fewer people are behind those requests.

## Five record silos exist, and none is vendor-blind or verifiable

Every tool records some mix of prompts, tool calls, and model, token and cost data, but the records sit in five silos. The first is the transcripts and telemetry each harness keeps locally, which are plaintext and cover one harness each. The second is the vendors' compliance feeds, which see only what reaches the vendor. Anthropic's compliance transcripts "show what Claude was asked to do and what it returned, not what occurred on the device", and OpenAI warns that "Conversation visibility alone does not establish a complete record of local actions" ([Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions); [OpenAI governance](https://learn.chatgpt.com/docs/enterprise/governance)). The third is provenance stored in git or files (Entire, git-ai, Agent Trace, SpecStory, AgentFS), which anyone with the repository can read. The fourth is gateways and observability backends (Tailscale Aperture, Coder, Cloudflare, Langfuse, LangSmith, Braintrust, Arize, Datadog), which see only the traffic that passes through them or whatever hooks export. The fifth is security vendors, which keep verdict logs in their own consoles.

**No commercial agent-work record in the set is vendor-blind or verifiable by a third party.** The only signed Merkle log among them, Anthropic's Access Transparency log, records Anthropic staff access to customer content, not agent work ([Access Transparency log](https://platform.claude.com/docs/en/manage-claude/access-transparency-log)).

The table has two consequences. The table-stakes rows are the floor a security review will check. They include identity on every entry; OTel and SIEM export mapped to the GenAI conventions' `invoke_agent` and `execute_tool` spans; redaction, search, resume and sharing; and intake of hook events from Claude Code, Codex and Cursor. None of these is a reason to buy. The absent rows, by contrast, map almost one for one onto the designed record: customer keys, approval binding, third-party verification, selective disclosure, erasure, per-client partitions, message provenance, and the inbound reach that the sidecar's own forwards and public edge create.

Signing alone is not on that list, because it is already common. Anthropic runs signed-log infrastructure in the C2SP tile format, an open specification for transparency logs. Entire signs its checkpoint commits only when its signer works; otherwise "the commit is created unsigned and a warning is logged" ([Entire checkpoint signing](https://github.com/entireio/cli/blob/HEAD/docs/architecture/checkpoint-signing.md)). GitHub has signed every Copilot cloud-agent commit since 3 April 2026 ([GitHub](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/)). And open-source projects such as Obsigna sign every tool call ([Obsigna](https://github.com/agent-receipts/obsigna)). What nobody offers is signing, customer-held keys and coverage across harnesses together.

The market is also losing its independent record vendors. **Git AI's team joined OpenAI's Codex group on 11 September 2026** ([Git AI](https://usegitai.com/blog/git-ai-is-joining-openai)), ClickHouse acquired Langfuse in January ([Langfuse](https://langfuse.com/blog/joining-clickhouse)), and SpaceX agreed in June to buy Cursor, according to press reports ([Techzine](https://www.techzine.eu/news/devops/142197/spacex-acquires-cursor-for-60-billion/)). The 2025 agent-security startups went to Palo Alto, SentinelOne, Cato and CrowdStrike, and CrowdStrike's AIDR collector reaches end of support on 30 November 2026 ([CrowdStrike](https://aidr-docs.crowdstrike.com/docs/aidr/collectors)). Entire removed its file-restore feature and relaunched as a git forge on 26 October ([Entire](https://entire.com/news/entire-launches-an-independent-git-forge-for-agent-human-collaboration.md)), and Agent Trace remains at v0.1.0, with its canonical repository returning a 404 error ([AAIF working group](https://github.com/aaif/wg-observability-and-traceability/blob/HEAD/working-documents/PRIOR-WORK.md)).

At the same time, each harness vendor is improving the record of its own harness. GitHub streams Copilot CLI, VS Code and JetBrains sessions to customers' SIEMs in preview, and Anthropic's Compliance API now returns local Claude Code transcripts ([GitHub](https://github.blog/changelog/2026-07-02-copilot-agent-session-streaming-is-now-in-public-preview/); [Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions)). Keeping a record is becoming a harness feature. What stays scarce is a record that is neutral across harnesses and held under the customer's keys. A correct undo across all tool paths is scarce too: users demand it loudly, and the major vendors have narrowed or withdrawn it.

## Buyers ask which AI you use; "who approved it" hardens from December 2027

The earlier positioning set the trigger at the first questionnaire or SOC 2 request asking what agents touched. That request is rare today.

### Questionnaires and auditors ask about tools, not agent actions

Every major family of security questionnaires now carries AI content. That includes the Cloud Security Alliance's 320-question AI-CAIQ, the SIG 2026 AI domain, HECVAT 4, and Vanta's AI Security Assessment. Vanta's basic tier covers companies with "software built with AI", which reaches any team that builds with coding agents ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-aicm-v1-1-update-20260730-csa-styled/); [Vanta](https://www.vanta.com/resources/introducing-vantas-ai-security-assessment)). But the public material asks about use and data flow: which tools and models are used, whether customer data trains them, which subprocessors are involved, and whether a human reviews the output. CSA's July 2026 revision of its AI controls added no controls for logging, audit trails or provenance. No independent measure exists of how often AI questions appear; the figures in circulation come from vendors.

Auditors are on the same timeline. SOC 2 still runs on the 2017 Trust Services Criteria. On 28 October 2026, the AICPA published an exposure draft of 2027 criteria with AI points of focus. It is open for comment until 15 January 2027 and would apply to **engagements that begin on or after 31 December 2027** ([AICPA](https://www.aicpa-cima.com/news/article/aicpa-proposes-update-of-soc-2-r-trust-services-criteria-to-enhance-the-relevance-usability-and-value-of-cpas-reports)). One consultancy's reading finds AI points in 17 criteria, including "controls against unsanctioned AI tools" and access reviews that cover AI accounts. Both are questions of inventory and identity ([Elevate](https://elevateconsult.com/insights/soc-2-trust-services-criteria-2027/)).

Until then, change management treats AI like any other technology. An A-LIGN auditor, quoted second-hand in Vanta's community forum, is "not seeing fully AI-only code review (no human) accepted as standard", and reports that "Most clients keep a human at the approval/push-to-prod step" ([Vanta Community](https://community.vanta.com/x/grc/nwnr9uwkwu1y/ai-only-code-reviews-and-soc-2-change-management-e)). Auditors of AI products ask for per-inference logs containing "a redacted prompt or prompt hash", not plaintext ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-soc2-ai-controls-gap-20260830-csa-styled/)). ISO/IEC 42001's event-log and human-oversight controls fit the record, but only **271 accredited certificates** existed worldwide at the end of 2025 ([DQS](https://www.dqsglobal.com/es/acerca-de/sala-de-prensa/iso-survey-2025-las-certificaciones-iso-crecen-un-11-en-el-mundo-y-un-28-en-espana)).

### Contracts and regulated systems already demand proof

Contracts are where demands for proof already exist, though unevenly. Microsoft's supplier Data Protection Requirements (DPR) v12 apply to suppliers that "use AI Systems in connection with" their work. Requirement 33 says change logs "must track changes, provide information regarding the reason for the change, and include the name and title of the designated approver", with 90 days of records available on request. Section K adds logs of failures, hallucinations and misuse, plus "Processes for reproducing system failures" ([Microsoft DPR v12](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/accex/documents/presentations/FY26-Microsoft-Supplier-Data-Protection-Requirements-v12_en-US.pdf)).

Law and the public sector show the same pattern. Only 20 of 1,054 public outside-counsel guidelines mention AI, but those that do ask for disclosure at the level of the task; Zscaler asks timekeepers to note AI use "in their time entry" ([Fulkerson Advisors](https://www.fulkersonadvisors.com/research/ai-in-outside-counsel-guidelines)). California's judicial branch requires contractors to notify it before including GenAI in deliverables, and treats undisclosed use as a possible material breach ([Judicial Branch of California](https://courts.ca.gov/genai-contract-provisions)).

Federal reach to coding agents is narrow. The Office of Management and Budget (OMB) excludes AI "used at the option of a contractor". The General Services Administration's LLM clause, effective 19 October 2026, removes itself for incidental use. And the FY2026 NDAA bars Defense Department contractors from "covered AI" such as DeepSeek ([OMB M-25-22](https://www.whitehouse.gov/wp-content/uploads/2025/02/M-25-22-Driving-Efficient-Acquisition-of-Artificial-Intelligence-in-Government.pdf); [Crowell](https://www.crowell.com/en/insights/client-alerts/gsa-issues-final-rule-on-large-language-model-procurements); [CRS](https://www.everycrsreport.com/reports/IF13197.html)).

Sector rules reach a coding agent only when it acts inside the regulated system. PCI DSS requires logs of "all actions taken by any individual with administrative access, including any interactive use of application or system accounts", kept for 12 months. DORA requires change logs protected against "tampering, deletion, and unauthorised access". FINRA's 2026 report asks firms to consider "how to track agent actions and decisions" in business uses ([PCI 10.2.1.2](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/10/02/01/02/); [PCI 10.5.1](https://ce.prod.cloudaware.com/frameworks/pci-dss-v4.0.1/10/05/01/); [DORA RTS Art. 12](https://www.springlex.eu/en/packages/dora/rts-rmf-regulation/article-12/); [FINRA](https://www.finra.org/rules-guidance/guidance/reports/2026-finra-annual-regulatory-oversight-report/gen-ai)).

Insurers are changing policy wording rather than applications. In a small check run by a vendor, none of five cyber-insurance application forms asked about AI ([Nonimo](https://nonimo.ai/resources/guides/cyber-insurance-questionnaire-ai-questions/)). The agent-specific standard, AIUC-1, certifies agent vendors. Since July it has made secret-leakage and secure-code requirements mandatory for agents that generate code ([NYU Shanghai RITS](https://rits.shanghai.nyu.edu/ai/aiuc-1-the-ai-agent-certification-turns-to-coding-agents/)).

### Narrow the trigger and answer today's question with evidence

Three implications follow. First, the beachhead's trigger should narrow from "the first questionnaire" to the five situations where a demand for proof already exists. One is a supplier to Microsoft completing DPR Section K. Another is a consultancy, agency or legal-services team bound by client disclosure terms. A third is a team that wants to remove human approval from low-risk change tiers and needs evidence an auditor will accept. The last two are a fintech or health vendor whose agents act with administrative access on in-scope systems, and a team that ships agents and faces questions like AIUC-1's.

Second, the record's first job is to answer today's question with evidence rather than prose. That means an inventory compiled from actual runs (which harness, version and model ran, and under whose identity), and an approver change log that matches Microsoft's requirement 33 field for field. Per-run activity entries should hold hashes of prompts rather than the prompts themselves. Then, when the 2027 criteria ask "what did agents touch", the answer will already exist.

Third, the team record should keep at least 12 months, with 90 days immediately searchable. That covers PCI and Microsoft and exceeds the AI Act's six-month floor. The Act's repeated phrase "under their control" favours logs the customer holds ([AI Act Art. 26](https://artificialintelligenceact.eu/article/26/)). An archive of transcripts would itself become client-confidential material under data-handling terms such as the FDIC's outside-counsel rule against putting its work product into open GenAI tools, or the GSA clause's flowdown to anyone who stores government data ([Fulkerson Advisors](https://www.fulkersonadvisors.com/research/ai-in-outside-counsel-guidelines); [Crowell](https://www.crowell.com/en/insights/client-alerts/gsa-issues-final-rule-on-large-language-model-procurements)). That argues again for a team record that leads with metadata.

The weak spot is measurement. No vendor of governance, risk and compliance software publishes how often AI questions appear, and no founder or forum thread describing this trigger was found.

## Five platforms already price AI spend per shipped change

Measuring AI's impact is a crowded field. Every engineering-intelligence (EI) platform has an AI-impact module, and the category has converged on three layers: adoption data from vendor APIs, outcomes from git and CI joined to AI labels, and, since mid-2026, spend per outcome. Five platforms now price that spend. Faros defines "cost per outcome" by team, model and tool. Swarmia spreads each person's daily AI cost across the pull requests they touched. Span reports dollars per agent session. Waydev markets an "AI Spend Hub". And Git AI's Teams tier links tokens to pull requests ([Faros](https://www.faros.ai/solutions/ai-coding-roi); [Swarmia](https://help.swarmia.com/features/ai-tools/ai-cost); [Span](https://www.span.app/); [Waydev](https://waydev.co/); [Git AI](https://usegitai.com/)). Large deals confirm the demand: Atlassian agreed to buy DX for a reported US$1B in September 2025, and Span raised $25M that November ([BNN Bloomberg](https://www.bnnbloomberg.ca/business/2025/09/18/atlassian-to-acquire-developer-productivity-platform-dx-for-us1-billion); [AI Journal](https://aijourn.com/span-raises-25m-to-bring-clarity-to-engineering-teams-navigating-ai-transformation/)).

The harness vendors supply per-user data for their own harness only, each with its own caveats. Anthropic calls its contribution metrics "deliberately conservative" and notes that its count of accepted lines "does not track subsequent deletions" ([Claude analytics](https://code.claude.com/docs/en/analytics)). Its analytics API also excludes subscription seats, leaving one admin to write "We have gone completely blind" ([#27780](https://github.com/anthropics/claude-code/issues/27780)). Cursor warns that commit hashes "are not unique or immutable" ([Cursor](https://cursor.com/docs/account/teams/ai-code-tracking-api)). GitHub leaves Copilot cloud-agent pull requests out of its review-time figures ([GitHub](https://docs.github.com/en/copilot/reference/copilot-usage-metrics/copilot-usage-metrics)).

The buyer's need is real, and it has moved from adoption to accountability; the figures that follow come from different populations, so they should not be combined. Leaders distrust usage metrics: LeadDev's 2026 report found **58% of engineering leaders calling token-usage metrics ineffective** ([LeadDev](https://leaddev.com/the-ai-impact-report-2026/)). Costs are rising fast. Jellyfish's platform data shows the median cost per AI user rising from about $5 to $81 a month between August 2025 and May 2026 ([Jellyfish](https://jellyfish.co/state-of-ai-software-engineering/)), and Gartner predicts AI coding costs could exceed the average developer's salary by 2028 ([CFOtech](https://cfotech.co.uk/story/gartner-warns-ai-coding-costs-may-top-developer-pay-by-2028)). Companies are responding with caps: Uber reportedly limited spending to $1,500 per employee per month per tool after using up its 2026 budget in about four months ([Simon Willison](https://simonwillison.net/2026/Jun/3/uber-caps-usage/)). Yet DX reports that while leaders want to cap spend by team or job title, "most usage-based enterprise plans lack that granularity" ([DX](https://getdx.com/blog/how-are-engineering-leaders-approaching-2026-ai-tooling-budget/)). Quality worries ride alongside cost. Faros's data from its own customers shows median review time five times higher, and incidents per pull request roughly tripled, among heavy adopters ([Faros](https://faros.ai/research/ai-acceleration-whiplash)), and the 2025 DORA report still finds AI negatively related to delivery stability ([DORA](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).

The record adds something where every data source shares a blind spot. Today's sources cannot see local command-line work committed under a human's identity. They cannot attribute work consistently across harnesses, or record approvals of individual actions. Their provenance does not survive squash and rebase merges done on the hosting service. And none can say whether agent code is still there weeks later.

Three metrics could fill these gaps, each with a caveat. The first is **actual cost per run, across harnesses**, including usage on the customer's own API keys, Bedrock and Vertex, which vendor APIs miss. It is more accurate than spreading cost by the day, but it is not new, so the pitch is "the only cost-per-change figure you can audit." The second is **survival per run, across harnesses**, which is new only if it survives squash merges. A local process cannot see those merges, so this metric needs a reconciler running in CI or as a repository bot, keyed to content hashes compatible with Agent Trace's `content_hash` ([Agent Trace](https://agent-trace.dev/)). The third is an **approval-to-revert ratio**: reverts or incidents per hundred human-approved actions, set against actions approved by configuration or hooks, by role and permission mode. It appears in no product reviewed. But no survey shows leaders asking for it, and because approvers are individuals, it carries the highest surveillance risk.

Academic work warns against simple vendor rankings. Variation between agents exceeds the gap between agents and humans in how long code survives, and revert rates differ sharply by vendor ([Rahman & Shihab](https://arxiv.org/abs/2601.16809); [Kraishan](https://arxiv.org/abs/2609.17598)).

As a dashboard, measurement is a feature of other platforms, and the harnesses themselves are converging on it. Git AI's founders joined OpenAI, reportedly to work on "better data on how coding agents perform and the returns they generate" ([The New Stack](https://thenewstack.io/openai-hires-git-ai/)). The record should instead be the data layer those platforms ingest and can audit: an attribution export compatible with Agent Trace, plus approvals and what happened to the code after merge. It should also put a cost line where developers asked for one. That means the run's handoff note and pull request ("This feature took 4 Claude sessions and 3.2M tokens"), and cost per client for consultancies ([#34803](https://github.com/anthropics/claude-code/issues/34803); [#55768](https://github.com/anthropics/claude-code/issues/55768)). Measurement is also where the surveillance backlash lands hardest, which the section on privacy inside the team takes up.

## Linux dropped its AI tag after ten months on a tenth of commits

Open source has converged on human accountability rather than machine provenance. Almost every major project now has a written AI policy, and the policies fall into three groups. Gentoo, NetBSD, QEMU, Servo, Zig and GNOME's extension store ban AI contributions; Ghostty, LLVM, Fedora, Node.js, Mesa, curl and the Linux kernel require disclosure plus human accountability; and Debian and CPython encourage disclosure without requiring it. Their shared core is that a human must understand and answer for the code, and only a human may sign the Developer Certificate of Origin ([kernel](https://www.kernel.org/doc/Documentation/process/coding-assistants.rst); [QEMU](https://www.qemu.org/docs/master/devel/code-provenance.html); [Debian](https://www.debian.org/vote/2026/vote_002)).

Commit trailers are a minority mechanism, and they are retreating. The kernel added an `Assisted-by` tag in December 2025. In July it cut the model name from the tag as "free advertising to proprietary software companies". On 14 October 2026 it removed the tag from its documentation, because "its absence says nothing about how a patch was made" ([Brauner commit](https://github.com/torvalds/linux/commit/816d9992d9ed); [Levin commit](https://github.com/torvalds/linux/commit/1e035297ffda)). About **10% of the 18,533 changesets** in the 7.3 cycle carried the tag, while a senior maintainer estimated that "probably 90%" of contributors use LLMs ([LWN](https://lwn.net/SubscriberLink/1099594/6e351ed3aecb2ae4/)). Maintainers still want to know how a patch was made, but in the cover letter rather than the permanent changelog. Other projects moved the same way. Mesa now says "Do not advertise the model". Node.js keeps brand names to the pull-request description. And LLVM says its labels are "intended to facilitate reviews, and not to track which parts of LLVM are generated" ([Mesa](https://docs.mesa3d.org/submittingpatches.html); [Node.js](https://github.com/nodejs/node/blob/main/doc/contributing/ai-guidelines.md); [LLVM](https://llvm.org/docs/AIToolPolicy.html)).

### Developers strip vendor trailers they never chose

Developers push harder against attribution than projects do, and their target is specific: markers the vendor chose, on by default, carrying a brand, public and permanent. Claude Code's default of adding a session URL to commits drew 116 +1s and a 209-point Hacker News thread ("I cancelled my subscription over this"). VS Code reverted a Copilot co-author default within two weeks, after 244 thumbs-down reactions. Cursor's default drew complaints on its forum ([#66504](https://github.com/anthropics/claude-code/issues/66504); [HN](https://news.ycombinator.com/item?id=49498201); [VS Code #314311](https://github.com/microsoft/vscode/issues/314311); [Cursor forum](https://forum.cursor.com/t/co-author-added-without-consent-and-cant-be-turned-off/150096)).

The reasons people give are practical and principled at once. The trailer advertises the vendor, and the US Copyright Office says not to list AI as an author ([#66602](https://github.com/anthropics/claude-code/issues/66602)). Vendors' noreply addresses misattribute commits to strangers, and vendor branding leaks into other people's repositories when a fix goes upstream ([#103691](https://github.com/anthropics/claude-code/issues/103691)). Organisations want control of their own audit trail, since disclosure in history "should be that organisation's decision, made deliberately — not a default applied silently" ([#83226](https://github.com/anthropics/claude-code/issues/83226)). And stigma is real: kernel contributors fear an "anti-LLM witch hunt" ([LWN](https://lwn.net/SubscriberLink/1099594/6e351ed3aecb2ae4/)). One user built a CI check "to protect my repos from my own tooling" ([#83813](https://github.com/anthropics/claude-code/issues/83813)).

Public adoption figures therefore measure vendor defaults. Explicit markers appeared on 2.93% of commits across 5,682 repositories of critical packages in the year to July 2026, and 57% of those markers were Claude Code's ([Nesbitt](https://nesbitt.io/2026/08/06/a-year-of-ai-disclosure-in-critical-packages.html)).

### Maintainers judge people and outcomes, not records

The signals maintainers actually use are reputation and results. GitHub's answer to the flood of AI pull requests was limits on open pull requests, collaborator-only repositories, and exemptions based on account age and merge history; its May update listed no AI-labelling feature, shipped or planned. Ghostty closes pull requests from anyone not vouched for, and its vouching tool has 5,147 stars. And curl's Daniel Stenberg wrote that reporters "rarely mention exactly which AI tool or model they used (and really, we don't care)" ([GitHub #197319](https://github.com/orgs/community/discussions/197319); [vouch](https://github.com/mitchellh/vouch); [curl](https://daniel.haxx.se/blog/2026/04/22/high-quality-chaos/)).

Direct demand for private, verifiable records is thin but specific. A Claude Code feature request, with no reactions yet, asks for receipts that hold "only hashes", so that "The author reveals the transcript on request, so private prompts stay private" ([#101813](https://github.com/anthropics/claude-code/issues/101813)). In the Hacker News thread about session URLs, one developer suggested cataloguing sessions "within the local session metadata" rather than in the public source tree. Another called a link from commit to session "a lifesaver" for debugging old commits ([HN](https://news.ycombinator.com/item?id=49498201)).

The law points the same way. US copyright treats AI as a tool, not an author ([Copyright Office](https://www.copyright.gov/ai/)). In March 2026 the Supreme Court declined to hear Thaler v. Perlmutter, leaving the human-authorship rule in place ([Holland & Knight](https://www.hklaw.com/en/insights/publications/2026/03/the-final-word-supreme-court-refuses-to-hear-case-on-ai-authorship)). And the AI Act's transparency duty for published text exempts content that "has undergone a process of human review" ([AI Act Art. 50](https://artificialintelligenceact.eu/article/50/)). Provable human review is the legally useful fact; a trailer naming AI as co-author asserts the wrong one.

### Link commits to runs privately and disclose on request

This settles the question of public versus private provenance. The record should **never write public trailers by default**; it should link commits to runs inside the private record instead, which gives the developer the "lifesaver" without publishing anything. It should offer a disclosure the developer chooses to attach at review time, which by default names the tools without brands and states that a human reviewed the work, that tests ran and that the session is on file, matching kernel, Node.js, LLVM and Ghostty norms. And it should disclose a run or an approval only on request, to a maintainer or client, through selective disclosure.

For contributors to projects that ban AI, a private record has value only if it never leaks. No evidence suggests maintainers would check signatures in routine review. A verifiable record's value to open source lies in disputes instead: a security incident, or a licence question that needs AI-written code traced and rewritten ([cargo-msrv](https://github.com/foresterre/cargo-msrv/blob/main/CONTRIBUTING.md)). The paying customer for selective disclosure is the client relationship described earlier, not the maintainer.

## The record can prove integrity and custody, never completeness

The sidecar is a process the harness launches, so what it can claim depends on which evidence reaches it. Four sources do, each with a different reach.

| Source | What it sees | What it misses |
|---|---|---|
| The sidecar's own MCP traffic | Every store write, forward, published name, message and membership change it performs. Under the MCP revision of 28 July 2026, clients should identify themselves on every request and can pass trace context ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) | Anything the harness does without calling the sidecar. Protocol-level sessions were removed, so the sidecar must create its own run IDs |
| Harness hooks (33 events in Claude Code, 12 in Codex, 21 in Cursor) | Prompts, tool inputs and outputs, shell commands, subagent starts. Admins can enforce company-managed hooks ([Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex hooks](https://learn.chatgpt.com/docs/hooks)) | Claude Code fires no hook when the human answers a permission prompt, and its permission-request event omits the tool-call ID. Files referenced with `@` skip the pre-tool hook, and session-end hooks get 1.5 seconds ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). Codex does not yet support "ask" on its pre-tool hook. Cursor lets an action through when a Claude Code-format hook exits with an unexpected code ([Cursor third-party hooks](https://cursor.com/docs/reference/third-party-hooks)) |
| Harness telemetry (OTel) | Claude Code's `tool_decision` event, which records whether configuration, a hook or the user decided, under the same tool-call ID as the action. Codex has an equivalent event ([Claude monitoring](https://code.claude.com/docs/en/monitoring-usage)) | Content is redacted by default, events can arrive more than once, and Cursor sends no client-side traces |
| The sidecar watching the filesystem and git | The effects of every tool path: Bash, `sed -i`, subagents, reverts, manual edits | Which tool or person made a change (that needs hooks), file reads, and network calls |

Some things no source shows. No hook sees the request body the harness assembles and sends to the model ([#44868](https://github.com/anthropics/claude-code/issues/44868)). The record can list the instruction files and file reads it observed, but not exactly what the model was given. Network calls the harness makes on its own are visible only if they pass through a proxy the sidecar runs; Claude Code documents this as replacing its built-in sandbox proxy ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Cloud agents are out of reach unless the sidecar is installed in their environment. And every parser of harness-internal storage is fragile. Claude Code says its transcript format "is internal to Claude Code and changes between versions", and SpecStory's maintainers say they are "at the mercy of their whims" ([Sessions](https://code.claude.com/docs/en/sessions); [SpecStory #82](https://github.com/specstoryai/getspecstory/issues/82)).

These limits are structural, not engineering debt. A separate process recording across harnesses is stronger than a harness reporting on itself. An open proposal for the in-toto attestation format, written for "audit sidecars", makes this argument: it says application logs fall short because "the entity writing the log is the same entity whose behavior needs verification" ([in-toto #588](https://github.com/in-toto/attestation/pull/588)). But the harness launches the sidecar, so the sidecar is not independent. Code running inside the agent can also get around userspace hooks, or forge receipts if the signing key sits in its process, as the open-source Obsigna project concedes about itself ([Obsigna](https://github.com/agent-receipts/obsigna); [Endor Labs](https://www.endorlabs.com/learn/when-the-guardrails-slip-the-case-for-hook-based-governance-across-agent-platforms)). Anthropic's own signed log "does not prove that every access was recorded". An IETF draft on the limits of audit records warns that "Each mechanism establishes a narrower fact than it is often taken to establish" ([Access Transparency log](https://platform.claude.com/docs/en/manage-claude/access-transparency-log); [draft-zhang](https://datatracker.ietf.org/doc/draft-zhang-audit-record-limits/)).

The record can therefore claim four things: **integrity**, meaning entries are signed and unaltered; **custody**, meaning the team holds the keys; **time**, through checkpoints countersigned by witnesses; and **observed effects**, meaning what actually changed on disk. It cannot claim completeness, the truth of what a harness reported, or independence from the team that runs it.

Those limits become features when the record states them. Each run should carry a coverage entry listing which sources were live: whether hooks were installed and company-managed, whether telemetry was on, the permission mode, and whether the filesystem watcher was running. An auditor can then tell "no approval was given" apart from "approval could not be observed". Runs in which auto or bypass mode pushed edits through Bash should be flagged. The filesystem change set should be reconciled against the tool calls that hooks reported, and unexplained changes marked as unattributed rather than credited to the human; crediting the human is how git-ai misattributes deletions made through Bash today ([git-ai #387](https://github.com/git-ai-project/git-ai/issues/387)). Signing keys belong in a separate daemon or the operating system's key store, the pattern Obsigna uses. Session receipts should commit to the head of the chain, so that truncation or rollback shows ([draft-bailey](https://datatracker.ietf.org/doc/draft-bailey-scitt-agent-session-receipt/)).

The sentence for customers follows: the record shows every action through the sidecar, every harness event you connect and every change in the working tree, bound to whoever approved it, and it says plainly what it could not see. A harness log reporting on itself cannot tell an auditor what it missed. The record can.

## Mid-2026 RFCs make "verify without trusting us" a small build

The cryptography the positioning implies is now standard and cheap.

### Self-hosted tile logs let clients verify without seeing content

Transparency logs built from tiles are production-grade, and a team can host its own. Tessera reached v1.0 in September 2025. Rekor v2 became generally available in October 2025, with a POSIX server described as "lightweight, no cloud dependencies". And the C2SP specifications for checkpoints, tiles, witnesses and proofs are stable ([Tessera](https://github.com/transparency-dev/tessera/releases); [rekor-tiles](https://github.com/sigstore/rekor-tiles); [C2SP](https://github.com/C2SP/C2SP)).

The IETF published three relevant standards in mid-2026. The Supply Chain Integrity, Transparency and Trust (SCITT) architecture (RFC 9943) and COSE Receipts (RFC 9942) came on 30 June. COSE Hash Envelope (RFC 9995) followed on 14 July; under it, "access to the original payload is not required for signature validation" ([RFC 9943](https://datatracker.ietf.org/doc/rfc9943/); [RFC 9942](https://datatracker.ietf.org/doc/rfc9942/); [RFC 9995](https://datatracker.ietf.org/doc/rfc9995/)). An entry in the agent record can therefore be a standard signed statement. A team can run its own log of entry hashes, and a client can verify two things without seeing any content: that an entry is included, and that the log has only ever been appended to.

The one immature piece is independent countersigning. The public witness network says "Production: Not available yet", so today's witnesses are staging operators (Mullvad runs one), customers, or their auditors ([witness tables](https://github.com/transparency-dev/witness-network/blob/main/site/content/witness-tables.md)).

### An approval signed with the human's SSH key is the strongest differentiator

Approvals are where signatures earn the most. GitHub verifies SSH commit signatures and calls them "the simplest to generate", while keyless gitsign signatures still show as unverified there ([GitHub Docs](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification); [gitsign](https://github.com/sigstore/gitsign)). An approval signed with the human's own registered SSH key turns "who approved this" from a claim the sidecar makes into a signature anyone can check. That is the strongest single cryptographic differentiator available.

Harness vendors do not offer it. Anthropic closed a request for "cryptographic attestation that a git commit (or other action) was taken by a Claude agent" as not planned ([#80551](https://github.com/anthropics/claude-code/issues/80551)), and Copilot signs its own commits with a key GitHub holds. For export, the in-toto framework (v1.2.0) and its DSSE signing envelopes are mature, but no format for agent records has been accepted. At least eight proposals are open, including the one written for "gateways, proxies, audit sidecars" ([in-toto releases](https://github.com/in-toto/attestation/releases); [in-toto #588](https://github.com/in-toto/attestation/pull/588)).

### SD-JWT proves an approval without the code, so BBS is unnecessary

Selective disclosure needs nothing exotic. SD-JWT (RFC 9901, November 2025) defines salted-hash commitments with decoy digests ([RFC 9901](https://datatracker.ietf.org/doc/rfc9901/)). Combined with a Merkle inclusion proof and a witnessed checkpoint, it lets a team show a client that a named person approved a specific commit, under a specific policy, at a specific time, and that this was logged before a given checkpoint, without revealing code or any other entry.

The advanced alternatives are neither ready nor needed. BBS signatures remain a draft of the IRTF's Crypto Forum Research Group and a W3C candidate draft, and JSON Web Proofs are a working-group draft ([BBS draft](https://datatracker.ietf.org/doc/draft-irtf-cfrg-bbs-signatures/); [W3C BBS](https://www.w3.org/TR/vc-di-bbs/)). No standard exists for redactable signatures. Zero-knowledge proofs are practical only for narrow credential checks, such as Google's age-assurance library ([Google](https://blog.google/technology/safety-security/opening-up-zero-knowledge-proof-technology-to-promote-privacy-in-age-assurance/)). Unlinkability, the main benefit of BBS, is also the wrong goal for a team that wants its disclosures attributed to it.

### Erasure needs salted commitments in the entry format from day one

Erasure is the subtle part, and the European Data Protection Board's final blockchain guidelines (version 2.0, adopted 7 July 2026) set the bar. They hold that encrypted personal data "is still personal data", that salted or keyed hashes remain personal data until the salt or key is gone, and that "unsalted or unkeyed hashes should, in general, not be considered sufficient". A perfectly hiding commitment, by contrast, becomes "useless" once the data and its witness are deleted, and "technical impossibility cannot be invoked to justify non-compliance" ([EDPB v2.0](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). No regulator text says that deleting the keys to encrypted data counts as erasure.

The defensible design works like this. Each log entry keeps only metadata, a commitment over salted content, and a pointer to that content. A per-entry content key and a 256-bit salt live only inside the encrypted content envelope. To erase an entry, delete both everywhere, including escrow copies whose holders confirm the deletion, and then append an erasure entry. The chain still verifies, because it covers commitments that no longer link to anyone. The claim should be "designed to the EDPB's commitment pattern", reviewed by counsel.

One sequencing point outweighs the rest: **commitments and per-entry keys cannot be added later to entries already logged.** The entry format must carry them from the first release, even if the disclosure and erasure tools ship later.

| Feature | Standard and status | Verdict for a team of one to ten people |
|---|---|---|
| Signed, hash-chained entries holding only metadata | COSE signatures, or in-toto statements in DSSE envelopes; Ed25519 keys | Build. Table stakes, not a differentiator alone |
| A Merkle log the team owns, with signed checkpoints | RFC 9162 trees, C2SP log specifications, Tessera v1.0 | Build. The core of "verifiable without trusting us" |
| Independent countersigning | C2SP witness protocol; the public network is staging only | Build the hook, and let customers and auditors run witnesses |
| Approvals signed by humans | SSH signatures that GitHub verifies; gitsign with OIDC | Build. The strongest differentiator |
| Proof of an approval without the code | SD-JWT salted digests plus an inclusion proof | Build. Little code on standard parts |
| Erasure with the chain intact | Per-entry keys and salted commitments; EDPB v2.0 patterns | Build into the format now; make claims only with counsel |
| Evidence of delegation | Token exchange (RFC 8693), Rich Authorization Requests (RFC 9396), Enterprise-Managed Authorization for MCP ([MCP EMA](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)), the IETF's AI identity draft ([WIMSE AIMS](https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/)) | Record the identifiers they produce; do not define a new identity scheme |
| Export formats | SCITT with COSE Receipts, in-toto statements, OTel GenAI conventions (still "Development") | Emit them, and help standardise an agent format |
| BBS, JSON Web Proofs, redactable signatures, zero-knowledge proofs over logs | Drafts or research | Over-engineering |
| A public SCITT service, a key-transparency directory, hardware attestation | SCITT's API is in the RFC Editor's queue; the others are drafts | Later, if ever |
| Blockchain anchoring as the main source of trust | Keybase precedent; URnetwork already commits network roots on-chain | An optional second anchor at most |

### URnetwork's Merkle code does not fit, but the AUDIT BoF does

Two design points follow for URnetwork. The company's SDK already builds Merkle trees, but its OpenZeppelin-compatible tree sorts its leaves and hashes each pair without regard to order. That suits proofs of membership on-chain, but the tree keeps no sequence and cannot prove that a log was only appended to, so reusing it would leave the record unverifiable by standard log clients ([urnetwork/sdk merkle](https://github.com/urnetwork/sdk/blob/main/sn/merkle/merkle.go)). The record should use Tessera, and treat roots committed on-chain as a second anchor at most. That also follows the EDPB's advice to use other tools where a blockchain's integrity property is not needed. Second, public checkpoints reveal how active a team is, so each team should have its own log, with checkpoints published in batches.

Formats will not be a moat: in 2026, 42 Internet-Drafts with "receipt" in the name and 15 with "audit" were updated ([datatracker](https://datatracker.ietf.org/api/v1/doc/document/?name__contains=receipt&type=draft&time__gte=2026-01-01)). The useful contribution is an implementation report, with test vectors, for a record that is content-optional, erasable and countersigned by witnesses. The venue is the IETF's AUDIT BoF on 17 November 2026, a session held to decide whether to form a working group. It plans a profile of the Verifiable Agent Conversation Records format drafted by Birkholz, Heldt and Steele ([AUDIT BoF request](https://datatracker.ietf.org/doc/bofreq-kuhlewind-audit-agent-use-of-delegation-and-interaction-traceability/); [draft-birkholz](https://datatracker.ietf.org/doc/draft-birkholz-verifiable-agent-conversations/)). URnetwork could also help merge the open in-toto agent proposals into one. A talk at the BoF would be on the public record, unlike the IETF 124 presentation the company cites, of which this round again found no trace ([datatracker slides](https://datatracker.ietf.org/api/v1/doc/document/?type=slides&name__startswith=slides-124&title__icontains=urnetwork)).

## German law treats an employer-readable record as workplace monitoring

The earlier line, "private from us, complete for your admins", handles the boundary with the vendor. It ignores a second boundary, inside the team.

Developers object to raw sessions becoming visible to colleagues. One wrote that "the trust boundary for 'who can see the code' is not the same as 'who should see the raw AI session history'" ([Entire #340](https://github.com/entireio/cli/issues/340)). Another put it more bluntly: "I am not willing to share my sheepish prompts with my team" ([HN](https://news.ycombinator.com/item?id=46966815)). Judging by reactions, they object even more to vendors keeping sessions they cannot delete. A request to delete web and desktop sessions drew 96 +1s, and a Codex user insisted that "Archiving is not deletion" ([#13514](https://github.com/anthropics/claude-code/issues/13514); [Codex #24610](https://github.com/openai/codex/issues/24610)).

Admins pull the other way. They ask for per-user usage and, in several organisations, the content of prompts and responses in their own telemetry pipelines ([#27780](https://github.com/anthropics/claude-code/issues/27780); [#88490](https://github.com/anthropics/claude-code/issues/88490); [#89594](https://github.com/anthropics/claude-code/issues/89594)). No developer in the research said a manager had actually read their sessions. The objections are anticipatory, which makes them a design input rather than a measured harm.

The tools already tilt toward the employer, often without telling the developer. Anthropic's compliance reviewers can read Enterprise developers' Claude Code prompts, tool calls and file text, and "Nothing masks URLs, credentials, or personal data". GitHub streams prompts, responses and tool calls from Copilot command-line and IDE sessions to the employer's SIEM. Claude Code's company-managed settings can force telemetry on and override variables the developer has set, and the documentation describes no notice to the developer ([Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions); [GitHub](https://github.blog/changelog/2026-07-02-copilot-agent-session-streaming-is-now-in-public-preview/); [Claude monitoring](https://code.claude.com/docs/en/monitoring-usage)).

Measurement has already caused backlash. In September 2026, Meta dropped AI-usage metrics from engineer reviews after staff ran up token counts to climb internal leaderboards ("tokenmaxxing"). Duolingo's CEO reportedly backtracked on evaluating staff on AI use. In a survey of 700 practitioners and managers commissioned by the vendor Harness, 54% feared evaluations tied to their AI use ([The Decoder](https://the-decoder.com/meta-drops-ai-usage-from-engineer-performance-reviews-after-tokenmaxxing-backfires/); [Fortune](https://dc.fortune.com/2026/04/13/duolingo-ceo-luis-von-ahn-ai-usage-requirement-employee-performance-evaluations); [IT Brew](https://www.itbrew.com/stories/developers-fear-performance-evaluations-based-on-ai-data-survey)). Vendors are split. Span says sessions "belong to the engineer" and its reports are "never people". DX advises against evaluating individuals. GitHub suppresses team reports for teams with fewer than five users. Anthropic's dashboard, by contrast, ships a top-ten leaderboard and suggests using it to "identify power users" ([Span](https://www.span.app/); [DX](https://getdx.com/blog/ai-measurement-framework-guide/); [Claude analytics](https://code.claude.com/docs/en/analytics)).

### The legal trigger is capability, not intent

In Germany this is a matter of law, not taste. Under §87(1) No. 6 of the Works Constitution Act, an employer must reach agreement with the works council "before introducing monitoring-capable AI". Covington rates the risk as high: injunctions and suspension of the tool are possible, and measures introduced without consent may be "legally ineffective" ([Covington](https://www.cov.com/-/media/files/corporate/publications/2026/07/works-council-rights-in-ai-implementation-projects.pdf)). The trigger is capability, not intent. A German labour court reportedly found that the works council had no co-determination right where employees used their own ChatGPT accounts and the employer had no access to usage data ([CMS](https://cms.law/de/deu/legal-updates/kein-mitbestimmungsrecht-des-betriebsrats-bei-chatgpt-amp-co)). A record held "under the team's keys" is readable by the employer by design, so it will likely need an agreement. Keeping each person's content under their own keys, and exporting only aggregates above a minimum group size, may narrow the exposure; this needs legal review.

### Split keys between the developer's sessions and the team's actions

The answer is two key domains. The developer's domain holds raw transcripts, prompts, replies and files read, encrypted under that developer's keys. The developer discloses them, one run or one subset at a time, to a teammate, a lead or a client. The team's domain holds actions, approvals, change-set hashes, the agent inventory, cost and coverage, and admins can read it. Its pointers to content resolve only when the developer discloses that content.

Some teams must retain content, such as firms supervised by FINRA keeping "prompt and output logs" ([FINRA](https://www.finra.org/rules-guidance/guidance/reports/2026-finra-annual-regulatory-oversight-report/gen-ai)). For them, there should be one access path that users can see. Element's AuditBot is one model: it "is visible to your users" and "cannot be hidden". Disclosed key escrow with a private option for each member, as in Proton for Business, is another ([Element](https://ems-docs.element.io/books/element-cloud-documentation/page/audit-bot); [Proton](https://proton.me/support/private-users)). Every admin read should become an entry the developer can see. That goes further than Amp, which logs admin access to private threads and requires a passkey for it ([Amp](https://ampcode.com/security)). Metrics stay at team level, with a minimum group size and no leaderboards. The team tier should ship with a works-council packet: a data inventory, the purposes of processing, retention periods, an access log, and a clause ruling out use in individual performance reviews.

The claim becomes: URnetwork cannot read any of it, your admins see what agents did and who approved it, and your raw sessions stay yours unless you share them. The split also eases data protection, since most personal content never enters the team's log. And it differs from Span in mechanism. Span enforces author-only access to prompts through access control on its own servers ([Span security overview](https://span-knowledge-base.help.usepylon.com/articles/8922907265-span-agent-trace-analytics-security-overview)); the sidecar can enforce the same boundary with keys.

## Ship the session vault, change set and approval receipts first

The features below are ranked on five tests: the weight of user evidence, whether a buyer has asked for the feature, whether any product already offers it, how mature the standards it needs are, and how much of it URnetwork's design already covers. The first five ship in the first release, because they share one capture engine (the sidecar's own traffic, hooks, telemetry and filesystem watching) and one entry format. Three of them, plus each developer's own approval history, are free for individuals; the shared, signed approval ledger and the team inventory open a paid team tier from the first day. The next five extend that tier, and the last two come later.

The first three features carry the product. The vault is why a developer installs it, because it answers the most widespread loss. The change set is why it keeps running every day, because it works where the harness's own checkpoints fail. Approval receipts are why a lead pays, because they are the one artifact that both today's change-management evidence and the 2027 criteria need. Inventory, handoff notes and private commit links come almost free from the same capture.

Restore needs care. Cursor's revert crossed workspace boundaries and deleted files without a preview ([Cursor forum](https://forum.cursor.com/t/cursor-ide-revert-to-message-operation-crosses-workspace-boundaries-and-silently-targets-ignored-files/176032)). So restore must show a preview first, stay inside the run's own change set, and record itself.

Some things are deliberately left out. An engineering-intelligence dashboard is left to the platforms that already sell one. Public commit trailers are off by default, because developers strip them. BBS signatures, zero-knowledge proofs and redactable signatures are over-engineering. So are a public SCITT service, on-chain anchoring as the main source of trust, and any gateway that reads content.

All seven designed features find a place. The encrypted git store holds the vault, the snapshots and the handoff notes, while port forwarding and the TLS edge produce reach receipts. The inbox becomes the approval channel and the source of message provenance, and team auth defines the two key domains and the sponsors. The audit trail is the spine. The protocol is MCP over stdio, which now carries client identity and trace context on every request.

The demonstration should change to match. It opens with Claude Code in auto mode editing through Bash, while the record still shows every file and can restore it. Codex, in another terminal, then starts from the handoff note. A database migration waits for an approval that the lead signs with an SSH key, and the lead sends the client a packet proving that approval without the code. A packet capture shows that URnetwork saw only ciphertext. And the developer can see that the admin opened only the approval entries.

Pricing follows the same split. Individuals get the vault, the change set, the handoff note and their own approval history free, with many concurrent agents. A per-seat team tier covers the shared, signed approval ledger, the inventory, the verifiable log, exports, disclosure packets and the works-council configuration. That is consistent with the market norm of charging per human seat and leaving agents unmetered.

## Harness owners are one feature away, and Span is one key away

The most direct threat is that each harness keeps improving its own record and moves into attribution. OpenAI hired Git AI's founders in September ([Git AI](https://usegitai.com/blog/git-ai-is-joining-openai)). Anthropic's Compliance API keeps local Claude Code transcripts for six years, and in October Claude Code's telemetry began recording the auto-mode classifier's verdict and the permission mode on each tool decision ([Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). GitHub streams local Copilot sessions to customers' SIEMs in preview and, according to its changelog, now also counts usage from other tools that call Copilot models ([GitHub changelog](https://github.blog/changelog/2026-10-23-usage-metrics-api-adds-usage-from-tools-like-opencode)). Cursor attributes lines to agents or humans with Cursor Blame ([Cursor Blame](https://cursor.com/docs/integrations/cursor-blame)).

Anthropic could close the verifiability gap for its own harness quickly, because it already runs a signed log in the C2SP format for staff access. What the harness owners are unlikely to close are two other gaps. One is custody they cannot read, because their compliance, data-loss and analytics products depend on reading content. The other is neutrality across rivals, because each earns money when work stays on its own runtime.

### Span's recorder sits one key and one approval feature away

Span is the closest existing product to the record. Its recorder runs on developer machines, installed through device management rather than as a proxy. It captures "prompts, tool calls, model choices, file edits, and token spend", and prices each session. Sessions are private by default, so that they "belong to the engineer", and reports are by repository and team, "never people". It strips secrets on the device. Its named customers include Ramp, Writer, Carvana and Fin ([Span](https://www.span.app/)).

Span's gaps are the ones this report ranks highest. Its security overview places hosting on AWS in the US with no customer-managed keys mentioned and keeps traces for 90 days by default. It does not describe approval capture or any tamper-evidence, and it lists a "Pause Collection" control as still "coming soon" ([Span security overview](https://span-knowledge-base.help.usepylon.com/articles/8922907265-span-agent-trace-analytics-security-overview)). If Span adds customer keys and approval capture, the sidecar's lead narrows to tamper-evidence, selective disclosure, custody under team keys, an open cross-harness format, and the networking features.

Span also sells top-down, to engineering leadership through device management, while the sidecar enters when a developer installs a subprocess. The two approaches can coexist, but only if the free vault is good enough that developers bring it in themselves.

Others stand one encryption feature away from the same ground. Entire has $60M of funding, support for eight harnesses and a forge launched on 26 October. SpecStory has the broadest harness coverage and a vendor-reported 233,573 installs ([TechCrunch](https://techcrunch.com/2026/02/10/former-github-ceo-raises-record-60m-dev-tool-seed-round-at-300m-valuation/); [SpecStory](https://specstory.com/api/badge?stat=installs)). Security vendors that build on hooks are well funded, Zenity among them with a $125M Series C. And Microsoft Defender already discovers about 60 local agents on Windows ([SecurityWeek](https://www.securityweek.com/zenity-raises-125-million-in-series-c-funding/); [Defender](https://learn.microsoft.com/defender-endpoint/ai-agent-support-matrix)).

### Harness churn, late demand and the surveillance frame are structural

Several risks are structural rather than competitive. Harness changes break capture: transcript formats change between versions, auto mode moved edits into Bash, Codex retired its strictest approval policy, and some hooks let actions through when they fail. That makes filesystem watching and the sidecar's own traffic hedges rather than extras. Demand timing cuts the other way, because compliance demands harden in 2027–28 and the product must live on developer pull until then. Keybase gave away encrypted git and teams and ended up as Zoom's acquisition, and Vibe Kanban found that "the vast majority are free users"; both argue for charging for the team layer from the first release ([Keybase](https://keybase.io/blog/keybase-joins-zoom); [Vibe Kanban](https://www.vibekanban.com/blog/shutdown)). Crowded standards could strand an early format choice, so the format should follow the AUDIT working group if one forms.

The surveillance framing is already live. One Hacker News post linked the Agent Trace repository under the title "Big Brother Is Watching", and works councils can suspend tools ([HN](https://news.ycombinator.com/item?id=46854637)). The vault itself becomes a target, because it holds sessions that contain secrets alongside the keys that sign approvals, which raises the stakes on redacting before saving and on keeping keys outside the agent's process. The earlier positioning's risks also still apply. Privacy claims will be tested against a malicious server, as TeleMessage learned when it sold encryption "through to the corporate archive" and was found to ship plaintext to its own archive ([Micah Lee](https://micahflee.com/despite-misleading-marketing-israeli-company-telemessage-used-by-trump-officials-can-access-plaintext-chat-logs/)). And a security reviewer will see URnetwork's residential-proxy footprint before seeing the record.

The signals to watch are concrete. They are Anthropic extending its transparency log to compliance transcripts, GitHub's session streaming leaving preview or opening beyond Enterprise Managed Users, Span announcing customer-managed keys or approval capture, and Codex shipping attribution in the style of Git AI. Two dates matter as well: whether the AUDIT BoF yields a chartered working group after 17 November, and the AICPA's final 2027 criteria once comments close on 15 January 2027.

## Ten earlier conclusions bend under the new evidence

The earlier central finding holds. The record is the object worth defending. A record of local actions at the source is the gap. And the sidecar must be separated from URnetwork's egress network. What changes is the order in which value arrives, and where the privacy boundaries fall.

## Conclusion

The new evidence reverses the order in which the record earns its keep. The earlier plan sold an audit trail to a lead facing a client's question. The evidence says the developer's bad day comes first and to far more people: a session silently deleted, or an auto-mode edit that no checkpoint saw. The client's question comes in 2027–28, and its first form is "who approved the change". Because one capture engine serves both, the free developer product is how the paid compliance product gets installed on every machine that matters. The moat is time. A team that turns on the team tier in 2026 will hold a year of signed approval receipts and inventory when the new SOC 2 criteria and EU dates arrive. A latecomer cannot recreate a log's unbroken, witnessed history, even if the underlying data exports as plain git.

Two further shifts change what URnetwork should be proud of. The cryptography that once looked like a moat became standard in 2026, and it is cheap. What is scarce is an honest place to capture from, outside every harness, together with the willingness to tell an auditor what the record did not see, a claim no harness reporting on itself can make. And privacy acquired a second boundary. Keeping the vendor out is what the market rewards; keeping the employer out of developers' raw sessions is what lets the record onto developers' machines, and past German works councils, at all. Splitting keys between developer and team turns both boundaries into one product property. That split, more than encryption alone, is the clearest line between this record and the Span recorder already standing on nearby ground.
