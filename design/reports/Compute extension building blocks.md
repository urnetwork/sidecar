# Build thin Go cores, verify every enclave

As of November 2026, sidecar should write five thin Go cores itself and borrow the schemas around them rather than the code. The five are: a small Pi-shaped agent loop, because PiG is a **1.04-million-line, pre-stable port** whose core packages lack the definitions needed to build for `GOOS=js` ([PiG README](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/README.md)); LiteRT-LM reached through its new **C API 1.0** on desktop and through host-app bridges on iOS, Android and the browser; a loopback gateway that terminates the OpenAI Responses, Anthropic Messages and Chat Completions wire APIs over one internal item model; `golang.org/x/crypto/ssh` for people plus a smaller framed exec protocol for agents; and go-git behind a single `git(argv)` tool that never shells out. The confidential-computing evidence is the sharper finding. The systems that earn trust (Apple Private Cloud Compute, Meta Private Processing, Tinfoil) verify attestation on the client, pin vendor roots and minimum firmware (TCB) levels in client code, encrypt to a key that exists only inside the attested TEE, and accept only measurements published in a log the operator cannot rewrite. All of them still rest on hardware whose vendors exclude sophisticated physical attacks, and TEE.fail showed that a **sub-$1,000 DDR5 interposer** can forge Intel TDX quotes, including against a dstack deployment ([TEE.fail](https://tee.fail/)). NEAR AI's November 2026 breach added the second admitted limit: attestation proves which software runs, not that it is free of bugs ([CSA research note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/11/CSA_research_note_near_ai_sglang_confidential_inference_breach_20261111-csa-styled.pdf)). Both limits bite hardest on sidecar's rentable enclaves. Those are persistent, addressable, per-user VMs, and Google concedes that such state cannot be shielded from targeting. Tinfoil Bunkers (launched 2026-11-19) is the closest production analog, and no surveyed system documents an SSH host key bound to attestation, so sidecar will be designing that piece rather than copying it ([Tinfoil Bunkers](https://tinfoil.sh/blog/2026-11-19-introducing-tinfoil-bunkers)). The product claim should therefore be scoped to "the operator's software cannot read your data", with user-held keys, hardware allowlists and an egress credential proxy carrying the weight that attestation alone cannot.

The table condenses the recommendation for each building block; the sections that follow give the evidence.

| Building block | Use | Avoid | Main risk to manage |
|---|---|---|---|
| Embedded Harness | Own Go loop copying `pi-agent-core` (prompt, steer, follow-up, abort, subscribe; typed events; `Execute(ctx, id, args, onUpdate)` tools); Pi's JSONL session entries and JSON event shapes as the app wire format; stock `pig`/`pi --mode rpc` inside enclaves | Vendoring PiG's `coding` SDK into apps or wasm | Owning compaction, retries and provider adapters |
| On-device inference | LiteRT-LM C API loaded with purego on desktop; Kotlin `litertlm-android` (AICore where present) and the Swift package or `CLiteRTLM.framework` (Apple Foundation Models for short tasks) behind Go interfaces on mobile; `@litert-lm/core` in an extension offscreen document | Static single-binary builds; shipping the Python `litert-lm serve` | Preview-grade Swift and JS APIs, GPU numeric bugs, releases every 2–4 weeks |
| Loopback gateway | `/v1/responses`, `/v1/messages`, `/v1/chat/completions` on 127.0.0.1 over an Open Responses-style item model; Host and Origin checks; per-harness tokens issued by command | Binding 0.0.0.0; stateful Responses features; tokens in harness env blocks | Translation bugs at stop reasons, thinking blocks and reasoning state |
| SSH and git | x/crypto/ssh ≥ v0.56.0 with overlay-identity auth and attested host certificates for people; framed exec for agents; go-git behind one argv tool | gliderlabs as a dependency; libgit2/git2go; a real git binary, hooks or pagers | Auth-callback advisories, hostile repositories, go-git memory on phones and in wasm |
| TEE inference and enclaves | Client-side verification, encrypt-to-attested-key, a measurement log checked by projection, hardware allowlists, user-held disk keys, an egress credential proxy | Server-side "oracle" verification, operator debug paths, host-editable LUKS headers | Physical attacks on operator-held hardware; bugs inside the attested software |

## PiG's million lines stop short of wasm, so copy Pi's six-file core

PiG is a faithful Go port of Mario Zechner's Pi coding agent. It is pinned to Pi 1.5.0, licensed MIT, and labeled "a pre-stable 0.x release" ([PiG README](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/README.md)). Scale is the first problem. The repository holds **1,044,460 lines of non-test Go** ([PiG tree](https://github.com/MichaelKinsy/PiG/tree/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae)). Its headless embedding example builds to **36.7 MB** on linux/amd64, against 69.7 MB for the full `pig` binary ([PiG SDK docs](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/sdk.md#L360-L384)). Churn is the second. The SDK docs tell embedders to "Pin an exact release or commit" ([PiG SDK docs](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/sdk.md#L13)), and v0.5.3 (23 October) and v0.7.0 (5 November) both shipped breaking Go API changes ([PiG releases](https://github.com/MichaelKinsy/PiG/releases)). The project went public with 0.2.0 on 2026-09-25 and has 893 stars. Its creator is listed as maintainer, release authority and security-response owner ([MAINTAINERS.md](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/project/MAINTAINERS.md)), and its AGENTS.md opens with "Operating rules for AI agents maintaining `pig`" ([AGENTS.md](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/AGENTS.md)). Most of that code exists to match a moving TypeScript target byte for byte, which sidecar does not need.

The targets settle the question. PiG's narrowest seam is the `agent` package, and it pulls in the `ai` provider package. `ai` defines required functions such as `authFileRevision` only in files tagged `unix` or `windows`, so the closure has no definition for `GOOS=js` or `wasip1` ([ai/auth_revision_unix.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/ai/auth_revision_unix.go#L17)). The only wasm-targeted code in the repository is `durable/core`, a storage state machine whose design record is still "proposed" ([corewasm](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/durable/core/cmd/corewasm/main.go)). PiG uses no cgo, and its release matrix builds Android but not iOS ([release workflow](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/.github/workflows/release-candidate.yml#L37-L55)). Importing `agent` also runs an `init()` that hardens `http.DefaultTransport` for every client in the process, a side effect sidecar's own networking would inherit ([tlsdistrust.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/internal/tlsdistrust/tlsdistrust.go)). The public `coding` SDK leaks internal types: its tool-definition constructors take option structs from `internal/codingagent/tools`, which no outside module can import ([tool_definitions.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/coding/tool_definitions.go#L24-L56)). The built-in tools exec `bash`, `rg` and `fd`, none of which can run inside an iOS app. PiG also says it "does not provide a security sandbox" for tools or shell commands ([PiG README](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/README.md)). These build conclusions come from reading build tags, not from compiling. A sandboxed `GOOS=js go build ./agent ./ai` takes minutes and should precede the final decision.

The design worth copying is upstream Pi's `pi-agent-core`, which PiG's parity table records as **six source files** ([PiG parity coverage](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/test/parity/coverage.md)). Its API is one Agent with `prompt`, `continue`, `steer`, `followUp`, `abort`, `waitForIdle` and `subscribe`. It emits `agent_*`, `turn_*`, `message_*` and `tool_execution_*` events, runs tools through `execute(toolCallId, params, signal, onUpdate)` with `beforeToolCall` and `afterToolCall` hooks, and runs tool calls in parallel by default ([Pi agent README](https://github.com/earendil-works/pi/blob/main/packages/agent/README.md)). PiG supplies the Go shapes. A tool is `Name`, `Label`, `Schema`, `Execute(ctx, toolCallID, params json.RawMessage, onUpdate)` and an execution mode. Each progress update is a complete-so-far snapshot, not a delta, and a result carries ordered text and image content plus `StructuredContent` and `Details` ([tool interface](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/agent/agent.go#L361-L402); [tool result](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/agent/agent.go#L249-L299)). Several loop rules deserve copying verbatim. A steering message lands after the current turn and before the next model request, and a follow-up lands only when the agent has no work left ([how PiG works](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/how-pig-works.md)). When a turn stops on `length`, every tool call in it is failed rather than executed, because its arguments may be truncated ([agent_loop.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/agent/agent_loop.go#L288-L333)). Compaction and auto-retry live outside the core loop. PiG compacts when context exceeds the window minus a 16,384-token reserve and never splits a tool call from its result ([compaction docs](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/compaction.md)), and it retries a failed turn 3 times from a 2-second base delay ([settings.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/internal/codingagent/settings.go#L181-L196)). Sidecar writes both itself, which is the real cost of not vendoring.

For apps that render agent output as UI components, Pi's event union is the right contract and PiG's renderers are not. `RenderCall` and `RenderResult` return terminal components ([tool.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/coding/extension/tool.go#L166-L205)), and PiG says its TUI is not a stable application SDK ([TUI docs](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/tui.md)). Sidecar should emit Pi's JSON event shapes. In them each `message_update` carries one streaming delta and the final `message_end` is authoritative ([JSON mode](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/json.md)). Each tool should return `StructuredContent` typed against a small component schema (diff, file view, command output, approval card) that SwiftUI, Compose and the extension map to native widgets. Pi's RPC mode already defines the host-prompt vocabulary: `select`, `confirm`, `input` and `editor` dialogs that expect an answer, plus fire-and-forget `notify`, `setStatus` and `setWidget` ([RPC extension UI](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/rpc-extension-ui.md)). A `BeforeToolCall` hook that blocks with a reason maps directly onto an approval dialog. Two details matter on phones. PiG's listeners run synchronously and the run waits for each callback ([lifecycle.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/agent/lifecycle.go#L25-L30)), so the gomobile bridge must buffer events instead of blocking the loop on UI work. And gobind passes only basic types, byte slices, and structs or interfaces built from them ([gobind](https://pkg.go.dev/golang.org/x/mobile/cmd/gobind)), so events should cross as JSON bytes.

Pi's session format suits sidecar's encrypted, append-only storage almost unchanged. It is JSONL version 3: a header line, then entries whose `id` and `parentId` form a tree with an active leaf. Compaction summaries are stored as entries, and unknown fields survive a rewrite ([session format](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/session-format.md)). Adopting it keeps sidecar records readable by Pi tooling without adopting Pi code. Inside an enclave the trade reverses. A Debian VM has a shell, so stock `pig --mode rpc`, or upstream `pi --mode rpc`, runs unmodified and speaks Pi 1.5.0's JSONL RPC protocol on stdin and stdout ([RPC mode](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/docs/site/docs/rpc.md)). The app drives that remote harness over an exec channel and renders the same events as the local one. Sidecar must write the client, because PiG's `coding/rpcclient` can only spawn a local binary ([rpcclient](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/coding/rpcclient/types.go#L10-L24)). The strongest case for vendoring PiG is the desktop daemon. A pinned `agent` plus `ai` brings ten wire APIs ([ai/types.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/ai/types.go#L51-L62)) and a `StreamOptions.Fetch` hook that routes provider traffic through a caller-owned `*http.Client`, and so through URnetwork, without a fork ([ai/types.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/ai/types.go#L816)). Even so, the product would have two agent loops, because the browser and iOS still need their own. One piece deserves a separate look: PiG's `mcp` client documents no dependency on other PiG packages ([mcp/doc.go](https://github.com/MichaelKinsy/PiG/blob/40b509fbdf108c21ad95ce0d8e0108586dc8c5ae/mcp/doc.go)), a claim this research did not verify.

## LiteRT-LM's C API 1.0 opens a Go path, but each platform needs its own bridge

LiteRT-LM is Google's successor to the MediaPipe LLM Inference API. It is Apache-2.0 and reached v0.19.1 on 2026-11-05, its 35th release since June 2025 ([LiteRT-LM releases](https://github.com/google-ai-edge/LiteRT-LM/releases)). Google calls it production-ready and says it powers on-device features in Chrome, Chromebook Plus and Pixel Watch. Its Kotlin, C++, Python and CLI surfaces are labeled stable, but **Swift and JavaScript remain "Early Preview"**, and those are the two the iOS app and the browser extension need ([README](https://github.com/google-ai-edge/LiteRT-LM/blob/main/README.md)). The change that makes Go practical landed three weeks ago. v0.19.0 shipped a versioned **C API 1.0.0** in which fallible functions return a status code with results in out-parameters, and only `litert_lm_*` symbols are exported ([v0.19.0](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.19.0)). A runtime handshake, `litert_lm_get_api_version`, lets a dynamic loader refuse a library with a different major version ([engine.h](https://github.com/google-ai-edge/LiteRT-LM/blob/main/c/engine.h)). The Conversation API takes OpenAI-shaped JSON for messages and tools, streams through a C callback, and exposes `tool_choice`, thinking budgets and constrained decoding ([conversation.h](https://github.com/google-ai-edge/LiteRT-LM/blob/main/c/conversation.h)). Google publishes no Go binding; the only third-party binding on the tracker is for Rust ([#1050](https://github.com/google-ai-edge/LiteRT-LM/issues/1050)).

The C header dictates the Go design. Handles are not thread-safe. Stream callbacks run on library-owned threads shared by every stream of an engine. A callback may call back into the engine only to cancel, and a cancelled session or conversation "MUST NOT be reused; only delete it" ([engine.h](https://github.com/google-ai-edge/LiteRT-LM/blob/main/c/engine.h)). A Go wrapper therefore gives each handle one owning goroutine, lets the callback do nothing but copy text into a channel, and implements cancel as delete-and-rebuild from saved history. Static single-binary builds are not on offer. The prebuilt C API zip holds only shared libraries: **22.8 MB** for Android arm64, **51.0 MB** for macOS arm64, **53.0 MB** for Windows x86_64 and **85.1 MB** for Linux x86_64, with no iOS slice and no static archives ([C API 1.0.0 zip](https://github.com/google-ai-edge/LiteRT-LM/releases/download/v0.19.1/litert_lm_c_api-1.0.0.zip)). The GPU accelerator is a closed, dynamically loaded plugin whose open-sourcing "has been delayed" ([#1050](https://github.com/google-ai-edge/LiteRT-LM/issues/1050)). v0.19.1 also regressed to a hard dependency on `libwebgpu_dawn`, even for apps that use only the CPU or Metal ([#4611](https://github.com/google-ai-edge/LiteRT-LM/issues/4611)). There are no `windows_arm64` or `macos_x86_64` prebuilts ([prebuilt](https://github.com/google-ai-edge/LiteRT-LM/tree/main/prebuilt)).

| Target | Recommended path | Why | Watch for |
|---|---|---|---|
| CLI and daemon on macOS arm64, Linux x86_64/arm64, Windows x86_64 | Load `liblitert-lm` with purego (no cgo), downloaded on first use with its Dawn and constraint-provider libraries beside it | The C API is built for dynamic loading, and Go stays cross-compilable | The Dawn dependency ([#4611](https://github.com/google-ai-edge/LiteRT-LM/issues/4611)); Windows GPU needs DirectXShaderCompiler ([build guide](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/getting-started/build-and-run.md)) |
| Windows ARM64 and Intel Macs | llama.cpp through [yzma](https://github.com/hybridgroup/yzma), [ONNX Runtime GenAI](https://raw.githubusercontent.com/microsoft/onnxruntime-genai/main/README.md), or remote TEE inference | No LiteRT-LM prebuilts | yzma's matrix lists neither platform either |
| Android app (gomobile AAR) | Kotlin `litertlm-android` behind a Go interface implemented in Kotlin; AICore/Gemini Nano first on supported devices | The stable, supported path ([Kotlin README](https://github.com/google-ai-edge/LiteRT-LM/blob/main/kotlin/README.md)); Google's own model card calls AICore "the recommended path for production" ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)) | Two JNI crossings per stream; GPU samplers failing to load from AARs and silently falling back to CPU if the `.so` files are bundled directly ([#2211](https://github.com/google-ai-edge/LiteRT-LM/issues/2211)) |
| iOS app (gomobile framework) | The Swift `LiteRTLM` package, or the embedded dynamic `CLiteRTLM.framework` (about 48 MB), behind a Go interface; Apple Foundation Models for short tasks | gomobile emits a static framework, while LiteRT-LM ships a dynamic one ([xcframework](https://github.com/google-ai-edge/LiteRT-LM/releases/download/v0.19.1/CLiteRTLM.xcframework.zip)) | Early Preview API; inference broken in the arm64 simulator ([#2504](https://github.com/google-ai-edge/LiteRT-LM/issues/2504)) |
| Browser extension | `@litert-lm/core` (WASM plus WebGPU) in an offscreen document, driven from Go wasm by message passing | Go wasm cannot host the native core | No documented browser, worker or WebGPU requirements ([JS guide](https://developers.google.com/edge/litert-lm/js)) |

The offscreen-document choice rests on community reports that WebGPU inference cannot run in a Manifest V3 service worker, which the Gemma Gem extension works around this way ([Gemma Gem](https://github.com/kessler/gemma-gem)). MLC's WebLLM ships a service-worker example that contradicts those reports ([WebLLM example](https://github.com/mlc-ai/web-llm/blob/HEAD/examples/chrome-extension-webgpu-service-worker/)), so a one-day spike should settle it.

Gemma 4 E2B is the default model. Its base file is 2.59 GB, its GPU build 2.34 GB and its web build 2.01 GB ([E2B files](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm/tree/main)). Gemma 4 has been Apache-2.0 since 2026-04-02, so URnetwork can mirror it without the gated downloads Gemma 3 required ([Google Open Source Blog](https://opensource.googleblog.com/2026/03/gemma-4-expanding-the-gemmaverse-with-apache-20.html)). The base model supports a 32k context and the web build 128k ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)). Google's published E2B decode rates are about **52 tokens/s on a Galaxy S26 Ultra GPU, 56–57 on an iPhone 17 Pro GPU, 160 on an M4 Max GPU and 8 on a Raspberry Pi 5 CPU** ([LiteRT-LM overview](https://developers.google.com/edge/litert-lm/overview)). For an agent the bottleneck is prefill. On phone and laptop CPUs it runs at roughly 260–900 tokens/s, which costs seconds of time-to-first-token for every thousand tokens of tool output, so the harness should prefer GPU and keep tool results short. Google publishes no minimum RAM, so device tiers must be inferred from peak-memory benchmarks. E4B (3.3–3.7 GB) peaked at 9.4 GB on an Intel Lunar Lake CPU, which points it at GPU laptops, and the 12B model (6.2–6.9 GB) at 16 GB GPU laptops ([Gemma 4 on LiteRT-LM](https://developers.google.com/edge/litert-lm/models/gemma-4)). Each accelerator wants its own file (CPU, GPU, web, and one per NPU chip), so sidecar needs a per-device model manifest rather than one URL ([E2B files](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm/tree/main)). NPU builds fix their context length at compile time ([E2B card](https://huggingface.co/litert-community/gemma-4-E2B-it-litert-lm)), which makes NPU a later optimization.

The harness has to route around known defects. Constrained decoding keeps tool-call syntax valid, but it cannot be combined with a custom LLGuidance constraint on the same Conversation, so structured outputs need a separate Conversation ([constrained decoding](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/cpp/constrained-decoding.md)). Tool-call arguments come back as JSON objects, while the Responses API carries them as strings, so the gateway must convert them ([tool use](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/cpp/tool-use.md)). The GPU path's default FP16 activations corrupt digits past roughly 2,000–3,700 tokens on iOS and Adreno GPUs, and Float32 fixes it ([#3913](https://github.com/google-ai-edge/LiteRT-LM/issues/3913), [#4001](https://github.com/google-ai-edge/LiteRT-LM/issues/4001)). An agent that copies IDs, amounts or addresses should run Float32 activations on GPU. Other open bugs: interleaved conversations silently lose state ([#2807](https://github.com/google-ai-edge/LiteRT-LM/issues/2807)), destroying a Conversation mid-prefill crashes ([#3771](https://github.com/google-ai-edge/LiteRT-LM/issues/3771)), and Android native memory grows about 30 MB per request when multi-token prediction meets `Conversation.clone()` ([#4641](https://github.com/google-ai-edge/LiteRT-LM/issues/4641)). The safe pattern is one Conversation per agent thread, no interleaving on an engine, and exact version pins per platform, gated by sidecar's own regression suite, since breaking changes and regressions both arrive in minor releases.

System models need no download but are narrow. Apple's on-device Foundation Model allows **4,096 tokens per session**, input and output combined, which tool schemas alone can exhaust ([TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window)). LiteRT-LM ships an adapter that plugs its models into the iOS 27 `LanguageModel` protocol, so a Swift-side abstraction can switch between Apple's model and Gemma 4 ([LiteRTLanguageModel.swift](https://github.com/google-ai-edge/LiteRT-LM/blob/main/swift/apple_fm/LiteRTLanguageModel.swift)). Android AICore serves Gemini Nano only to Kotlin callers on supported devices ([ML Kit GenAI](https://developers.google.com/ml-kit/genai)). On desktop, yzma loads llama.cpp through purego without a C compiler and covers Metal, CUDA, Vulkan and browser WebGPU, but documents no mobile builds ([yzma](https://github.com/hybridgroup/yzma)). LiteRT-LM's own `litert-lm serve` speaks OpenAI chat completions with tools and streaming, but it is a Python `http.server` program, fine for development and wrong for a shipped CLI ([serve](https://github.com/google-ai-edge/LiteRT-LM/tree/main/python/litert_lm_cli/commands/serve)). Remote TEE inference is the last fallback, and the only one for devices too small for E2B or browsers without WebGPU.

## The loopback gateway must speak three dialects, and Codex accepts only one

Codex is the strictest client. It deprecated Chat Completions on 2025-12-09 and removed it in early February 2026, so `wire_api = "chat"` is now a startup error ([Codex discussion #7782](https://github.com/openai/codex/discussions/7782); [model-provider-info](https://github.com/openai/codex/blob/5f645d732cc2905c0d7e02a5d1683631fe8a02e7/codex-rs/model-provider-info/src/lib.rs)). Serving Codex takes a streaming `POST /v1/responses` that accepts stateless, full-history requests: `store: false`, item ids the gateway never issued, and `include: ["reasoning.encrypted_content"]` ([client.rs](https://github.com/openai/codex/blob/5f645d732cc2905c0d7e02a5d1683631fe8a02e7/codex-rs/core/src/client.rs)). Codex reads complete items from `response.output_item.done` and ignores function-call argument deltas. It requires `response.completed` to carry an `id` and integer token counts, and it treats a stream that closes before a terminal event as a disconnect and retries ([sse/responses.rs](https://github.com/openai/codex/blob/5f645d732cc2905c0d7e02a5d1683631fe8a02e7/codex-rs/codex-api/src/sse/responses.rs)). A retried turn re-runs inference, so it is billed twice unless the gateway deduplicates. On a custom provider Codex never uses `previous_response_id`, `conversation`, `background` or WebSockets, which default off ([model-provider-info](https://github.com/openai/codex/blob/5f645d732cc2905c0d7e02a5d1683631fe8a02e7/codex-rs/model-provider-info/src/lib.rs)). When a prepaid balance runs out, the gateway should fail with `insufficient_quota`, which Codex treats as non-retryable quota exhaustion instead of a transient error to retry ([error.rs](https://github.com/openai/codex/blob/5f645d732cc2905c0d7e02a5d1683631fe8a02e7/codex-rs/codex-api/src/error.rs)). Provider settings must live in the user-level `~/.codex/config.toml`, because project files ignore them. Since Codex 0.134.0, `codex --profile <name>` overlays `~/.codex/<name>.config.toml`, so sidecar can keep its provider in its own file without clobbering the user's OpenAI setup ([advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced)). The provider table should fetch a short-lived token with `auth.command`. It should also point `model_catalog_json` at a catalog that declares each model's context window and turns off OpenAI-only freeform tools such as `apply_patch` ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). Field reports also recommend `web_search = "disabled"` and turning off multi-agent tools, since both break or hang on third-party backends ([Opper](https://opper.ai/blog/codex-router)).

Claude Code is the most forgiving client and the least supported one. Anthropic says it "doesn't support routing Claude Code to non-Claude models through any gateway" ([Claude Code LLM gateways](https://code.claude.com/docs/en/llm-gateway)), so local and TEE backends run best-effort. Its published compatibility guide is still precise ([gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol)). The gateway needs `POST /v1/messages`, to which Claude Code appends `?beta=true`. It must send the full SSE sequence through `message_delta` and `message_stop`, emit `ping` events during long pauses, and forward `anthropic-beta` verbatim; buffering stalls the client. For model ids it does not recognize, Claude Code sends adaptive thinking, effort, context management and mid-conversation `role: "system"` messages, and it retries without each feature when a 400 error names it. The gateway should accept and ignore those fields so the first turn does not cost two requests. Since v2.1.323 Claude Code assumes a 1M-token window for unknown ids, so the generated settings must set `CLAUDE_CODE_MAX_CONTEXT_TOKENS` to the real window. A gateway that rewrites context-limit errors in its own words breaks auto-compaction. Pointing `ANTHROPIC_DEFAULT_HAIKU_MODEL` at the local LiteRT-LM model keeps cheap background calls on the device. Claude Code returns thinking blocks verbatim, so their `signature` field, like Responses' `encrypted_content`, can carry the gateway's own authenticated envelope of backend reasoning state; the gateway drops it when a turn moves to a different backend. The gateway must never open an empty thinking block, because Claude Code then rejects the stream and retries without streaming, doubling the call ([LiteLLM fix](https://github.com/BerriAI/litellm/pull/17106)).

The table draws on each tool's documentation ([OpenCode](https://opencode.ai/docs/providers/), [Goose](https://github.com/aaif-goose/goose/blob/main/documentation/docs/getting-started/providers.md), [Aider](https://aider.chat/docs/llms/openai-compat.html), [pi](https://unpkg.com/@earendil-works/pi-coding-agent@0.83.0/docs/models.md), [Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/use-byok-models), [Zed](https://zed.dev/docs/ai/use-api-access), [Gemini CLI](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md)) and on reports for Cursor and Amp ([Cursor and localhost](https://dev.to/orchidfiles/why-localhost-doesnt-work-as-openai-base-url-in-cursor-and-how-to-fix-it-589e); [Amp](https://ampcode.com/news/no-more-byok)). Three endpoints on one loopback port cover nearly every harness that can reach a local server, and a Gemini `generateContent` endpoint would add Gemini CLI. "One sidecar config" therefore means rendering one file per harness, each with its own token.

Inside, the gateway should translate every dialect into one canonical item model close to Open Responses. That vendor-neutral spec was first published on 2026-01-15 and revised on 2026-04-24. Its items carry ids and status, its reasoning items have an opaque `encrypted_content` slot, and every stream must end in a terminal event ([Open Responses](https://www.openresponses.org/specification)). Routing Chat Completions and Messages through that model loses less than translating Messages straight to Chat Completions. The mature gateways fail at the same seams, which is where sidecar's golden-stream tests belong. LiteLLM documents that encrypted reasoning "without a peer" is dropped when a turn crosses providers ([LiteLLM Responses](https://docs.litellm.ai/docs/response_api)). Bifrost emitted `end_turn` instead of `tool_use` after a vLLM stream mixed text and tool calls, so clients ended the turn without running the tool ([Bifrost #3638](https://github.com/maximhq/bifrost/issues/3638)). Reasoning has no standard home in Chat Completions, and pi alone lists eight backend dialects for it ([pi models](https://unpkg.com/@earendil-works/pi-coding-agent@0.83.0/docs/models.md)). Sidecar should terminate both client APIs itself and speak native LiteRT-LM or Chat Completions to backends. Backends' own Responses and Messages endpoints are partial; Ollama's Responses support, for example, covers only the stateless subset ([Ollama](https://docs.ollama.com/api/openai-compatibility)). Two details matter for remote TEE backends. Codex's `prompt_cache_key` is a good affinity key for keeping a thread on one backend's cache. And an SSE `ping` every 10–15 seconds keeps a queued or prefilling backend under Claude Code's 5-minute idle timeout ([env vars](https://code.claude.com/docs/en/env-vars)) and Codex's 300,000 ms `stream_idle_timeout_ms` default ([config reference](https://learn.chatgpt.com/docs/config-file/config-reference)).

Local security follows from one rule: the gateway is a loopback service that browsers can never use. It binds 127.0.0.1 and ::1 only. It rejects any `Host` other than `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`, which defeats DNS rebinding, the flaw behind Ollama's CVE-2024-28224 ([NCC Group](https://www.nccgroup.com/research/technical-advisory-ollama-dns-rebinding-attack-cve-2024-28224/)). The binding matters on its own: when NVIDIA NemoClaw started Ollama on `0.0.0.0`, Ollama skipped its Host validation and became open to model poisoning, per secondary reports of CVE-2026-65105 ([CSA note](https://labs.cloudsecurityalliance.org/research/csa-research-note-nvidia-nemoclaw-model-poisoning-20260827-c/)). The gateway refuses requests carrying `Origin` or `Sec-Fetch-*` headers, which CLI harnesses never send and browsers do, and it sends no CORS headers, following the MCP spec's rules for local HTTP servers ([MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)). Chrome 142's Local Network Access permission adds a browser-side layer but does not replace these checks ([Chrome LNA](https://developer.chrome.com/blog/local-network-access)). Unix sockets cannot carry harness traffic, because none of the base-URL settings found accepts one and Codex's provider code has no socket support. They remain right for sidecar's own token-minting channel. Each harness gets its own token of at least 128 bits, bound to its wire API, its models and a spend cap within the prepaid balance. The gateway accepts it as `Authorization: Bearer` or `x-api-key`, since Claude Code can send either ([Connect Claude Code](https://code.claude.com/docs/en/llm-gateway-connect)). Sidecar's invariant I-7 keeps network credentials out of an agent's environment. That favors command-issued tokens (Codex `auth.command`, Claude Code `apiKeyHelper`) over an `ANTHROPIC_AUTH_TOKEN` in a settings `env` block, which ordinary process inheritance would hand to every shell the agent spawns. Invariant I-17 already requires local servers to authenticate callers and check Host. Tokens buy attribution, revocation and protection from browsers and other users, not isolation from malware running as the same user.

## SSH is for people; agents need exec frames and an in-process git

`golang.org/x/crypto/ssh` is the only SSH foundation worth building on. v0.59.0 shipped on 2026-11-11 ([Go module proxy](https://proxy.golang.org/golang.org/x/crypto/@latest)), with hybrid post-quantum `mlkem768x25519-sha256` key exchange first in its default list ([common.go](https://github.com/golang/crypto/blob/v0.59.0/ssh/common.go)). It implements OpenSSH certificates, though the package disclaims Go's API stability promise ([doc.go](https://github.com/golang/crypto/blob/v0.59.0/ssh/doc.go)). It is a protocol toolkit, not a server. You accept channels and handle `exec`, `pty-req`, `env`, `shell`, `subsystem`, `window-change`, `signal` and `exit-status` yourself ([RFC 4254](https://www.rfc-editor.org/rfc/rfc4254)). The usual convenience wrapper, gliderlabs/ssh, has seen no push since 2025-01-27 ([gliderlabs/ssh](https://github.com/gliderlabs/ssh)). Its maintained descendants are Charm's `charm.land/ssh` v0.4.3 ([charmbracelet/ssh](https://github.com/charmbracelet/ssh)) and Tailscale's own fork, `gliderssh` ([tailssh.go](https://github.com/tailscale/tailscale/blob/main/ssh/tailssh/tailssh.go)). The security record argues for writing the few hundred lines of session code yourself and pinning tightly, because the advisories cluster in authentication-callback semantics. The Go team announced **13 x/crypto/ssh issues on 2026-05-22** ([golang-announce](https://groups.google.com/g/golang-announce/c/a082jnz-LvI)). Until v0.55.0, source-address restrictions were not enforced for permissions returned by `NoClientAuthCallback`, the very callback overlay-authenticated designs rely on ([GO-2026-6303](https://pkg.go.dev/vuln/GO-2026-6303)). Channel deadlocks that allowed denial of service were fixed in v0.56.0 ([GO-2026-6354](https://pkg.go.dev/vuln/GO-2026-6354)). Pin x/crypto at v0.56.0 or later. Disable agent forwarding outright: Go's agent package silently stripped destination constraints from forwarded keys until v0.52.0 ([GO-2026-5006](https://pkg.go.dev/vuln/GO-2026-5006)).

The SSH client runs everywhere sidecar does; servers do not. Go's `net` package on js and wasip1 is in-memory "fake networking" ([net_fake.go](https://github.com/golang/go/blob/master/src/net/net_fake.go)), so a browser SSH client needs a `net.Conn` tunneled over WebSocket or WebTransport. Tailscale's SSH Console proved that shape by compiling WireGuard, a userspace netstack and an SSH client to wasm, with xterm.js as the terminal ([Tailscale SSH Console](https://tailscale.com/blog/ssh-console)). iOS apps cannot `fork` and `exec` ([ios_system](https://github.com/holzschu/ios_system)), and Tailscale compiles its SSH server only for desktop operating systems ([tailssh.go](https://github.com/tailscale/tailscale/blob/main/ssh/tailssh/tailssh.go)). The research team's local builds (Go 1.27.4, stripped, unpublished) agree. The x/crypto client and an exec-only server compiled for android/arm64, js/wasm and wasip1. ios/arm64 executables required cgo external linking, so iOS goes through `gomobile bind`. And [creack/pty](https://github.com/creack/pty) failed to build for wasm. In those builds the client added about 2.6 MB to a linux/amd64 binary and about 1.2 MB gzipped to a wasm one. Phones and the browser therefore hold client roles only; shells live in enclaves and on desktops.

Systems that already authenticate the transport keep SSH for compatibility and drop SSH's own user authentication. Tailscale accepts auth method `none` and authorizes by the WireGuard peer's identity ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)). Coder sets `NoClientAuth: true` over its tailnet ([Coder agentssh](https://github.com/coder/coder/blob/main/agent/agentssh/agentssh.go)). Fly and Teleport instead mint short-lived OpenSSH certificates ([Fly](https://fly.io/blog/ssh-and-user-mode-ip-wireguard/); [Teleport](https://goteleport.com/docs/reference/architecture/authentication/)). Kubernetes dropped SSH-style protocols entirely, moving exec to a WebSocket subprotocol with stdin, stdout, stderr, status, resize and close channels ([Kubernetes](https://kubernetes.io/blog/2024/08/20/websockets-transition/)). Sidecar should split the two audiences. Agent-to-enclave traffic uses a small framed exec protocol over sidecar's existing end-to-end encrypted stream. An `open` message carries argv or a shell, an environment allowlist and an optional pty. Three stdio channels, resize and signal messages, and an `exit` message with a code or signal follow. Tools return `{exit_code, stdout, stderr, truncated, duration}` with output caps. The pty stays off by default, because it merges stderr into stdout. People and stock tools (OpenSSH, sftp, VS Code Remote) get a real x/crypto SSH server in the enclave, reachable only over the overlay. Its `NoClientAuthCallback` maps overlay identity to a local user and policy, it allowlists environment variables as Tailscale's `acceptEnv` does, and it keeps port forwarding and SFTP behind explicit policy, not on by default as Coder does. For human terminals, xterm.js 6.0 covers the web ([xterm.js](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0)). SwiftTerm covers AppKit, UIKit, wasm and headless use under MIT ([SwiftTerm](https://github.com/migueldeicaza/SwiftTerm)). On Android, use Termux's Apache-2.0 terminal libraries rather than its GPLv3 app ([Termux license](https://github.com/termux/termux-app/blob/master/LICENSE.md)).

The enclave's host identity is where sidecar breaks new ground. The OpenSSH certificate format is now an IETF draft. Verifiers must ignore unknown extensions and reject unknown critical options, and custom names are domain-qualified ([draft-miller-ssh-cert](https://datatracker.ietf.org/doc/html/draft-miller-ssh-cert)). x/crypto exposes `CertChecker` and an arbitrary `HostKeyCallback` ([certs.go](https://github.com/golang/crypto/blob/v0.59.0/ssh/certs.go)), and stock OpenSSH accepts `@cert-authority` lines or a `KnownHostsCommand` ([ssh_config(5)](https://github.com/openssh/openssh-portable/blob/master/ssh_config.5)). That suggests the following design. The enclave generates its host key inside the TEE. A network CA issues a short-lived host certificate only after verifying the enclave's attestation. The certificate names the enclave's sidecar identity as principal and carries a custom `attestation@<domain>` extension holding the measurement digest. Sidecar's own client checks both the certificate and the extension, and stock clients need one `@cert-authority` line and ignore the extension. Freshness should bind to the SSH exchange hash or session ID, the role Trail of Bits recommends the handshake transcript play for attested TLS ([Trail of Bits](https://blog.trailofbits.com/2026/04/07/what-we-learned-about-tee-security-from-auditing-whatsapps-private-inference/)). No production system documents attestation-bound SSH host keys. Tinfoil Bunkers says only that it verifies "end-to-end before you connect" ([Tinfoil Bunkers](https://tinfoil.sh/blog/2026-11-19-introducing-tinfoil-bunkers)). This design therefore needs its own security review before launch.

For git, go-git is the only library that keeps one Go codebase across enclave, phone and browser. Its stable release is v5.19.3, and v6.0.0-beta.1 shipped the same day, 2026-10-04. Both are Apache-2.0 and pure Go ([go-git](https://github.com/go-git/go-git)). Its compatibility matrix covers clone, fetch and push over smart HTTP, ssh, git and file transports, plus status, add, commit, reset, rm, mv, branch, basic checkout, log, diff, blame and grep. Merge is **fast-forward only**, stash, rebase, revert and apply are **missing**, and the pack protocol v2 is unsupported ([COMPATIBILITY.md](https://github.com/go-git/go-git/blob/main/COMPATIBILITY.md)). Two extension points matter: custom transports and a pluggable `Storer`. Pack traffic can ride sidecar's authenticated stream instead of HTTP, which sidesteps CORS in the browser, and objects can live in sidecar's encrypted store. Two caveats are serious. In 2026, advisories about hostile repositories and servers arrived roughly monthly, including worktree operations that followed symlinks ([GHSA-hc8v-wwc9-vgxm](https://github.com/advisories/GHSA-hc8v-wwc9-vgxm)) and reference names that wrote outside reference storage ([GHSA-qgq7-7hm3-q39j](https://github.com/advisories/GHSA-qgq7-7hm3-q39j); [OSV](https://osv.dev/list?ecosystem=Go&q=github.com%2Fgo-git%2Fgo-git)). Memory is also heavy. In the research team's local test, an in-memory full clone of a 101 MB repository peaked at **2.15 GB of RSS, about 20 times the pack size**. v6 beta was also about ten times slower in a `file://` test, though v6 generates the pack in-process there, which muddies the comparison. Phones and browsers therefore need shallow, single-branch fetches and file-backed storage; OPFS- or IndexedDB-backed storage in the browser is untested. The same local builds showed v5 compiling for js/wasm but failing for wasip1, while v6 builds for both. Start on v5 behind sidecar's own interface, and move to v6 at general availability after benchmarking it over a network transport.

The alternatives lose on the targets. libgit2 is GPLv2 with a linking exception ([COPYING](https://github.com/libgit2/libgit2/blob/main/COPYING)). It needs cgo, so it cannot link into Go's wasm build, and its Go binding, git2go, has not released since v34.0.0 in 2022 ([git2go](https://github.com/libgit2/git2go)). gitoxide is fast but still lists push, merge, rebase and stash as unfinished ([crate status](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md)). isomorphic-git has merge, stash and cherry-pick, but it is JavaScript and needs a CORS proxy for hosted remotes ([commands](https://github.com/isomorphic-git/isomorphic-git/blob/main/docs/alphabetic.md); [quickstart](https://github.com/isomorphic-git/isomorphic-git/blob/main/docs/guide-quickstart.md)).

The agent should see git as one `git` tool that takes argv and returns exactly what git would print. Harness prompts already speak git CLI. Gemini CLI tells the model to run `git status && git diff HEAD && git log -n 3` and never `git add -A` unprompted ([Gemini CLI prompts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/prompts/snippets.ts)). Codex forbids `git reset --hard` without approval ([Codex prompt](https://github.com/openai/codex/blob/main/codex-rs/core/gpt_5_codex_prompt.md)). There is some evidence that fewer, more familiar tools help, though not from git. Vercel replaced its data agent's 17 specialized tools with one bash tool: average time fell from 274.8 s to 77.4 s, success rose from 4 of 5 to 5 of 5, and tokens fell 37%, on a small SQL benchmark ([Vercel](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)). Structured tools are not automatically safer either. The reference MCP git server shipped argument injection in `git_diff` and `git_checkout` (CVE-2025-68144) and path traversal in `git_add` (CVE-2026-27735). It now has to neutralize repository-supplied hooks, fsmonitor, filters and pagers ([MCP git server](https://github.com/modelcontextprotocol/servers/blob/main/src/git/README.md); [GHSA-9xwc-hfwc-8w59](https://github.com/advisories/GHSA-9xwc-hfwc-8w59)). An in-process implementation removes that surface entirely. It needs a getopt-style parser per subcommand with a flag whitelist, paths confined to the repository root, no hooks, filters or pagers, and deterministic "not supported by this git" errors. The minimum command set is status; diff over the worktree, the index, `HEAD`, ranges and paths, with `--stat`; log and show; add, rm, mv and commit; restore and reset; branch and switch; rev-parse, ls-files, blame and grep; 3-way merge, stash and worktree; and fetch, pull and push against sidecar storage. go-git covers about two thirds of that. Sidecar must add stash, 3-way merge, worktrees on v5, revision syntax and git-identical output formatting. If MCP tools are wanted, they should be thin wrappers over the same parser, so there is one validation path.

## Production confidential AI verifies on the device and still loses to physical access

The systems worth copying verify attestation on the user's device and fail closed. Meta's WhatsApp client hardcodes the AMD root key, revocation lists for AMD's intermediate certificates, minimum TCB versions, guest and platform policy, and its transparency provider's signing key. Each request also carries the client's timestamp and TCB values, and the service applies the stricter of the client's and its own, so a stale server policy cannot weaken the client's ([Meta white paper V3](https://ai.meta.com/static-resource/private-processing-technical-whitepaper)). Tinfoil's SDK verifies the AMD certificate chain and a Sigstore bundle and compares measurements. Only then does it open TLS and match the server's key to the attested one ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)). Apple goes furthest. A PCC verifier never compares a single field against a reference value. It projects every measured value into a release record, hashes it, and requires that digest to appear in Apple's append-only Merkle log, so a rolled-back firmware security version matches no entry ([PCC software transparency](https://security.apple.com/documentation/private-cloud-compute/googlecloudsoftwaretransparency)). A separately logged hardware ledger means "a node therefore cannot certify its own hardware" ([PCC roots of trust](https://security.apple.com/documentation/private-cloud-compute/googlecloudrootsoftrust)). Clients reach the log through third-party MASQUE proxies, which resists split views ([PCC release transparency](https://security.apple.com/documentation/private-cloud-compute/releasetransparency)). The weaker designs are instructive too. Google's September 2026 brief still lists client-side attestation verification as future work ([Google Private AI Compute brief](https://services.google.com/fh/files/misc/private_ai_compute_technical_brief.pdf)). Brave's gateway checks NEAR's TEEs against an "oracle" server today, with checking in the browser planned ([Brave](https://brave.com/blog/browser-ai-e2ee/)). Server-side verification is exactly the trust in operator servers that sidecar's end-to-end encryption rule forbids. The exception is a verifier that is itself an enclave the device has verified. Apple's proxy nodes check workers against the log revision the device committed to ([PCC transitive trust](https://security.apple.com/documentation/private-cloud-compute/transitivetrust)), and Tinfoil's router pins each model enclave ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)).

For sidecar, this means a Go verifier in every client. It pins AMD, Intel and NVIDIA roots and minimum TCBs. It fetches evidence through URnetwork servers acting as untrusted proxies; in Tinfoil's words, a proxy "can withhold material but cannot forge it" ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)). And it accepts a provider only when its evidence, projected into a canonical release record, appears in a log sidecar controls. Apple's projection method suits a mixed fleet of third-party providers, because it gives every combination of TDX or SEV-SNP quote and GPU report one canonical form to log. Aggregators need the same scrutiny. Phala's documentation says its attestation covers the Phala gateway, not each upstream model's environment, and that "A valid hardware quote alone does not verify a particular response" ([Phala](https://docs.phala.com/phala-cloud/confidential-ai/verify/verify-attestation)). NEAR's Intel Trust Authority tokens move the verdict from the operator to Intel's verifier, which improves on an operator oracle but is still not verification on the device ([NEAR AI](https://near.ai/blog/near-ai-cloud-integrates-intel-trust-authority)). Two open-source Go building blocks exist. Tinfoil's verifier supports SEV-SNP and TDX according to a package listing seen only in search results ([tinfoilsh/verifier](https://pkg.go.dev/github.com/tinfoilsh/verifier@v0.10.15)). OpenPCC is a PCC-inspired framework with a Go client, an OHTTP gateway and a third-party relay ([OpenPCC](https://github.com/openpcc/openpcc)).

Evidence is bound to the channel in one of two ways. The first is encrypting to an attested key. Apple's device generates a per-request data key and HPKE-wraps it to each validated node's request key. That key lives in the node's Secure Enclave, is bound to the node's measurements, and is deleted at expiry, so nothing can decrypt traffic sent to a retired key ([PCC request handling](https://security.apple.com/documentation/private-cloud-compute/requesthandling); [PCC request termination](https://security.apple.com/documentation/private-cloud-compute/requesttermination)). Azure's KMS releases its OHTTP private key only to a gateway whose attestation token satisfies a key-release policy, and it records policy changes in a transparency ledger ([Azure deep dive](https://techcommunity.microsoft.com/blog/azure-ai-services-blog/azure-ai-confidential-inferencing-technical-deep-dive/4253150)). Tinfoil's EHBP applies the idea to HTTP bodies for clients that cannot pin certificates, such as browsers ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)), which is exactly the extension's situation. The second way is terminating TLS inside the TEE with a hash of the TLS key and a client nonce in the attestation report, as Meta, Contrast and Phala do ([Meta white paper V3](https://ai.meta.com/static-resource/private-processing-technical-whitepaper); [Contrast](https://docs.edgeless.systems/contrast/architecture/attestation/overview)). Freshness is where audits find holes. Trail of Bits found that WhatsApp's attestation reports "could be saved and replayed indefinitely". The fix put the TLS `client_random` into every report, and Trail of Bits recommends binding to the handshake transcript instead ([Trail of Bits](https://blog.trailofbits.com/2026/04/07/what-we-learned-about-tee-security-from-auditing-whatsapps-private-inference/)). Apple adds single-execution semantics, so a gateway cannot replay one request to many nodes to mount side channels ([PCC threat model](https://security.apple.com/documentation/private-cloud-compute/attacks)). Sidecar's relayed inference should encrypt to attested keys, so URnetwork servers carry only ciphertext and routing headers. That also covers the extension's inability to pin certificates. GPU evidence needs its own binding, because NVIDIA attestation reports are not tied to a particular confidential VM and can be borrowed from another machine ([TEE.fail](https://tee.fail/)). dstack concedes that a live relay to a genuine remote GPU cannot be ruled out on current Hopper and Blackwell deployments ([dstack security model](https://github.com/Dstack-TEE/dstack/blob/master/docs/security/security-model.md)). Apple's mitigation is the one to copy. It embeds GPU measurement transcripts in the CPU-attested event log, requires identical measurements across all GPUs, and matches each GPU's identity against the logged hardware ledger ([PCC node attestation](https://security.apple.com/documentation/private-cloud-compute/googlecloudnodeattestation)).

Consumer-scale systems also stop the operator from singling out a user. Apple's Token Granting Service issues batches of one-time tokens built on RSA blind signatures (RFC 9474), as used in Privacy Pass (RFC 9578), so redeeming a token cannot be linked to its issuance. Requests travel through OHTTP relays run by Cloudflare and Fastly. The OHTTP and token keys are published to the transparency log, so "only one set of keys is in use in a given time period" ([PCC anonymous request routing](https://security.apple.com/documentation/private-cloud-compute/requestflow)). Meta distributes its key configurations through Fastly, signed with a key hardcoded in the client ([Meta white paper V3](https://ai.meta.com/static-resource/private-processing-technical-whitepaper)). Apple also meters variable token costs without identity. Each node returns a signed cost token inside the encrypted response, and the device later redeems its accumulated cost tokens over OHTTP for refunded token denominations ([PCC anonymous request routing](https://security.apple.com/documentation/private-cloud-compute/requestflow)). That design transfers directly to prepaid inference from third-party providers, who would see only an anonymous token and ciphertext. URnetwork can serve as the relay, provided it never also runs the gateway or holds an attested key. Business-to-business services make no such claim: Tinfoil's usage records carry no prompt text but are tied to the account through its API key ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)). Rentable enclaves cannot be untargetable at all. Google says its per-user memory "does not claim network-level non-targetability" because each request must reach that user's store ([Google Private AI Compute brief](https://services.google.com/fh/files/misc/private_ai_compute_technical_brief.pdf)), and a persistent per-user VM is the same case. The product should say so.

Production inference services are stateless, which sidecar's enclaves cannot be. PCC nodes randomize their data-volume keys on every boot and keep no log that survives a reboot ([PCC stateless computation](https://security.apple.com/documentation/private-cloud-compute/statelesscomputation)). Apple's hardened Google Cloud images leave out OpenSSH entirely. Debug images that add SSH carry different measurements that Apple never publishes, "so a node booted from a debug image can't decrypt user requests" ([PCC debug and hardened images](https://security.apple.com/documentation/private-cloud-compute/appendix_googleclouddebugandhardenedimages)). Telemetry passes an allowlist enforced "in the daemon rather than in the emitting process, so a compromised component cannot bypass it" ([PCC management](https://security.apple.com/documentation/private-cloud-compute/management)). Across turns PCC keeps no keys, because the device supplies them with each request ([PCC multi-turn agent](https://security.apple.com/documentation/private-cloud-compute/multiturnagent)). Enclaves are persistent Debian VMs, so the closest precedents are the new sandbox products and the weaknesses they document. Tinfoil Bunkers wraps SSH keys under the owner's passkey PRF. It binds the owner's key hash into each enclave's configuration so that "one bunker should never be able to impersonate another". It uses raw dm-crypt with dm-integrity initialized to fixed values, because the host can alter LUKS metadata. Its "Perimeter", a separate confidential VM on separate hosts, gives the agent placeholder credentials, swaps in the real ones on outbound requests, and rejects any credential used in an unexpected place ([Tinfoil Bunkers](https://tinfoil.sh/blog/2026-11-19-introducing-tinfoil-bunkers)). dstack warns that its LUKS2 volumes carry no authentication tag and that an operator can restore an earlier encrypted disk, so applications "must anchor a monotonic version" against rollback ([dstack security model](https://github.com/Dstack-TEE/dstack/blob/master/docs/security/security-model.md)). Tinfoil's encrypted inference volumes admit the same gap ([Tinfoil attestation](https://docs.tinfoil.sh/verification/attestation-architecture)). Secrets the enclave needs follow three documented patterns. Keys can be generated inside the TEE and never exported. They can come from a key broker that releases them only against attestation, as Azure's KMS, dstack's KMS and CoCo's Trustee do. Or a CA can issue identities only after attestation, as dstack does when it signs a certificate request only after verifying the attestation embedded in it ([dstack security model](https://github.com/Dstack-TEE/dstack/blob/master/docs/security/security-model.md)). CoCo warns that the broker must itself run in a trusted environment ([CoCo](https://confidentialcontainers.org/docs/attestation/)), so on third-party hardware it must not run on the same provider's machines. Taken together, sidecar's enclaves should hold disk keys that only the user's device can unwrap, use integrity-protected storage with fixed metadata and a version counter anchored outside the provider, keep the bundled SSH server as the user's own path rather than an operator debug path, and route the agent's API keys, including its own inference credentials, through a Perimeter-style egress proxy.

Audits and incidents have surfaced a recurring set of pitfalls, and together they make a checklist for sidecar's verifier.

| Pitfall | Where it surfaced | Check for sidecar |
|---|---|---|
| Unmeasured inputs: with an injected `LD_PRELOAD`, "The attestation would still verify as valid"; ACPI tables were unmeasured | WhatsApp audit ([Trail of Bits](https://blog.trailofbits.com/2026/04/07/what-we-learned-about-tee-security-from-auditing-whatsapps-private-inference/)) | Measure the config (Tinfoil hashes it onto the kernel command line), environment, compose file, and model weights through a dm-verity root hash ([Tinfoil](https://docs.tinfoil.sh/verification/attestation-architecture); [dstack TDX](https://github.com/Dstack-TEE/dstack/blob/master/docs/attestation-tdx.md)) |
| TCB levels read from the report instead of the vendor certificate | WhatsApp audit | Read TCB from the vendor-signed certificate (for SEV-SNP, the VCEK's X.509 extensions) and enforce minimums in client code |
| Replayable evidence | WhatsApp audit | A nonce bound to the channel transcript, TLS or SSH |
| GPU evidence not bound to the CPU TEE | TEE.fail; dstack | SPDM transcripts in the CPU event log, plus a GPU identity allowlist |
| Development modes accepted in production | dstack | Publish and accept only hardened measurements |
| Host-editable storage and rollback | dstack; Tinfoil | dm-integrity with fixed metadata and an external monotonic version |
| Credentials written to logs | NEAR AI breach | Allowlisted telemetry in a measured daemon, and credentials only in the egress proxy |
| Bugs inside the attested software | NEAR AI breach | Fast patching, per-request isolation, runtime recycling |
| Physical interposers forging quotes | TEE.fail | Hardware allowlists, known locations, and high-value keys kept off provider hardware |

The admitted limits decide what sidecar can promise. TEE.fail, published at IEEE S&P 2026 and disclosed in October 2025, built a DDR5 interposer for under $1,000. It recovers Intel's per-CPU provisioning certification key, so forged TDX quotes, "cryptographically indistinguishable from legitimate ones", pass Intel's verification at the up-to-date level ([TEE.fail](https://tee.fail/)). The authors showed that a malicious dstack host could run a workload in a non-confidential VM while forging both TDX and NVIDIA attestations. Intel calls interposer attacks out of scope, AMD plans no SEV-SNP firmware fix, and NVIDIA says it has no mitigation on its side ([TEE.fail](https://tee.fail/)). NVIDIA's own white paper excludes "sophisticated physical attacks" ([NVIDIA white paper](https://docs.nvidia.com/nvidia-secure-ai-with-blackwell-and-hopper-gpus-whitepaper.pdf)). Apple notes that Blackwell GPUs isolate model weights and activations in memory but do not encrypt them ([PCC node architecture](https://security.apple.com/documentation/private-cloud-compute/googlecloudnodearchitecture)). Hyperscaler deployments answer with physical security, hardware ledgers and CPU allowlists. Independent GPU providers who own their machines are precisely the attacker these vendors exclude.

The other limit is software. In November 2026, a remote-code-execution bug in the SGLang inference engine gave an attacker code execution on a NEAR AI inference server. The attacker could have observed requests processed there on November 8, including confidential-mode ones, and API keys written to logs leaked as well. NEAR's own summary is that confidential computing "does not protect against a vulnerability in the software running inside the environment" ([CSA research note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/11/CSA_research_note_near_ai_sglang_confidential_inference_breach_20261111-csa-styled.pdf)). Inside a sidecar enclave, the agent harness and the inference engine are that software. Apple's PCC Agent shows how to contain agents in particular. Tools the agent does not implement run back on the user's device. Delegated tools run on separate attested workers. Every external call is logged and streamed, encrypted, to a report on the device ([PCC Agent](https://security.apple.com/documentation/private-cloud-compute/pccagent)). That maps naturally onto sidecar's own records.

## Conclusion

The five building blocks teach one lesson: the durable assets are schemas and protocols, while the code around them churns. Pi's event and session formats, Open Responses items, the OpenSSH certificate format, git's command-line syntax and HPKE envelopes are stable interfaces with large installed bases. Meanwhile PiG broke its Go API in two releases thirteen days apart, LiteRT-LM broke its C API in a minor release, go-git shipped security fixes about monthly, and x/crypto announced thirteen SSH issues in a single day. Sidecar should therefore invest less in any one library and more in conformance tests at those seams. Those are golden streams captured from real Codex and Claude Code sessions, Pi event fixtures shared by the local and remote harnesses, and negative tests that feed the attestation verifier replayed, rolled-back and debug-mode evidence. The remaining unknowns are cheap to settle with three experiments: a `GOOS=js` build of the minimal agent loop, `gomobile bind` sizes with LiteRT-LM linked on both phones, and a WebGPU inference test in an extension offscreen document.

The deeper implication concerns what "TEE-only" can mean when the hardware belongs to an independent provider. Attestation turns "trust the operator" into "trust the chip vendor and whoever holds the machine", and on rented provider hardware the holder can be the counterparty, which is the case TEE.fail demonstrated. Sidecar's strongest enclave guarantees will therefore come from what never enters the enclave: disk keys the device holds, credentials kept in an egress proxy, and context kept to a minimum. Attestation is an added barrier, not the foundation. Attestation-bound SSH host certificates would set a pattern no production system has published yet. That makes them a differentiator and also an unreviewed risk, which deserves an outside security review before launch.
