## Scopes and boundaries

**§1 CTX.** What the sidecar infrastructure is and is not. The two products and the apps, and what each needs from the infrastructure. Goals and non-goals. A requirements catalog traced to PLAN.md and product sources. Tiers and limits as stated in PLAN.md, with conflicts against other sources raised as questions. Pricing mechanics belong to §20.

**§2 TRUST.** Assets, actors, adversaries, and trust boundaries. A per-service visibility matrix: what URnetwork's servers can see for each service (plaintext, metadata, nothing), and where each kind of TLS or encryption terminates. Key custody: who holds which key. The precise "private from us" statement and every exception to it, each as an owner question. Security invariants that every other section must satisfy. A threat and mitigation table. Do not design the mechanisms (those are §5-§18); state the properties they must have.

**§3 ARCH.** Wave C synthesis. A component map (client side, server side, external parties), the repo dependency graph, control plane vs data plane, and runtime topologies (laptop CLI/daemon, apps, extension, headless cloud agent). End-to-end sequence diagrams for the key scenarios: enroll a sidecar; write a file and notify subscribers; add a member to a repo; publish a local HTTPS service; send mail; receive mail; reach a subnet behind another client; a harness recording work through MCP. It references the owning sections and introduces nothing new. If it finds a contradiction, it records it as a Q-ARCH item.

**§4 REPO.** The sidecar repo tree in detail (root package files grouped by filename prefix per CODESTYLE package layering; `protocol/`, `mcp/`, `cli/`; where MLS lives). A placement table: every component and where it lives (sidecar, server, sdk, connect changes, warp/config/vault, extension/apps). The precise split between sidecar and server for the server-side services: which logic lives in sidecar (owner rule: new pieces in the sidecar repo) and what server hosts and wires (persistence, routes, deploy). Module path, Go version, the dependency policy and how it is enforced, how server and sdk consume sidecar (replace directives, `server/local/source-graph/lock.yml`). The `sidecar` branch workflow across repos: coordination, rebasing on main, merge criteria. Protobuf generation, gomobile and wasm build targets, CLI distribution, versioning (match sdk's calendar versioning if that is the convention), licensing, CI.

**§5 CORE.** `sidecar.Sidecar`: fields (authenticated JWT, connect client, api, encryption key), lifecycle, the component model (how evs, sockets, mail, bridge, and MCP attach), events and callbacks, and concurrency. Local state: directory layout, the `--instance` flag, encryption at rest, the daemon (`ur daemon`, `ur install-daemon`), and how several harness processes share one daemon. Identity: what a sidecar client is (a connect client id in a network), login and enrollment flows (interactive and headless token), the AUTHZ1 rule that a client token cannot administer the network and how admin operations are done anyway, token refresh and revocation. Local key management: the client's long-term identity and signature keys, the local "encryption key", passphrase-protected keychain (cli/UI.md), OS key stores, backup and recovery, multi-device. Platform variants (CLI on darwin/linux/windows, gomobile in sdk, wasm in the extension) at the level of the core. The MLS protocol is §10; the evs format is §11.

**§6 PROTO.** The sidecar subprotocol on connect's subprotocol layer. Id allocation (reserved range or not), envelope, versioning, capability negotiation (peer query), and message-size budget with chunking above the frame limit. Request/response RPC (reuse connect's subprotocol RPC if it exists). **Streams**: open, accept, data, flow-control window, half-close, reset, keepalive; head-of-line blocking; throughput; the alternative of userspace TCP over the IP path. **Server push**: how server services send messages to clients in real time, given that the control id refuses subprotocol frames (a platform client?). Peer authentication: what the receiver can trust about the source id, and what needs sidecar-level signatures. Contracts and transfer accounting for sidecar traffic. A message catalog index that the other sections fill. Protobuf and codec conventions.

**§7 TEAM.** Today's network, user, and client model and its limits. Then the additions: multiple users per network (members, roles such as owner, admin, member, auditor, billing; invitations); SSO for the Team tier (OIDC, SAML or not, domain verification); client enrollment (auth keys, reusable or ephemeral or tagged, headless `ur connect --token`, OAuth clients for automation); device approval; client names, tags (e.g. `tag:recurd`), and groups; scoped tokens for admin actions from the CLI; the customer-held key authority (signing membership and policy, a Tailnet Lock equivalent) and whether it is v1; an audit log of admin actions; the API routes and migrations in server. Policy semantics are §8. MLS group membership is §10, which must stay consistent with team membership.

**§8 ACL.** The access-control model: principals (client, user, group, tag, network, member autogroups, external networks), resources (client, group, network, abstract socket, subnet and ports, evs repo and path, DNS name and edge endpoint, mail send-as), and actions (dial, listen, route, read, write, admin, publish, send). The policy language and its evaluation (deny by default). Storage and versioning on the server, compilation to each client's slice, and real-time distribution ("the rules that affect each client are sent in real time to each client"). Coordinate with §17, which needs the same channel for bridge rules; own the channel here. Enforcement points: server (contract creation between clients, socket scheduling, evs HTTP authorization, edge routing, mail send-as) and client (listener accept, bridge provider, evs membership). Cross-network sharing and invites. Defaults per tier. Policy tests, change audit, and propagation latency. How ACL and MLS membership stay in agreement.

**§9 SOCK.** Abstract socket listeners: the `<net>:<name>` grammar, listen, unlisten, drain, the find-listener plus accept handshake, the fair scheduler (SO_REUSEPORT-like: algorithm, weights, affinity, load reports, health), and the sockets service (state, horizontal scaling, failure handling). The client API (`Listen`, `Dial`, Go `net.Listener`/`net.Conn` adapters), ACL hooks, and quotas. Streams themselves are §6. Consumers are §13 TLS edge, §15 inbound mail, and §17 bridge forwards.

**§10 KEYS.** Group key management for evs. The PLAN choice is MLS (RFC 9420), implemented in the sidecar repo: the RFC subset, ciphersuite, credentials bound to client ids (and who attests that binding), and test vectors. The GKM service as MLS Delivery Service: ordering commits, KeyPackages, Welcome, GroupInfo, external commits for offline catch-up, and tree snapshots. The key hierarchy: epoch, exporter secret, the per-repo session key PLAN.md says is "stored in GKM", and content keys. Membership flows: add a device, add a member, remove, rotate. Revocation semantics: lazy re-wrap, and PLAN's rule that a client that detects a needed rewrap sends a new checkpoint. Recovery when devices are lost. Authorization of MLS operations against §8. Separate key domains for recURd's needs (author-only sessions vs admin-readable approvals). Compare honestly with simpler schemes (per-repo key wrapped to each member, Keybase-style per-team key generations), keep PLAN's MLS choice unless the evidence is decisive, and raise the comparison as a Q.

**§11 EVS.** The evs repo model (naming, creation, sharing, deletion). The encryption format following the git-crypt model: paths in plaintext, contents encrypted. Settle deterministic encryption, commit messages and author fields, and what leaks. Diff and checkpoint storage: diffs, with a full checkpoint every N commits per file, sent by clients, including how this coexists with git objects and packfiles. The git-over-https service (smart HTTP v2, auth, enforcement of git identity = sidecar client id, signed commits) and whether a custom git extension is needed. The head-read API ("last checkpoint plus commits after that, all encrypted"). Subscriptions and change notifications over the subprotocol. The local side: how harnesses see plaintext (local git server or working tree), sync, and conflicts. The file cluster layout (minio), metadata in postgres, quotas, GC, and large files. Keys come from §10.

**§12 DNS.** ur.network as its own zone: registrar delegation, nameservers (own authoritative service vs managed provider), DNSSEC, TTLs. How `<net>` derives from network_name (validation, normalization, reserved labels, renames). "A network has a dns zone <me>.ur.network and owns all entries in the zone": record types a network may set, automatic records (edge hosts, MX, SPF/DKIM/DMARC, ACME challenges), quotas (5/200/2000). Custom domains (Team). Public Suffix List inclusion. CT and enumeration privacy. Abuse takedown hooks (detail in §21).

**§13 TLS.** The ingress path: DNS to the load balancer, nginx passing TLS unterminated by SNI to `tlsedge` (PROXY protocol for the client address), then `tlsedge` terminating TLS (PLAN.md) and dialing the listener through §9 via find-listener and accept. Settle how `tlsedge` exists as a connect client ("opens a client on a network"): per network, or a platform client. Settle the privacy conflict of edge termination: an optional passthrough mode where the client holds the key, raised as an owner question. Certificate issuance for every listened TLS endpoint (ACME challenge type, wildcard per network, rate limits, PSL, CT exposure, key storage, renewal). Port 80, non-HTTP TLS ports, quotas (1/20/200), ECH, DDoS and abuse hooks.

**§14 SMTP.** Outbound mail through `smtpedge`: quotas (N/day, small for free; PLAN pricing 5/200/20000), connection model (TLS end to end from the local mail server to the destination MX through the edge), the plaintext preamble (PROXY-protocol-like TLV header) declaring the routing path and Message-ID, the zero-knowledge proof that those values appear in the first N bytes of the encrypted stream (soundness requirements, binding to the TLS session keys, cost, maturity), and a phased v0 if ZK is not ready. DKIM, SPF, and DMARC for per-network domains, IP pools, warm-up, rDNS. Abuse report ingestion (ARF, DMARC) joined back to the sending network, and the halt rule ("abuse reports against the message id halt sending for a day from that network"). STARTTLS downgrade policy.

**§15 MAIL.** The local SMTP server in the sidecar that "terminates a public mail.<net>.ur.network" and writes incoming mail to encrypted storage. Inbound path from the internet: MX to the edge, then to a listener (SNI splice after STARTTLS vs edge termination), and what each reveals. Behavior when no device is online (temporary failure, multiple listeners, a hosted fallback). Mailbox format in evs. Aliases (`alias@<net>.ur.network`), group inboxes, the admin address, and sending through §14. The **burner email product**: address format (the mocks show `swift-otter-4821@burner.ur`), linkability (burners must not reveal the owning network), shared-domain routing, reply handling, spam filtering, and what the apps need (password-manager entries, notes, one-time codes, "Used at").

**§16 MCP.** The stdio MCP server in `sidecar/mcp`: the tool, resource, and notification catalog mapped to the components; how the `ur` CLI speaks stdio MCP by default; sharing one daemon across harness processes; harness integrations (Claude Code, Codex, Cursor) and "integrate with harness to ingest data into encrypted storage" (what is ingested, how, and where in evs); the infrastructure primitives recURd's record needs (append-only entries, signatures, approvals, reach receipts, retention, erasure), and the boundary between this design and a separate recURd record design (X20); local security (prompt injection, tool permissions, local auth); relation to the existing remote MCP server (`server/mcp`).

**§17 BRIDGE.** IP addresses and port forwarding. The address plan (per-client private addresses, IPv4/IPv6 ranges). Subnets associated with a client, and the routing decision ("look up a client associated with that ip and send to that client instead of the default route"). Port mapping ("map a destination ip and port to a new destination ip and port ... when ip providing a packet from same network"). The rules model on the server, real-time delivery to clients over the §8 channel, and the client rules engine on the packet path (performance, CODESTYLE packet-path rules). Insertion points in connect and sdk, and the abstractions the Sidecar implements for the sdk device. The `ur bridge` and `ur tun` commands in cli/UI.md. ACL integration.

**§18 SDK.** `sdk/sidecar.go`: the exported API under gomobile constraints, and the device abstractions the Sidecar implements (IP address, port forward). Where the sidecar runs on each platform (macOS/iOS/Android apps and network extensions with their memory budgets, linux/windows, the extension's web worker via wasm, ur.io quick tools), background execution limits, and what works offline. Seams only; app UI is out of scope.

**§19 OPS.** Deployment of every new service via warp (service blocks, lb routes, ports, nginx stream config for SNI passthrough), horizontal scaling and shared state (postgres, redis, the new minio file cluster: sizing, durability, erasure coding, backups), a schema and migration summary across services, observability (metrics, logs, dashboards, alerts), capacity estimates, SLOs, failure modes and runbooks, environments (local, canary, main, community), feature flags and rollout.

**§20 QUOTA.** The tier table from PLAN.md (Community, Pro, Team at $100/month plus usage overage; storage 1/20/200 GB; emails per day 5/200/20000; DNS entries 5/200/2000; TLS edge 1/20/200; IP and port forward unlimited; recURd all; SSO and custom domain Team only; "all of these count towards transfer balance"). Enforcement points and counters per service, metering pipeline, transfer-balance integration, Team overage billing, behavior at limits and on downgrade. Resolve or raise conflicts with pitch5 and cli/UI.md.

**§21 ABUSE.** Mail abuse (spam, phishing, the halt rule), hosted-content abuse on `*.ur.network` (phishing, malware; interstitials; Safe Browsing), DNS abuse, legal process (DMCA, law-enforcement requests) given end-to-end encryption, what metadata is retained for abuse joins and for how long, takedown mechanics per host and per network, reputation, and a transparency posture.

**§22 TEST.** Testing across repos: connect in-process transports, server local integration tests (postgres, redis, minio), MLS interop vectors, protocol fuzzing (SMTP, git, DNS, PROXY v2, subprotocol), end-to-end scenario tests mirroring §3, load tests, privacy assertions (the server never receives plaintext or keys), security review (external audit), and conformance (git clients, MTAs, ACME).

**§23 PHASE.** A dependency-ordered build plan: milestones with exit criteria, what recURd design partners need first vs what burner email needs first (raise the ordering conflict for the owner), per-milestone branch and merge plan, which open questions block which milestone, and the review gates the owner requires before implementation.

## OWNER DIRECTIVE 2026-11-03 (binding; see CONVENTIONS.md §0)

"End to end encryption is a must. The storage, tls edge, mail must only see encrypted bytes and some small header values like sni and spam headers." X1 is decided: passthrough, with the key in the sidecar. X2, X6, and X7 are decided in principle: servers see ciphertext plus small header values only. The owning sections (§13, §11, §15, §14) design to the decision and raise only the residual sub-questions listed in CONVENTIONS.md §0. §2 TRUST's visibility matrix must show this as the design, not as one option among several. Every section must treat any server-side plaintext exposure of storage, published-service, or mail content as a design error.
